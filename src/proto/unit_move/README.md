# 유닛 이동 조작감 프로토타입

방 안에서 **개별 유닛을 골라 움직이는 층**을 시험한다.
목적은 기능 목록을 채우는 것이 아니라 **손맛을 재는 것**이다.

전투는 범위 밖이다. 공격 · 체력 · 피해 · 사거리는 하나도 없다.

> **지도 화면과 다른 층이다.** [`14-squad.md`](../../../docs/design/14-squad.md) §14.2 의
> "스쿼드는 판 위에서 말 하나"는 **방과 방 사이 이동**을 가리킨다. 방 그래프 위에서
> 스쿼드가 하나로 움직이는 것과, 방 안에서 대원을 따로 고르는 것은 층이 다르다.
> 그래서 이 프로토타입은 기존 설계와 충돌하지 않는다.

```
godot --path . res://src/proto/unit_move/unit_move_proto.tscn
```

에디터에서는 `src/proto/unit_move/unit_move_proto.tscn` 을 열고 **현재 씬 실행**(F6).
`main.tscn` 과 완전히 독립이라 무엇도 건드리지 않는다.

## 2. 구조

```
src/proto/unit_move/
├── core/                    # 노드에 의존하지 않는 순수 로직
│   ├── nav_grid.gd          # 통행 격자 · 시야 판정 · 흐름장 생성
│   ├── flow_field.gd        # 목적지 하나로 향하는 방향 격자
│   ├── formation.gd         # 대형 자리 만들기와 배정
│   ├── unit_agent.gd        # 유닛 하나의 이동 상태
│   ├── unit_field.gd        # 시뮬레이션 본체 (조향 · 상태 판정 · 도착)
│   ├── unit_step.gd         # 걸음 고르기 (빈 거리 재기 · 우회 후보 · 회전 제한)
│   ├── unit_yield.gd        # 비켜주기 (전진 중인 유닛의 진로에서 남을 옆으로)
│   ├── unit_push.gd         # 「비켜라」 전파와 뒤로 물러나기
│   ├── unit_jam.gd          # 막힘 기억과 길 다시 찾기
│   ├── unit_selection.gd    # 선택 상태
│   ├── control_groups.gd    # 부대 지정과 연타 판정
│   └── move_tuning.gd       # 조절 가능한 수치의 정의와 현재 값
├── unit_move_proto.tscn/gd  # 진입점. 입력 해석과 화면 반영
├── terrain_view.gd          # 바닥과 벽 (거의 안 바뀌므로 따로)
├── field_view.gd            # 유닛 · 선택 · 명령 표시
├── debug_draw.gd            # 개발 표시 (흐름장 · 뜻과 결과 · 자리 · 상태)
└── tuning_panel.gd          # 슬라이더 조절판
```

**이동 로직과 그리는 방식이 갈려 있다.** `core/` 는 좌표와 속도만 알고 무엇으로 보이는지는
모른다. 나중에 배경과 스프라이트가 들어오면 `*_view.gd` 만 갈아 끼우면 된다.

`core/` 를 `src/core/` 가 아니라 이 폴더 안에 둔 이유는 **프로토타입이기 때문이다.**
살아남기로 정해지면 그때 `src/core/` 로 옮긴다. 클래스 이름에 `Proto` 를 붙인 것도
같은 이유다 — 본 코드의 이름 공간을 미리 차지하지 않는다.

## 3. 이동을 어떻게 처리하는가

```
   우클릭
     |
     +--> 목적지를 통행 가능한 곳으로 보정 (벽을 찍어도 명령은 산다)
     +--> 흐름장 한 번 계산  ......... 명령을 받은 전원이 공유한다
     +--> 대형 자리 만들고 배정 ...... 각자 다른 목표를 받는다
     |
   매 물리 프레임
     +--> 자기 자리로 향하는 힘 (도착 반경 안에서는 감속)
     +--> 이웃을 밀어내는 힘 + 앞을 막은 상대는 옆으로 비껴가기
     +--> 회전 속도 제한 -> 가속 한계
     +--> 앞선 유닛보다 빨리 갈 수 없다 (접촉 제약)
     +--> 이동. 이웃의 몸에 막히는 만큼 깎아서 옮긴다 + 남은 겹침 뒤처리
     +--> 도착 · 기다림 · 막힘 판정
```

### 유닛은 서로를 밀지 못한다

**이 게임은 물리력 게임이 아니다.** 다른 유닛을 밀쳐서 갈 수 없다.
예전에는 겹친 몸을 위치로 떼어 놓으면서 **서 있는 쪽을 더 많이 옮겼고**, 그래서 지나가려는
유닛이 남을 밀쳐 내고 그 자리를 차지했다. 지금은 세 겹으로 막는다 — 아래 §9 를 보라.

### 왜 흐름장인가

유닛마다 경로를 따로 찾으면 두 가지가 나쁘다. 같은 곳으로 가는 스무 명이 같은 계산을
스무 번 하고, 남에게 밀려 경로를 벗어날 때마다 재탐색이 필요하다. 그 재탐색이 여럿에게
동시에 걸리면 **웹 단일 스레드에서 그대로 프레임 끊김**이 된다.

칸마다 방향이 미리 놓여 있으면 밀려난 유닛도 지금 서 있는 칸의 방향을 읽으면 된다.

다만 흐름장은 8방향이라 그대로 따르면 열린 방에서 계단처럼 꺾여 걷는다.
그래서 **자기 자리가 그대로 보이면 흐름장을 무시하고 직선으로 간다.**
장애물이 낀 구간에서만 흐름장이 일한다.

### 왜 대형 자리인가

전원에게 같은 좌표를 주면 그 한 점을 두고 영원히 밀어댄다. 밀치기만으로 흩어 놓는 방식은
인원이 늘수록 도착 지점이 부풀고 마지막 몇 명이 자리를 못 잡아 계속 떤다.
**자리를 먼저 정해 두면 각자 자기 목표에서 멈추므로 도착이 끝난다.**

자리는 육각 격자로 만들고 중심에서 가까운 순으로 정렬한다. 배정은 안쪽 자리부터
가장 가까운 유닛을 데려간다 — 앞선 유닛이 안쪽을 차지하고 뒤따르는 유닛이 바깥을 채우므로
**접근 순서가 그대로 대형이 된다.**

## 4. 조절 가능한 값

조절판(Tab)에서 전부 슬라이더로 만진다. **기본값 복원** 버튼이 언제든 되돌린다.

| 값 | 기본 | 무엇이 바뀌는가 |
| --- | --- | --- |
| 최대 속도 | 230 | 초당 픽셀 |
| 가속 | 2600 | **클릭 반응이 여기서 갈린다** |
| 회전 속도 | 900 | 초당 각도. 진행 방향이 꺾이는 한계 |
| 도착 반경 | 6 | 자기 자리에 이만큼 들면 멈춘다 |
| 감속 반경 | 52 | 이 거리부터 속도를 줄인다 |
| 조향 평활 | 0.12 | 초. 흐름장이 칸마다 튀는 것을 다듬는다 |
| 비켜라 전파 | 1 | 0 이면 바로 앞 한 쌍만 비킨다 (§15) |
| 막히면 길 다시 찾기 | 1 | 0 이면 처음 길만 쓴다 (§14) |
| **막힘 비용** | **4.0** | **막힌 칸이 무는 값. 0 이면 기억이 없는 것과 같다 (§26)** |
| 대형 간격 | 1.25 | 유닛 지름의 배수 |
| 대형 유지 | 0.55 | 앞선 유닛이 뒤를 기다리는 정도 |

값을 하나 추가하려면 `core/move_tuning.gd` 의 `DEFS` 에 한 줄 넣으면 된다.
슬라이더는 그 정의에서 저절로 만들어진다.

`막힘 비용` 은 원래 `nav_grid.gd` 의 상수였다. **슬라이더로 옮긴 이유는 §26 이다** -
이 값을 고른 근거였던 측정이 전부 무효였고(§25), 다시 고르려면 돌려 볼 수 있어야 했다.
돌려 볼 수 있으니 사람이 직접 띄워서도 견줄 수 있다.

**열넷이었다가 여덟이 됐다가 다시 열하나다.** 없어진 여섯은 전부 "민다 · 밀린다 · 떼어 놓는다"로 설명되던
값이다 - 분리 반경 · 분리 강도 · 옆으로 비껴가기 · 양보 · 겹침 해소 · 겹침 해소 상한.
유닛이 남을 밀 수 없으면 이웃과의 관계에서 정할 세기가 없다(§11). 남은 여덟은 전부
**자기 몸의 성질**이거나 **대형의 모양**이고, 기본값은 하나도 바꾸지 않았다.

**`포기 시간` 은 없어졌다.** 아래 §8 을 보라.

## 5. 개발 표시 (F1)

`CLAUDE.md` §8 대로 판의 상태를 최대한 드러낸다.
유닛이 이상하게 도는 것을 보고도 그것이 흐름장 탓인지 분리력 탓인지 대형 속도 탓인지는
**눈으로 구분할 수 없다.**

| 표시 | 색 |
| --- | --- |
| 흐름장 방향 | 옅은 파랑 화살표 |
| 대형 자리 | 분홍 가위표 |
| 자기 자리로 향하는 힘 | 노랑 화살표 |
| 이웃을 밀어내는 힘 | 파랑 화살표 |
| 목표까지의 선 | 회색 실선 |
| 포기한 유닛 | 빨강 테두리 |
| 유닛별 상태 | 선택한 유닛 옆에 글자 (12 명 이하일 때) |

위쪽 요약에는 유닛 수 · 선택 · 이동중 · fps · **이동 계산 시간(평균과 최악)** ·
명령 수 · 장애물 시드 · 기본값에서 바뀐 수치 개수 · 부대 현황이 나온다.

체크상자로 흐름장 · 힘 · 자리를 따로 끌 수 있다. 셋을 다 켜면 서로를 가린다.

## 6. 검증

```
godot --path . -s res://tools/capture_unit_move.gd                       # 장면 캡처 7 장
godot --path . -s res://tools/capture_unit_move.gd -- bench 20 50 100 200 300   # 인원별 프레임
godot --headless --path . -s res://addons/gut/gut_cmdln.gd               # 단위 테스트
```

캡처는 `.captures/` 에 남는다. **헤드리스로는 그림이 나오지 않는다** — 창이 있어야 한다.

단위 테스트는 조작감이 갈리는 네 지점을 지킨다. 손맛을 알려 주지는 못하지만
한번 잡아 둔 손맛이 조용히 무너지는 것은 막는다.

| 지점 | 지키는 것 |
| --- | --- |
| 반응 지연 | 명령 뒤 세 프레임 안에 속도가 붙는가 |
| 뭉침 | 두 유닛이 같은 목표를 받지 않는가, 멎은 뒤 몸이 겹치지 않는가 |
| 도착 | 전원이 유한 시간에 멎는가, 멎은 뒤 다시 움직이지 않는가 |
| 대형 | 같이 갈 때 무리가 흩어지지 않는가 |
| 멈춤 판정 | `test_proto_unit_stop.gd` — 아래 넷 |
| 지터 | 칸을 넘을 때 조향 방향이 뛰지 않는가 (`test_proto_nav_grid.gd`) |
| 밀치기 | `test_proto_unit_push.gd` — 아래 다섯 |

멈춤 판정은 넷을 못 박는다 — **영원히 비비지 않는다 · 정말 갈 수 없으면 멎는다 ·
막은 쪽이 비키면 스스로 재개한다 · 기다림이 포기로 바뀌지 않는다.**

밀치기는 다섯을 못 박는다 — **서 있는 유닛은 밀려나지 않는다 · 몸을 통과하지 못한다 ·
여럿이 몰려도 파고들지 않는다 · 밀치기는 이동 수단이 아니다 · 멎은 뒤 몸이 겹쳐 있지 않다.**

## 7. 지터를 어떻게 찾았고 무엇을 고쳤나

**눈으로 "떤다"고 말하는 것과 무엇이 떨게 하는지 아는 것은 다르다.**
`tools/measure_unit_move.gd` 로 먼저 지표를 만들고 고치기 전 값을 재고 시작했다.

```
godot --headless --path . -s res://tools/measure_unit_move.gd          # 상황별 지표
godot --headless --path . -s res://tools/measure_unit_move.gd -- probe # 장치 하나씩 꺼 보기
```

처음 세운 지표(한 프레임에 방향이 뒤집힌 횟수)는 어느 상황에서도 0 이었다.
**회전 속도 제한이 프레임당 15 도라 한 프레임 안에서는 뒤집힐 수가 없다.**
지터는 한 프레임의 반전이 아니라 여러 프레임에 걸친 왕복이므로 누적 꺾임 각도로 갈아탔다.

### 원인

| 의심 | 잰 것 | 결과 |
| --- | --- | --- |
| 분리력이 조향을 압도한다 | 분리 > 조향인 프레임 비율 | **아니다.** 좁은 곳 3%, 열린 곳 4% 로 같다 |
| 힘 하나가 범인이다 | 항을 하나씩 끄고 꺾임 | **아니다.** 어느 하나도 15% 안팎 |
| 조향 방향 자체가 튄다 | 조향이 가리키는 방향의 꺾임 | **이것이다.** 좁은 곳 102, 열린 곳 21 도/초 |

조향 꺾임은 **흐름장을 읽는 프레임 비율과 그대로 맞물렸다**(좁은 곳 29~46%, 열린 곳 1%).
흐름장은 칸마다 8 방향 중 하나를 들고 있어, 유닛이 칸 경계를 넘는 순간 조향이 45 도 통째로 뛴다.
회전 속도 제한은 그 뜀을 없애 주지 않는다 — **튀는 목표를 쫓게 만들어 좌우 왕복으로 바꾼다.**

### 고친 것

| 무엇 | 어디 |
| --- | --- |
| 둘레 네 칸을 섞어 읽어 격자를 연속적인 장으로 만든다 | `flow_field.gd` `_blended_direction` |
| 벽 회피가 90 도 꺾던 것을 45 도로 줄이고 양쪽이 열리면 안 건드린다 | `flow_field.gd` `_avoid_wall` |
| 조향 방향에 지수 평활을 건다 | `unit_field.gd` `_smoothed` |
| 비껴가기 방향을 늘 같은 손으로 고정한다 (부호가 뒤집히지 않는다) | `unit_field.gd` `_separation` |
| 양보 — 목적지에 가까운 쪽에 우선권, 뒤에 선 쪽은 밀지 않고 비킨다 | `unit_field.gd` `_separation` |
| 한 프레임에 밀어내는 거리에 상한 | `unit_field.gd` `_resolve_overlaps` |

### 해 보고 걷어낸 것 — 다시 하지 마라

- **좁은 통로에서 한 줄 세우기.** 좌우로 비집는 힘을 걷어내는 방식과 비껴가기만 끄는 방식
  둘 다 만들어 봤는데, **한 칸짜리 문에서 도리어 나빠졌다**(정지 9.35 → 10.08 초,
  통과 6.53 → 7.02 초). 좌우 힘을 걷어내면 유닛이 문 입구에 자기를 맞추지 못해 벽에 붙어 막힌다.
  줄을 세우려면 밀치기를 깎을 게 아니라 **통로 한가운데로 끌어당겨야** 한다. 그건 벽까지의
  거리를 재는 조회가 따로 필요해서 손대지 않았다.
- **미는 방향을 진행 방향의 접선으로 돌리기.** 한 칸 폭 복도에서는 접선이 곧 벽 쪽이라
  몸이 벽으로 밀리고, `push_out` 이 그 몸을 100 픽셀 너머로 옮겨 **앞을 막은 유닛 여섯을
  통째로 통과했다.**

> 이 절의 실패담은 **밀치기가 있던 판에서의 것이다.** §9 에서 밀치기를 걷어내면서 판이
> 달라졌다 — 이제는 좌우로 비집는 힘을 깎는 대신 **속도를 앞선 유닛에 맞추는** 방식으로
> 줄이 선다(§10). 여기 적힌 두 실패의 교훈("좌우 힘을 걷어내면 문 입구에 자기를 맞추지
> 못한다", "미는 축을 돌리면 그 축이 지터가 된다")은 그대로 유효하고, 실제로 §10 에서
> 두 번째 교훈을 한 층 위에서 다시 배웠다.

### 지나가다 잡은 것

`nav_grid.gd` `push_out` 의 걸음이 16 픽셀이었다. 한 칸 폭 통로에서 몸이 들어갈 수 있는 띠는
8 픽셀뿐이라 **그 띠를 매번 뛰어넘어 유닛이 100 픽셀 너머로 순간이동했다.** 이 레인이 넣은
버그가 아니라 원래 있던 것이고, 걸음을 몸 크기에 묶어 고쳤다.

## 8. 포기 시간을 무엇으로 대체했나

의뢰인의 관찰이 결정적이었다 — **"포기한 거 다시 가라고 하면 가는 경우가 있다."**
실제로는 막히지 않았는데 막혔다고 잘못 결론 낸 것이고, 포기 시간은 그 오판을 시간으로 덮는
장치였다. 늘리면 굼떠지고 줄이면 일찍 포기하니 어느 쪽으로 돌려도 나아지지 않는다.

이제 `unit_field.gd` `_update_states` 가 **셋 중 하나에 걸릴 때만** 멈춘다.

| 무엇 | 어떻게 아는가 | 되돌아오는가 |
| --- | --- | --- |
| 도착 | 자기 자리에 들었다 | 아니다 |
| 정말 갈 수 없다 | 흐름장이 내가 선 칸까지 못 닿았다 (`_unreachable`) | 아니다 |
| 앞이 막혔다 | 나를 막은 것이 **이미 자리를 잡은 아군**이다 | **그렇다** (`HOLDING`) |

셋째가 포기 시간을 대신한다. 안쪽에 도착한 유닛부터 바깥으로 자리 잡음이 번져 나가고,
**막고 있던 유닛이 비키면 조건이 저절로 풀려 다시 간다. 재명령이 필요 없다.**

판정은 속도가 아니라 **실제로 줄어든 거리**로 한다. 앞이 막힌 유닛은 속도가 살아 있다 —
조향이 밀어 넣고 겹침 해소가 그만큼 도로 밀어내서, 속도계는 초당 160 픽셀을 가리키는데
목적지까지의 거리는 한 뼘도 줄지 않는다. 속도로 물었을 때 이 유닛이 영원히 "나아가는 중"으로
남아 결국 막힘으로 떨어지는 것을 보고 고쳤다.

`test/unit/test_proto_unit_stop.gd` 가 네 성질을 못 박는다.

## 9. 밀치기를 어떻게 걷어냈나 (1 단계)

의뢰인의 지적이 출발점이다 — **"이게 물리력 게임은 아니니까 다른 유닛을 밀쳐서 이동할 수는
없어야 하는데, 이런 부분들에 물리력이 작용하면서 지터가 더 심해지는 것 같기도 해."**

맞았다. 그리고 **두 문제가 같은 하나였다.**

### 무엇이 밀치기였나

`_resolve_overlaps` 는 겹친 몸을 위치로 떼어 놓으면서 **양쪽을 다 옮겼고**, 서 있는 쪽이
0.75 를 졌다. 그래서 지나가려는 유닛은 남의 몸 안으로 걸어 들어가기만 하면 상대가 알아서
비켜 났다 — 그것이 "비집고 간다"의 정체다. 게다가 조향이 밀어 넣고 겹침 해소가 그만큼 도로
밀어내는 왕복이 매 프레임 벌어졌는데, 이 왕복은 **속도계에 잡히지 않고 위치에만 나타난다.**

### 걷어낸 것과 대신 넣은 것

| 걷어낸 것 | 대신 |
| --- | --- |
| 겹친 쌍을 위치로 떼어 놓아 이동을 뚫는 것 | `_advance` 가 **이동을 몸에 막히는 만큼 깎는다** |
| 서 있는 유닛이 0.75 만큼 밀려나던 것 | `_push_share` 가 서 있는 쪽에 0 을 준다. **벽과 같다** |
| 서 있는 유닛의 버티는 힘을 절반으로 깎던 것 | 깎지 않는다. 밀 수 없으니 붙기 전에 돌아야 한다 |

이제 `_resolve_overlaps` 는 이동의 일부가 아니라 뒤처리다. 여기까지 오는 겹침은 스폰이
겹쳐 놓았거나 벽 보정(`push_out`)이 몸을 옮긴 경우뿐이다. **남을 옮기는 코드가 아예 없다** —
유닛마다 자기가 빠져나올 몫만 옮기므로 밀치기가 되살아날 자리가 남지 않는다.

### 막힌 유닛은 무엇을 하는가 — 그리고 왜

의뢰인이 고를 것을 넷 주었다. 고른 것은 **"돌아간다, 안 되면 선다"** 이고 순서가 있다.

| 순서 | 무엇 | 어디 |
| --- | --- | --- |
| 1 | **비스듬히 부딪히면 몸을 타고 미끄러진다** | `_clip_move` 가 접선 성분을 남긴다 |
| 2 | **앞을 막은 서 있는 아군은 크게 돌아 나간다** | `_ROUND_SETTLED` — 접선 힘을 2 배 넘게 얹는다 |
| 3 | **정면으로 막히면 그 자리에 선다** | 다가가는 성분이 통째로 깎여 속도가 0 이 된다 |
| 4 | **비키면 스스로 재개한다** | `HOLDING` (§8). 앞 레인이 세운 성질을 그대로 쓴다 |

**억지로 부드럽게 비벼서 통과시키지 않는다.** 의뢰인이 "교착에 빠지더라도 너무 스무딩하게
움직이려는 게 있다"고 한 지점이다. 정면으로 막히면 정말 멈춘다.

2 번이 없으면 어떻게 되는지 재어 보았다 — **열린 방에서도 백 명 중 서른이 앞선 아군에 붙어
그대로 굳었다.** 돌아갈 자리가 넉넉한데도 돌지 않았다. 밀 수 있을 때는 반경 방향 힘이 곧
전진이었지만, 밀 수 없는 몸에게 반경 방향 힘은 **서게 만들 뿐**이기 때문이다.

### 정말 없어졌는가 — 숫자와 테스트

지표를 둘 새로 만들었다. 눈으로 "안 밀리는 것 같다"는 증거가 아니다.

| 지표 | 무엇 | 결과 |
| --- | --- | --- |
| `정지밀림` | 움직이는 유닛이 서 있는 유닛을 밀어낸 총 거리 | **여섯 상황 모두 0.00 px** |
| `최대겹침` | 몸이 파고든 최대 깊이 (몸 지름 18 px 에 닿으면 통과다) | 2.1 ~ 5.6 px |
| `막힌이동` | 이웃의 몸에 막혀 깎여 나간 이동 거리 | 465 ~ 13842 px. **어디에도 쓰이지 않고 사라진다** |

`밀린거리`(겹침 해소가 위치를 옮긴 총량)는 좁은 통로 100 명에서 **57202 px 에서 1844 px 로**
떨어졌다. 96 퍼센트가 사라졌고 남은 것은 벽 보정 뒤처리다.

`test/unit/test_proto_unit_push.gd` 가 다섯을 못 박는다. 특히 한 칸 폭 복도에서 막고 선 아군
앞에 유닛을 세워 12 초를 굴리고 **아군의 좌표가 0.001 px 도 변하지 않았는지** 확인한다.
`test_proto_unit_stop.gd` 의 `_run_pinned` 도 바꿨다 — 예전에는 밀려나지 않게 **못을 박아야
했는데**, 이제 되돌리지 않고 정말 그 자리에 있었는지 확인한다.

## 10. 그다음 지터 (2 단계)

밀치기를 빼면 지터가 저절로 좋아질 줄 알았다. **아니었다.**

| 상황 | 밀치기 있음 | 밀치기 뺀 직후 |
| --- | --- | --- |
| 좁은 통로 40 꺾임 | 165 | **215** |
| 좁은 통로 100 꺾임 | 267 | **423** |

밀치기가 있을 때는 앞이 막혀도 밀고 나가면 됐다. 밀 수 없게 되자 **아무도 기다리지 않은 채**
전원이 같은 자리로 계속 파고들었고, 위치 자르기가 매 프레임 다른 접선으로 튕겨 냈다.
그 접선의 뒤바뀜이 그대로 꺾임이었다.

### 먼저 지표를 고쳤다 — 속도가 아니라 위치로 잰다

`tools/measure_unit_move.gd` 가 꺾임 · 역주행 · 굽이를 **속도 벡터**로 재고 있었다.
막힌 유닛은 속도계가 초당 160 픽셀을 가리키면서 한 뼘도 못 간다. 그 속도를 세면 **가지도 않은
거리를 갔다고 하고, 서 있는 유닛의 꺾임을 이동의 꺾임으로 센다.** 실제로 옮겨 간 위치로
갈아타니 밀치기 시절의 좁은 통로 꺾임이 76 이 아니라 **165** 로 나왔다 — 밀치기가 만드는
튐은 애초에 속도에 나타나지 않는 종류였던 것이다. 이 표의 모든 숫자는 새 지표로 다시 잰 값이다.

### 원인을 어떻게 짚었나

`-- probe` 로 항을 하나씩 껐다. **범인이 없었다.**

| 끈 것 | 좁은 통로 40 꺾임 |
| --- | --- |
| 아무것도 안 끔 | 215 |
| 조향 평활 끔 | 222 |
| 양보 끔 | 231 |
| 겹침 상한 풀기 | 215 |
| 비껴가기 끔 | 213 |

어느 힘도 원인이 아니었다. 원인은 힘이 아니라 **구조**였다 — 줄을 서는 규칙이 없었다.

### 고친 것 — 접촉 제약

**앞선 유닛보다 그쪽으로 빨리 갈 수 없다.** 부딪히기 전에 속도를 맞춘다.
앞선 유닛이 **실제로** 나아가는 만큼만 따라간다(뜻이 아니라 결과를 본다 — `advance`).
앞선 유닛이 서 있으면 0 이 되어 그 자리에 선다.

여기까지 오는 데 두 번 틀렸고, 두 번 다 **같은 이유**였다.

| 시도 | 좁은 통로 100 꺾임 | 왜 틀렸나 |
| --- | --- | --- |
| 다가가는 성분을 잘라 낸다 | 619 | 앞을 막은 이웃이 바뀌면 **자르는 축**도 바뀌어 방향이 널뛴다 |
| 다가가는 비율만큼 속도를 통째로 줄인다 | 91 (**86 명이 문을 못 넘음**) | 앞이 0 이면 비스듬히 가려는 속도까지 0 이 된다 |
| 얼마나 정면으로 가려는지에 따라 제약을 걷어 준다 | **246** | 축이 아니라 세기를 다루므로 방향이 튀지 않는다 |

**자르는 축이 곧 지터의 씨앗이다.** 위치 자르기에서 배운 교훈을 한 층 위에서 되풀이했다.

### 함께 고친 것

- **막혔다고 속도를 눌러 쓰지 않는다.** 눌러 쓰면 다음 프레임 조향이 그 눌린 속도에서
  방향을 다시 잡아 매 프레임 다른 쪽을 가리킨다(꺾임 507 대 423). 속도는 조향의 **뜻**이고
  위치는 그 뜻이 몸에 막히고 남은 **결과**다. 어차피 속도는 최대 속도로 묶여 있어 쌓였다
  터지지 않는다.
- **따라가기가 보는 각도를 막힘 판정보다 넓게 잡았다**(78 도 대 57 도). 둘은 묻는 것이 다르다.
  좁게 잡았더니 잼 한가운데에서 비스듬히 낀 유닛을 못 보고 그 사이로 빠르게 비집으려 들었고,
  그 옆걸음이 그대로 꺾임이었다. 이 하나로 좁은 통로 100 명 꺾임이 302 에서 211 로 떨어졌다.
- **격자 해시 칸 크기의 바닥을 몸이 닿는 거리로 잡았다.** 예전에는 분리 반경만 봤는데, 슬라이더를
  최소로 내리면 칸이 몸 지름보다 작아져 부딪힐 이웃을 놓친다. 통과 금지는 슬라이더가 어디에
  있든 지켜져야 한다.
- **겹침 뒤처리를 이동과 같은 훑기 안에서 끝냈다.** 둘 다 유닛마다 이웃을 훑는 일이라
  따로 돌면 격자 조회가 한 벌 더 든다(100 명 기준 3.96 → 2.90 ms).

## 11. 힘을 전부 걷어냈다 (3 단계)

의뢰인이 방향을 못 박았다.

> 보면 **수치에도 밀어낸다 이런게 있는데**
> **이동으로는 물리력 작용 안될거니까 해당 요소를 우선 다 빼고 다시 생각하라고 해**

### 왜 약하게 줄이지 않고 뺐나

§9 · §10 은 **밀치기를 줄이는 방향**이었다. 서 있는 쪽의 몫을 0 으로 만들고, 겹침 해소에
상한을 걸고, 비껴가기 배수를 낮췄다. 그래도 지터는 남았고 의뢰인 눈에는 그대로였다.

남아 있던 것을 정직하게 세면 이렇다 — **이웃을 밀어내는 힘 · 옆으로 흘리는 힘 · 양보로
비키는 힘 · 겹친 몸을 위치로 떼어 놓는 처리 · 서 있는 아군을 돌아 나가는 접선 배수.**
전부 "민다 · 밀린다 · 떼어 놓는다" 로 설명되는 것이고, 전부 **조향과 싸운다.**
조향이 한쪽을 가리키는데 힘이 다른 쪽으로 몸을 옮기면, 다음 프레임 조향은 옮겨진 자리에서
다시 방향을 잡는다. 그 되먹임이 지터다. **싸울 힘이 없으면 안 싸운다.**

### 걷어낸 것

| 무엇 | 어디 |
| --- | --- |
| 분리 반경 · 분리 강도 | `move_tuning.gd` `DEFS`, `unit_field.gd` `_separation` 통째로 |
| 옆으로 비껴가기 | 같은 곳 |
| 양보 | 같은 곳 |
| 겹침 해소 · 겹침 해소 상한 | `move_tuning.gd` `DEFS`, `unit_field.gd` `_resolve_overlaps` · `_push_share` 통째로 |
| 서 있는 아군을 돌아 나가는 접선 배수 | `_ROUND_SETTLED` |
| 접촉 제약(앞선 유닛에 속도 맞추기) | `_follow` · `contact_normal` · `contact_speed` · `contact_near` |
| 이동을 깎던 위치 자르기 | `_clip_move` |

슬라이더는 **열넷에서 여덟로** 줄었다.

### 남긴 것과 그 이유

`push_out` 은 남겼다. **이것은 유닛 사이의 힘이 아니라 지형 보정이다** — 몸이 벽 안에 들어간
경우에만 부른다. 스폰이 벽에 겹쳐 놓는 경우가 실제로 있고, `test_proto_nav_grid.gd` 가
이 함수를 못 박고 있다. 다만 이제는 **평상시에 한 번도 불리지 않아야 정상**이라서,
서 있는 유닛이 여기서 움직이면 `settled_push_total` 에 잡히도록 계기를 달아 두었다.

`회전 속도` · `가속` · `조향 평활` 은 남겼다. 이웃을 미는 힘이 아니라 **자기 몸의 운동 한계**다.
`대형 유지`(`group_sync`)도 남겼다 — 남을 밀지 않고 자기 속도를 줄이는 것뿐이다.

### 힘 없이 이동을 어떻게 다시 짰나 — 걸음 고르기

힘이 없으면 남는 질문은 하나다. **"저기로 갈 수 있는가 없는가."**

매 프레임 유닛마다 이렇게 한다.

```
1. 가고 싶은 방향을 정한다 ......... 자기 자리가 보이면 직선, 아니면 흐름장 (예전과 같다)
2. 그 방향으로 얼마나 갈 수 있는지 잰다 ... 이웃의 몸과 벽까지의 빈 거리
3. 앞이 트여 있으면 그냥 간다
4. 막혀 있으면 좌우로 벌린 후보 방향을 같이 재고, **가장 많이 나아가는 것 하나를 고른다**
5. 고른 방향으로도 못 가면 **그 자리에 선다**
```

여기에는 **다른 유닛을 움직이는 코드가 한 줄도 없다.** 유닛은 자기 위치만 바꾸고,
그 위치는 반드시 비어 있는 자리다. 그래서 몸이 겹칠 수가 없고, 겹친 뒤에 떼어 놓을 일도 없다.

**연속 좌표에 두고 빈 거리를 재는 쪽을 골랐다. 칸 단위 점유가 아니다.** 근거는 셋이다.

1. **몸 크기가 종류마다 다르다**(9 · 11 · 12). 칸 하나에 유닛 하나로 두면 칸을 가장 큰 몸에
   맞춰야 하고, 그러면 정찰병은 자기 몸의 세 배 넓이를 차지한다. 대형이 종류에 따라
   부풀었다 줄었다 한다.
2. **칸 중심 사이를 보간하면 §7 에서 잡은 지터가 그대로 돌아온다.** 흐름장이 칸마다 45 도씩
   뛰어서 생긴 문제였는데, 이동 자체를 칸 단위로 만들면 **목표가 칸 경계에서 뛰는 구조**가
   한 층 더 생긴다. 보간으로 부드럽게 만들 수는 있어도 원인은 남는다.
3. **자리를 세는 것은 어차피 연속 좌표로 할 수 있다.** "저 자리가 비었는가" 는 이웃과의
   거리 하나로 답이 나오고, 그것이 칸 점유표가 주는 보장과 정확히 같다 —
   순서대로 처리하면 앞선 유닛의 **새 위치**를 보고 비었는지 판단하므로 두 유닛이
   같은 자리를 동시에 차지할 수 없다.

### 부딪히기 전에 선다 — 제동 거리로

빈 거리가 0 이 될 때까지 최고 속도로 달리면 몸이 닿는 순간 속도가 통째로 사라진다.
그 뜀이 눈에는 튕김으로 보인다. 그래서 **앞의 빈 거리 안에 멈출 수 있는 속도로 미리 줄인다**
(`sqrt(2 · 가속 · 빈거리)`). 이것은 이웃이 나에게 주는 힘이 아니라 **내가 내 브레이크를 밟는
것**이고, 앞선 유닛이 천천히 가면 나도 천천히 따라가는 줄서기가 여기서 저절로 나온다.

### 좌우 후보는 "비비기" 가 아니다

옆으로 벌린 후보를 두는 것이 예전의 비껴가기와 무엇이 다른가.

| 예전 (힘) | 지금 (고르기) |
| --- | --- |
| 이웃이 있으면 **늘** 옆으로 미는 힘이 붙는다 | 앞이 **막혔을 때만** 후보를 잰다 |
| 힘의 합이 방향을 정하므로 이웃이 바뀌면 방향이 널뛴다 | 후보 중 하나를 고르고, 직전에 고른 것에 가산점을 준다 |
| 몸이 겹친 뒤 떼어 놓는다 | 애초에 빈 자리로만 간다 |
| 앞이 막혀도 비비면 나아간다 | 후보가 전부 막히면 **선다** |

### 걷어내고 나서 세 번 틀렸다 — 그 셋이 이 설계의 급소다

힘을 빼자마자 이동이 멈췄다. 고치는 과정이 곧 이 방식의 약점 목록이다.

| 무엇이 일어났나 | 왜 | 어떻게 고쳤나 |
| --- | --- | --- |
| 열린 방 꺾임이 33 에서 217 로 뛰었다 | 우회를 켜고 끄는 문턱이 하나뿐이라 대형 간격(30 px) 안에서 매 프레임 켜졌다 꺼졌다 했다. **켜짐 자체가 지터였다** | 드는 문턱(10 px)과 푸는 문턱(24 px)을 따로 뒀다 |
| 좁은 문 앞에서 마흔 명이 **전원 속력 0** 으로 얼어붙었다 | 벽에 몸을 붙인 유닛은 벽면을 따라 **정확히 90 도**로만 나갈 수 있는데 후보가 55 도까지였다. 벽 표본 간격도 11 px 이라 5 px 만 가면 되는 정렬을 못 봤다 | 후보에 90 도를 넣고 옆걸음에 최소 점수를 줬다. 벽 표본을 3 px 로 촘촘히 했다 |
| 백 명 중 일흔이 4 초 만에 **포기**하고 그 몸이 벽이 되어 뒤를 막았다 | 안전망(`_watch_grinding`)이 "줄을 서서 못 감"과 "지형에 낌"을 구분하지 못했다 | 아군에게 눌린 동안은 세지 않는다. 포기 대신 몇 번은 기다림으로 떨어뜨린다(예산 3 회) |

여기서 배운 것 하나 — **힘을 걷어내면 "고르는 것"이 새 지터가 된다.** 힘의 지터가 방향의
연속적인 왕복이었다면, 고르기의 지터는 **후보가 갈아 끼워지는 깜빡임**이다. 문턱을 둘로
가르고 직전 선택을 이어 가는 것이 여기서의 평활이다.

### 아직 안 한 것 — 그리고 지금 무엇이 망가져 있는가

**진짜 돌아가기(경로 재계산)는 안 넣었다.** 걸음 고르기는 몸 하나를 돌아 나가는 국소
판단이고, "이 문이 막혔으니 저 문으로" 는 흐름장을 다시 계산해야 한다.

그리고 **좁은 문이 망가졌다. 이것이 이번 판의 가장 큰 사실이다.**

| 상황 | 힘 있을 때 | 힘 걷어낸 지금 |
| --- | --- | --- |
| 좁은 통로 40 통과 | 6.23 s 전원 | **못함 (5 명 남음)** |
| 좁은 통로 100 통과 | 못함 (1 명) | **못함 (83 명 남음)** |

원인은 국소 판단으로 고칠 수 있는 것이 아니다. **힘이 없으면 빽빽하게 뭉친 무리는 스스로
자리를 바꿀 수 없다.** 밀 수 있을 때는 무리가 액체처럼 문으로 흘러들었는데, 밀 수 없게 되자
각자 "빈 자리가 있으면 간다"만 따르다가 문 앞을 통째로 메우고 그대로 굳는다. 굳은 뒤에는
어느 유닛도 혼자 힘으로 빠져나올 수 없다 — 물러나기를 넣어 열둘과 스물넷은 풀렸지만
마흔은 안 풀렸다.

**다음 사람이 볼 곳은 여기다.** 국소 걸음을 더 손보는 것으로는 안 된다. 뭉치는 것 자체를
막아야 하고, 그러려면 **자리를 미리 잡아 두는 방식**(칸 점유 예약, 문 통과 순번)이나
**뭉치기 전에 다른 길로 보내는 것**(경로 재계산)이 필요하다. 둘 다 힘이 아니다.

## 12. 비켜주기 (5 단계) — 미느냐가 아니라 어떻게 미느냐

§11 에서 힘을 전부 걷어냈고, 그 대가로 **좁은 문이 무너졌다**(100 명 중 83 명이 못 넘음).
진단은 이랬다 — "힘이 없으면 빽빽하게 뭉친 무리는 스스로 자리를 바꿀 수 없다."

밀기가 좁은 통로 통과의 **수단**이었던 것이다. 그런데 밀기가 지터를 만든 것도 사실이다.
둘은 모순이 아니다.

| | §9 이전에 하던 것 | 이번 비켜주기 |
| --- | --- | --- |
| 방향 | **대칭** — A 가 B 를 밀면 B 도 A 를 민다 | **비대칭** — 전진 중인 쪽만 민다 |
| 결과 | 서로 밀어 되튀김 → **진동** | 한쪽만 비킨다 → 되튀길 상대가 없다 |
| 적용 | **속도에 힘을 더함** → 지나침 | **위치를 직접 옮김** → 한 번에 수렴 |

**대칭 스프링은 구조적으로 진동한다.** 우리는 진동하는 쪽을 만들어 놓고 "밀기가 문제다"
라고 결론지었다. 이번에는 진동할 수 없는 모양으로 다시 만든다.

### 규칙 다섯

1. **전진 중인 유닛만 민다.** 멈춰 있거나 잼에 껴서 못 가는 유닛은 미는 쪽이 되지 못한다
2. **비켜준 쪽은 되밀지 않는다.** 상호작용이 한 방향이라 되튀김이 성립하지 않는다
3. **둘 다 전진 중이면 서로 안 민다.** 대칭이 생길 여지를 원천 차단한다. 이 경우는 §11 의
   걸음 고르기가 푼다
4. **힘이 아니라 위치로 민다.** 속도에 항을 더하지 않는다
5. **비켜준 유닛은 자기 목적지를 잃지 않는다.** 옆으로 물러났다가 제 갈 길을 다시 잡는다

`_is_advancing` 이 이 설계의 전부다. **"움직이는 중"을 상태(`MOVING`)로 물으면 안 된다** —
잼 한가운데에서 한 뼘도 못 가는 유닛도 상태는 `MOVING` 이고, 그것들이 서로 미는 쪽이 되면
곧바로 대칭으로 되돌아간다. 그래서 **실제로 옮겨 간 거리**(`advance`)로 묻는다.

### 겹친 뒤 떼어 놓는 것이 아니라, 닿기 전에 비켜서게 한다

예전 `_resolve_overlaps` 는 **겹친 다음에** 풀었다. 그러면 겹침이 있어야 하고, 겹침이
있으려면 몸이 서로 파고들어야 하고, 파고든 만큼 통과 위험이 생긴다.

비켜주기는 **앞서 일어난다.**

```
전진 중인 유닛의 진행 방향으로 앞을 본다
  +--> 그 진로 안(반경 안)에 전진하지 않는 아군이 있는가
  +--> 있으면 그 아군을 진로 밖으로 밀어낸다 — 진행 방향의 수직으로만
  +--> 그 아군이 벽이나 다른 몸에 막혀 못 비키면 그만큼만 비킨다
  +--> 그다음에 §11 의 걸음 고르기가 돈다. 진로가 열렸으면 그냥 간다
```

**진행 방향의 수직으로만 민다.** 진행 방향으로 밀면 그것이 "밀고 나아가기"이고, 앞선 유닛을
목적지까지 떠밀어 버린다. 옆으로만 밀면 밀린 유닛은 **길에서 비켜설 뿐 어디로도 가지 않는다.**

**이동을 막는 판정(`_room`)은 그대로 둔다.** 비켜주기는 길을 열어 줄 뿐이고, 안 열리면
못 간다. 그래서 한 칸 폭 복도에서는 옆으로 비킬 자리가 없어 여전히 못 지나간다 —
`test_proto_unit_push.gd` 가 지키는 성질이 그대로 남는다.

### `정지밀림` 지표의 뜻이 바뀐다

§9 · §11 에서 이 값은 **0 이어야 하는 값**이었다. 이제는 **비켜준 거리**이고 0 이 아니어야
정상이다. 대신 물어야 할 것이 바뀐다 — **되밀림이 있는가**(대칭이 되살아났는가)와
**진행 방향으로 밀렸는가**(밀고 나아갔는가). 둘 다 구조적으로 불가능하게 짰고, 테스트가
그것을 못 박는다.

### 재 본 결과 — 작은 규모는 풀렸고 100 명은 안 풀렸다

**4 · 8 · 12 · 24 · 40 · 100 을 전부 쟀다.** 지금까지 40 과 100 만 재어서 정작 흔한 규모에서
어떤지 아무도 몰랐다. 스쿼드 정원은 서넛이고 소환수와 다른 스쿼드가 겹쳐야 수십이 된다.

좁은 문 통과 시간(괄호는 못 넘은 인원).

| 인원 | 힘 있을 때 | 힘 걷어낸 뒤 | 비켜주기 |
| --- | --- | --- | --- |
| 4 | - | - | **4.33 s** |
| 8 | - | - | **4.85 s** |
| 12 | - | - | **5.48 s** |
| 24 | - | - | **6.15 s** |
| 40 | 6.23 s | 못함 (5 명) | 못함 (18 명) |
| 100 | 못함 (1 명) | 못함 (83 명) | 못함 (46 명) |

**작은 규모는 전부 풀렸다.** 힘을 걷어낸 판에서는 24 명도 문 앞에서 굳었는데
비켜주기가 그것을 통째로 되돌렸다. 40 과 100 은 여전히 못 넘는다.

꺾임과 튕김.

| 상황 | 꺾임 · 힘 있을 때 | 꺾임 · 힘 뺀 뒤 | 꺾임 · 비켜주기 | 튕김 · 비켜주기 |
| --- | --- | --- | --- | --- |
| 좁은 통로 40 | 165 | 280 | 335 | **0.0 px** |
| 좁은 통로 100 | 246 | 366 | 495 | **0.0 px** |
| 열린 곳 40 | 64 | 184 | 246 | **0.0 px** |
| 열린 곳 100 | 75 | 237 | 263 | **0.0 px** |

**꺾임이 합격선을 못 넘었다. 숨기지 않고 적는다.** 튕김 0 은 지켰고 도착 후 진동도 0 이다.

꺾임이 나빠진 이유는 둘로 갈린다. 하나는 지표가 **비켜서는 유닛의 옆걸음을 이동의 꺾임으로
센다**는 것이다 - 초당 140 픽셀로 옆으로 밀리면 그 프레임의 진행 방향은 옆이고, 지표는
그것을 방향이 꺾인 것으로 읽는다. 다른 하나는 진짜다 - **막히면 서고 트이면 가는 걸음**이
잼에서 자주 갈아 끼워진다. 지금 지표는 이 둘을 못 가른다.

### 비켜주기 속도 하나가 통과와 꺾임을 맞바꾼다

| 초당 픽셀 | 통로 40 통과 | 통로 100 못 넘음 | 꺾임 100 | 열린곳 100 꺾임 | 이동 계산 100 |
| --- | --- | --- | --- | --- | --- |
| 140 | 못함 (18 명) | **46 명** | **495** | **263** | **5.19 ms** |
| 220 | 못함 (12 명) | 76 명 | 514 | 271 | 2.10 ms |
| 300 | **33.37 s 전원** | 55 명 | 683 | 291 | 7.47 ms |

300 이 40 명 판을 유일하게 뚫지만 이동 계산이 7.47 밀리초로 웹 예산을 넘긴다.
140 을 골랐다 - 성능 한도를 지키고 꺾임이 가장 낮고 100 명 판에서 못 넘은 인원도 가장 적다.

**어느 값도 100 명을 뚫지 못한다.** 값을 돌려서 될 문제가 아니라는 뜻이고, 그것이 이번
측정의 결론이다. 다음은 **좁은 목의 순서 정하기**(먼저 지나가기)와 **흐름장에 벽 거리
비용 넣기**다 - 둘 다 "누가 어디서 기다리느냐"를 정하는 것이고, 비켜주기처럼 이미 뭉친
무리를 푸는 것이 아니라 **뭉치는 것 자체를 막는다.**

### 자리 폴백 버그 - 좁을수록 커지던 폭탄

`build_slots` 가 통행 불가로 걸러져 자리가 모자라면 **남은 인원 전부에게 목표 지점 한 점을
줬다.** 대형 자리를 만든 이유 자체가 "전원에게 같은 좌표를 주면 그 한 점을 두고 영원히
밀어댄다"였는데(§3), 폴백이 그것을 되살려 놓고 있었다.

**좁은 곳일수록 걸러지는 자리가 많으니 좁을수록 폴백이 커진다.** 하필 우리가 못 푸는 판에서
최악이 되는 모양이었다.

이제 자리가 모자라면 **격자를 넓힌다**(반지름 두 배씩 세 번). 훑는 순서는 예전 그대로
행 우선으로 두었다 - 고리 단위로 바꿨더니 같은 거리의 자리 중 뽑히는 것이 달라져
대열 폭이 152 에서 156 으로 벌어졌다. **넓히는 것과 훑는 순서는 따로 두어야 한다.**

| 구석 24 명 | 정지 | 꺾임 |
| --- | --- | --- |
| 밀치기 있던 시절 | 3.02 s | 162 |
| 폴백 버그와 함께 | 4.23 s | 389 |
| 폴백 고친 뒤 | **3.02 s** | **332** |

**밀치기 시절 값으로 정확히 돌아왔다.** 다른 판은 거의 안 움직였다 - 열린 곳에서는
걸러지는 자리가 없어 폴백이 애초에 안 걸렸기 때문이고, 그것이 이 고침이 **버그 수정이지
기법이 아니라는** 증거이기도 하다.

### 산개는 이미 되어 있었다

"100 명이 전부 같은 좌표를 목표로 한다"는 지적이 있었는데 **그렇지 않다.**
`issue_move` 가 명령마다 `ProtoFormation.build_slots` 로 인원수만큼 자리를 만들고
`assign` 으로 나눠 준다(§3). 유닛은 각자 다른 좌표를 목표로 하고 있다.
배정 방식에 개선할 점은 남아 있다 - **접근 방향을 안 본다**(§13).

## 13. 프레임 드랍을 잡는다 (6 단계)

의뢰인이 직접 굴려 보고 말했다.

> **"엄청 많이 움직였을 때 초기 버전이랑 다르게 프레임 드랍이 너무 심해서 최적화가 필요해"**

**"초기 버전이랑 다르게" 가 핵심이다. 회귀다.** 우리가 무언가를 넣으면서 나빠졌다.

### 안 보이던 값을 먼저 드러냈다

두 가지가 프레임을 먹고 있었는데 **하나는 지표에 아예 안 잡히고 있었다.**

| 무엇 | 언제 도는가 | 왜 안 보였나 |
| --- | --- | --- |
| 매 프레임 조향 | 60 번 / 초 | `last_step_usec` 이 재고 있었다 |
| **흐름장 생성** | 명령마다 한 번 | **지표 도구가 명령 한 번 주고 40 초를 굴린다.** 평균에 묻힌다 |

흐름장 생성은 **우클릭을 처리하는 그 프레임 안에서 동기로 돈다.** 60 x 34 판에서 재어 보니
**44 ~ 48 밀리초** — 프레임 예산 16.7 밀리초의 세 배다. **우클릭할 때마다 세 프레임이 멎었다.**
`flow_build_peak` 을 달고 `tools/bench_flow_field.gd` 를 만들어 이 값을 항상 보이게 했다.

### 원인은 알고리즘이 아니라 함수 호출 횟수였다

`_integrate` 와 `_derive_directions` 는 칸마다 이웃 여덟을 보면서 `is_walkable` ·
`cell_index` · `_diagonal_open`(그 안에서 또 두 번)을 불렀다. 2040 칸이면
**GDScript 함수 호출만 오만 번**이고, 그 호출 비용이 계산 비용보다 컸다.

알고리즘은 한 글자도 안 바꿨다. 이웃을 좌표가 아니라 **평평한 번호의 덧셈**으로 짚고,
벽 판정을 배열에서 바로 읽고, 경계 검사를 지역 변수로 직접 한다.

### 걸음 고르기는 벽이 없으면 벽을 안 본다

걸음 고르기는 잼에 낀 유닛마다 후보를 열둘까지 재고 **후보마다 벽 표본이 다섯**이다.
그런데 열린 방에서는 그 표본이 전부 헛일이다.

벽 거리는 §12 에서 지형당 한 번 구워 두었으므로(`_clearance`) **"내 둘레에 벽이 없다"를
배열 읽기 한 번으로 알 수 있다.** 그러면 유닛당 예순 번의 원-벽 판정이 통째로 사라진다.
포화 지점을 두 칸에서 세 칸으로 늘린 것이 이것 때문이다 — 값을 매기는 데는 두 칸이면 되는데,
"벽이 아예 없다"를 안전하게 말하려면 몸 반지름 12 에 내다보는 거리 32 를 더한 만큼이 필요하다.

비켜주기의 `_yield_room` 이 **쌍마다 배열을 새로 만들던 것**도 걷어냈다. 잼 한가운데에서
프레임마다 배열이 수백 개씩 생겼다 사라졌다.

### 결과

| 무엇 | 밀치기 시절 | 힘 걷어낸 뒤 | 비켜주기 뒤 | **지금** |
| --- | --- | --- | --- | --- |
| 흐름장 생성 (평균) | 44 ms | 44 ms | 44 ms | **8.0 ~ 8.5 ms** |
| 흐름장 생성 (최악) | ~56 ms | ~56 ms | ~56 ms | **9.7 ~ 12.3 ms** |
| 100 명 이동 계산 (지표) | 3.24 ms | 5.19 ms | 7.70 ms | **3.63 ms** |
| 100 명 이동 계산 (벤치) | 3.24 ms | 6.07 ms | 6.07 ms | **3.87 ms** |
| 100 명 최악 프레임 | - | 35.6 ms | 42.6 ms | **12.1 ms** |
| 100 명 fps | 124 | 104 | 90 | **111** |

**흐름장이 프레임 예산 안으로 들어왔다.** 44 밀리초에서 8 밀리초로, 다섯 배 남짓이다.
그리고 **최악 프레임이 42.6 에서 12.1 밀리초로 내려갔다** — 의뢰인이 본 뚝뚝 끊김이
이 값이다. 평균 fps 보다 이쪽이 체감에 가깝다.

### 이것이 순수한 최적화라는 증거

지표 도구의 **모든 이동 결과가 한 자리도 안 바뀌었다.** 걸음꺾임 · 방향반전 · 통과 시간 ·
정지 시간 · 튕김이 최적화 전과 정확히 같은 값으로 나온다. 계산 순서와 자료 접근만 바꿨고
판단은 그대로라는 뜻이다. **빨라지면서 조용히 달라진 것이 없다.**

### 아직 안 한 것

- **웹 실측이 없다.** 네이티브 8 밀리초가 웹 단일 스레드에서 얼마인지는 모른다. 제출물이
  웹이므로 이건 재야 한다
- 100 명 이동 계산이 3.87 밀리초로 초기 3.24 에 아직 0.6 밀리초 못 미친다. 남은 차이는
  걸음 고르기의 후보 훑기다
- **막힌 유닛이 경로를 다시 잡지 않는다.** 의뢰인이 "살짝 돌았다가 바로 다시 막힌 길을
  탐색하려 한다"고 했다. 흐름장이 전역 최단을 계속 가리키므로 국소 회피가 풀리는 순간
  도로 당겨진다. **빠진 것은 막혔다는 기억과 이력현상이다.** 다음 순번이고, 흐름장이
  8 밀리초가 된 지금은 다시 굽는 것도 선택지에 들어온다

## 14. 막힘 기억 (7 단계)

의뢰인이 본 것 — **"살짝 돌았다가 바로 다시 막힌 길을 탐색하려 한다."**

정확한 관찰이다. 걸음 고르기(§11)는 몸 하나를 돌아 나가는 **국소 판단**이라, 돌아 나가는
순간 흐름장이 도로 원래 길로 당긴다. **흐름장이 막힘을 모르기 때문이다.**
빠진 것은 길 찾기가 아니라 **기억과 이력현상**이다.

### 설계 판단 둘

| 물음 | 고른 것 | 왜 |
| --- | --- | --- |
| 기억의 주인은 누구인가 | **명령 받은 무리** | 유닛마다 구우면 8 밀리초 곱하기 인원이다. 같은 목적지로 같이 가는 무리는 실제로 같은 곳에서 막힌다 |
| 어떻게 피하나 | **막지 않고 값을 물린다** | 아예 막으면 길이 하나뿐일 때 갈 곳이 없어진다. 값이면 돌아갈 길이 있을 때만 돌아간다 |
| 언제 푸나 | **그 칸이 실제로 비었는지 보고** | **시간으로 풀면 도로 당겨진다** — 의뢰인이 본 증상이 정확히 그 모양이다 |
| 얼마나 자주 굽나 | **판 전체에 상한** (`_REBAKE_GAP`) | 막힘이 잦으면 굽기도 잦다. 한 번이 8 밀리초라도 초당 여럿이면 그게 다시 프레임 문제다 |

이력현상은 **확인 횟수**로 준다(`_JAM_FORGET`). 막힌 칸은 세 번의 확인 동안 비어 있어야
풀린다 — 한 프레임 스쳐 비는 것에 속지 않으면서, 정말 비면 반드시 풀린다.

### 잰 것 — 40 명이 처음으로 뚫렸고 100 명은 나빠졌다

| 좁은 통로 | 기억 없음 | 기억 (값 3.0 / 간격 30) | **기억 (값 1.2 / 간격 60)** |
| --- | --- | --- | --- |
| 40 통과 | 못함 (4 명) | 못함 (8 명) | **10.32 s 전원** |
| 100 통과 | 못함 (39 명) | 못함 (37 명) | 못함 (58 명) |
| 40 방향반전 | 0.49 | 0.51 | 0.58 |
| 100 방향반전 | 0.36 | 0.62 | 0.55 |

**40 명이 이 판에서 처음으로 전원 통과했다.** 밀치기를 걷어낸 뒤로 한 번도 못 하던 것이다.
대신 100 명이 39 에서 58 로 나빠졌고, **방향반전이 어디서나 올라갔다** — 흐름장을 다시
구우면 그 명령의 전원이 새 방향을 받으므로, 잘 가던 유닛까지 방향이 한 번 꺾인다.
**공유 기억의 대가가 여기서 보인다.**

값 1.2 · 간격 60 을 골랐다. 40 명 전원 통과는 **넘느냐 못 넘느냐의 문턱**이고,
100 명의 39 대 58 은 어느 쪽이든 실패한 판 안에서의 정도 차이다. 다만 **이 선택은 약하다** —
다음 사람이 뒤집어도 좋고, 뒤집을 근거가 위 표에 다 있다.

### 곁다리 — 순환은 원인이 아니었다

`blocker_id` 한 줄로 **막힘 그래프**가 생겼다. 빈 거리를 재는 훑기가 이미 "나를 가장 늦추는
이웃"을 고르고 있어서 추가 비용이 0 이다. 유닛마다 나가는 간선이 최대 하나라 기능 그래프이고,
순환 찾기가 유닛 수만큼만 든다.

| 상황 | 순환 수 | **순환 최대 길이** | 순환에 묶인 유닛 | 못 넘은 인원 |
| --- | --- | --- | --- | --- |
| 좁은 통로 100 | 5 | **2** | 10 | 37 |
| 좁은 통로 40 | 2 | **2** | 4 | 8 |
| 한 칸 문 40 | 4 | **2** | 8 | 37 |
| 맞교차 40 | 6 | **2** | 12 | - |
| 열린 곳 100 | 6 | **2** | 12 | - |

**답이 나왔다. 순환은 원인이 아니다.**

- **어디서나 순환 길이가 정확히 2 다.** 셋 이상이 물고 도는 고리가 한 번도 안 나왔다.
  둘이 마주 보고 서로를 막는 것뿐이고, 그건 비켜주기와 걸음 고르기가 다루는 상황이다
- **순환에 묶인 유닛이 100 명 중 열 명이다.** 못 넘은 37 명의 3 분의 1 도 안 된다.
  **나머지는 그냥 문이 좁아 줄이 긴 것이다**
- **열린 곳 100 과 맞교차 40 에도 순환이 똑같이 있다**(6 개, 12 명). 그런데 둘 다 전원 도착한다.
  순환이 있다고 못 가는 게 아니라는 뜻이다

조사 레인 예측 하나는 빗나갔다 — "폭 1 통로는 다리라 순환이 없다"였는데 **한 칸 문에서
순환 4 개가 나왔다.** 칸 그래프에서는 다리가 맞지만 **우리는 연속 좌표**라, 한 칸 폭 안에서도
둘이 좌우로 어긋나 서로를 가장 늦추는 이웃으로 지목할 수 있다. 칸 기준의 정리를 연속 좌표에
그대로 옮길 수 없다는 증거가 하나 더 늘었다.

### 웹 실측은 못 했다

**내보내기 템플릿이 안 깔려 있다.**

```
예상된 경로에서 찾은 내보내기 템플릿이 없습니다:
C:/Users/adohi/AppData/Roaming/Godot/export_templates/4.7.1.stable/web_nothreads_release.zip
```

`export_presets.cfg` 에 `Web` 프리셋은 있고(`build/web/index.html`) 설정도 서 있지만,
템플릿 내려받기는 1 기가바이트에 가깝고 이 레인이 임의로 할 일이 아니라 판단해 멈췄다.
**네이티브 대비 배수는 아직 모른다.** 흐름장 8 밀리초가 웹에서 몇 배가 되는지 모르는 채이므로,
`_REBAKE_GAP` 이 지금 값으로 충분한지도 확정할 수 없다. **템플릿이 깔리면 이것부터 재라.**

## 15. 양보 우선순위와 전파 (8 단계) — 좁은 문이 뚫렸다

의뢰인이 직접 굴려 보고 둘을 지적했다.

> **"여전히 전파해서 자리 비켜주는 거 안 되고 있고, 막혀 있을 때 돌아가는 것도 잘 구현 안 되어 있어"**

전파는 만든 적이 없었으므로 맞는 지적이다. 이번에 만들었다.

### 먼저 양보 우선순위 — 공짜였다

§12 의 비켜주기에는 구멍이 있었다. **"둘 다 전진 중이면 서로 안 민다"** 로 대칭을 피했는데,
대칭은 확실히 없어졌지만 **둘 다 가는 중일 때 아무도 안 비켰다.** 문 앞은 정확히 그 상황이다.

비대칭을 지키면서 비키게 하려면 **누가 먼저인지 정하면 된다.** 그 순위가 이미 있었다 —
**흐름장이 칸마다 들고 있는 목적지까지의 비용**이다. 배열 조회 한 번이라 추가 계산이 0 이고,
거리와 달리 **실제로 가야 하는 길이**라 문 앞에서 누가 먼저인지가 그대로 나온다.
전순서라 **순환 교착이 구조적으로 불가능하다.**

**한 번 크게 틀렸다.** 진로에 들기만 하면 순위로 밀게 했더니 옆걸음이 세 배 반으로 뛰고
(17 → 60 px) 좁은 문 40 명이 전원 통과에서 열 명 낙오로 되돌아갔다. 스쳐 지나가는 상대까지
계속 밀어 대면서 줄이 흐트러진 것이다. **순위는 길을 다투는 자리에서만 쓴다** —
`blocker_id` 가 그 상대를 가리키고 있을 때만.

### 그 위에 전파

의뢰인의 발상이 그대로다 — *"비키다가 또 막혀 있으면 계속 비키라고 전파하면 결국 교착이
풀리지 않을까."*

§12 의 비켜주기는 **바로 앞의 한 쌍만 본다.** 문 앞에서 굳는 것은 비킬 자리가 없어서인데,
그 자리를 만들어 줄 수 있는 것은 **앞의 유닛**이고 아무도 걔한테 말을 안 걸었다.

`blocker_id` 사슬을 따라가며 차례로 "비켜라"를 물려준다. **추가 훑기가 0 이다** —
빈 거리를 재는 훑기가 이미 "나를 가장 늦추는 이웃"을 고르고 있었다.

| 지킨 것 | 왜 |
| --- | --- |
| **깊이 상한 8** | 사슬이 길면 한 프레임에 판 전체를 훑는다 |
| **방문 표시** | 고리에 걸리면 영원히 돈다. **억지로 풀지 않고 세기만 한다** |
| **`HOLDING` 확정 순간에만** | 매 프레임 다시 고르는 것이 지터의 씨앗이다(§7 · §10) |
| **미는 방향은 뒤에 선 유닛의 진로** | 앞을 어디론가 보내는 게 아니라 길에서 비켜서게 한다 |

PIBT(Okumura 외, IJCAI 2019)의 우선순위 상속이 같은 발상이다. 다만 **그쪽의 완전성 보장은
우리에게 무효다** — 격자 점유 · 같은 몸집 · 동기 이산 시간 · 한 걸음 이동이라는 전제가
우리 판에서 넷 다 깨진다. **발상만 가져오고 보장은 쫓지 않았다.**

### 결과 — 100 명이 처음으로 전원 통과했다

| 좁은 통로 | 힘 있을 때 | 힘 뺀 뒤 | 비켜주기 | 막힘 기억 | **전파** |
| --- | --- | --- | --- | --- | --- |
| 4 / 8 / 12 | - | 굳음 | 전원 | 전원 | **4.33 / 4.97 / 5.03 s** |
| 24 | - | 굳음 | 6.15 s | 6.08 s | **5.53 s** |
| 40 | 6.23 s | 못함 (5) | 못함 (18) | 10.32 s | **12.85 s** |
| **100** | 못함 (1) | 못함 (83) | 못함 (46) | 못함 (58) | **24.47 s 전원** |

**밀치기를 걷어낸 뒤로 100 명이 문을 넘은 것은 이번이 처음이다.** 24 명은 6.15 에서
5.53 초로 함께 빨라졌다. 열린 곳과 맞교차는 전원 도착 그대로다.

지킬 것도 지켰다 — **튕김 0.0 px**(좁은 문 둘만 6.0), **도착 후 진동 0**, 상호 통과 불가,
최악 프레임 11.7 ms, 이동 계산 100 명 3.99 ms.

**한 칸 문 40 명은 여전히 못 넘는다**(39 명). 폭이 한 칸이면 옆으로 비켜설 자리가 없고,
그때는 전파해도 아무도 못 비킨다. **이건 고칠 것이 아니라 맞는 결과다** —
`test_proto_unit_push.gd` 가 지키는 성질이 바로 그것이다.

### 아직 못 넘은 것

**걸음꺾임이 여전히 기준선 위다** — 좁은 통로 100 에서 364(기준 246), 열린 곳 100 에서
241(기준 33). 열린 곳이 특히 멀다. 다만 §13 에서 갈라 둔 **방향반전**(진짜 지터)은
열린 곳에서 0.22 회/초로 낮다. **걸음꺾임이 큰 것은 떨어서가 아니라 막히면 서고 트이면
가는 걸음이 각져서**일 가능성이 높은데, 그것을 가르는 지표가 아직 없다.

### 보이게 만들었다

숫자만으로는 "되고 있다"를 말할 수 없다는 것이 이번 지적의 핵심이었다.

- **전파가 밀어낸 유닛에 주황 고리가 번쩍인다**(24 프레임 남는다). 개발 표시(F1)
- 위쪽 요약에 **전파 횟수 · 옮긴 수 · 고리에 걸린 횟수 · 길 다시 찾기 횟수 · 흐름장 시간**
- 조절판(Tab)에 **`비켜라 전파`** 와 **`막히면 길 다시 찾기`** 를 0 · 1 로 껐다 켠다.
  직접 껐다 켜며 견주면 무엇이 일을 하는지 눈으로 갈린다

**돌린 횟수와 옮긴 수를 나란히 낸 이유**가 있다. 둘이 크게 벌어지면 전파가 헛도는 것이고,
그러면 필요한 것은 전파가 아니라 다른 길이다. 실제로 24 명 판에서 534 회 돌려 498 번
옮겼고 388 번은 고리에 걸렸다 — **고리가 그만큼 흔하다는 것도 이 숫자로 처음 보인다.**

## 16. 전파는 도는데 왜 아무 일도 안 일어나는가 (진단)

의뢰인이 `c8d06d3` 을 만져 보고 말했다.

> **"돌아가는 건 잘 돼. 근데 전파해서 뒤에 막힌 애들이 비켜주는 건 안 돼"**

요약줄은 `전파 534 회 (옮김 498, 고리 388)` 을 찍는다. **돌긴 도는데 눈에 아무 일도 안
일어난다.** 어딘가에서 헛돈다. **고치기 전에 어디서 헛도는지 재기로 했다.**

계기를 여덟 개 달았다 — 사슬이 앞으로 뻗는지 뒤로 뻗는지, 깊이 상한에 걸리는 비율,
고리 길이 분포, 눌린 프레임 대 기다림 확정 수, **비켜설 자리가 없어 실패한 횟수**,
그리고 **실제로 옮긴 거리**.

**성공 한 번에 0.6 픽셀이다.** 사람이 볼 수 있는 크기가 아니다. 그리고 **시도의 54 퍼센트는

1. **미는 양이 구조적으로 작다.** `_step_aside` 는 "뒤에 선 유닛의 중심선에서 벗어날

2. **자리가 없으면 그냥 실패한다.** 비켜서라는 말은 전해졌는데 그 유닛도 갇혀 있다.
   **그 유닛의 옆자리를 차지한 놈에게는 아무도 말을 안 건다.** `blocker_id` 는

**비켜설 방향을 막은 상대를 가리키는 간선**이다. 빈 거리를 재는 훑기가 이미 이웃을 보고
있으므로 그 간선을 만드는 값은 거의 0 이다.

**다음에 할 것은 둘이다** — 미는 양을 "중심선 탈출"이 아니라 **몸이 실제로 빠져나갈 만큼**으로
키우고, 자리가 없을 때 **그 자리를 막은 놈으로 사슬을 잇는 것.** 아직 안 고쳤다.

## 17. 전파가 실제로 몸을 움직이게 만들다 (9 단계)

§16 의 진단은 **"성공 한 번에 0.6 픽셀"** 이었다. 전파는 도는데 몸이 안 움직였다. 셋을 고쳤다.

### 1. 미는 양 — 몸 반지름만큼은 옮긴다

예전에는 "뒤에 선 유닛의 중심선에서 벗어날 만큼"만 밀었다(`touch - lateral`). 빽빽한 잼에서는
두 몸이 이미 거의 나란해서 그 값이 1 픽셀 언저리다. **몸 반지름의 0.6 배를 바닥으로 깔았다.**

**밀치기로 되돌아가지 않는 경계는 그대로다** — 미는 방향은 여전히 **뒤에 선 유닛의 진로에
수직**이라 진행 방향 성분이 0 이고, 되밀지 않으며, 밀린 유닛은 목적지도 명령도 그대로 든다.
`test_proto_unit_push.gd` 와 `test_yielding_is_one_way` 가 그것을 계속 못 박는다.

### 2. 자리가 없으면 **그 자리를 막은 놈**으로 사슬을 잇는다

진단에서 가장 큰 숫자였다 — **시도의 54 퍼센트가 자리가 없어 실패**했다. `blocker_id` 는
"내 진로를 막은 놈"만 알고 "내가 비켜설 자리를 막은 놈"은 모른다. 그 둘은 다른 유닛이다.

`_shove` 가 그 둘째 간선을 탄다. **방문 표시를 두 간선이 함께 쓴다** — 섞어 타면 고리가
늘 수 있어서 한쪽에서 이미 본 유닛은 다른 쪽에서도 안 본다.

### 3. 사슬을 화면에 그린다

노랑 화살표는 **진로를 막은 상대**, 하늘 화살표는 **내가 비켜설 자리를 막은 상대**.
주황 고리는 0.4 초에서 **1.5 초**로 늘렸다(의뢰인이 못 봤다). 진단에서 잰 "앞으로 59 / 뒤로 41"이
이 그림에서 그대로 보인다.

### 잰 것

| 못 비킴 | 2761 (시도의 54 %) | **798 (28 %)** |
| 옮긴 거리 | 1404 px | **9279 px** |

**한 칸 문에서 못 넘는 인원이 절반으로 줄었다.** 폭이 한 칸이라 옆으로 비킬 자리가 없는
판인데, 자리를 막은 놈으로 사슬을 이으면서 **줄줄이 밀려 앞이 트이는 경우**가 생긴 것이다.

### 대가 두 가지

- **열린 곳 100 이 느려졌다**(11.45 → 18.27 초). 전파가 대형 안에서도 돌아 자리를 흩는다.

- **열린 곳 40 의 도착 후 진동이 9.8 px 다.** 다른 판은 전부 0 인데 여기만 남았다.
  **지켜야 할 성질이 0 이므로 이건 고쳐야 한다.** 아직 원인을 못 짚었다

성능은 지켰다 — 최악 프레임 12.6 ms, 이동 계산 100 명 4.29 ms.

## 18. 양보는 되돌려지는가 (진단)

의뢰인의 물음 — **"비키라고 명령 가도 잠깐 비키려고 하다가 다음 스케줄에서 다시 목적지로
가려고 해서 병목 생길 수 있음."**

맞다면 지금까지의 증상이 한 번에 설명된다. 밀어 놓아도 순수 변위가 0 이면 아무 일도 안
일어난 것과 같고, 계기만 "옮겼다"고 말한다.

### 재는 법을 한 번 고쳤다

처음에는 밀린 뒤 0.3 초의 **순수 변위 크기**를 쟀다. 남은 비율이 어디서나 266~1658 퍼센트로
나왔다 — "되돌아오기는커녕 훨씬 멀리 갔다"는 뜻인데, **유닛이 제 발로 걸은 거리가 섞여
있었다.** 20 프레임이면 어차피 많이 움직인다.

**밀린 방향으로 투영해야** "밀어 준 그 방향으로 남아 있는가"가 갈린다. 그렇게 다시 쟀다.

### 결과 — 사실이다. **그리고 잼이 심할수록 심하다**

| 상황 | 밀린 합 | 0.3 초 뒤 (밀린 방향 투영) | **남은 비율** |
| --- | --- | --- | --- |
| 맞교차 40 | 273 px | 49 px | **18 %** |
| 한 칸 문 40 | 6053 px | 2842 px | **47 %** |
| 좁은 통로 100 | 6025 px | 3478 px | **58 %** |
| 좁은 통로 40 | 658 px | 810 px | 123 % |
| 열린 곳 100 | 2069 px | 2052 px | 99 % |
| 열린 곳 24 | 133 px | 350 px | 264 % |
| 열린 곳 8 | 11 px | −16 px | **−141 %** |

**의뢰인의 가설이 맞다.** 다만 어디서나 그런 것이 아니라 **막힌 판에서만** 그렇다.

- **맞교차 40 은 82 퍼센트가 되돌려진다.** 마주 오는 둘이 서로 밀고 서로 되돌아온다
- **한 칸 문과 좁은 통로 100 은 절반이 되돌려진다.** 밀어 준 몫의 절반이 사라진다
- **여유 있는 판에서는 100 퍼센트 넘게 남는다.** 비킨 김에 그쪽으로 계속 가기 때문이다
- **열린 곳 8 은 음수다.** 밀린 방향의 **반대로** 더 갔다 — 완전히 취소되고 제자리를 지나쳤다

즉 **양보는 한 프레임짜리 충격일 뿐이고, 다음 프레임 조향이 곧바로 목적지를 다시 가리킨다.**
잼에서는 목적지 방향이 곧 되돌아오는 방향이라 밀어 준 것이 그대로 지워진다.

### 그래서 필요한 것은 「양보 상태의 지속」이다

명령이 한 번의 변위가 아니라 **비켜설 자리에 실제로 도달할 때까지 유지되는 상태**여야 한다.
다만 여기서 **물러남 ↔ 목적지 복귀의 왕복**이 생길 위험이 크다. §14 에서 쓴 이력현상 —
**시간이 아니라 조건 확인으로 푸는 것** — 이 여기서는 "앞이 실제로 트였는지 확인"이 된다.

**아직 안 고쳤다. 진단에서 끊는다.**

## 19. 양보를 상태로 바꾸다 (10 단계)

§18 에서 쟀다 — **잼에서 양보의 절반 이상이 0.3 초 안에 지워진다**(맞교차 18 %,
한 칸 문 47 %, 좁은 통로 100 은 58 %). 밀어 놓아도 다음 프레임 조향이 곧바로 목적지를
다시 가리키고, **잼에서는 목적지 방향이 곧 되돌아오는 방향**이라 밀어 준 것이 사라진다.

그래서 양보를 **한 번의 변위가 아니라 상태**로 바꿨다.

### 무엇을 바꿨나

| 예전 | 지금 |
| --- | --- |
| 밀린 그 프레임에만 위치가 바뀐다 | **비켜설 자리**를 들고 그쪽으로 계속 간다 |
| 다음 프레임 조향이 목적지를 가리킨다 | 비켜서는 동안 조향이 **비켜설 자리**를 가리킨다 |
| 되돌아오는 것을 막을 방법이 없다 | 자리에 닿거나 **앞이 트여야** 푼다 |

### 푸는 조건은 시간이 아니다

§14 에서 배운 것을 그대로 옮겼다. **"그 칸이 비었는지"** 를 **"앞이 실제로 트였는지"** 로
바꿔 물으면 된다.

| 조건 | 왜 |
| --- | --- |
| 비켜설 자리에 닿았다 | 할 일을 다 했다 |
| 부탁한 쪽이 사라졌거나 멎었다 | 물어볼 상대가 없다 |
| **부탁한 쪽이 더 이상 나에게 막혀 있지 않다** | **앞이 실제로 트였다** |

시간으로 풀면 아직 안 트였는데 도로 당겨진다 — 의뢰인이 본 *"살짝 돌았다가 바로 다시
막힌 길을"* 이 정확히 그 모양이었다.

**자기 자리에 다 온 유닛에게는 안 건다.** 걸면 전원이 멎은 뒤에도 그 유닛이 계속 걸어
도착 후 진동이 되살아난다 — 어렵게 0 으로 만든 계약이다.

### 잰 것 — 지워지던 것이 남는다

| 남은 비율 | §18 (변위) | **지금 (상태)** |
| --- | --- | --- |
| 좁은 통로 100 | 58 % | **72 %** |
| 한 칸 문 40 | 47 % | **64 %** |
| 열린 곳 100 | 99 % | 111 % |
| 맞교차 40 | 18 % | **−39 %** |

**가장 나빴던 둘이 가장 크게 올랐다.** 잼이 심할수록 상태가 하는 일이 크다는 뜻이고,
설계 의도와 맞는다.

| 통과 | §18 | **지금** |
| --- | --- | --- |
| 한 칸 문 40 | 못함 (18 명) | **못함 (14 명)** |
| 좁은 통로 40 | 8.28 s | **8.02 s** (정지 12.45 → 10.90) |
| 좁은 통로 100 | 26.12 s | 33.85 s |
| 열린 곳 100 | 14.62 s | **13.90 s** |

**한 칸 문에서 못 넘는 인원이 또 줄었다**(20 → 18 → 14). 옆이 벽인 판에서 상태가 유지되니
한 번 비켜선 유닛이 도로 안 들어온다.

### 대가와 이상한 것

- **좁은 통로 100 이 26.12 에서 33.85 초로 느려졌다.** 비켜선 유닛이 자리에 닿을 때까지
  제 갈 길을 안 가므로 전체가 늦어진다. 전원 통과는 유지된다
- **맞교차 40 이 18 %에서 −39 %로 뒤집혔다.** 마주 오는 둘이 서로에게 상태를 걸고
  서로의 비켜설 자리로 가면서 더 엉킨다. 도착은 전원 8.72 초라 기능은 멀쩡하다
- **열린 곳 8 의 −141 %는 그대로다.** §18 에서 이상하다고 적어 둔 값이고 상태를 넣어도
  안 움직였다. 표본이 작아서인지 다른 문제인지 아직 모른다

지킬 것은 지켰다 — **도착 후 진동 전 구간 0**, 튕김 0(좁은 문 둘만 6.0), 상호 통과 불가,
좁은 통로 100 전원 통과, 최악 프레임 18.5 ms.

**2(뒤로 물러나기)와 3(깊이 역순)은 아직 안 넣었다.** 하나씩 넣고 하나씩 잰다.

## 20. 뒤로 물러나기 (11 단계) — **아직 못 쓴다**

좁은 통로에서 옆은 벽이다. 옆으로 비킬 자리가 구조적으로 없으니 **뒤로 물러날 수밖에 없다.**
`blocker_id` 의 **반대 간선**(내가 막고 있는 놈)을 따라 "물러나라"를 물려준다.
물러남도 §19 의 상태로 걸어서 지워지지 않게 했다.

**물러남은 밀치기가 아니다.** 금지된 것은 남을 밀쳐서 **전진하는** 것이고, 물러남은 전진의
반대다. 미는 쪽은 뒤가 물러나 준 만큼만 앞이 트이므로 밀어서 나아가는 것이 아니다.

### 잰 것 — 하나는 크게 좋아졌고 둘은 깨졌다

| | §19 (지속만) | **지금 (물러나기)** | |
| --- | --- | --- | --- |
| 좁은 통로 100 통과 | 33.85 s | **19.98 s** | 크게 좋아졌다 |
| 좁은 통로 100 정지 | 37.63 s | **23.53 s** | |
| 좁은 통로 40 통과 | 8.02 s | 8.13 s | 그대로 |
| **한 칸 문 40** | 못함 (14 명) | **못함 (28 명)** | **두 배로 나빠졌다** |
| **좁은 통로 24 뒤진동** | 0.0 px | **8.2 px** | **계약 위반** |
| **최악 프레임** | 18.5 ms | **22.4 ms** | **예산 초과** |
| 열린 곳 100 정지 | 13.90 s | 17.92 s | 나빠졌다 |

**세 가지가 걸려 이 상태로는 못 쓴다.**

1. **최악 프레임 22.4 ms.** 예산이 16.7 ms 이고 20 ms 를 넘으면 사람이 느낀다.
   사슬이 두 방향(옆 · 뒤)으로 뻗으면서 한 번의 전파가 훑는 유닛이 늘었다
2. **좁은 통로 24 의 도착 후 진동이 8.2 px.** 어렵게 0 으로 만든 계약이 깨졌다.
   물러난 유닛이 자기 자리에서 멀어진 채로 남는 경우가 있는 것으로 보인다
3. **한 칸 문 40 이 14 명에서 28 명으로 두 배 나빠졌다.** 가장 크게 풀릴 것으로 본 판이
   가장 크게 나빠졌다 — **예상이 틀렸고, 왜 틀렸는지 아직 모른다.**
   한 칸 폭에서는 물러날 곳도 줄 뒤뿐이라, 앞을 트이게 하는 대신 **줄 전체를 뒤로 밀어**
   문에서 멀어지게 만드는 것이 아닌가 의심하지만 재지 않았다

좁은 통로 100 이 33.85 에서 19.98 초로 내려간 것은 진짜 소득이다(밀치기 시절 5.63 초에는
아직 멀다). **다만 셋을 고치기 전에는 이 판을 켜면 안 된다.**

### 조건을 방향이 아니라 결과로 뒤집었다

**"옆이 막혔으니 뒤로" 가 정확히 반대였다.** 옆이 막힌 곳이야말로 **뒤로 가도 길에서 못 빠지는
곳**이다. 한 칸 폭에서 물러나면 줄 전체가 문에서 멀어질 뿐 길은 그대로 막혀 있다.

그래서 **"물러나면 길에서 빠지는가"** 로 바꿔 묻는다. 물러날 자리의 벽 거리가 두 칸은 되어야
몸이 옆으로 빠질 폭이 실제로 있다. 벽 거리는 지형당 한 번 구워 둔 값이라 조회가 공짜다.

| | 물러나기 (조건 전) | **조건 뒤집은 뒤** | §19 기준선 |
| --- | --- | --- | --- |
| 한 칸 문 40 | 못함 (28 명) | **못함 (18 명)** | 못함 (14 명) |
| 좁은 통로 100 통과 | 19.98 s | 24.62 s | 33.85 s |
| 좁은 통로 24 뒤진동 | 8.2 px | **8.2 px** | 0.0 px |
| 최악 프레임 | 22.4 ms | **22.2 ms** | 18.5 ms |

**한 칸 문이 28 에서 18 명으로 돌아왔다.** 조건이 그 판에서 물러나기를 꺼 준 결과다
(물러날곳없음 93 회). 대신 좁은 통로 100 의 소득이 19.98 에서 24.62 초로 일부 돌아갔다 -
그래도 §19 의 33.85 초보다는 크게 낫다.

**남은 둘은 안 고쳐졌다.** 최악 프레임 22.2 ms 는 여전히 예산 밖이고, 좁은 통로 24 의
도착 후 진동 8.2 px 도 그대로다.

### 맞교차에서는 물러나기가 **한 번도 안 걸린다**

세어 보니 **0 회**다(물러날곳없음도 0 회). 조건이 걸러낸 것이 아니라 **들어오지도 않는다.**

이유는 들어오는 길에 있다. 물러나기는 **옆으로 비켜서기가 실패했을 때만** 불린다. 그런데
맞교차는 열린 곳이라 옆이 늘 트여 있어서 비켜서기가 성공하고, 그러면 물러나기까지 오지 않는다.
**논리적으로는 맞교차야말로 물러나기가 통해야 하는 판인데** - 마주 오는 둘 중 하나가 넓은
곳까지 물러나 길을 내주는 것이 유일한 해법이니까 - 지금 구조로는 그 자리에 닿지 못한다.

**들어오는 조건이 "옆이 막혔는가" 하나뿐인 것이 문제다.** 다음에 볼 곳이다.

### 진입 조건과 사슬 예산을 고쳐 봤고 — **되돌렸다**

둘을 더 고쳤다. **마주 보는 상대에게는 옆과 함께 뒤도 보게** 해서 맞교차에 도달하지 못하던
것을 열었고, 간선마다 따로 두어 **곱해지던** 깊이 상한(앞 8 x 옆 3 x 뒤 6)을 **하나의
예산으로 합쳤다.**

| | 물러나기 | 조건 뒤집기 | 예산 합치기 | **§19 (되돌린 곳)** |
| --- | --- | --- | --- | --- |
| 최악 프레임 (지표) | 22.4 ms | 22.2 ms | 19.0 ms | 18.5~20.7 ms |
| 좁은 통로 24 뒤진동 | 8.2 px | 8.2 px | 8.2 px | **0.0 px** |
| 한 칸 문 40 | 28 명 | 18 명 | 19 명 | **14 명** |
| 좁은 통로 100 통과 | 19.98 s | 24.62 s | 31.88 s | 33.85 s |

**멈추는 규칙 둘을 다 못 만족했다** — 프레임은 예산 밖이고 도착 후 진동은 그대로였다.
예산을 합치는 것으로 프레임이 22.2 에서 19.0 으로 내려갔지만 16.7 에는 못 닿았고,
그 사이 좁은 통로 100 의 소득(19.98 초)은 31.88 초까지 되돌아가 **얻은 것도 거의 없어졌다.**

그래서 `core/` 와 `debug_draw.gd` 와 지표 도구를 §19 상태로 되돌렸다.
**되돌리는 것이 실패가 아니다** — 계약 둘이 살아 있는 상태가 기능 하나보다 낫다.

### 남기는 것 — 다음 사람이 아낄 반나절

1. **방향이 아니라 「길에서 빠지는가」다.** 사용자가 "뒤로 물러나야 한다"고 했을 때 요점은
   방향이 아니었다. 한 칸 폭에서 뒤로 물러나면 **줄 전체가 문에서 멀어질 뿐 길은 그대로
   막혀 있다.** 벽 거리로 "물러나도 안 빠지는 곳"을 걸러내면 한 칸 문이 28 에서 18 명으로
   돌아온다 — 조건은 이 방향이 맞다
2. **진입 조건이 맞교차를 통째로 놓친다.** 물러나기가 "옆으로 비켜서기가 실패했을 때만"
   불리는데, 열린 곳에서는 옆이 늘 트여 비켜서기가 성공한다. **맞교차에서 물러남 0 회**였다.
   마주 보는 조건을 더해도 결과는 안 바뀌었으므로, **진입만 열어서 되는 문제가 아니다**
3. **깊이 상한은 간선마다 두면 곱해진다.** 앞 8 x 옆 3 x 뒤 6 이면 한 번에 백 명을 훑는다.
   **예산은 하나로 두고 나눠 써야 한다** — 이것만으로 22.2 에서 19.0 ms 를 얻었고,
   이 교훈은 되돌린 뒤에도 다음 판에 그대로 쓸 수 있다
4. **뒤로 물러나기는 도착 후 진동을 만든다.** 물러난 유닛이 자기 자리에서 멀어진 채 남는
   경로가 있다. 8.2 px 이 어디서 나오는지는 못 짚었다

## 21. 프레임 판정을 고치다 — **§19 는 예산 안이다**

되돌리면서 알아챈 것이 있다. **§19 가 예산 안이라고 확인된 적이 없었다.**
"최악 프레임 12.6 ms" 는 §17(`eb32f0f`, 지속 상태 들어가기 전) 값이고, §19 의 프레임은
그때 재지 않았다. 되돌린 뒤 재니 18.94 ms 였다.

### 최악값 하나로 판정한 것이 틀렸다

**최악값은 외부 간섭에 가장 취약한 통계다.** 다른 프로세스가 한 번 튀면 그 값이 우리 코드의
값이 된다. 실제로 같은 코드에서 지표 최악값이 18.5~20.7 ms 를 오갔다 — 코드는 한 줄도
안 바뀌었는데. **그 값을 근거로 판단해 왔다.**

병렬 작업 중에 "한가한 기계" 를 만드는 것은 불가능하다. 그래서 **재는 법을 바꿨다**
(`tools/bench_frame_budget.gd`).

| 무엇 | 왜 |
| --- | --- |
| **분위수로 잰다** (중앙 · 95 · 99 · 최악) | 한 번의 딸꾹질이 판정을 뒤집지 못한다 |
| **우리 계산과 프레임을 따로 잰다** | 우리 계산이 4 ms 인데 프레임이 26 ms 면 우리 탓이 아니다 |
| **넘친 프레임에서 우리 몫을 센다** | 남의 탓과 우리 탓이 숫자로 갈린다 |

`last_step_usec` 이 **우리가 이동에 쓴 시간**이고 `_process` 의 delta 가 **프레임 전체
시간**이다. 프레임마다 짝지어 모으면 넘친 프레임에서 우리 몫이 얼마였는지 바로 나온다.

**판정 기준은 95 분위로 삼는다.** 중앙값은 스파이크를 통째로 놓치고 최악값은 남의 딸꾹질
하나에 뒤집힌다. 스무 프레임에 한 번 넘치는 것은 사람이 알아채므로 95 분위면 충분히 엄하다.

### 잰 것 — 600 프레임씩

| 인원 | 이동 계산 중앙 / 95 / 99 / 최악 | 프레임 중앙 / 95 / 99 / 최악 | 넘친 프레임 | **그중 우리 탓** |
| --- | --- | --- | --- | --- |
| 40 | 1.47 / 2.06 / 2.46 / 2.53 | 4.76 / 5.56 / 6.06 / 14.06 | 0 / 600 | **0** |
| **100** | 4.38 / 5.43 / 6.66 / 8.50 | 9.72 / **13.27** / 15.19 / 26.41 | 3 / 600 | **0** |
| 200 | 10.11 / 12.95 / 17.85 / 20.36 | 32.80 / 58.33 / 66.52 / 73.19 | 600 / 600 | 564 |

**§19 는 웹 안전선 100 명에서 예산 안이다.** 95 분위 프레임이 13.27 ms 로 16.7 아래이고,
600 프레임 중 넘친 것이 셋(0.5 %)뿐이며 **그 셋 다 우리 탓이 아니다** — 넘친 프레임에서
우리 계산은 예산의 절반도 안 썼다. **18.94 ms 는 통째로 외부 간섭이었다.**

40 명은 넘친 프레임이 하나도 없다. **200 명은 예산 밖이고 그것은 우리 탓이다**(600 중 564) —
다만 200 은 애초에 안전선 밖이라 목표가 아니다.

### 이 논쟁은 이것으로 닫힌다

앞으로 프레임을 말할 때는 **95 분위와 「그중 우리 탓」을 함께** 낸다. 최악값 하나로
판정하면 다음에 또 같은 자리에서 헛돈다.

**웹 실측은 여전히 없다.** 네이티브에서 예산 안이어도 웹에서 아닐 수 있고, **진짜 답은
거기 있다.** 내보내기 템플릿이 깔리면 이 도구를 그대로 웹에서 돌리면 된다.

## 22. 웹 실측 — **웹에서는 100 명이 예산 밖이다**

내보내기 템플릿이 깔려 드디어 쟀다. **이 레인이 계속 "웹 실측이 없다"고 적어 온 자리다.**

### 어떻게 쟀나

내보낸 웹 빌드는 `run/main_scene` 하나만 띄우고 `-s` 로 스크립트를 못 돌린다. 그래서
같은 측정을 **장면**으로 옮겼다(`tools/web_frame_bench.tscn`). **네이티브에서도 같은 장면을
돌려** 렌더 경로와 스레드 차이만 남게 했다.

내보낼 때만 `run/main_scene` 을 이 장면으로 잠깐 돌리고 끝나면 되돌린다 —
`project.godot` 은 커밋되지 않는다. `build/web/` 은 `.gitignore` 에 넣었다.

**결과를 행마다 즉시 내도록 고쳐야 했다.** 처음에는 마지막에 몰아서 냈는데, 웹에서 200 명
판이 안 끝나 앞의 결과도 못 봤다. 200 명은 아예 빼고 40 · 100 만 쟀다.

### 잰 것 — 300 프레임씩, 같은 장면

| | 계산 중앙 | 계산 95 | 계산 최악 | 프레임 중앙 | 프레임 95 | 넘친 프레임 | **그중 우리 탓** |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 네이티브 40 | 1.70 | 1.92 | 2.34 | 5.00 | 5.56 | 0 / 300 | 0 |
| **웹 40** | 1.70 | 3.20 | 3.80 | 15.28 | 24.80 | 82 / 300 | **0** |
| 네이티브 100 | 4.35 | 5.03 | 5.67 | 10.42 | 11.67 | 0 / 300 | 0 |
| **웹 100** | 6.00 | **11.10** | 21.30 | 20.00 | **41.00** | 168 / 300 | **74** |

### 네이티브 대비 배수

| | 40 명 | 100 명 |
| --- | --- | --- |
| 계산 중앙 | **1.00 배** | 1.38 배 |
| 계산 95 분위 | 1.67 배 | **2.21 배** |
| 계산 최악 | 1.62 배 | 3.76 배 |
| 프레임 95 분위 | 4.46 배 | **3.51 배** |

**계산 중앙값은 40 명에서 1.00 배다** — 부하가 낮으면 웹 단일 스레드가 네이티브만큼 한다.
**인원이 늘고 분위가 높아질수록 배수가 커진다**(1.00 → 1.38 → 2.21 → 3.76). 웹은 평균이
아니라 **꼬리가 나쁘다.**

### 판정

- **40 명은 우리 코드가 예산 안이다.** 프레임이 300 중 82 번 넘쳤지만 **그중 우리 탓은 0** —
  넘친 프레임에서 우리 계산은 예산의 절반도 안 썼다. 브라우저 · 렌더 쪽이다
- **100 명은 우리 탓이다.** 계산 95 분위가 **11.10 ms** 로 예산 16.7 의 3 분의 2 를 혼자 쓰고,
  넘친 168 프레임 중 **74 가 우리 계산 때문**이다. **웹 안전선 100 명은 지금 코드로 못 지킨다**
- 프레임 95 분위 41 ms 는 초당 24 프레임이다. 사람이 확실히 느낀다

**네이티브에서 예산 안이었던 것이 웹에서는 밖이다.** 이 레인이 여러 판에서 "네이티브 기준으로
예산 안"이라고 적어 온 판정은 **웹에서 다시 해야 한다.**

### 곁들여 본 것

- **웹 빌드가 한 번 죽었다** — `memory access out of bounds`(wasm). 200 명 · 600 프레임으로
  내보낸 첫 판에서 났고, 40 · 100 · 300 프레임으로 줄인 뒤에는 안 났다. **인원이나 표본이
  많으면 웹에서 메모리로 죽을 수 있다**는 신호다. 원인은 안 팠다
- WebGL 경고가 여럿 났다(`INVALID_OPERATION: delete: object does not belong to this context`).
  장면을 바꿔 끼우는 이 측정 장면 탓일 수 있어 게임 쪽 문제라고 단정하지 않는다
- **폰트는 문제없었다.** 글리프 검사가 통과하고 웹에서 두부가 안 났다

## 23. 웹 천장은 몇 명인가

**웹 100 명이 안 된다는 것은 알았는데 몇 명까지 되는지를 몰랐다.** 그걸 모르고 최적화하면
필요 없는 일을 하거나, 해도 부족하다. 그래서 인원을 훑었다.

**판정선은 「계산 95 분위가 예산의 절반(8.35 ms) 이하」다.** 우리 계산이 예산의 절반을 넘으면
렌더와 브라우저에 남는 여유가 없다.

### 잰 것 - 웹, 300 프레임씩

| 인원 | 계산 중앙 | 계산 95 | 계산 최악 | 프레임 중앙 | 프레임 95 | 넘친 프레임 | 우리 탓 | 판정 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 8 | 0.40 | 1.00 | 1.30 | 6.67 | 6.94 | 0 / 300 | 0 | 통과 |
| 16 | 0.70 | 1.20 | 1.60 | 8.33 | 11.11 | 2 / 300 | 0 | 통과 |
| 24 | 1.00 | 1.70 | 2.10 | 9.26 | 10.61 | 1 / 300 | 0 | 통과 |
| 40 | 1.70 | 2.20 | 3.30 | 10.61 | 12.70 | 2 / 300 | 0 | 통과 |
| **56** | 2.50 | 2.90 | 3.40 | 12.96 | 14.47 | **3 / 300** | 0 | 통과 |
| 72 | 3.30 | 4.20 | 8.90 | 15.60 | 20.30 | **57 / 300** | 1 | 통과 |
| 100 | 4.70 | 6.50 | 8.50 | 23.81 | 29.17 | **300 / 300** | 1 | 통과 |

### 답 - **우리 계산은 100 명에서도 병목이 아니다**

**계산 95 분위가 100 명에서 6.50 ms 로 판정선(8.35) 안이다.** 인원에 거의 비례해 늘고
(1.00 -> 6.50) 어디서도 판정선을 안 넘는다. **최적화가 필요 없다는 뜻이다.**

그런데 **프레임은 다르다.**

| 기준 | 천장 |
| --- | --- |
| **우리 계산**(95 분위 <= 8.35 ms) | **100 명 이상** |
| **프레임 체감**(넘친 프레임이 드묾) | **56 명** |
| 프레임 경계(넘침이 눈에 들기 시작) | 72 명 (57 / 300) |
| 프레임 무너짐 | 100 명 (300 / 300, 중앙 42 fps) |

**병목은 우리 이동 계산이 아니라 렌더와 브라우저다.** 100 명에서 넘친 300 프레임 중
**우리 탓은 1 건**이다. 우리 계산은 4.7 ms 를 쓰는데 프레임이 23.8 ms 니, 남은 19 ms 는
그리기와 브라우저 몫이다.

**기획에 줄 숫자: 웹에서 편안한 것은 56 명, 경계가 72 명이다.** 스쿼드 정원이 서넛이므로
**"수십 명이 한 방에서 만나는 것"은 웹에서 된다.** 100 명은 프레임이 42 fps 로 떨어진다.

### 앞선 측정과 어긋난다 - 숨기지 않는다

§22 에서 웹 100 명을 **계산 95 분위 11.10 ms, 우리 탓 74 / 168** 로 쟀다.
이번에는 **6.50 ms, 우리 탓 1 / 300** 이다. **같은 빌드, 같은 장면인데 두 배 가까이 다르다.**

무엇이 달랐나 - §22 는 40 과 100 만 쟀고 이번은 8 부터 차례로 올라왔다. **100 을 잴 때
이미 여섯 판을 돌아 wasm JIT 과 캐시가 데워져 있었다.** 웹에서는 그 차이가 두 배로 나타난다.

**그래서 웹 수치는 한 번 재서 결론 내면 안 된다.** 이 판에서 "최악값 하나로 판정하면 안 된다"를
배웠는데, 웹에서는 **한 번의 실행 전체가 최악값처럼 흔들린다.** 앞으로 웹을 잴 때는
**작은 인원부터 차례로 올려 데운 다음** 재고, 그 조건을 함께 적어야 한다.

보수적으로 읽으면 **§22 쪽(차게 시작)이 사용자가 처음 접속했을 때에 가깝고**,
이번 쪽(데워진 뒤)이 한동안 놀고 난 뒤에 가깝다. **둘 다 참이고 조건이 다르다.**

### 웹에서 재는 절차 - 다음 사람이 같은 벽을 넘지 않게

**이 절차가 이 판에서 가장 재사용될 것이다.** 던전 생성 · 방 시각화 · UI 킷도 웹 실측이
미확인으로 남아 있다. 공용 문서(`docs/web-build.md`)로 옮길 값이 있다.

1. **내보내기 템플릿이 깔려 있어야 한다.** `AppData/Roaming/Godot/export_templates/4.7.1.stable/`
   에 들어가고, 우리가 쓰는 것은 `web_nothreads_release.zip` 이다 - 프리셋이
   `thread_support = false` 라 `nothreads` 가 맞다
2. **재려는 것을 「장면」으로 만들어라.** 웹 빌드는 `run/main_scene` 하나만 띄우고 `-s` 로
   스크립트를 못 돌린다. `SceneTree` 스크립트로 만든 측정 도구는 웹에서 못 쓴다
3. **`run/main_scene` 을 그 장면으로 임시로 돌리고 내보낸 뒤 되돌려라.**
   `project.godot` 은 커밋하지 않는다. `build/web/` 은 `.gitignore` 에 들어 있다
4. **HTTP 로 서빙해라.** `file://` 로는 안 뜬다. `python -m http.server 8231` 로 충분하다
5. **결과는 `print()` 로 내면 브라우저 콘솔에 그대로 온다.** 화면 `Label` 에도 함께 내라 -
   콘솔을 못 볼 때 사람이 바로 본다

**함정 다섯:**

- **결과를 마지막에 몰아서 내면 못 본다.** 처음에 그렇게 만들었더니 마지막 인원 판이 안 끝나
  앞의 결과까지 잃었다. **행이 끝나는 대로 즉시 내라**
- **인원과 표본이 많으면 wasm 이 죽는다.** 200 명 · 600 프레임에서
  `memory access out of bounds` 가 났다. 100 명 · 300 프레임까지는 안 났다
- **rAF 이 조절될 수 있다.** 브라우저 창이 화면에 안 그려지면 초당 아홉 프레임까지 떨어진다.
  **그때 프레임 시간은 못 믿는다 - 다만 우리 계산 시간(`last_step_usec`)은 rAF 과 무관하게
  유효하다.** 둘을 갈라 두면 반쪽이라도 건진다
- **데워진 정도가 두 배를 만든다.** 위 §23 을 보라. **작은 인원부터 차례로 올려 데운 뒤 재고
  그 조건을 적어라**
- **네이티브에서도 같은 장면을 돌려야** 배수가 뜻을 가진다. 다른 도구로 잰 값과 견주면
  렌더 경로 · 스레드 차이에 도구 차이까지 섞인다

## 24. 대기 교착을 풀고, 저울 둘을 재어 남긴다

### 전원 대기 교착 - 한 줄이었다

열린 곳 100 명이 안 멎었다. **"누가 먼저 가나"는 정해져 있었는데(`_outranks`) "누가 먼저
푸나"가 없었다.** A 가 B 를 기다리고 B 가 A 를 기다리면 둘 다 안 푼다.

순위는 흐름장 비용이라 **전순서**다. 부탁한 쪽보다 내가 앞서 있으면 내가 먼저 갈 차례이므로
기다림을 푼다. 값이 같으면 번호로 가른다 - **난수를 쓰지 않는다.** 추가 계산은 0 이다.

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 열린 곳 100 정지 | **못함** | **24.92 s** |
| 좁은 통로 40 통과 | 9.87 s | **7.82 s** |
| 좁은 통로 100 통과 | 21.73 s | 22.00 s |

### 조여 두었던 값 셋 - 하나씩 풀고 각각 쟀다

프레임 예산이 되돌리기 조건이던 시절에 조인 값들이다. 조건이 없어진 뒤에도 계속 조여
놓고 있었다.

| 값 | 결과 | 판정 |
| --- | --- | --- |
| **ⓑ 막힘 비용 1.2 -> 3.0** | 좁은 통로 100 통과 22.00 -> **18.83 s**, 나머지 그대로 | **채택** |
| ⓒ 재굽기 간격 60 -> 30 | 좁은 통로 100 **17.33 s**, 한 칸 문 40 **처음으로 전원 통과(28.75 s)**. 그런데 **열린 곳 100 이 다시 안 멎는다** | 되돌림 |
| ⓐ 멎은 유닛만 세는 것 | 못 풀었다 | 미착수 |

### 비킬 자리를 입구에서 먼 쪽으로 - 재고 되돌렸다

세 번째 요구다. 비킨 유닛이 문 앞에 서 있으면 뒤가 다 막히므로, 어느 쪽으로 비킬지 고를 때
**흐름장 비용이 높은 쪽**(목적지에서 먼 쪽)을 고르게 했다. 거의 정면으로 막고 선 경우에만
그렇게 하고, 몸이 이미 치우쳐 있으면 치우친 쪽으로 둔다 - 치우친 몸을 반대로 돌려세우면
그 거리가 그대로 지터가 된다.

| | 지금 | 입구 먼 쪽 우선 |
| --- | --- | --- |
| **한 칸 문 40 못 넘은 인원** | 27 명 | **12 명** |
| **열린 곳 100 정지** | 24.92 s | **17.57 s** |
| 좁은 통로 100 통과 | 18.83 s | 24.47 s |
| 좁은 통로 40 통과 | 7.82 s | 8.72 s |
| **열린 곳 40 정지** | 18.92 s | **못함** |

**한 칸 문이 27 에서 12 명으로 절반 넘게 줄고 열린 곳 100 도 빨라진다.** 방향은 맞다.
그런데 **열린 곳 40 이 안 멎는다.** 아침에 사람이 띄우면 바로 보이는 종류라 되돌렸다.

**다음 사람이 볼 곳은 여기다** - 한 칸 문의 답이 이 방향에 있는 것은 거의 확실하고,
열린 곳 40 만 깨지는 이유를 짚으면 그대로 채택할 수 있다.

#### 40 언저리를 훑었다 - **매끄러운 추세가 아니라 한 점만 튄다**

열린 곳을 32 · 36 · 40 · 44 · 48 로 재 보았다(입구 먼 쪽 우선을 켠 채로).

| 인원 | 정지 | 못비킴 | 옮긴 거리 | 남은 비율 |
| --- | --- | --- | --- | --- |
| 32 | 10.47 s | 45 | 343 px | 96 % |
| 36 | 9.42 s | 0 | 353 px | 98 % |
| **40** | **못함** | **147** | **1737 px** | **86 %** |
| 44 | 12.00 s | 8 | 674 px | 110 % |
| 48 | 14.42 s | 4 | 903 px | 101 % |

**40 만 튄다.** 앞뒤 인원은 전부 멎고, 40 에서만 **못비킴이 3 에서 30 배**로 뛰고
**옮긴 거리가 두 배 넘게** 늘고 **남은 비율이 86 퍼센트로 유일하게 100 아래**다.

즉 **인원이 늘어서 나빠지는 종류가 아니다.** 40 이라는 값에서만 나는 무언가이고,
이 레인에서 같은 모양을 이미 한 번 겪었다(§19 의 도착 후 진동 9.8 px 도 40 에서만 났고
원인은 `resume()` 이 묵은 조향을 안 버린 것이었다).

**아직 원인은 못 짚었다.** 다만 **범위가 좁혀졌다** - 못비킴이 147 이라는 것은
비켜서기가 실패하는 자리가 그 판에만 특별히 많다는 뜻이다. 짐작으로 고치지 않았다.

#### 한 명 단위로 훑었다 - **구간이 아니라 흩어진 점이다**

37 부터 43 까지 하나씩 재 보았다(입구 먼 쪽 우선을 켠 채로).

| 인원 | 37 | 38 | 39 | 40 | 41 | 42 | 43 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 정지 | 9.53 s | **못함** | 14.43 s | **못함** | 11.25 s | 11.20 s | 9.43 s |

**깨지는 것이 38 과 40 이고 그 사이의 39 는 멀쩡하다.** 39~41 이 함께 깨졌으면 밀도나
임계값이었을 텐데 그렇지 않다. **구간이 아니다.**

그리고 **내 가설(스폰 격자 6 열의 나머지)도 틀렸다.** 나머지로 보면 38 은 2, 40 은 4 로
깨지고 37(1) · 39(3) · 41(5) · 42(0) · 43(1) 은 멀쩡한데, **앞서 잰 32 도 나머지가 2 인데
멀쩡했다.** 나머지 하나로는 설명이 안 된다.

**남는 결론은 이것이다 - 이 방식은 열린 곳에서 아슬아슬하게 안정하고, 특정 배치가 그것을
넘어뜨린다.** 인원이 늘어서도, 나머지가 어때서도 아니고, 그 판의 몸 배치가 우연히 맞물릴 때
무너진다. **법칙이 아니라 칼날 위다.**

**그래서 「입구 먼 쪽 우선」은 지금 모양으로는 못 쓴다.** 한 칸 문을 27 에서 12 명으로
줄이고 열린 곳 100 을 24.92 에서 17.57 초로 당기는 것은 분명한 소득이지만, **어느 인원에서
안 멎을지 예측할 수 없는 것을 켤 수는 없다.**

#### 안 멎는 판에서 무슨 일이 벌어지나 - **두 명이 제자리에서 왕복한다**

| --- | --- | --- | --- | --- |
| 1~5 (전부 동일) | **2 명** | 568.9 px | **1.9 px** | **305.6** |

- **전원이 아니라 두 명이다.** 정지 판정 임계값 문제가 아니라 **국소 라이브락**이다.

  **제자리에서 왕복한다.** 조향이 매 프레임 뒤집힌다는 뜻이다
- **다섯 번이 소수점까지 같다.** 순서 의존 경합이 아니라 **결정론이다.** 난수를 안 쓰니

**그래서 고칠 수 있는 것이다.** 두 명이 물리는 자리를 찾으면 되고, 인원을 특별 취급할 일이

## 25. 막힘 기억이 정확히 뒤집혀 있었다

**고치러 간 것이 아니라 ⓐ 를 넣으려고 코드를 읽다 나왔다.**

`unit_jam.gd` 는 막힌 칸에 `_JAM_FORGET`(3)을 적고, 그 칸이 비면 확인할 때마다 하나씩
깎는다. 그런데 값을 쓰는 쪽인 `nav_grid.gd` 의 `_cell_step` 은 이렇게 물었다.

```gdscript
if index < _jam.size() and _jam[index] == 1:
	step *= 1.0 + _JAM_PENALTY
```

**`== 1` 이다.** 그래서 이렇게 됐다.

| 칸의 상태 | 적힌 값 | 값을 무는가 |
| --- | --- | --- |
| **지금 막혀 있다** | 3 | **안 문다** |
| 비고 한 번 확인 지났다 | 2 | 안 문다 |
| 비고 **두 번** 확인 지났다 | 1 | **문다** |
| 잊었다 | 0 | 안 문다 |

**기억이 정확히 뒤집혀 있었다.** 지금 막힌 칸은 그냥 지나가고, **비운 지 40 프레임 된 칸만**
비싸게 매겼다. `nav_grid.gd` 의 주석이 "1 이면 막힘"이라 적어 둔 것과 `unit_jam.gd` 가
나중에 넣은 확인 횟수 세기가 어긋난 것이고, 그 사이에 아무도 값을 다시 안 봤다.

> **그러므로 §14 와 §24 의 `_JAM_PENALTY` 비교(3.0 대 1.2)는 전부 무효다.**
> 뒤집힌 표 위에서 잰 값이라 무엇을 골랐든 근거가 없다. 고친 뒤에 다시 골라야 한다.

### ⓐ - 멎은 유닛만 세던 것을 정체까지 센다

사용자가 세 번 짚은 요구다 - **"막히면 막혔다는 걸 직접 안 가보고도 알 수 있는 거 아니야?"**

막힘 기억이 `HOLDING` 과 `BLOCKED` **만** 셌다. 멎지는 않았는데 느리게 가는 유닛이 선 칸은
기억에 안 남고, **실제로 가장 오래 걸리는 칸이 거기다.** 그래서 「안 가보고 안다」가 절반이었다.

**`grind_frames` 로는 못 센다.** 그쪽은 아군에 눌리면 0 으로 되돌아간다 - 줄을 서서 못 가는
것과 지형에 낀 것을 가르려고 일부러 그렇게 두었고 그 판단은 지금도 옳다. 그래서 시계를 하나
따로 뒀다(`creep_frames`) - **눌렸든 아니든 목적지가 가까워졌는가만** 본다.

**이 시계가 줄서기와 정체를 저절로 가른다.** 줄이 나아가면 앞이 한 몸씩 빠질 때마다 뒤도
그만큼 가까워져 0 으로 되돌아가고, 제자리에서 맴돌 때만 오른다. 1.5 초(`_JAM_CREEP` 90)를
넘긴 유닛의 칸만 막힘으로 적는다.

하나 바뀌면 또 뒤집힌다**고 봐야 한다.

**왜 값으로 안 되는지도 분명하다.** 막힘 비용은 **돌아갈 길이 있을 때** 돌아가게 하는 값이다.
한 칸 문에는 돌아갈 길이 없다. 그러니 이 값이 하는 일은 "문 앞을 얼마나 비싸게 만들어
흐름장을 얼마나 헷갈리게 하는가"뿐이고, 그건 저울이 아니라 잡음이다.

**구조가 필요하다.** 폭이 한 칸이면 옆으로 비킬 자리가 없으므로 **줄을 서야** 하는데,
지금 판에는 「줄」이라는 것이 없다. §25 에서 「막고 선 놈 자신이 물러나기」를 넣어 봤다가
되돌린 이유가 그대로다 - **물러난 유닛이 줄의 어디로 갈지를 정하는 정보가 없어서 앞자리만
계속 바뀐다.** 필요한 것은 값이 아니라 **문 앞의 차례를 나타내는 무언가**다
(흐름장 비용으로 매긴 순위는 이미 있으니, 그 순위를 **자리**로 바꾸는 것이 다음 걸음이다).

> 값을 고르면 다음 인원에서 뒤집힌다. **이웃값이 같은 답을 낼 때만 그것이 근거다.**

### 자 - 옛 칸은 그대로 두고 새 칸을 붙였다

「정지」를 고치면 §11 부터의 표가 통째로 끊긴다. 그래서 **안 건드렸다.** 대신 옆에
**`전원끝`** 칸을 붙였다 - `이동`도 `양보`도 없어진 시각이다.

| 칸 | 무엇을 재는가 |
| --- | --- |
| **정지** | `이동` 상태가 없어진 시각. **`양보`는 안 센다** |
| **전원끝** | `이동`도 `양보`도 없어진 시각. **이쪽이 "전원이 끝났다"이다** |

구현은 옛 칸을 뽑아낸 **뒤에** 마저 돌린다. 그래서 지표 열여섯 칸이 소수점까지 그대로인 것을
확인하고 붙였다(밀리초 세 칸만 흔들렸고, 그건 원래 못 믿는 칸이다).

**붙이자마자 답이 나왔다. 열다섯 판 중 열이 「전원끝 못함」이었다.**

| 상황 | 정지 | 전원끝 (예산 넣기 전) |
| --- | --- | --- |
| 구석 24 | **3.22 s** | **못함** |
| 열린 곳 12 | 8.63 s | 못함 |
| 열린 곳 40 | 11.37 s | 못함 |
| 열린 곳 100 | 13.50 s | 못함 |
| 좁은 통로 24 / 40 / 100 | 10.43 / 11.87 / 29.05 s | 못함 |
| 맞교차 40 | 8.63 s | 못함 |
| 한 칸 문 40 | 39.45 s | 못함 |

**구석 24 를 보라. 3.22 초에 멎었다고 적어 온 판이 사실은 한 번도 안 끝났다.**

### 대상 - `양보`에 예산을 준다

`양보`가 풀리는 길이 둘뿐이었다. 내 자리를 남이 차지했거나(`_slot_taken`), 앞이 트이거나
(`_settled_ahead`). **앞의 유닛이 `도착`으로 굳으면 둘 다 영원히 안 풀린다.**

**한 번 틀렸다. 그 틀림이 이 절에서 제일 값진 것이다.**

처음에는 **「판이 조용하면」**(아무도 `이동` 중이 아닌 채 반 초) 자리를 잡게 했다. 지표는
좋아졌는데 **테스트 둘이 깨졌다.**

| 깨진 테스트 | 무엇을 지키던 것인가 |
| --- | --- |
| `test_waiting_unit_resumes_when_the_blocker_leaves` | 막은 쪽이 비키면 **재명령 없이** 스스로 간다 |
| `test_waiting_never_becomes_giving_up` | 25 초를 기다려도 포기로 안 떨어진다 |

**조용한 판이야말로 "기다리면 언젠가 비킨다"가 성립하는 판이다.** 막고 선 유닛이 가만히
있다는 것은 가망이 없다는 뜻이 아니라 아직 안 비켰다는 뜻일 뿐이다. **조용함으로는 못 가른다.**

가르는 것은 **누가 막고 있는가**다. 가망이 없는 짜임은 하나뿐이다.

> **같은 명령을 받은 무리가 전부 자리를 잡았고, 나를 막고 선 것이 그중 하나일 때.**

자리를 잡은 유닛은 다시 안 움직이고 같은 명령의 누구도 더 걷지 않으니, 판이 바뀔 계기가
남아 있지 않다. 남이 막은 경우(명령이 다른 유닛, 세워 둔 유닛)는 안 걸린다 - 그쪽은 언제든
비킬 수 있고 비키면 `_settled_ahead` 가 풀어 준다. **테스트 둘이 다시 통과한다.**

`_slot_taken` 이 "내 자리에 남이 서 있으면 여기가 내 자리다"라고 한 판단을 **한 칸 넓힌 것**이고,
`_watch_grinding` 이 `hold_retries` 로 이미 배운 **"되돌아올 수 있는 정지에는 예산이 있어야
한다"** 를 마지막 한 곳에 마저 단 것이다.

### 앞 레인의 "튕김 6 px" 보고는 어디서 어긋났나

앞 레인은 튕김 최대 6 px 이라고 적었고 통합 후 같은 도구로 재니 12.7 px 이 나왔다.
**측정 조건 차이가 아니라 표가 낡은 것이었다.**

`_resolve_overlaps` 에는 상한(`push_cap`)을 **깊은 겹침에서는 풀어 주는 예외**가 있다
(`_DEEP_OVERLAP`). 이 예외는 통과 버그를 잡느라 **나중에** 들어갔고, 그때 표를 다시 재지
않았다. 실제로 이 예외만 꺼 보니 여섯 상황 모두 정확히 **6.0 px** 이 나왔다 — 상한이
`max(0.5 × 반지름, 최대속도 × 1.2 / 60)` 이라 12 반지름에서 정확히 6.0 이다.
6 px 은 상한을 지킨 값이었고 12.7 px 은 예외가 걸린 값이다. **둘 다 맞고, 표만 옛것이었다.**

### 아직 나쁜 것

- **정지 시간이 길어졌다.** 특히 구석 24 명이 3.02 초에서 **10.02 초**로 나빠졌다.
  구석은 자리가 한 점에 겹치는 구간인데, 밀 수 없으니 바깥 유닛이 안쪽을 못 뚫는다.
  90 퍼센트가 멎는 시간은 6.30 초라 **뒤끝 하나가 표를 끌고 있다** — `_GRIND_FRAMES`(4 초)
  안전망에 걸려 끝나는 유닛이다.
- **좁은 통로 100 명에서 한 명이 40 초 안에 문을 못 넘는다.** 밀치기 시절에는 5.63 초에
  전원이 넘었다. 밀고 나갈 수 없게 된 대가가 가장 크게 나타나는 지점이다.
- **`HOLDING` 이 크게 늘었다.** 예전에는 100 명 판에서 한둘이었는데 지금은 30~58 명이다.
  밀려나지 않는 아군 뒤에 서는 유닛이 그만큼 생겼다는 뜻이고, **의도한 결과이지만
  대형이 그만큼 헐거워진다.** 자기 자리에 못 들어가고 그 근처에 서는 유닛이 는다.
- **좁은 문에서 여전히 줄을 서지는 않는다.** 접촉 제약이 속도를 맞춰 주므로 예전처럼 서로
  파고들지는 않지만, 문 앞에서는 여전히 뭉친다. 통로 한가운데로 끌어당기는 힘이 없어서다(§7).
- **대형 자리 배정이 밀치기를 전제로 하고 있다.** 안쪽 자리부터 가까운 유닛을 데려가는
  방식이라, 왼쪽에서 접근한 무리 중 일부가 **오른쪽 바깥 자리**를 받는다. 밀 수 있을 때는
  대열을 뚫고 갔지만 이제는 통째로 돌아가야 한다. 다음 사람이 볼 곳은 여기다 —
  **접근 방향을 배정에 넣으면 정지 시간과 `HOLDING` 이 함께 내려갈 것으로 본다.**
- **대형은 속도만 맞춘다.** 앞선 유닛이 뒤를 기다릴 뿐, 대열의 **모양**은 지키지 않는다.
- **장애물 회피는 격자 굵기까지만 한다.** 칸(32 픽셀)보다 얇은 틈은 표현되지 않는다.
