# 유닛 이동 조작감 프로토타입

방 안에서 **개별 유닛을 골라 움직이는 층**을 시험한다.
목적은 기능 목록을 채우는 것이 아니라 **손맛을 재는 것**이다.

전투는 범위 밖이다. 공격 · 체력 · 피해 · 사거리는 하나도 없다.

> **지도 화면과 다른 층이다.** [`14-squad.md`](../../../docs/design/14-squad.md) §14.2 의
> "스쿼드는 판 위에서 말 하나"는 **방과 방 사이 이동**을 가리킨다. 방 그래프 위에서
> 스쿼드가 하나로 움직이는 것과, 방 안에서 대원을 따로 고르는 것은 층이 다르다.
> 그래서 이 프로토타입은 기존 설계와 충돌하지 않는다.

---

## 1. 실행

```
godot --path . res://src/proto/unit_move/unit_move_proto.tscn
```

에디터에서는 `src/proto/unit_move/unit_move_proto.tscn` 을 열고 **현재 씬 실행**(F6).
`main.tscn` 과 완전히 독립이라 무엇도 건드리지 않는다.

## 2. 구조

```
src/proto/unit_move/
├── core/                    # 노드에 의존하지 않는 순수 로직
│   ├── nav_grid.gd          # 통행 격자 · 시야 판정 · 흐름장 생성
│   ├── flow_field.gd        # 목적지 하나로 향하는 방향 격자
│   ├── formation.gd         # 대형 자리 만들기와 배정
│   ├── unit_agent.gd        # 유닛 하나의 이동 상태
│   ├── unit_field.gd        # 시뮬레이션 본체 (조향 · 분리 · 도착)
│   ├── unit_selection.gd    # 선택 상태
│   ├── control_groups.gd    # 부대 지정과 연타 판정
│   └── move_tuning.gd       # 조절 가능한 수치의 정의와 현재 값
├── unit_move_proto.tscn/gd  # 진입점. 입력 해석과 화면 반영
├── terrain_view.gd          # 바닥과 벽 (거의 안 바뀌므로 따로)
├── field_view.gd            # 유닛 · 선택 · 명령 표시
├── debug_draw.gd            # 개발 표시 (흐름장 · 힘 · 자리 · 상태)
└── tuning_panel.gd          # 슬라이더 조절판
```

**이동 로직과 그리는 방식이 갈려 있다.** `core/` 는 좌표와 속도만 알고 무엇으로 보이는지는
모른다. 나중에 배경과 스프라이트가 들어오면 `*_view.gd` 만 갈아 끼우면 된다.

`core/` 를 `src/core/` 가 아니라 이 폴더 안에 둔 이유는 **프로토타입이기 때문이다.**
살아남기로 정해지면 그때 `src/core/` 로 옮긴다. 클래스 이름에 `Proto` 를 붙인 것도
같은 이유다 — 본 코드의 이름 공간을 미리 차지하지 않는다.

## 3. 이동을 어떻게 처리하는가

```
   우클릭
     |
     +--> 목적지를 통행 가능한 곳으로 보정 (벽을 찍어도 명령은 산다)
     +--> 흐름장 한 번 계산  ......... 명령을 받은 전원이 공유한다
     +--> 대형 자리 만들고 배정 ...... 각자 다른 목표를 받는다
     |
   매 물리 프레임
     +--> 자기 자리로 향하는 힘 (도착 반경 안에서는 감속)
     +--> 이웃을 밀어내는 힘 + 앞을 막은 상대는 옆으로 비껴가기
     +--> 회전 속도 제한 -> 가속 한계 -> 이동
     +--> 몸이 겹친 쌍을 위치로 떼어 놓기
     +--> 도착 · 포기 판정
```

### 왜 흐름장인가

유닛마다 경로를 따로 찾으면 두 가지가 나쁘다. 같은 곳으로 가는 스무 명이 같은 계산을
스무 번 하고, 남에게 밀려 경로를 벗어날 때마다 재탐색이 필요하다. 그 재탐색이 여럿에게
동시에 걸리면 **웹 단일 스레드에서 그대로 프레임 끊김**이 된다.

칸마다 방향이 미리 놓여 있으면 밀려난 유닛도 지금 서 있는 칸의 방향을 읽으면 된다.

다만 흐름장은 8방향이라 그대로 따르면 열린 방에서 계단처럼 꺾여 걷는다.
그래서 **자기 자리가 그대로 보이면 흐름장을 무시하고 직선으로 간다.**
장애물이 낀 구간에서만 흐름장이 일한다.

### 왜 대형 자리인가

전원에게 같은 좌표를 주면 그 한 점을 두고 영원히 밀어댄다. 밀치기만으로 흩어 놓는 방식은
인원이 늘수록 도착 지점이 부풀고 마지막 몇 명이 자리를 못 잡아 계속 떤다.
**자리를 먼저 정해 두면 각자 자기 목표에서 멈추므로 도착이 끝난다.**

자리는 육각 격자로 만들고 중심에서 가까운 순으로 정렬한다. 배정은 안쪽 자리부터
가장 가까운 유닛을 데려간다 — 앞선 유닛이 안쪽을 차지하고 뒤따르는 유닛이 바깥을 채우므로
**접근 순서가 그대로 대형이 된다.**

## 4. 조절 가능한 값

조절판(Tab)에서 전부 슬라이더로 만진다. **기본값 복원** 버튼이 언제든 되돌린다.

| 값 | 기본 | 무엇이 바뀌는가 |
| --- | --- | --- |
| 최대 속도 | 230 | 초당 픽셀 |
| 가속 | 2600 | **클릭 반응이 여기서 갈린다** |
| 회전 속도 | 900 | 초당 각도. 진행 방향이 꺾이는 한계 |
| 도착 반경 | 6 | 자기 자리에 이만큼 들면 멈춘다 |
| 감속 반경 | 52 | 이 거리부터 속도를 줄인다 |
| 분리 반경 | 38 | 이 안의 이웃을 밀어낸다 |
| 분리 강도 | 1.05 | 0 이면 서로 통과한다 |
| 옆으로 비껴가기 | 0.85 | **0 이면 마주 오는 둘이 정면에서 굳는다** |
| 겹침 해소 | 0.70 | 겹친 몸을 위치로 떼어 놓는 비율 |
| 대형 간격 | 1.25 | 유닛 지름의 배수 |
| 대형 유지 | 0.55 | 앞선 유닛이 뒤를 기다리는 정도 |
| 포기 시간 | 1.1 | 이만큼 못 나아가면 그 자리에 선다 |

값을 하나 추가하려면 `core/move_tuning.gd` 의 `DEFS` 에 한 줄 넣으면 된다.
슬라이더는 그 정의에서 저절로 만들어진다.

## 5. 개발 표시 (F1)

`CLAUDE.md` §8 대로 판의 상태를 최대한 드러낸다.
유닛이 이상하게 도는 것을 보고도 그것이 흐름장 탓인지 분리력 탓인지 대형 속도 탓인지는
**눈으로 구분할 수 없다.**

| 표시 | 색 |
| --- | --- |
| 흐름장 방향 | 옅은 파랑 화살표 |
| 대형 자리 | 분홍 가위표 |
| 자기 자리로 향하는 힘 | 노랑 화살표 |
| 이웃을 밀어내는 힘 | 파랑 화살표 |
| 목표까지의 선 | 회색 실선 |
| 포기한 유닛 | 빨강 테두리 |
| 유닛별 상태 | 선택한 유닛 옆에 글자 (12 명 이하일 때) |

위쪽 요약에는 유닛 수 · 선택 · 이동중 · fps · **이동 계산 시간(평균과 최악)** ·
명령 수 · 장애물 시드 · 기본값에서 바뀐 수치 개수 · 부대 현황이 나온다.

체크상자로 흐름장 · 힘 · 자리를 따로 끌 수 있다. 셋을 다 켜면 서로를 가린다.

## 6. 검증

```
godot --path . -s res://tools/capture_unit_move.gd                       # 장면 캡처 7 장
godot --path . -s res://tools/capture_unit_move.gd -- bench 20 50 100 200 300   # 인원별 프레임
godot --headless --path . -s res://addons/gut/gut_cmdln.gd               # 단위 테스트
```

캡처는 `.captures/` 에 남는다. **헤드리스로는 그림이 나오지 않는다** — 창이 있어야 한다.

단위 테스트는 조작감이 갈리는 네 지점을 지킨다. 손맛을 알려 주지는 못하지만
한번 잡아 둔 손맛이 조용히 무너지는 것은 막는다.

| 지점 | 지키는 것 |
| --- | --- |
| 반응 지연 | 명령 뒤 세 프레임 안에 속도가 붙는가 |
| 뭉침 | 두 유닛이 같은 목표를 받지 않는가, 멎은 뒤 몸이 겹치지 않는가 |
| 도착 | 전원이 유한 시간에 멎는가, 멎은 뒤 다시 움직이지 않는가 |
| 대형 | 같이 갈 때 무리가 흩어지지 않는가 |

## 7. 지금 상태와 아직 나쁜 것

| 지점 | 상태 |
| --- | --- |
| 반응 지연 | **좋다.** 명령은 그 프레임에 처리되고 세 프레임 안에 속도가 붙는다 |
| 뭉침 | **쓸 만하다.** 자리 배정 + 옆으로 비껴가기로 정면 교착이 사라졌다 |
| 도착 | **쓸 만하다.** 전원이 멎고 멎은 뒤 떨지 않는다. 다만 뒤끝이 길다 (아래) |
| 대형 | **약하다.** 늘어지지는 않지만 대열 모양은 유지되지 않는다 (아래) |

### 아직 나쁜 것

- **도착 뒤끝.** 대부분이 자리에 든 뒤 마지막 한둘이 1 초 남짓 비비다 포기 시간으로 멎는다.
  눈에 띄게 어색하지는 않지만 "딱 멈춘다"는 아니다.
- **대형은 속도만 맞춘다.** 앞선 유닛이 뒤를 기다릴 뿐, 대열의 **모양**은 지키지 않는다.
  줄을 세워 행군시키려면 자리를 목적지가 아니라 경로 위에 두는 방식이 따로 필요하다.
- **좁은 문 통과.** 여럿이 한 줄로 서지 않고 문 앞에서 뭉쳤다 하나씩 빠진다.
  흐름장은 모두에게 같은 문을 가리키고, 줄을 서게 하는 규칙은 없다.
- **장애물 회피는 격자 굵기까지만 한다.** 칸(32 픽셀)보다 얇은 틈은 표현되지 않는다.
