# 유닛 이동 조작감 프로토타입

방 안에서 **개별 유닛을 골라 움직이는 층**을 시험한다.
목적은 기능 목록을 채우는 것이 아니라 **손맛을 재는 것**이다.

전투는 범위 밖이다. 공격 · 체력 · 피해 · 사거리는 하나도 없다.

> **지도 화면과 다른 층이다.** [`14-squad.md`](../../../docs/design/14-squad.md) §14.2 의
> "스쿼드는 판 위에서 말 하나"는 **방과 방 사이 이동**을 가리킨다. 방 그래프 위에서
> 스쿼드가 하나로 움직이는 것과, 방 안에서 대원을 따로 고르는 것은 층이 다르다.
> 그래서 이 프로토타입은 기존 설계와 충돌하지 않는다.

## 2. 구조

```
src/proto/unit_move/
├── core/                    # 노드에 의존하지 않는 순수 로직
│   ├── nav_grid.gd          # 통행 격자 · 시야 판정 · 흐름장 생성
│   ├── flow_field.gd        # 목적지 하나로 향하는 방향 격자
│   ├── formation.gd         # 대형 자리 만들기와 배정
│   ├── unit_agent.gd        # 유닛 하나의 이동 상태
│   ├── unit_field.gd        # 시뮬레이션 본체 (조향 · 분리 · 도착)
│   ├── unit_selection.gd    # 선택 상태
│   ├── control_groups.gd    # 부대 지정과 연타 판정
│   └── move_tuning.gd       # 조절 가능한 수치의 정의와 현재 값
├── unit_move_proto.tscn/gd  # 진입점. 입력 해석과 화면 반영
├── terrain_view.gd          # 바닥과 벽 (거의 안 바뀌므로 따로)
├── field_view.gd            # 유닛 · 선택 · 명령 표시
├── debug_draw.gd            # 개발 표시 (흐름장 · 힘 · 자리 · 상태)
└── tuning_panel.gd          # 슬라이더 조절판
```

**이동 로직과 그리는 방식이 갈려 있다.** `core/` 는 좌표와 속도만 알고 무엇으로 보이는지는
모른다. 나중에 배경과 스프라이트가 들어오면 `*_view.gd` 만 갈아 끼우면 된다.

`core/` 를 `src/core/` 가 아니라 이 폴더 안에 둔 이유는 **프로토타입이기 때문이다.**
살아남기로 정해지면 그때 `src/core/` 로 옮긴다. 클래스 이름에 `Proto` 를 붙인 것도
같은 이유다 — 본 코드의 이름 공간을 미리 차지하지 않는다.

## 3. 이동을 어떻게 처리하는가

```
   우클릭
     |
     +--> 목적지를 통행 가능한 곳으로 보정 (벽을 찍어도 명령은 산다)
     +--> 흐름장 한 번 계산  ......... 명령을 받은 전원이 공유한다
     +--> 대형 자리 만들고 배정 ...... 각자 다른 목표를 받는다
     |
   매 물리 프레임
     +--> 자기 자리로 향하는 힘 (도착 반경 안에서는 감속)
     +--> 이웃을 밀어내는 힘 + 앞을 막은 상대는 옆으로 비껴가기
     +--> 회전 속도 제한 -> 가속 한계 -> 이동
     +--> 몸이 겹친 쌍을 위치로 떼어 놓기
     +--> 도착 · 포기 판정
```

### 왜 흐름장인가

유닛마다 경로를 따로 찾으면 두 가지가 나쁘다. 같은 곳으로 가는 스무 명이 같은 계산을
스무 번 하고, 남에게 밀려 경로를 벗어날 때마다 재탐색이 필요하다. 그 재탐색이 여럿에게
동시에 걸리면 **웹 단일 스레드에서 그대로 프레임 끊김**이 된다.

칸마다 방향이 미리 놓여 있으면 밀려난 유닛도 지금 서 있는 칸의 방향을 읽으면 된다.

다만 흐름장은 8방향이라 그대로 따르면 열린 방에서 계단처럼 꺾여 걷는다.
그래서 **자기 자리가 그대로 보이면 흐름장을 무시하고 직선으로 간다.**
장애물이 낀 구간에서만 흐름장이 일한다.

### 왜 대형 자리인가

전원에게 같은 좌표를 주면 그 한 점을 두고 영원히 밀어댄다. 밀치기만으로 흩어 놓는 방식은
인원이 늘수록 도착 지점이 부풀고 마지막 몇 명이 자리를 못 잡아 계속 떤다.
**자리를 먼저 정해 두면 각자 자기 목표에서 멈추므로 도착이 끝난다.**

자리는 육각 격자로 만들고 중심에서 가까운 순으로 정렬한다. 배정은 안쪽 자리부터
가장 가까운 유닛을 데려간다 — 앞선 유닛이 안쪽을 차지하고 뒤따르는 유닛이 바깥을 채우므로
**접근 순서가 그대로 대형이 된다.**

## 4. 조절 가능한 값

조절판(Tab)에서 전부 슬라이더로 만진다. **기본값 복원** 버튼이 언제든 되돌린다.

| 값 | 기본 | 무엇이 바뀌는가 |
| --- | --- | --- |
| 최대 속도 | 230 | 초당 픽셀 |
| 가속 | 2600 | **클릭 반응이 여기서 갈린다** |
| 회전 속도 | 900 | 초당 각도. 진행 방향이 꺾이는 한계 |
| 도착 반경 | 6 | 자기 자리에 이만큼 들면 멈춘다 |
| 감속 반경 | 52 | 이 거리부터 속도를 줄인다 |
| 분리 반경 | 38 | 이 안의 이웃을 밀어낸다 |
| 분리 강도 | 1.05 | 0 이면 서로 통과한다 |
| 옆으로 비껴가기 | 0.85 | **0 이면 마주 오는 둘이 정면에서 굳는다** |
| 겹침 해소 | 0.70 | 겹친 몸을 위치로 떼어 놓는 비율 |
| 양보 | 0.70 | **목적지에 가까운 쪽에 길을 낸다.** 0 이면 서로 밀며 제자리에서 떤다 |
| 조향 평활 | 0.12 | 초. 흐름장이 칸마다 튀는 것을 다듬는다 |
| 겹침 해소 | 0.70 | 겹친 몸을 위치로 떼어 놓는 비율 |
| 겹침 해소 상한 | 0.50 | **한 프레임에 밀어내는 거리를 몸 반지름의 이 배수로 묶는다** |
| 대형 간격 | 1.25 | 유닛 지름의 배수 |
| 대형 유지 | 0.55 | 앞선 유닛이 뒤를 기다리는 정도 |

값을 하나 추가하려면 `core/move_tuning.gd` 의 `DEFS` 에 한 줄 넣으면 된다.
슬라이더는 그 정의에서 저절로 만들어진다.

**`포기 시간` 은 없어졌다.** 아래 §8 을 보라.

## 5. 개발 표시 (F1)

`CLAUDE.md` §8 대로 판의 상태를 최대한 드러낸다.
유닛이 이상하게 도는 것을 보고도 그것이 흐름장 탓인지 분리력 탓인지 대형 속도 탓인지는
**눈으로 구분할 수 없다.**

| 표시 | 색 |
| --- | --- |
| 흐름장 방향 | 옅은 파랑 화살표 |
| 대형 자리 | 분홍 가위표 |
| 자기 자리로 향하는 힘 | 노랑 화살표 |
| 이웃을 밀어내는 힘 | 파랑 화살표 |

| 포기한 유닛 | 빨강 테두리 |

명령 수 · 장애물 시드 · 기본값에서 바뀐 수치 개수 · 부대 현황이 나온다.

체크상자로 흐름장 · 힘 · 자리를 따로 끌 수 있다. 셋을 다 켜면 서로를 가린다.

## 6. 검증

```
godot --path . -s res://tools/capture_unit_move.gd                       # 장면 캡처 7 장
godot --path . -s res://tools/capture_unit_move.gd -- bench 20 50 100 200 300   # 인원별 프레임
godot --headless --path . -s res://addons/gut/gut_cmdln.gd               # 단위 테스트
```

캡처는 `.captures/` 에 남는다. **헤드리스로는 그림이 나오지 않는다** — 창이 있어야 한다.

단위 테스트는 조작감이 갈리는 네 지점을 지킨다. 손맛을 알려 주지는 못하지만
한번 잡아 둔 손맛이 조용히 무너지는 것은 막는다.

| 지점 | 지키는 것 |
| --- | --- |
| 반응 지연 | 명령 뒤 세 프레임 안에 속도가 붙는가 |
| 뭉침 | 두 유닛이 같은 목표를 받지 않는가, 멎은 뒤 몸이 겹치지 않는가 |
| 도착 | 전원이 유한 시간에 멎는가, 멎은 뒤 다시 움직이지 않는가 |
| 대형 | 같이 갈 때 무리가 흩어지지 않는가 |
| 멈춤 판정 | `test_proto_unit_stop.gd` — 아래 넷 |
| 지터 | 칸을 넘을 때 조향 방향이 뛰지 않는가 (`test_proto_nav_grid.gd`) |

멈춤 판정은 넷을 못 박는다 — **영원히 비비지 않는다 · 정말 갈 수 없으면 멎는다 ·
막은 쪽이 비키면 스스로 재개한다 · 기다림이 포기로 바뀌지 않는다.**

## 7. 지터를 어떻게 찾았고 무엇을 고쳤나

**눈으로 "떤다"고 말하는 것과 무엇이 떨게 하는지 아는 것은 다르다.**
`tools/measure_unit_move.gd` 로 먼저 지표를 만들고 고치기 전 값을 재고 시작했다.

```
godot --headless --path . -s res://tools/measure_unit_move.gd          # 상황별 지표
godot --headless --path . -s res://tools/measure_unit_move.gd -- probe # 장치 하나씩 꺼 보기
```

처음 세운 지표(한 프레임에 방향이 뒤집힌 횟수)는 어느 상황에서도 0 이었다.
**회전 속도 제한이 프레임당 15 도라 한 프레임 안에서는 뒤집힐 수가 없다.**
지터는 한 프레임의 반전이 아니라 여러 프레임에 걸친 왕복이므로 누적 꺾임 각도로 갈아탔다.

### 원인

| 의심 | 잰 것 | 결과 |
| --- | --- | --- |
| 분리력이 조향을 압도한다 | 분리 > 조향인 프레임 비율 | **아니다.** 좁은 곳 3%, 열린 곳 4% 로 같다 |
| 힘 하나가 범인이다 | 항을 하나씩 끄고 꺾임 | **아니다.** 어느 하나도 15% 안팎 |
| 조향 방향 자체가 튄다 | 조향이 가리키는 방향의 꺾임 | **이것이다.** 좁은 곳 102, 열린 곳 21 도/초 |

조향 꺾임은 **흐름장을 읽는 프레임 비율과 그대로 맞물렸다**(좁은 곳 29~46%, 열린 곳 1%).
흐름장은 칸마다 8 방향 중 하나를 들고 있어, 유닛이 칸 경계를 넘는 순간 조향이 45 도 통째로 뛴다.
회전 속도 제한은 그 뜀을 없애 주지 않는다 — **튀는 목표를 쫓게 만들어 좌우 왕복으로 바꾼다.**

### 고친 것

| 무엇 | 어디 |
| --- | --- |
| 둘레 네 칸을 섞어 읽어 격자를 연속적인 장으로 만든다 | `flow_field.gd` `_blended_direction` |
| 벽 회피가 90 도 꺾던 것을 45 도로 줄이고 양쪽이 열리면 안 건드린다 | `flow_field.gd` `_avoid_wall` |
| 조향 방향에 지수 평활을 건다 | `unit_field.gd` `_smoothed` |
| 비껴가기 방향을 늘 같은 손으로 고정한다 (부호가 뒤집히지 않는다) | `unit_field.gd` `_separation` |
| 양보 — 목적지에 가까운 쪽에 우선권, 뒤에 선 쪽은 밀지 않고 비킨다 | `unit_field.gd` `_separation` |
| 한 프레임에 밀어내는 거리에 상한 | `unit_field.gd` `_resolve_overlaps` |

### 해 보고 걷어낸 것 — 다시 하지 마라

- **좁은 통로에서 한 줄 세우기.** 좌우로 비집는 힘을 걷어내는 방식과 비껴가기만 끄는 방식
  둘 다 만들어 봤는데, **한 칸짜리 문에서 도리어 나빠졌다**(정지 9.35 → 10.08 초,
  통과 6.53 → 7.02 초). 좌우 힘을 걷어내면 유닛이 문 입구에 자기를 맞추지 못해 벽에 붙어 막힌다.
  줄을 세우려면 밀치기를 깎을 게 아니라 **통로 한가운데로 끌어당겨야** 한다. 그건 벽까지의
  거리를 재는 조회가 따로 필요해서 손대지 않았다.
- **미는 방향을 진행 방향의 접선으로 돌리기.** 한 칸 폭 복도에서는 접선이 곧 벽 쪽이라
  몸이 벽으로 밀리고, `push_out` 이 그 몸을 100 픽셀 너머로 옮겨 **앞을 막은 유닛 여섯을
  통째로 통과했다.**

### 지나가다 잡은 것

`nav_grid.gd` `push_out` 의 걸음이 16 픽셀이었다. 한 칸 폭 통로에서 몸이 들어갈 수 있는 띠는
8 픽셀뿐이라 **그 띠를 매번 뛰어넘어 유닛이 100 픽셀 너머로 순간이동했다.** 이 레인이 넣은
버그가 아니라 원래 있던 것이고, 걸음을 몸 크기에 묶어 고쳤다.

## 8. 포기 시간을 무엇으로 대체했나

의뢰인의 관찰이 결정적이었다 — **"포기한 거 다시 가라고 하면 가는 경우가 있다."**
실제로는 막히지 않았는데 막혔다고 잘못 결론 낸 것이고, 포기 시간은 그 오판을 시간으로 덮는
장치였다. 늘리면 굼떠지고 줄이면 일찍 포기하니 어느 쪽으로 돌려도 나아지지 않는다.

이제 `unit_field.gd` `_update_states` 가 **셋 중 하나에 걸릴 때만** 멈춘다.

| 무엇 | 어떻게 아는가 | 되돌아오는가 |
| --- | --- | --- |
| 도착 | 자기 자리에 들었다 | 아니다 |
| 정말 갈 수 없다 | 흐름장이 내가 선 칸까지 못 닿았다 (`_unreachable`) | 아니다 |
| 앞이 막혔다 | 나를 막은 것이 **이미 자리를 잡은 아군**이다 | **그렇다** (`HOLDING`) |

셋째가 포기 시간을 대신한다. 안쪽에 도착한 유닛부터 바깥으로 자리 잡음이 번져 나가고,
**막고 있던 유닛이 비키면 조건이 저절로 풀려 다시 간다. 재명령이 필요 없다.**

판정은 속도가 아니라 **실제로 줄어든 거리**로 한다. 앞이 막힌 유닛은 속도가 살아 있다 —
조향이 밀어 넣고 겹침 해소가 그만큼 도로 밀어내서, 속도계는 초당 160 픽셀을 가리키는데
목적지까지의 거리는 한 뼘도 줄지 않는다. 속도로 물었을 때 이 유닛이 영원히 "나아가는 중"으로
남아 결국 막힘으로 떨어지는 것을 보고 고쳤다.

`test/unit/test_proto_unit_stop.gd` 가 네 성질을 못 박는다.

### 아직 나쁜 것

- **좁은 문에서 줄을 서지 않는다.** 뭉쳤다 하나씩 빠지는 모습은 그대로다. 꺾임과 통과 시간은
  좋아졌지만 **줄 세우기는 못 넣었다** — 두 방식을 재 보고 둘 다 나빠서 걷어냈다(§7).
  다음 사람은 `통로 한가운데로 끌어당기기`부터 보면 된다.
- **`HOLDING` 이 실제로는 드물게 걸린다.** 서 있는 아군은 지나가는 유닛에게 밀려나도록
  되어 있어서(`_push_share` 가 서 있는 쪽에 0.75), 대개는 막히기 전에 밀고 나간다.
  100 명 판에서 한둘 나온다. 규칙은 맞게 도는데 **판이 그 상황을 잘 안 만든다.**
  그래서 테스트는 못 박은 아군으로 상황을 만들어 판정만 검증한다.
- **구석에 몰아넣을 때는 여전히 꺾임이 크다**(122 도/초). 자리가 목표 지점 하나로 겹쳐
  버리는 구간이라 흐름장 평활이 도와주지 못한다.
- **대형은 속도만 맞춘다.** 앞선 유닛이 뒤를 기다릴 뿐, 대열의 **모양**은 지키지 않는다.
- **장애물 회피는 격자 굵기까지만 한다.** 칸(32 픽셀)보다 얇은 틈은 표현되지 않는다.
- **한 칸 폭 복도에서 몸이 스치는 순간이 있다.** `push_out` 은 고쳤지만, 폭 32 픽셀에
  지름 24 면 여유가 8 픽셀뿐이라 밀치기와 벽 보정이 겹치는 프레임이 남는다.
