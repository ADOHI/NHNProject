> **이 문서는 작업 중에 쓴다.** 끝나고 쓰는 것이 아니다 ([`../CLAUDE.md`](../CLAUDE.md) 개발 원칙 1).
>
> 사용자 지시: *"무엇보다 계획적으로, 코드 모듈화 커플링 분리, 리팩토링도 같이 가면서 진행해"*

## 1. 먼저 쟀다 — **추측으로 리팩토링하지 않는다**

레인 열넷이 접히면서 `src/` 가 커졌다(테스트 623 → 1986). **커진 것이 곧 썩은 것은 아니므로**
고칠 곳을 정하기 전에 재기부터 했다.

### 1.1 지켜지고 있는 것 — **손대지 마라**

| 검사 | 결과 |
| --- | --- |
| `src/core/` 가 노드를 아는가 (`extends Node` · `get_node` · `@onready` · `add_child`) | **0건** |
| `src/core/` 가 `src/ui/` · `src/entities/` 를 아는가 | **0건** |
| 화면이 게임 난수를 굴리는가 | 1건 — **개발용 열람기의 「무작위 인물」 버튼**이라 규칙이 아니다 |

> **이 저장소의 핵심 규율은 지켜지고 있다.** `개발 원칙 2`(코어는 노드 비의존 순수 클래스)와
> `conventions.md §3.1`(게임 규칙은 전부 `src/core/`)이 열넷의 레인을 거치고도 안 뚫렸다.
>
> **그러므로 이 정리는 「썩은 것을 도려내는 일」이 아니다.** 아래 셋만 고친다.

### 1.2 진짜 위반 하나 — **출시 코드가 프로토타입에 기댄다**

```gdscript
# src/core/combat/sparring_field.gd:114
var approach_speed: float = ProtoMoveTuning.new().default_of("max_speed")
```

`src/core/` 가 **`src/proto/` 를 부른다.** 방향이 거꾸로다 —
프로토타입은 **버리려고 만든 것**인데 출시되는 전투가 그것에 매달려 있다.

**의도는 좋았다.** 주석이 이렇게 적고 있다.

> **수를 지어내지 않는다.** 값은 이동 레인의 실제 유닛 속도다.
> 계단의 평평한 쪽이라 어느 수를 골라도 결과가 같은데,
> **그러면 고를 이유가 있는 수를 고른다.**

**그 원칙은 옳고 유지한다.** 틀린 것은 **의존의 방향**이다 —
*"고를 이유가 있는 수"* 를 얻으려고 *"버릴 코드"* 에 링크를 걸었다.
값을 **옮겨 오고 출처를 주석으로 남기면** 둘 다 지켜진다.

### 1.3 없는 것 둘 — **`conventions.md` 가 자리를 비워 뒀는데 아직 안 찼다**

`conventions.md §1` 은 `src/systems/` 를 **"씬 전환, 저장, 오디오"** 라고 정의했다.
셋 중 **오디오만** 있다.

| 없는 것 | 지금 어떻게 되고 있나 | 없으면 |
| --- | --- | --- |
| **씬 전환** | `main.tscn` 하나가 전부다. `change_scene` 호출 **0건** | [08](design/08-ui-ux.md) §8.1 의 화면 흐름(타이틀 → 주둔지 → 던전 → 정산)이 **성립하지 않는다** |
| **저장** | `user://` 를 쓰는 게임 코드 **0건** | PC 출시인데 **껐다 켜면 다 사라진다** |

**둘 다 「나중에 필요할 것」이 아니라 「지금 없어서 화면이 안 이어지는 것」이다.**
타이틀도 아지트도 던전도 각자 씬으로 서 있는데 **서로 갈 길이 없다.**

### 1.4 쌓이고 있는 것 — `main.gd`

310줄 · 함수 20개 · 협력자 11개(`DungeonBoard` · `PressPage` · `PressPlate` ·
`RekkaFeedView` · `DebugOverlay` · `RekkaFeed` · `DungeonRun` · `SampleDungeons` ·
`DungeonCatalog` · `DungeonGrade` · `UiTheme`).

**아직 신전(god object)은 아니다.** 다만 [`architecture.md`](architecture.md) 가 스스로 이렇게 적어 뒀다.

> 콘텐츠가 생기면 이 씬은 **진입점 역할만** 남긴다.
> (어떤 씬을 띄울지 결정 → 해당 씬으로 전환) **플레이 로직을 여기에 쌓지 않는다.**

**콘텐츠가 생겼다.** 그런데 진입점이 아니라 **던전 화면 그 자체**가 되어 있다.
씬 전환 체계(§1.3)가 생기면 이 문제가 저절로 풀린다 — **`main` 은 고르는 자가 되고
던전은 제 씬으로 내려간다.** 그래서 §1.3 과 §1.4 는 **같은 작업이다.**

### 1.5 출시 빌드가 프로토타입을 싣는다

`export_filter="all_resources"` 라 `src/proto/` 넷(이동 · 애니 조절판 · 조명 · 효과음 데모)이
**PC 빌드와 웹 빌드에 다 들어간다.** 조명 실험실 하나가 705줄이다.

**빼는 것이 옳다** — 다만 §1.2 를 먼저 끊어야 뺄 수 있다. **지금 빼면 전투가 죽는다.**
그래서 순서가 정해진다.

## 2. 무엇을 하는가 — 셋

**순서가 있다.** ①이 ②의 전제이고, ③은 둘과 안 겹친다.

```
① 결합 끊기 (core → proto)  ──→ ② 프로토를 빌드에서 뺀다
                                         ↕ 안 겹침
③ 씬 흐름 + 저장 (src/systems/) ──→ main.gd 가 진입점으로 돌아간다
```

| # | 작업 | 건드리는 곳 | 왜 지금 |
| --- | --- | --- | --- |
| **①** | `core/combat` → `proto` 의존 끊기 | `src/core/combat/` | 유일한 진짜 방향 위반 |
| **②** | 프로토를 출시 빌드에서 제외 | `export_presets.cfg` | ① 뒤에만 가능 |
| **③** | **씬 흐름 + 저장** (`src/systems/`) | `src/systems/` · `src/main/` | 화면들이 서로 갈 길이 없다 |

### 2.1 안 하는 것 — **크기는 죄가 아니다**

1000줄짜리 파일이 셋 있다(`slash_sheet` · `backpack_board` · `radial_stage`).
**안 쪼갠다.** 셋 다 **한 가지 일**을 하고 있고, 줄 수가 많은 이유는
이 저장소가 **주석에 근거를 적기 때문**이다. 근거를 지우는 리팩토링은 손해다.

> **리팩토링의 기준은 줄 수가 아니라 「이유가 몇 개인가」다.**
> 이유가 하나면 길어도 둔다. 이유가 둘이면 짧아도 가른다.

`src/core/ui/` 의 30 파일도 안 건드린다 — **전부 순수 함수**이고 이미 파일 단위로 갈려 있다.

## 3. 검증 — 리팩토링은 「고쳤는데 안 돌아간다」가 허용되지 않는다

`CLAUDE.md` 개발 원칙 4. **리팩토링 커밋은 반드시 실행 검증을 거친다.**

```bash
godot --headless --path . --import
godot --headless --path . --quit-after 120
python tools/run_gut_retry.py --expect-tests 1986
python tools/run_lint_retry.py
```

**기준선 1986/1986 · 스크립트 174.** 리팩토링이므로 **이 수가 줄지도 늘지도 않는 것이 정상**이다
(②는 빌드 설정이라 테스트가 안 변한다). 늘어나면 새 기능이 섞여 들어간 것이고,
줄어들면 무언가를 잃은 것이다.

구조를 옮기는 변경은 **`.godot/` 캐시를 지우고** 검증한다 — 캐시가 깨진 경로를 가려 준다.

**그리고 PC 빌드를 실제로 뽑아 돌린다.** ②는 빌드 설정을 바꾸므로 테스트로는 안 잡힌다.

## 5. ①과 ② 를 했다 — **결합 분리 레인**

§2 의 셋 중 **①과 ②**다. ③(씬 흐름 + 저장)은 다른 레인이 맡았고 겹치지 않는다.

### 5.1 ① 값은 옮기고 **관계는 시험으로 내렸다**

문제의 한 줄은 이것이었다.

```gdscript
# src/core/combat/sparring_field.gd:114 (고치기 전)
var approach_speed: float = ProtoMoveTuning.new().default_of("max_speed")
```

**주석에 적힌 의도는 옳다** — *"수를 지어내지 않는다"* (§1.2).
그래서 **값의 출처는 안 건드리고 의존의 방향만 뒤집었다.**

| 어디로 | 무엇 |
| --- | --- |
| `SparringField.DEFAULT_APPROACH_SPEED := 230.0` | `ProtoMoveTuning.DEFS` 의 `max_speed` 기본값을 **확인하고 그대로 베꼈다** |
| 그 상수의 주석 | 어느 파일 어느 항목에서 왔는지 · §28.20.50 의 길 · **왜 부르지 않고 베꼈는지** |
| `test/unit/test_sparring_queue.gd` | 베낀 상수와 `ProtoMoveTuning` 의 기본값이 **같은지 본다** |

#### 베끼면 어긋난다 — 그래서 어긋남을 붙드는 자리를 시험으로 내렸다

§28.20.50 이 세운 원칙은 *"수가 아니라 관계로 적는다 — 남이 값을 옮기면
고칠 곳이 하나다"* 였다. **출시 코드는 이제 그 관계를 적을 수 없다** —
적는 순간 방향이 다시 거꾸로가 된다.

**그러면 시험이 적는다.** 시험은 `test/*` 라 **빌드에 안 들어가므로** 프로토를 불러도
방향 문제가 없다. 이동 레인이 `max_speed` 를 옮기면 그 시험이 빨개지고,
그때 고칠 곳은 여전히 **한 줄**이다.

> **이 자리 바꿈으로 잃은 것이 하나 있다.** 전에는 값이 *저절로* 따라왔고
> 이제는 **시험이 알려 주면 사람이 옮긴다.** 자동이 반자동이 됐다.
> 대신 얻은 것이 **출시 빌드가 프로토타입을 안 싣는 것**이라 거래가 맞는다.

#### `src/core/` 에 프로토 의존은 이것 하나뿐이었다

```bash
grep -rn "Proto[A-Z]" src/core/ --include=*.gd
```

지금 남은 것은 **주석 안의 언급 다섯**뿐이다 — `nav_grid.gd` 의 유래 설명과
`sfx_event.gd` 의 「이 신호가 어디서 나는가」 표. **부르는 곳은 0건이다.**

### 5.2 ② 지우는 게 아니라 **내보내기에서만** 뺐다

`[preset.0]`(Web)과 `[preset.1]`(Windows Desktop) **둘 다**의 `exclude_filter` 에
`src/proto/*` 를 더했다. 까닭은 프리셋 옆 주석에도 적어 뒀다.

**파일은 그대로 있다.** 이 구분이 중요하다 — 지우면 아래가 같이 죽는다.

| 프로토를 여는 것 | 빌드에 들어가나 | 계속 돌아야 하나 |
| --- | --- | --- |
| `tools/capture_unit_move.gd` · `tools/bench_frame_budget.gd` | 들어간다(`tools/` 는 제외 안 함) | **에디터·헤드리스에서 돈다** |
| `tools/web_frame_bench.gd` · `tools/web_combat_bench.gd` | 들어간다 | 돈다 |
| `test/unit/test_proto_*.gd` 등 | **안 들어간다**(`test/*` 제외) | 돈다 |

넷 다 씬 경로를 **`preload` 가 아니라 문자열 상수**로 들고 있어서,
프로토가 빌드에서 빠져도 **다른 파일의 파싱이 깨지지 않는다.** 확인하고 뺐다.

#### 잰 것

| | `.pck` (두 프리셋 동일) |
| --- | --- |
| 빼기 전 | **27,244,172 B** (25.98 MiB) |
| 뺀 뒤 | **27,096,780 B** (25.84 MiB) |
| 차이 | **-147,392 B** (-143.9 KiB · **-0.54%**) |

GDScript 7,224줄이 압축된 바이트코드로는 이만큼이다. **용량이 목적이 아니었다** —
목적은 §1.5 가 적은 대로 *"버리려고 만든 것을 출시본이 안 싣는 것"* 이다.

검증은 이렇게 했다.

- `.pck` 안에서 `src/proto` 문자열을 센다 → **0건** (빼기 전에는 들어 있었다)
- `build/windows/Geum.exe --quit-after 180` → **오류 없이 종료**
  (OpenGL 3.3 compatibility 로 뜨는 것까지 확인)
- 두 익스포트 모두 경고·오류 **0건**

#### ⚠ §1.5 의 「31.7 MB」는 이 기계의 국소 현상이다 — **제출본은 그렇지 않다**

계획을 쓸 때 잰 31.7 MB 가 이 워크트리에서는 **27.2 MB** 로 나왔다. 4.5 MB 차이의
원인은 프로토가 아니라 **본체 체크아웃에만 있는 개발용 캡처 PNG** 다 —
루트의 `.capture_*.png` · `.chk_*.png` 24개(원본 29.5 MB).

이것들은 이름이 점으로 시작하지만 **디렉터리가 아니라 파일이라 Godot 이 임포트한다.**
`export_filter="all_resources"` 라 임포트된 것은 전부 실린다. **즉 이 기계의 릴리스
빌드는 디버그 스크린샷을 싣고 있었다.**

**제출물에는 영향이 없다.** 전부 gitignore 대상이라 CI 의 새 클론에는 없다 —
GitHub Actions 가 뽑는 빌드는 처음부터 27 MB 대다.

> **제안 (미착수 · 통합자 결정).** `exclude_filter` 에 `.capture_*` · `.chk_*` 를
> 더하면 **로컬에서 뽑은 빌드도 CI 와 같은 크기**가 된다. 이 레인의 지시 범위
> (`src/proto/*`) 밖이라 **넣지 않았다.**

#### ✅ 통합자가 받았다 — 그리고 **예상보다 컸다**

넣었다. 다만 **이 레인의 읽기 하나가 틀렸다** — 24개가 전부 gitignore 대상인 줄 알았는데
**`.chk_*.png` 15개는 git 에 추적되고 있다**(20 MB). 즉 **CI 빌드도 그것을 싣고 있었다.**
「제출본에는 영향이 없다」가 절반만 맞았다.

| | `.pck` |
| --- | --- |
| 이 기계, 빼기 전 | **31,707,676 B** |
| 이 기계, 뺀 뒤 | **17,710,672 B** |
| 차이 | **-13,997,004 B (-44 %)** |

**CI 빌드도 약 27 MB → 17.7 MB 로 준다** (추적된 `.chk_*` 20 MB 가 거기서도 빠지므로).

**패턴에 함정이 있었다.** `.capture_*` 로 적으면 **하나도 안 걸린다** —
Godot 의 `exclude_filter` 는 `res://.capture_x.png` 라는 **전체 경로**에 글롭을 맞추므로
앞에 `*` 가 있어야 한다. 처음에 `.capture_*` 로 넣고 크기가 그대로여서 알았다.
지금 값은 **`*.capture_*, *.chk_*`** 다.

안 지웠고 안 옮겼다. **참조가 0건인 것을 확인하고 빼기만 했다** —
`src/` · `tools/` · `docs/` 어디도 이 파일들을 가리키지 않는다.
검증 산출물이라 저장소에는 남긴다.

### 5.3 검증 — **두 번 빨갛게 뜬 것은 기계였다**

| 검사 | 결과 |
| --- | --- |
| `godot --headless --path . --import` | 오류 없음 |
| `godot --headless --path . --quit-after 120` | 오류 없음 |
| `python tools/run_gut_retry.py --expect-tests 1986` | **1986/1986 · 스크립트 174** |
| `python tools/run_lint_retry.py` | 지적 **0건** (폭사 후 재시도 19회) |

**테스트 수는 1986 그대로다.** 시험 함수를 더하지 않았다 —
`test_the_walking_speed_comes_from_the_movement_lane` **안에 단정을 하나 늘렸을 뿐**이다
(베낀 상수 ↔ 프로토 기본값). 리팩토링이므로 수가 안 변하는 것이 맞다 (§3).

GUT 가 **연속 두 번** 빨갛게 떴다. 그런데 실패한 시험이 **매번 달랐고**,
