## 30.1 이미 있는 것 — 다시 만들지 않는다

**이 레인의 절반은 남이 이미 만들었다.** 무엇을 어떻게 쓰는지 먼저 못 박는다.

| 무엇 | 어디 | 이 화면이 쓰는 방식 |
| --- | --- | --- |
| 아지트의 **규칙** | `src/core/guild/` (§22) | **그대로 쓴다.** 시설 · 배치 · 자원 · 정산을 새로 만들지 않는다 |
| 시설 배치표 | `FacilityAssignment` | ②의 "끌어서 넣기" 는 이 클래스의 `assign()` 을 부르는 손잡이일 뿐이다 |
| 군중 이동 | `src/proto/unit_move/core/` | ①의 바닥. §30.3 에 어떻게 얹는지 적었다 |
| 인물 · 관계 · 사건 | `src/core/npc/` (§24) | ⑤ 말풍선 **대사의 출처.** §30.6 |
| 출정 대상 | `src/core/gate/` (§22.5) | ⑥이 고르는 것 |
| UI 조형 | `src/ui/kit/` (§20) | **아직 안 붙인다.** §22.8.7 과 같은 이유 — 미확정 실험을 붙잡지 않는다 |

### 남의 코드를 복사하지 않는다 — 대신 얹는다

`src/proto/unit_move/` 는 **프로토타입 폴더**다. `src/` 본편이 프로토타입을 참조하면
프로토타입을 지울 수 없게 된다. 그래서 이 화면은 지금 그것을 `import` 하지 않는다.

**대신 좌표계를 맞춰 둔다** (§30.2). ①에 손댈 때 `unit_move/core/` 의 이동 코어를
`src/core/` 로 승격시키고 양쪽이 같은 것을 쓰게 하는 것이 계획이고,
그 승격이 승인되기 전까지는 배회를 시작하지 않는다.

### ⚠ 스쿼드 규칙과 어긋나지 않는다 — 확인했다

[`14-squad.md`](14-squad.md) §14.2 는 **"스쿼드는 판 위에서 말 하나다"** 를 확정했다.
아지트에서 대원 넷이 각자 돌아다니는 것이 이것과 어긋나는가 — **어긋나지 않는다.**

§14.2 가 말하는 "판" 은 **던전의 방 그래프**다. 근거 셋이 이미 저장소 안에 있다.

1. `src/proto/unit_move/README.md` 머리말이 같은 질문에 먼저 답했다 —
   *"방 그래프 위에서 스쿼드가 하나로 움직이는 것과, 방 안에서 대원을 따로 고르는 것은 층이 다르다."*
2. [`28-combat.md`](28-combat.md) §28.1 확정 8 — *"전투에 들어가면 스쿼드가 대원 3~4명으로 펼쳐진다."*
   이미 확정 사항이 "펼쳐진다" 를 인정한다.
3. §22.2 가 코드로 정한 경계 — `GuildMember × N → Squad → Actor 하나`.
   **접히는 순간은 편성이다.** 아지트는 접히기 *전*이므로 개체가 여럿인 것이 맞다.

> **못 박는다: 대원이 하나로 접히는 것은 `Squad.to_actor()` 한 지점뿐이다.
> 그 앞(아지트)과 그 뒤(전투)에서는 개별이다.**

## 30.2 ④ 시점 — 쿼터뷰는 그리기지 규칙이 아니다 (핵심 결정)

> **격자 좌표로 계산하고, 그릴 때만 마름모로 접는다.**

`LANE-RULES.md` §5 가 맵 파이프라인에 대해 못 박은 것과 같은 형태다 —
*"정면 텍스처 + 셰이더가 시점을 만든다. 원근을 판에 굽지 마라."*
여기서도 **원근을 데이터에 굽지 않는다.**

| 층 | 좌표 | 무엇이 산다 |
| --- | --- | --- |
| 규칙 | `Vector2i` 칸 | 건물 발자국 · 겹침 · 통행 · 배치 |
| 이동 | `Vector2` 평면 픽셀 | 배회 · 길찾기 (①. 아직 없다) |
| 그리기 | `Vector2` 화면 픽셀 | `IsoProjection` 이 만든다 |

이렇게 갈라 두면 얻는 것 셋이다.

1. **시점을 바꿔도 규칙이 안 깨진다.** 「아이소메트릭 혹은 쿼터뷰」라는 미정(★1)이
   `IsoProjection` 의 상수 두 개로 좁혀졌고, **실제로 그 둘만 고쳐서 시점을 바꿨다**
   (§30.2.1). `HideoutGrid` 도 테스트도 한 줄 안 바뀌었다. 이 설계가 값을 한 자리다.
2. **겹침 검사가 마름모 기하를 안 푼다.** 사각형 발자국 겹침이라 정수 비교로 끝난다.
3. **이동 코어를 그대로 얹는다.** `ProtoNavGrid` 는 평면 픽셀 격자다.
   아이소를 데이터에 구우면 저 코어가 통째로 못 쓰이게 된다.

### 투영식

**2:1 마름모 (현재 확정).** 칸 하나가 가로 `TILE_W` · 세로 `TILE_H` 이고 `TILE_W = 2 × TILE_H` 다.
(한때 3:1 로 두었다가 §30.12 로 되돌렸다. 식의 형태는 같고 상수만 다르다.)

```
screen.x = (cell.x - cell.y) * TILE_W / 2
screen.y = (cell.x + cell.y) * TILE_H / 2
```

역변환은 같은 식을 푼 것이고 `floor` 로 칸을 잡는다 (`world_to_cell`).
**둘이 왕복해도 같은 칸이 나오는지를 테스트가 지킨다** — 아이소에서 가장 흔한
버그가 클릭한 칸과 그려진 칸이 한 칸씩 어긋나는 것이다.

### 30.2.1 시점 비율 — ★1 (이력 → **2:1 확정**)

> **현재: dimetric 2:1. `TILE_W = 96 · TILE_H = 48`. 피치 30° · 마름모 모서리 26.57°.**
> 코드: `IsoProjection.DEFAULT_TILE_WIDTH/HEIGHT`. 아래는 **어떻게 여기 왔는지** 기록이다.

**1차 (폐기):** 인물 시트(`pp1_*`) 접지·장화를 보고 **3:1** 을 골랐다.
사용자 답 「쿼터뷰 (캐릭터와 맞춤)」에 맞춘 것이었으나, 시트는 게임 카메라 증거가 약했다
(§30.12.3).

| 비율 | 각 | 1차 판단 (시트 기준) | 이후 |
| --- | --- | --- | --- |
| **2:1** | **30°** | 인물이 판때기처럼 보임 | **채택** — 가림·건물 각 |
| 3:1 | 19.5° | 시트와 맞아 보임 | **폐기** — 2층이 판 43% 가림 |
| 4:1 | 14.5° | 칸 뭉개짐 | 폐기 |

**2차 (확정):** 배회에 사람을 세운 뒤 층 높이·가림을 재니 3:1 불가 (§30.12.2).
건물 그림 각도도 2:1. **`DEFAULT_TILE_HEIGHT` 32→48.**

> **고칠 때는 `IsoProjection` 상수만 고친다.** 격자·배치·배회는 칸 단위라 안 건드린다.
> 발주서·JSON 은 dump 로 다시 뽑는다.

### 30.2.2 게임 안에서 확인했다 — ★8

창을 띄워 `tools/capture_hideout.gd` 로 세 장 찍었다 (`.captures/hideout_*.png`).
**GPU 는 짧게 쓰고 바로 놓았다.**

| 본 것 | 결과 |
| --- | --- |
| 쿼터뷰가 게임 안에서도 그 각도로 서는가 | **선다.** PIL 로 본 것과 같다 |
| 건물이 판때기가 아니라 덩어리로 읽히는가 | **읽힌다** (벽 58px) |
| 앞 건물이 뒤를 가리는가 (깊이 정렬) | **가린다** |
| **가리킨 칸이 커서 밑에 정확히 붙는가** | **붙는다.** 공방 앞 칸 (3,4) 에 정확히 |

마지막 줄이 이 캡처의 진짜 목적이다. 한 칸 어긋남은 **눈으로만 잡히는 버그**다.

#### 찍으면서 걸린 것 둘

**하나. 바꾸고 그 자리에서 찍으면 바꾸기 전 화면이 나온다.**
`get_texture().get_image()` 는 이미 그려진 **마지막** 프레임을 준다.
처음에 그렇게 짰다가 확대 장면이 확대 전 화면으로 찍혔고 세 장이 통째로 한 칸씩 밀렸다.
**바꾸고 - 몇 프레임 두고 - 찍는다.**

**둘. 코드로 가리킨 것은 다음 프레임에 실제 마우스 자리로 덮인다.**
화면이 매 프레임 실제 커서를 읽기 때문이다. 그래서 `Input.warp_mouse` 로
**OS 커서를 진짜로 옮긴다** — 덤으로 사람이 쓰는 길과 같은 길을 시험하게 된다.

### 깊이 정렬

```
depth = cell.x + cell.y
```

마름모 판에서 이 값이 곧 "화면에서 아래쪽" 이다. 발자국이 여러 칸인 건물은
**가장 큰 값**(오른쪽 아래 모서리)을 쓴다 — 그래야 앞의 건물이 뒤를 가린다.

Godot 의 `YSort` 를 쓰지 않는 이유: 발자국이 큰 건물은 원점 하나로 정렬하면
반쯤 겹칠 때 틀린다. 정렬 키를 직접 계산하면 그 규칙을 테스트가 지킨다.

### 그림은 없다 — 도형으로 세운다

칸은 마름모 선, 건물은 **마름모 바닥 + 세로 기둥 + 마름모 지붕** 세 조각이다.
이 프로젝트의 다른 레인이 전부 그렇게 했고(§22.8), 그림이 오면 갈아 끼운다.

## 30.3 ① 배회 — 경계부터 정한다 (★4 진행 중)

`src/proto/unit_move/core/` 가 이미 푼 것을 다시 풀지 않는다.
**다만 통째로 물려받지도 않는다.** 이동 레인의 답이 그렇게 왔다.

| 지금 가져올 수 있다 | 아직 아니다 | 왜 |
| --- | --- | --- |
| `nav_grid` (통행 · 시야 · `push_out`) | `unit_field` · `gate` · `jam` · `yield` · `push` | **좁은 목에 40~100명일 때의 기계다.** 거점에 열몇 명이면 안 쓰는 장치다 |
| `flow_field` (목적지 하나로 가는 방향) | `formation` | **배회는 대열 자리가 없다** |
| (겹침이 중요해지면) `unit_step` · `unit_agent` | `unit_selection` · `control_groups` | RTS 조작이다. 아지트는 끌어 넣기지 부대 지정이 아니다 |

순서는 이렇다.

1. ✅ **경계 셋을 합의한다** (아래 §30.3.1)
2. ✅ **`nav_grid` + `flow_field` 둘만 `src/core/nav/` 로 옮겼다** (아래 §30.3.5)
3. 위층은 이동 레인이 표를 닫은 뒤

### 30.3.5 아래층만 올렸다 — `src/core/nav/`

```
src/core/nav/
├── nav_grid.gd     NavGrid    (전 ProtoNavGrid)
└── flow_field.gd   FlowField  (전 ProtoFlowField)
```

**`Proto` 접두사는 아래층에서만 뗐다.** 위층(`ProtoUnitField` · `ProtoUnitPush` · …)은
`src/proto/unit_move/` 에 그대로 있다. 접두사가 **"아직 프로토타입 전용"** 이라는 뜻을
지고 있고 그 뜻이 아직 참이기 때문이다. 올린 둘은 쓰는 곳이 둘이 되었으므로 더는 참이 아니다.

옮긴 것은 **파일 위치와 이름뿐이고 한 줄도 안 고쳤다.** `preload` 로 경로를 박은 곳이
하나도 없어서(전부 `class_name` 참조) 옮기는 데 경로 수정이 필요 없었다.

#### 검증 — 이동 레인의 자로 쟀다

이동 레인은 모든 판단을 `tools/measure_unit_move.gd` 의 **열다섯 판 표**로 한다.
그래서 옮기기 **전에 먼저 그 표가 실제로 돌고 있나부터 확인했다** (LANE-RULES §1).

> ⚠ **그 표는 스스로 흔들린다.** 손대지 않은 `main` 에서 세 번 돌렸더니
> `좁은 통로 100` 행이 1·3회차와 2회차 사이에서 갈렸다 — 정지 37.63s vs 31.02s(**21%**),
> 정지밀림 18943 vs 16223 px(**17%**). `한 칸 문 40` 도 드물게 갈린다.
> **나머지 열세 행은 세 번 다 완전히 같았다.**

그래서 비교 규칙을 이렇게 잡았다.

| | |
| --- | --- |
| 비교 대상 | **흔들리지 않는 열세 행** (`좁은 통로 100` · `한 칸 문 40` 제외) |
| 판정 | 이동 전 `main` 과 **완전히 같아야** 한다 |
| 결과 | **이동 후 세 번 모두 열세 행이 이동 전과 완전히 동일.** 전체 표도 1회차는 통째로 동일 |

`tools/bench_flow_field.gd` 도 돈다. 테스트 659/659 통과.

### 30.3.1 아래층에 물을 것은 셋뿐이다

배회가 이동 코어에 묻는 것은 이 셋이고, **이 셋 밖의 것은 안 묻는다.**
경계를 좁게 잡아 두면 아래층이 통째로 갈려도 배회는 안 깨진다.

| # | 묻는 것 | 서명 | 지금 누가 답하나 |
| --- | --- | --- | --- |
| 1 | **여기 설 수 있나** | `can_stand(cell: Vector2i) -> bool` | `HideoutGrid.is_walkable` — **이미 있다** |
| 2 | **저기로 가는 방향** | `direction_at(from: Vector2, goal: Vector2i) -> Vector2` | 없다. `flow_field` 가 답할 자리 |
| 3 | **이 방향으로 얼마나 갈 수 있나** | `free_run(from: Vector2, dir: Vector2, limit: float) -> float` | 없다. `nav_grid` 가 답할 자리 |

셋 다 **칸이나 평면 픽셀만 주고받는다.** 화면 좌표도 `IsoProjection` 도 넘어가지 않는다 —
넘어가는 순간 아래층이 시점을 알게 되고 §30.2 가 무너진다.

3번이 「부딪히면 멈춘다」를 배회 쪽에서 처리할 수 있게 해 준다.
아래층에 밀치기·양보를 맡기지 않아도 되는 이유가 이것이고,
그래서 `push`·`yield`·`jam` 을 안 가져와도 성립한다.

### 30.3.2 ⚠ `정지밀림 0` 계약을 그대로 못 물려받는다

이동 레인의 계약은 **「멎은 뒤 제 자리에서 멀어지지 않는다」** 인데,
**배회에는 「제 자리」가 없다.** 명령도 대열 자리도 없기 때문이다.

> **배회의 계약 (새로 정한다):**
> **1. 서 있는 동안 좌표가 바뀌지 않는다.** 남이 밀어서 움직이는 일은 없다 (밀림 0 은 그대로다)
> **2. 다시 움직이는 이유는 자기 결정뿐이다.** 남이 비켰다고 다시 가지 않는다
> **3. 막히면 그 자리에 선다.** 뚫으려 하지 않는다 — 거점에는 뚫어야 할 좁은 목이 없다

3번이 `jam`·`yield`·`gate` 를 안 가져오는 근거다. **교착이 문제가 아닌 판이다.**
설 자리를 못 찾으면 목적지를 다시 고르면 되고, 그것은 위층(배회)의 일이다.

### 30.3.3 ⚠ `ProtoMoveTuning` 기본값을 그대로 쓰지 않는다

그 값들은 **40~100명이 좁은 목을 지나는 판**에서 고른 것이다 (§23.2 시험 인원).
거점에 열몇 명이면 과하다.

- **`막힘 비용`(`_JAM_PENALTY`) 은 끈다** — 기억해 둘 막힘이 없다
- **`문 차례`(`yield`) 는 끈다** — 줄 설 문이 없다
- 벽 붙기 완화(`_WALL_PENALTY`)는 남긴다 — 건물에 몸이 걸리는 것은 거점에서도 보인다

### 30.3.4 시계가 붙어도 배회만 고치게 둔다 (★5 의 조건)

사용자 답: **시간은 나중에 정한다. 지금은 시계 없이 가고 배회는 연출이다.**
**조건이 붙었다 — 나중에 시계가 붙어도 배회 쪽만 고치면 되어야 한다.**

그래서 못 박는다.

> **`src/core/hideout/` 에는 시간이 없다.** 격자도 건물도 `delta` 를 모르고
> `tick` 도 `_process` 도 없다. 지금 그렇고, 앞으로도 그렇다.
> **흐르는 것을 아는 것은 배회 층 하나뿐이다.**

시계가 생기면 바뀌는 것은 「배회가 무엇을 보고 목적지를 고르는가」뿐이다 —
지금은 아무 빈 칸이나 고르고, 시계가 생기면 근무 시간표를 본다.
**고르는 자리가 한 곳이면 갈아 끼우는 것도 한 곳이다.**

이것이 §22.0 의 「타이머를 만들지 않았다」와도 안 부딪힌다. 아웃게임의 시간은
여전히 원정 횟수뿐이고, 배회의 움직임은 **시간이 아니라 연출**이다.

## 30.4 ③ 그리드 배치 — 선다

| 층 | 무엇 |
| --- | --- |
| `HideoutGrid` | 점유표 · `can_place` · `blocked_reason` · `place`/`move`/`remove` |
| **`HideoutPlacement`** | **놓는 중인 상태.** 겨누기 · 유효성 · 확정 · 취소 |
| `HideoutGhostView` | 미리보기 (된다/안 된다를 색으로) |

조작은 넷이다 — `1`·`2`·`3` 으로 짓기 시작, 왼클릭으로 확정, 건물을 왼클릭해 집기,
오른클릭·`ESC` 로 그만두기.

### 짓기와 옮기기를 한 클래스에 뒀다

둘은 **끝에서만 다르다.** 겨누기 · 유효성 · 미리보기 · 취소가 전부 같고
`commit()` 만 갈린다. 나누면 그 넷이 두 벌이 되고 한쪽만 고치는 일이 생긴다.

### 못 놓는 자리는 판을 안 건드린다

`commit()` 은 **확정하는 순간까지 판을 안 만진다.** 옮기는 중에도 원래 자리에 그대로 있고,
취소하면 되돌릴 것이 없다 — 애초에 안 옮겼기 때문이다.
되돌리기 코드를 만들지 않은 것이 이 설계의 요점이다. **되돌리기는 조용히 틀린다.**

### 옮길 때 제 몸은 걸림돌이 아니다

한 칸 옮기려는데 제 발자국이 겹쳐서 막히면 그것은 규칙이 아니라 버그다.
`blocked_reason(.., ignore_id)` 가 자기 자신을 빼고 본다.

### 잡은 자리를 기억한다

겨누는 칸이 곧 발자국의 왼쪽 위가 되면 2x3 건물이 커서 밑에서 튄다.
잡을 때의 어긋남을 들고 있다가 계속 더한다. **새로 짓는 것은 발자국 가운데를 잡은 셈** 친다.

### 발자국의 출처는 하나다

`HideoutBuilding.footprint_for()` 뿐이다. 처음에는 화면의 시작 배치표에 크기를 적어
두었는데, 「짓기」가 생기는 순간 같은 값이 두 곳에 살게 되었다.
**크기가 갈리면 미리보기와 실제 건물이 다른 크기가 된다.**

### 자원 소모는 아직 없다

사용자 지시가 "자원은 나중, 놓이고 겹침 검사되는 것부터"였다.
붙일 자리는 `Guild.funds` 이고 §22.6 의 정산이 이미 그 값을 움직인다 (★7).

### 30.4.1 조사가 틀려 있었다 — `KoreanJosa`

화면에 **"공방 와 겹친다"** 가 떴다. 받침이 있으면 "과" 다.

**코어가 문장을 만드는 이상(conventions.md §3.1) 조사도 코어의 몫이다.**
화면마다 고치면 화면마다 다르게 틀린다. 그래서 `src/core/text/korean_josa.gd` 로 뺐다 —
이 게임의 글자는 전부 한국어라 **두 번째 사용처가 생길 여지가 뻔하다**
(CLAUDE.md 원칙 2).

한글 음절은 `가`(0xAC00) 부터 초성 19 × 중성 21 × 종성 28 로 규칙적이라
`(코드 - 0xAC00) % 28` 이 0 이 아니면 받침이 있다. 표가 필요 없다.
**`로`/`으로` 만 예외다** — 받침이 ㄹ 이면 "로" 다.

시설 셋의 이름이 셋 다 다르게 갈리는 것이 그대로 테스트다 —
공방**과** · 정보실**과** · 접선처**와**.

### 30.9.1 ★2 판 크기 — 임시로 14 × 14 로 뒀다

**20 × 20 으로 세웠다가 창에 띄워 보고 줄였다.**

| | 20 × 20 | **14 × 14** |
| --- | --- | --- |
| 판 전체를 화면에 맞췄을 때 칸 폭 | 57 px — 뭉개진다 | **82 px — 줌 없이 읽힌다** |
| 건물 셋이 차지하는 비율 | 4 % (사백 칸에 흩어져 텅 빈 벌판) | **8 %** |
| 빈 칸 | 384 | 180 |

**마름모의 가로세로 비는 칸 수와 무관하다 — 타일 비가 정한다. 지금은 항상 2:1 이다.**
그래서 「세로를 늘리든 가로를 줄이든」으로 화면을 채울 방법이 없고,
**손잡이는 칸 수 하나뿐**이었다.

아지트는 **사람이 돌아다니는 것을 지켜보는 화면**이므로 줌 없이 다 보이는 쪽을 골랐다.
2:1 판을 16:9 화면에 넣으면 위아래가 남는데, 그 자리는 ⑥(메뉴 · 출정)이 앉을 곳이다.

**배회(①)를 넣어 보고 다시 정한다.** 열몇 명이 180 칸에서 어떻게 보이는지는
아직 아무도 못 봤고, 이 값은 그때 가장 크게 흔들릴 값이다.

## 30.10 ★ 건물 그림 규격 — 발주서

> **그림보다 규격이 먼저다.** 규격 없이 뽑으면 도착한 날 안 맞는 것을 알게 되고,
> 그때는 통째로 다시 뽑는다.

**숫자의 출처는 `src/core/hideout/hideout_building_art.gd` 하나다.**
이 절과 `hideout-building-art.json` 과 밑그림 PNG 는 전부 거기서 나온다.
**이 문서와 코드가 갈리면 코드가 맞다** — 화면이 실제로 쓰는 것은 그쪽이다.

```bash
godot --headless --path . -s res://tools/dump_hideout_art_spec.gd   # 규격 -> json
python tools/draw_hideout_art_template.py                           # json -> 밑그림 PNG
```

### 30.10.1 한 장에 필요한 것

> **아래 표는 2026-08-10 기준 코어 산출이다.** 갱신:
> `godot --headless --path . -s res://tools/dump_hideout_art_spec.gd`
> → `docs/design/hideout-building-art.json`. **표와 JSON 이 갈리면 JSON 이 맞다.**

| | 값 |
| --- | --- |
| 형식 | PNG · RGBA · 배경 투명 (생성 직후는 단색 배경 허용 → fit 이 키잉) |
| 시점 | **dimetric 2:1**, 내려보는 각 **30°**, 마름모 모서리 **26.57°** (`TILE 96×48`) |
| **한 층 높이** | **약 88 px** (`cell_height_px ≈ 58.79` × `STOREY_CELLS 1.5`) |
| **높이 상한** | **2층.** 가림은 `hidden_cells_behind` — 2:1 에서 1층 ≈ 1칸, 2층 ≈ 3칸 |
| 여백 | 사방 8 px |
| **정합** | **fit → 그리드 캔버스** (§30.10.7). 생성 원본을 발주 크기에 맞춘다 |
| **화풍** | **인물 화풍 그대로 — 전부 하나다** (LANE-RULES §5)<br>`1990s anime cel, high chroma, one small complementary accent area, hard specular highlights` |

건물 종류별 캔버스와 기준점 (**2:1 타일 기준, dump 결과**):

| 시설 | 발자국 | 바닥 마름모 | 캔버스 1층 | 캔버스 2층 | 기준점 (1층) |
| --- | --- | --- | --- | --- | --- |
| 공방 | 2 × 2 | **192 × 96** (2:1) | **208 × 200** | **208 × 288** | (104, 192) 가운데 x |
| 정보실 | 2 × 3 | **240 × 120** (2:1) | **256 × 224** | **256 × 312** | (**104**, 216) x 아님 |
| 접선처 | 3 × 2 | **240 × 120** (2:1) | **256 × 224** | **256 × 312** | (**152**, 216) x 아님 |

바닥 마름모는 발자국이 무엇이든 **항상 타일 비와 같다 (지금 2:1)**.
`half_width×(w+h)` 대 `half_height×(w+h)`.

### 30.10.2 기준점은 바닥 마름모의 **아래꼭짓점**이다

캔버스 왼쪽 위에서 재고, 밑그림에 **노란 십자**로 찍혀 있다.

> **가운데가 아니다.** 발자국이 정사각형(공방)일 때만 우연히 가운데와 겹친다.
> 2x3 과 3x2 는 캔버스 크기가 같은데 기준점이 다르다 — 104 와 152.

**왜 아래꼭짓점인가.** 캐릭터 파츠 레인이 같은 것을 겪었다 —
피벗을 밑변으로 잡으니 크기가 접지에 안 샜다. 건물도 같다.
**지붕을 높이거나 굴뚝을 얹어도 땅에 닿는 자리가 안 움직여야 한다.**
가운데를 기준으로 잡으면 그림이 위로 자랄 때마다 접지가 따라 움직인다.

두 번째 이유는 **그리는 차례와 같은 점**이라는 것이다. `IsoProjection.rect_depth` 도
발자국의 앞 모서리로 순서를 정한다 — 기준점과 정렬 기준이 같으면 어긋날 일이 없다.

### 30.10.3 ★ 높이 상한 — 재서 정했다

> **N 층 건물은 바로 뒤 2N 칸을 완전히 가린다.**

화면에서 대각선 위로 한 칸 물러나면 세로로 마름모 하나(`tile_height`, 지금 **48 px**)만큼 올라간다.
그래서 가려지는 칸 수는 **높이 ÷ tile_height** 다. 값은 `IsoProjection.hidden_cells_behind` 이 잰다.

| 높이 | 대략 px (2:1) | 뒤로 가리는 칸 (공식·실측) |
| --- | --- | --- |
| **1층** | **~88** | **1** |
| **2층** | **~176** | **3** |
| 3층 | ~264 | (상한 밖) |

**공식만 믿지 않았다.** `test_hideout_building_art.gd` 가 칸의 꼭짓점 넷을 건물 실루엣에
실제로 넣어 보고 세며, 그 개수가 공식과 같은지 확인한다. 1층·2층 둘 다 맞았다.
눈으로도 봤다 — `.captures/hideout_occlusion_1f.png` · `_2f.png`.

**상한을 2층으로 잡은 이유:** 판이 14 칸(§30.9.1)인데 3층이면 여섯 칸이 사라져
뒤쪽 절반이 안 보인다. 네 칸도 이미 크지만, 2층을 못 쓰면 건물이 전부 납작해져
아지트가 벌판이 된다. **잠정이고, 배회(①)에 사람을 세워 보면 다시 잰다** —
가려서 곤란한 것은 바닥이 아니라 **거기 서 있는 사람**이기 때문이다.

> ⚠ **같은 높이끼리는 서로를 완전히 가리지 못한다.** 둘 다 같은 만큼 올라가서
> 높이가 상쇄되기 때문이다. 가려지는 것은 **바닥과, 뒤 건물의 벽 아래쪽**이다.
> 그래서 「건물이 서로 파고드는」 문제는 높이가 아니라 **간격**의 문제다 —
> 앞 건물의 뒷모서리와 뒤 건물의 앞모서리가 깊이로 2 칸을 넘게 떨어져야 지붕이 다 보인다.

### 30.10.4 문은 한 방향뿐이다

**네 방향을 그리지 않는다.** 카메라도 건물도 돌지 않기 때문이다.

보이는 벽은 둘(남서 · 남동)이고, **문은 남서쪽 벽** — 화면에서 왼쪽 아래를 보는 면에
그린다. 밑그림에 **파란 면**으로 칠해 두었다.

대원이 들어갈 때 서는 칸(`HideoutBuilding.entrance_cell`)이 정확히 그 벽 바로 바깥이다.
그림과 규칙이 같은 곳을 가리키는지는 테스트가 지킨다.

> 건물을 돌릴 수 있게 되면 이 절이 깨진다. 그때는 남동쪽 벽 그림이 한 장 더 필요하다.
> **지금은 돌리는 기능이 없고, 넣을 계획도 없다.**

### 30.10.5 그림 한 장이 오면 이렇게 놓인다

```
그림 (208 x 208, 2층 공방)
  기준점 (104, 200) 이 바닥 마름모의 아래꼭짓점
        |
        v
HideoutBuilding(id, WORKSHOP, 2x2, origin, storeys = 2)
        |
        v
화면: IsoProjection.rect_polygon(origin, 2x2) 의 **아래꼭짓점**에 기준점을 맞춰 찍는다
      그리는 차례는 HideoutGrid.buildings_by_depth() 가 준다
```

**바꿀 것은 `HideoutBuildingView` 한 파일뿐이다.** 지금 도형 셋(지붕 · 벽 둘)을 그리는
자리에 `draw_texture` 한 줄이 들어간다. 격자도 배치도 가림도 안 바뀐다 —
전부 칸으로만 계산하기 때문이다 (§30.2).

### 30.10.6 아직 안 정한 것

| | 왜 |
| --- | --- |
| 지붕 위 장식 · 간판 | 캔버스에 들어가야 한다 (§30.10.7 — 굴뚝이 상한을 먹는다) |
| 밤/낮 · 불 켜진 창 | 조명 레인(§26)과 겹친다 |
| 짓는 중 그림 | 자원(★7)이 붙은 뒤 |

### 30.10.7 ★ 자르는 기준 — 받는 쪽이 정했다

생성기는 잠재공간이 64 배수를 받아 208x144 같은 크기로 못 뽑는다.
**큰 정사각으로 뽑아 이쪽에서 자른다.** 그 기준을 여기서 정한다.

```bash
python tools/fit_hideout_building_art.py <원본.png> --facility workshop --storeys 2
```

| 축 | 무엇에 맞추나 | 왜 |
| --- | --- | --- |
| **세로** | **알파의 맨 아래 -> 기준점**(바닥 마름모 아래꼭짓점) | 굴뚝 · 깃발 · 간판이 위로 자라도 **접지가 안 움직여야** 한다. 기준점을 밑변으로 잡은 이유와 같다 (§30.10.2) |
| **가로** | 알파 경계상자의 가운데 -> **캔버스 가운데** | 바닥 마름모의 **중심은 발자국이 무엇이든 캔버스 한가운데**다. 기준점과 달리 2x3 · 3x2 에서도 가운데다 |
| **배율** | 알파 경계상자의 **가로**가 바닥 마름모 가로와 같아지게 | 세로는 **못 믿는다** — 첨탑 하나에 통째로 흔들린다. 가로로 삐져나오면 **옆 칸을 침범**하고, 그것이 실제로 곤란한 실패다 |

> **경계상자의 위쪽은 안 본다.** 이것이 이 규칙의 전부다.
> 알파 경계상자만으로 맞추면 굴뚝 있는 건물과 없는 건물의 **접지가 서로 다른 데 앉는다.**

#### 캔버스가 곧 계약이다

**넘치면 자동으로 줄이지 않고 실패로 알린다.** 조용히 맞춰 두면 2층 상한(§30.10.3)이
그림에서만 깨진 채로 굴러간다.

굴뚝을 얹고 싶으면 **몸통을 그만큼 낮춘다.** 지붕 위 장식은 공짜가 아니다 —
그것도 뒤 칸을 가리기 때문이다. 시험 그림에서 굴뚝 70px 가 그대로 초과로 잡혔다.

넘친 그림은 **넘친 자리에서 자른다.** 0 으로 당겨 붙이면 접지가 조용히 어긋나고,
그러면 「맞지 않는다」가 「조금 이상하다」로 바뀌어 아무도 안 고친다.

#### 손보정은 규칙에 숨기지 않는다

자동 규칙이 어떤 그림에서도 맞을 리 없다.
`docs/design/samples/hideout_art/fit_overrides.json` 에 **파일별로** 적는다.

```json
{ "workshop_2l.png": { "dx": 0, "dy": -3, "scale": 1.02 } }
```

#### 검증

1024 정사각에 **배율도 위치도 제각각으로** 그린 시험 그림 둘(2x2 2층 · 3x2 1층)을 넣어
맞춘 뒤, 밑그림 위에 겹쳐 바닥 마름모와 기준점이 일치하는지 봤다. **일치했다** —
발자국이 정사각형이 아닌 3x2(기준점이 가운데가 아닌 것)도 맞았다.

도구가 같이 내는 것: 배율 · 놓인 자리 · 캔버스 초과 여부 · **가장자리 잉크 비율**
(0 이 아니면 배경 키잉이 실패했거나 잘려 나간 것이 있다).

## 30.11 노이즈 축에 대한 답 (UI 킷 §20.45.6)

세 물음에 답한다. **셋 다 실제 거점 화면 위에 얹어 보고 답했다.**

### 30.11.1 알갱이 장은 **UI 판 뒤에만** 깐다

**장면 위에는 깔지 않는다.** 지금은.

근거는 아직 없는 것에 있다 — **거점에서 읽어야 하는 것은 바닥이 아니라 배회하는 대원**인데
그 대원이 아직 없다. 없는 것을 놓고 「옅게 깔아도 읽힌다」를 정하면,
사람이 선 뒤에 뒤집힌다. LANE-RULES §1 — **이 판이 게임에 나오는가부터 묻는다.**

> **조건부로 열어 둔다.** 배회(①)가 서면 다시 잰다. 잴 기준도 정해 뒀다 —
> **대원 한 명을 집을 수 있는가**다. 대원은 화면에서 대략 한 칸(64 px) 크기이고,
> 그보다 작은 것에 알갱이를 걸면 실루엣이 먼저 무너진다.

### 30.11.2 배회하는 대원에게는 **걸지 않는다**

셋 다 같은 방향을 가리킨다.

1. **대원이 곧 클릭 대상이다.** ⑤(클릭 -> 줌 -> 말풍선)가 대원을 집는 것에서 시작한다
2. **킷이 스스로 적었다** — 「우리는 안 움직이는 것에서만 쟀다」. 배회는 계속 움직인다
3. 대원은 64 px 남짓이다. 작고 움직이는 것에 잡음을 걸면 **읽기가 가장 크게 깎이는 조합**이다

#### 대신 — 노이즈를 걸 자리가 이미 있다

노이즈 축이 **「아직 확실하지 않다」**를 뜻한다면, 거점에는 그 뜻이 정확히 맞는 자료가 있다.

| 자리 | 지금 상태 | 노이즈가 뜻할 것 |
| --- | --- | --- |
| **게이트 정보 공개 수준** | `GateDisclosure` 가 소문 · 정찰 · 해부 **세 칸으로 이미 있다** (§22.5) | 소문 0.42 · 정찰 0.18 · 해부 0.00 |
| 영입 후보 | 이름만 뜨고 영입은 미구현 (§22.7) | 아직 사람이 아니다 |

**세 칸짜리 사다리가 이미 코어에 있다.** 노이즈 사다리와 자리 수가 같고 뜻도 같다 —
정보실에 사람을 넣으면 흐릿하던 게이트가 또렷해지는 것이 **글자가 아니라 잡음으로** 보인다.
움직이지 않는 것이고, 클릭 대상이 아니라 **읽을 것**이라 킷이 잰 조건과도 맞는다.

**이쪽이 대원에게 거는 것보다 세다.** ⑥(메뉴 · 출정)이 킷을 쓸 때 같이 붙인다.

### 30.11.3 띠 격자는 **가로 한 벌이 맞다** — 재 봤다

**사선 구도와 싸울까 봐 걱정한 것과 결론이 반대다.**

거점 캡처 위에 띠를 얹어 넷을 견줬다(원본 · 가로 0도 · 마름모 모서리와 나란한 18.43도 · 가로 옅게).

| 띠 방향 | 결과 |
| --- | --- |
| **가로 0도** | **좋다.** 바닥 격자가 그대로 읽히고 건물 면도 안 무너진다 |
| **18.43도 (마름모 모서리와 나란히)** | **나쁘다.** 바닥 격자선과 **같은 방향이라 섞여 버린다** — 칸 경계가 띠에 먹힌다 |

**위험한 것은 구도가 아니라 바닥 격자선이었다.** 쿼터뷰 3:1 의 칸 모서리는 정확히
**±18.43도**(`atan(16/48)`)로 눕는다. 띠를 거기 맞추면 격자와 겹쳐 서로를 지운다.

**가로 0도는 ±18.43도 둘 모두에서 가장 먼 각이다.** 그래서 우연이 아니라 **가장 안전한 각**이다.
바꾸지 마라.

> 다만 이것은 킷의 셰이더가 아니라 **같은 주기의 띠로 흉내 낸 것**이다.
> `grain_field.gdshader` 를 실제로 얹으면 한 번 더 봐야 한다 — 각도 결론은 안 바뀔 것이다.

## 30.12 ① 배회 — 선다. 그리고 **사람이 서자마자 3:1 이 흔들렸다**

`HideoutCrowd` 하나가 전부다. `src/core/hideout/` 에서 **시간을 아는 유일한 파일**이고,
★5 의 조건(시계가 붙어도 배회만 고치면 된다)을 그 한 줄로 지킨다.

### 30.12.1 경계 셋 중 **하나만** 썼다

§30.3.1 의 셋 중 `can_stand` 만 부른다. `direction_at`(흐름장)도 `free_run` 도 안 부른다.

**거점에는 뚫어야 할 좁은 목이 없기 때문이다.** 배회 계약 3번(§30.3.2)이
「막히면 그 자리에 선다」이고, 그러면 길찾기가 필요 없다 — **막히면 목적지를 다시 고른다.**
그것이 위층의 일이고 `HideoutCrowd` 가 위층이다.

겹침도 힘으로 안 푼다. **밀치기를 만드는 대신 목적지를 안 겹치게 골랐다**
(`_GOAL_CLEARANCE`). 인원이 여섯이고 빈 칸이 180 개인 판에서는 이것으로 충분하다.

> **이동 레인의 위층(`unit_field`·`push`·`yield`·`jam`)을 안 가져온 판단이 여기서 값을 했다.**
> 100명·좁은 문에서 29초가 걸리는 기계를, 여섯 명이 벌판을 걷는 데 쓸 뻔했다.

### 30.12.2 ★ 사람을 세워 보니 3:1 의 값이 안 맞는다

창에 띄워 보고 바로 드러났다 — **1층 건물이 사람과 키가 비슷하다.**
건물이 「사람 한 명 높이」로 보이면 그것은 건물이 아니라 담이다.

칸 한 변을 2 m 로 보면 사람(1.7 m)은 0.85 칸, 한 층(3 m)은 1.5 칸이다. 그걸 넣고 재면:

| | 한 칸 높이 | 사람 | 한 층 | **1층이 가리는 칸** | **2층이 가리는 칸** |
| --- | --- | --- | --- | --- | --- |
| **3:1 (지금)** | 64.0 px | 54 px | 96 px | **3 칸** | **6 칸 — 판의 43%** |
| **2:1** | 58.8 px | 50 px | 88 px | **1 칸** | **3 칸 — 판의 21%** |

> **3:1 에서는 「제대로 된 층 높이」와 「2층」을 동시에 가질 수 없다.**
> 2층이 판의 43% 를 가린다. 지금 층 높이를 64 px 로 둔 것은 사람 키에서 나온 값이 아니라
> **격자에서 딱 떨어져서** 고른 값이었고(§30.10.1), 사람이 서니 그 대가가 보였다.

**2:1 로 가면 가림이 정확히 절반이 된다.** 같은 층 높이에 6 칸이 3 칸이 된다.

### 30.12.3 ★ 그래서 3:1 판단을 되짚는다 — 내 근거가 생각보다 약했다

§30.2.1 에서 3:1 을 고른 근거는 **인물 그림(`pp1_*`)의 접지 그림자와 장화 윗면**이었다.
그런데 그 그림들은 **전신 인물 시트**다 — 캐릭터 시트는 게임 카메라와 무관하게
정면으로 그리는 것이 보통이다. **게임 카메라의 각도를 가리키는 증거가 아닐 수 있다.**

레이맨 파츠(near/far)는 실제 게임 스프라이트 쪽이지만, 거기서 읽은 것은
**서 있는 자세의 좌우 벌림**이지 카메라 피치가 아니었다. 그것도 약하다.

지금 모인 것을 나란히 놓으면:

| | 3:1 (폐기) | **2:1 (채택 · 코드 반영)** |
| --- | --- | --- |
| 건물 그림 각도 | 안 맞음 | **dimetric 2:1, 26.57°** |
| 인물 시트의 접지 | 맞아 보였음 | 시트는 카메라 증거가 약했음 (§30.12.3 위) |
| 2층 가림 | 판의 43% | **약 21%** |
| 한 칸 세로 높이 | 64.0 px (딱 떨어짐) | ≈ 58.8 px |
| 전환 비용 | — | `DEFAULT_TILE_HEIGHT` 32→48 + dump/밑그림 재생성 |

**적용:** `IsoProjection.DEFAULT_TILE_HEIGHT = 48`. 격자·배치·배회는 칸 단위라 로직 변경 없음.
발주서·JSON 은 dump 로 다시 뽑는다 (§30.10).

> **확정.** 사람 키가 선 뒤의 가림 수치가 결정타였다. 인물 시트 각도는 기각.
> 게임용 인물 스프라이트도 2:1 에 맞춘다 (아직 없으면 잃을 것 없음).

### 30.12.4 아직 잠정인 것

| | 값 | 왜 잠정인가 |
| --- | --- | --- |
| 대원 키 | 54 px | 칸을 2 m 로 본 값이다. 격자 비율이 갈리면 같이 갈린다 |
| 걷는 빠르기 | 1.6 칸/초 | 실제 걸음(0.7 칸/초)은 화면에서 배회로 안 읽혔다. **연출이라 눈에 맞췄다** |
| 인원 | 6 | 스쿼드 정원은 3~4(§22.3)지만 아지트에는 남는 대원과 영입 후보가 있다 |
| 판 크기 14x14 | 그대로 둔다 | 여섯 명이 180 칸에서 **성기게** 보인다. 인원이 정해지면 같이 정한다 |

### 30.12.5 알갱이 장을 다시 잴 조건이 갖춰졌다

§30.11.1 에서 「대원이 아직 없어 못 정한다」고 미뤘던 것 — **이제 대원이 선다.**
잴 기준도 그때 적어 뒀다: **대원 한 명을 집을 수 있는가.**
대원은 화면에서 54 px 이고 몸통은 17 px 이다. UI 킷이 알갱이 장을 주면 그 위에 얹어 잰다.

## 30.13 ★10 건물 정합 — **그리드 + fit** (충돌식 · 「스티커」 폐기)

> **오해 정리 (2026-08-10):** 대화 중 「스티커」는 **그리드를 버리고 충돌로 자유 배치할 때**
> 의 비유였다. **그리드 + fit 경로의 아트 모드 이름이 아니다.**
> fit 으로 캔버스·기준점·가로에 맞춘 뒤에는 스티커 모드 같은 별칭이 필요 없다.
> 문서에 `art_mode: sticker` 를 넣었던 것은 **잘못**이었고 제거했다.

### 30.13.1 채택 / 폐기

| | |
| --- | --- |
| **채택** | **칸 그리드** (`HideoutGrid`) + **fit** (§30.10.7) → 규격 캔버스에 건물 그림 |
| **폐기** | 그리드 포기 후 **충돌 박스 자유 배치** (「스티커 붙이기」) |
| **보류** | 생성 각도가 어긋날 때 fit 에 호모그래피/전단을 더할지 — 필요하면 별도 허가 |

규칙은 칸이 진실이고, 그림은 **그 칸 발주서에 fit 된 텍스처**다.

### 30.13.2 생성 파이프라인

```
1) 사람: 이미지 생성 (GPT Image 등) — 프롬프트 §30.13.4
2) 원본 보관: docs/design/samples/hideout_art/in/
3) fit: python tools/fit_hideout_building_art.py <원본> --facility workshop --storeys 1
   → 그리드 발주 캔버스(workshop_1l 등)에 맞춤
4) 화면: hideout UI 가 fit 된 PNG 를 기준점에 그림
5) 검증: capture_hideout + GUT
```

**fit 이 맞추는 것 (§30.10.7):**

1. 세로 — 알파 맨 아래 → 기준점(바닥 마름모 아래꼭짓점)
2. 가로 — 알파 bbox 가운데 → 캔버스 가운데
3. 배율 — 알파 가로 ≈ 바닥 마름모 가로 (그리드 접지 폭)
4. 손보정 — `fit_overrides.json` (`dx` / `dy` / `scale`)

### 30.13.3 생성 프롬프트 — 공방 1층 (첫 장)

**목표 규격 (코드 dump):** 발자국 2×2 · 바닥 마름모 192×96 (2:1) · 캔버스 208×200 · 기준점 (104, 192).

생성 해상도 **1024×1024** 권장. 모델은 footprint 숫자를 못 지키므로 **비율·구도**로 말하고,
**fit 이 그리드 규격에 맞춘다.**

**Positive**

```
Single small guild workshop building prop for a 2D isometric game, isolated object only,
no ground plane texture, no grid lines, no UI, no characters, no text, no watermark.

Camera: true dimetric 2:1 isometric (side angles ~26.6°), looking down ~30 degrees,
same as classic SNES/iso city builders. NOT top-down, NOT side-view, NOT random 3/4 RPG tilt.

Footprint / massing (so the asset can be fit onto a 2:1 diamond tile footprint):
- The building sits on a diamond ground footprint whose width:height ratio is exactly 2:1
- Footprint covers about 2×2 map tiles (compact, not a skyscraper)
- Full subject bounding box including roof is roughly square (~1:1 width:height),
  about as tall as it is wide — one storey only, low roof, no tower, no tall chimney
- Building width on screen should feel ~2 tiles wide

Building: small urban hunter-guild workshop / garage-forge hybrid in a modern gate-fantasy city,
concrete and sheet metal, roll-up door on the southwest face (lower-left visible wall),
windows on the southeast face (lower-right wall), small roof equipment, humble not monumental.

Style: 1990s anime cel, high chroma, one small complementary accent area,
hard specular highlights, clean readable silhouette, game building prop,
flat solid color background (pure white or pure #00FF00 chroma key), full body of building visible with margin.

Composition: centered, entire building in frame, generous empty margin around silhouette,
ground contact is a clean bottom tip of the diamond (no floating), no drop shadow needed.
```

**Negative**

```
perspective vanishing points, 3-point perspective, top-down orthographic, side scroller view,
ultra tall building, multi-storey tower, skyscraper, huge chimney, characters, people, cars,
street, full city block, terrain, grass, asphalt ground plane filling the image,
text, logo, watermark, frame, UI, multiple buildings, collage, cropped roof, cropped base
```

정보실(2×3)·접선처(3×2)·2층은 같은 틀에서 발자국·층수만 바꾸고, 전체 bbox 비는
§30.10.1 표의 캔버스 비를 따른다.
