# 19. 렉카 문체 — 기사를 누가 쓰는가

> ## 이 문서는 §19.A 부터 읽어라
>
> **5차 이후 15차까지 이어진 탐색에서 형식 자체가 바뀌었다.**
> 아래 §19.0 ~ §19.11 은 5차 시점의 기록이고, **결론은 §19.A 가 대체한다.**
> 등급 체계와 사실 잠금 원칙은 살아 있으나, **출력 형식과 프롬프트는 전면 교체됐다.**

---

## 19.A 최종 결론 (15차) — SNS 게시글과 댓글

> **상태: 확정. `gpt-5.6-luna` 실제 호출로 검증.**
> 5차의 "제목 한 줄 + 본문 두 문장" 은 폐기됐다.

### 19.A.1 왜 바꿨는가

5차 결과에 대한 의뢰인 평가는 **"어색하다"** 였고, 원인은 셋이었다.

| 원인 | 실측 |
| --- | --- |
| 22편이 전부 같은 틀 (반말 사실 + 존댓말 훅) | 서로 다른 형태 짝 **2개**, 본문 형태 **1가지** |
| 화자가 렉카가 아니라 뉴스 앵커 | 완결된 문장만, 파편 없음 |
| 길이 제한이 어투를 죽임 | 제목 40자 / 본문 2문장이 틀을 고정 |

중간에 **라이브 중계**로 흘렀다가 다시 되돌렸다. 의뢰인 지적 —
**"나는 SNS 에 브리핑하는 느낌을 원한다. 그래야 유저가 보고 판단하지."**
시간순으로 주절거리는 실황 대본은 훑어보기가 안 된다.
계획 페이즈에서 플레이어는 **읽고 판단해야** 한다.

### 19.A.2 측정으로 확정된 다섯 가지

**전부 실제 호출로 재서 얻었다. 추정이 아니다.**

| # | 발견 | 근거 |
| --- | --- | --- |
| 1 | **프롬프트가 길수록 합니다체와 지어내기가 는다** | 188자 → 합니다체 8회 / 330자 → **26회**. 긴 쪽은 없는 계단·통로·카메라 노이즈까지 지어냈다 |
| 2 | **"짧게 끊어 난사" 는 명사형 종결을 부른다** | "회랑에서 바로 제압. 미나 완전 쓰러짐." 은 말이 아니라 메모다. 그 구절을 빼자 네 변형 모두 명사형 종결 **0** |
| 3 | **프롬프트를 쓴 문체가 결과에 옮는다** | 반듯한 문어체로 정리했더니 산출물이 앵커 말투로 회귀 |
| 4 | **글자·괄호·숫자 제거는 프롬프트가 아니라 후처리가 한다** | 프롬프트에 안 적으니 모델이 몸을 덜 사린다. 매 호출에서 실제로 걸러진다 |
| 5 | **분량은 프롬프트가 아니라 재료에서 나온다** | 사건 한 줄만 주고 길게 쓰라니 되풀이로 채웠다(395자 중 절반이 군더더기). **판 문맥을 주자 같은 길이에서 내용이 완전히 달라졌다** |

**5번이 이 탐색에서 가장 중요한 발견이다.**

### 19.A.3 기사는 판 상태를 가십으로 배달하는 장치다

사건 한 줄만 넘기면 할 말이 없다. 그래서 짧거나, 늘리면 되풀이하거나, 놓아주면 지어낸다.
**판이 이미 아는 것을 함께 넘기면 셋 다 사라진다.**

> `[속보]` 지난 판에 헤어진 사이였던 요한, 대박 먹은 미나를 회랑에서 그대로 눕힘 ㅋㅋ
>
> 두더지 미나는 쓰러졌고, **여긴 출구 가는 길목이라** 그냥 지나갈 수도 없음.
> 미나는 **두 턴 전 수장고에서 대박 건졌는데** 요한은 이번 판 아직 빈손임.
> **지난 판엔 협상하고 헤어진 사이라** 더 웃기노 ㅋㅋ
> 근데 **바로 옆방에 웃는 베른 있음.** 지금 지나가면 셋이 마주칠 각이다.

굵은 부분이 전부 **판단에 쓰이는 정보**다. 기사가 분위기가 아니라 **첩보**가 된다.
§13.5 의 "숫자의 절대값은 위험을, 변화량은 사람을 알려 준다" 와 같은 층위에서,
**기사는 판의 맥락을 알려 준다.**

**따라서 `RekkaPrompt` 는 사건뿐 아니라 판 문맥에 접근해야 한다** —
방의 역할(길목·막다른 방·출구 거리), 인물별 수확 이력, 관계도, 인접 상황.
이것은 아직 구현되지 않았다 (§19.A.7).

### 19.A.4 시스템 프롬프트 전문

**의뢰인이 직접 작성했고, 15차 검증을 통과한 것이다.**

```
너는 던전에서 벌어진 일을 SNS에 공개하는 사이코패스 악질 분탕충이야.

디시 펨코같은 커뮤니티 말투로 작성해.

제목은 한 줄로 어그로 끌듯이 작성하고 본문은 대여섯 줄, 그 밑에 댓글 몇 개.

댓글은 너보다 막 나가고 헛소리도 해.

준 사건 밖의 일을 네 입으로 확정하지 마. 댓글이 지어내는 건 놔둬.

댓글은 줄 앞에 대괄호로 닉네임을 적어
```

실측: 게시글 본문 **평균 207자**, **합니다체 0회**, 사실 오염 없음.

**짧다는 것이 이 프롬프트의 미덕이다.** 줄을 더할 때마다 나빠진다(발견 1).
고치고 싶으면 더하지 말고 **바꿔라.**

### 19.A.5 입력 형식

```
이번 턴 사건
- 회랑에서 <칼날의 요한>이 <두더지 미나>를 제압했다. <두더지 미나>는 쓰러졌다.
판이 이미 아는 것
- 회랑은 출구로 가는 길목이라 지나갈 수밖에 없는 방이다
- <두더지 미나>는 두 턴 전 수장고에서 대박을 건졌다
- <칼날의 요한>은 이번 판 들어 아직 아무것도 못 건졌다
- <칼날의 요한>과 <두더지 미나>는 지난 판에서 협상하고 헤어진 사이다
- 지금 회랑 옆방에 <웃는 베른>이 있다
```

**두 칸으로 나눈다.** 이번 턴에 벌어진 것과, 게임이 이미 들고 있는 상태.
후자는 전부 실제 값이어야 한다. 지어낸 설정을 넣으면 그 순간 기사가 거짓말이 된다.

**이름은 홑화살괄호로 감싼다.** 감싸지 않으면 이름을 서술로 읽는다.
`웃는 베른` → "베른이 웃고 있었습니다" 사고가 실제로 났다.
괄호는 **입력 전용**이고 출력에서는 후처리가 지운다.

### 19.A.6 후처리 — 프롬프트에서 뺀 것을 코드가 보장한다

| 처리 | 이유 |
| --- | --- |
| 홑화살괄호 제거 | 입력 표시가 새어 나온다 |
| 한글·영문·숫자·허용 문장부호 외 전부 제거 | 매 호출에서 `*` `…` `“ ”` 가 걸린다. **구자라트 문자가 나온 적도 있다** |
| 숫자 검출 | 등급으로만 말하기로 했으므로 남아 있으면 사고다 |

**알려진 결함**: 현재 숫자 필터가 `전리품 0개` 의 `0` 까지 지운다.
개수로서의 0 은 정보이므로 걸러내면 안 된다. 필터를 정교화해야 한다.

> **닫혔다.** 막는 것은 **수치화된 규모**(피해량 · 전리품 값어치 · 인원)뿐이고
> 순서 · 횟수 · 등수 · 개수 · 한글 수사는 남긴다. 규칙과 실측은 §19.B.3 에 있다.

## 19.B 구현 (16차) — 코드가 무엇을 보장하는가

> **상태: 구현 완료. `gpt-5.6-luna` 24편 실호출로 검증.**
> §19.A 는 "이렇게 하기로 했다" 이고 §19.B 는 "이렇게 만들었다" 이다.
> 형식과 프롬프트는 §19.A 그대로다. 바꾼 것이 없다.

### 19.B.0 파일과 경계

| 파일 | 맡은 것 |
| --- | --- |
| `src/core/rekka/rekka_prompt.gd` | 무엇이 사실인가. 시스템 프롬프트 전문과 입력 직렬화 |
| `src/core/rekka/rekka_context.gd` | **판이 이미 아는 것을 게임 상태에서 뽑는다** (§19.B.1) |
| `src/core/rekka/rekka_post.gd` | 모델이 뱉은 것에서 규칙 위반을 걷어낸다 (§19.B.3) |
| `src/core/rekka/rekka_handles.gd` | 제목 접두어와 댓글 닉네임 배정 (§19.B.4) |
| `src/core/rekka/korean_particle.gd` | 조사를 받침으로 고른다 (§19.B.5) |
| `tools/dump_rekka_prompts.gd` | 실제 판을 굴려 입력을 뽑는다 |
| `tools/clean_rekka_posts.gd` | 산출에 `RekkaPost.clean()` 을 걸어 표본을 만든다 |

**표본은 손으로 만들지 않는다.** 5차 표본의 "판이 이미 아는 것" 은 손으로 적은 것이었고,
그래서 수집기가 실제로 그런 줄을 뽑는지는 검증되지 않았다.
지금 표본의 모든 입력은 `DungeonGraph` · `EventLog` 를 읽어 만든 것이고,
모든 출력은 `RekkaPost.clean()` 을 그대로 통과한 것이다. **사람이 손댄 곳은 없다.**

### 19.B.1 판 문맥 수집기 — 무엇을 어디서 뽑는가

`RekkaContext.for_turn(run, events)` 가 최대 여섯 줄을 만든다.
잘려 나가는 것은 언제나 뒤쪽이므로 **순서가 곧 우선순위**다.

| # | 줄 | 출처 | 예 |
| --- | --- | --- | --- |
| 1 | 방의 상태 (종류 + 수색 여부) | `Room.kind` + `EventLog` 의 `SEARCHED` | `<밀실>은 귀중품이 있는 방인데 이번 판 들어 아직 아무도 손대지 않았다` |
| 2 | 인접 상황 | 이웃 방의 `Room.occupants()` 중 `Actor.is_mobile()` | `지금 <회랑> 옆방에 <웃는 베른>이 있다` |
| 3 | 인물 수확 이력 | `EventLog` 의 `ACQUIRED` **합** + 턴 차 | `<두더지 미나>는 두 턴 전 <수장고>에서 대박을 챙겼다` |
| 4 | 관계 이력 | `EventLog` 에서 **이번 판 안의** 협상·전투·조우·도주 | `<A>와 <B>는 한 턴 전 거래를 맺고 헤어진 사이다` |
| 5 | 방의 위상 | `DungeonGraph` 위상 + `Room.elevation` | `<회랑>은 <탈출 승강기>로 가는 길목이라 지나갈 수밖에 없는 방이다` |

#### 순서는 "화면에서 못 얻는 것이 먼저" 로 정했다

처음에는 방의 위상을 맨 앞에 뒀다가 심사에서 뒤집혔다 (§19.B.9 1차).

| 층 | 화면에서 얻을 수 있는가 |
| --- | --- |
| 방의 종류 · 수색 상태 | **못 얻는다.** 인접 위험도 합은 방에 무엇이 있는지 말해 주지 않는다 |
| 옆방에 누가 있는가 | **못 얻는다.** 합이 올랐다는 것까지만 보인다 (§7.2.5) |
| 인물별 수확 이력 | **못 얻는다.** 남의 가방은 화면에 없다 |
| 방의 위상 | **모른다.** [`07`](07-level-design.md) §7.2.4 의 "보이는 범위" 가 **미정**이다 |

판이 통째로 보이는 화면이면 갈래 수와 출구 거리는 플레이어가 이미 세고 있는 것이고,
그것을 기사로 다시 읽어 주면 **정보원이 아니라 나레이션**이 된다.
**미정인 것에 앞자리를 주지 않는다.**
`보이는 범위` 가 "인접 방만" 으로 정해지면 위상을 앞으로 올려야 한다.

같은 이유로 **갈래 수와 출구 거리 줄은 아예 없앴다.** 남긴 셋은 전부 계산이 필요한 것이라
화면에 그대로 나와 있지 않다.

| 판정 | 근거 | 왜 이 순서인가 |
| --- | --- | --- |
| 오를 수 없는 방 | `required_agility_from(지금 자리)` > 스쿼드 민첩 | 못 가는 방은 경로에서 통째로 빠진다 |
| 길목 | `d(지금,방) + d(방,출구) == d(지금,출구)` | 지나갈 수밖에 없다는 것은 경로를 정한다 |
| 막다른 방 | 이웃 수 1 | 들어가면 되돌아 나와야 한다 |

길목 판정에 **민첩을 넣지 않는다.** 넣으면 "누구 기준의 길목인가" 가 생기고
NPC 마다 민첩이 다르므로 답이 갈린다. 위상만으로 판정한다.

#### 조용한 턴에는 부재를 넘긴다

사건이 없으면 방도 인물도 없어서 위 여섯 줄이 **한 줄도 안 나온다.**
그런데 조용한 턴이야말로 문맥이 제일 필요한 턴이다 — 실측에서 사건 없는 두 편이
"아무 일도 없었다" 를 여섯 줄로 늘려 쓴 거의 같은 글이었다.

그래서 `_quiet_facts()` 가 **부재가 알려 주는 사실**을 대신 넘긴다.

```
- 던전에 아직 <웃는 베른>과 <두더지 미나>가 남아 있다
- <봉인된 금고>와 <밀실 2>는 이번 판 들어 아무도 손대지 않았다
```

#### 수확 등급은 판 전체의 합으로 낸다

제일 큰 한 건만 보고 매겼더니 나갈 때 합으로 계산된 등급과 어긋나,
같은 사람의 수확이 `한몫` 에서 `대박` 으로 **승격**됐다 (§19.B.9 1차).
값어치 등급은 플레이어가 "저 방에 아직 뭐가 남았나" 를 재는 축이라
소급 변경되면 축 자체가 못 쓰게 된다.

여러 번 챙겼으면 **방 이름을 대지 않는다.** 등급은 합이고 방은 그중 한 곳이라
둘을 한 문장에 붙이면 `계단참에서 대박` 처럼 그 방에서 다 나온 것처럼 읽힌다.

세 턴이 넘은 수확은 **언제였는지도 말하지 않는다.** 말하면
`두 턴 전` 부터 `일곱 턴 전` 까지 숫자만 하나씩 오르는 같은 줄이 판 끝까지 이어진다.

#### 수색 상태는 시제를 지킨다

이번 턴에 실제로 수색이 일어났을 때만 `이번 판 들어 N번째로 수색된 방이다` 를 쓴다.
아니면 `이번 판에 이미 수색이 끝난 방이다` 다.

지키지 않았더니 **같은 방이 세 턴 간격으로 두 번 처녀지가 됐다.**
그 글을 믿고 달려간 플레이어는 빈 방을 만나고,
**정보원의 신뢰는 한 번 깨지면 그 판의 기사 전부가 무가치해진다.**

#### 몬스터는 인접 상황에 넣지 않는다 — 임의 판단

`Actor.is_mobile()` 로 걸러 NPC 탐험가와 플레이어 스쿼드만 이름을 부른다.

이 게임의 핵심은 **인접 위험도 합만 보이고 그 구성은 안 보이는 모호함**이다
([`07`](07-level-design.md) §7.2, [`13`](13-information-design.md) §13.6).
옆방 몬스터를 이름으로 불러 주면 그 모호함이 통째로 무너진다 —
`옆방에 심부의 파수꾼이 있다` 한 줄이면 합 6 이 보스 하나임이 확정된다.
몬스터는 제자리를 지키므로 이미 숫자로 전달되고 있고, 움직이는 것만이 새 정보다.

**이것은 이 레인이 임의로 내린 판단이다.** 뒤집으려면 §13.6 부터 다시 봐야 한다.

### 19.B.2 아직 없어서 못 넣은 것

**지어낸 설정을 한 줄이라도 넣으면 그 순간 게시글이 거짓말이 된다.**
아래는 §19.A.3 이 넘기라고 적었지만 게임이 아직 들고 있지 않은 것들이다.

| 넘기고 싶었던 것 | 왜 못 넣었나 |
| --- | --- |
| **지난 판의 관계** | **판 사이를 잇는 상태가 없다.** `DungeonRun` 은 한 판이고 그것으로 끝이다. 메타 진행([`06`](06-progression.md))이 붙어야 생긴다. 지금은 **이번 판 안의 관계만** 넘긴다 |
| **주목도** | [`13`](13-information-design.md) §13.4 의 수치가 미구현이다. "누가 유명한가" 를 못 넘긴다 |
| 인물의 이동량 | 뽑을 수는 있으나(`MOVED` 수) 여섯 줄 예산에서 밀렸다. 방의 역할이 같은 자리를 더 잘 쓴다 |
| 몬스터가 죽었는가 | `DOWNED` 는 기록되지만 배치에서 빼는 코드가 판 쪽에 아직 없다 |
| `actor_kind` | `GameEvent` 에 주체의 종류가 없다(§19.9.3). 그래서 사건만 보고는 몬스터인지 탐험가인지 모른다. 지금은 `DungeonGraph` 에서 다시 찾아본다 |

### 19.B.3 숫자 규칙 — 다시 짰다

앞선 필터는 숫자를 보이는 대로 지웠고, 그래서
`전투 기록 0회` `수확량 0` `수확 1등` `세 번째` 의 숫자까지 사라졌다.
**그 숫자들은 정보다.** 허탕도 정보이고(§19.3.3 빈손), 등수와 횟수는 판을 읽는 재료다.

막아야 하는 것은 **수치화된 규모** — 피해량과 전리품 값어치와 인원수 — 뿐이다.

| 걸린다 | 어떻게 되는가 |
| --- | --- |
| `3명` `2마리` | `여럿` (하나면 `하나`) |
| `12 피해` `500골드` `8 값어치` | `얼마어치` |

| 남는다 | 왜 |
| --- | --- |
| `0회` `1등` `세 번째` `전리품 0개` | 순서 · 횟수 · 등수 · 개수는 규모가 아니다 |
| `50%` | 비율은 계량 감각을 만들지 않는다 |
| `중정 3` | 생성기가 붙인 방 번호다. 지우면 어느 방인지 모른다 |
| 한글 수사 (`셋이 마주칠 각`) | 세는 말이 아니라 말투다. 검증된 표본에서 제일 좋았던 표현이다 |

**지우지 않고 바꾼다.** 숫자만 지우면 `명 죽었다` 같은 부스러기가 남는다.
사람 수는 하나/여럿으로 접히므로 뜻이 보존되고, 값어치는 등급이 이미 본문에 있다.

#### 실측으로 잡은 오검출

`인` 을 인원 단위에 넣었더니 **`수확 0인데` 가 `수확 하나데` 로 망가졌다.**
지키려던 바로 그 숫자를 지우는 규칙이면 규칙이 틀린 것이다. `인` 을 뺐다.
`3인 파티` 가 새어 나가는 쪽이 훨씬 싸다 —
**못 잡은 것은 어색할 뿐이지만 잘못 잡은 것은 문장을 부순다.**

### 19.B.4 반복은 코드가 없앤다

한 편만 보면 안 보이고 스무 편째에 보이는 결함이라 **모델은 스스로 못 고친다.**
모델은 턴마다 새로 불려서 자기가 방금 뭘 썼는지 모른다.

| 결함 | 실측 | 어떻게 없앴나 |
| --- | --- | --- |
| `[속보]` 가 매번 붙는다 | 24편 중 **13편** | `RekkaHandles.TAGS` 12칸 중 **절반이 빈 칸**이다. 모델이 붙인 접두어는 버리고 배정된 것으로 갈아 끼운다 |
| 닉네임이 편끼리 겹친다 | 닉 139개 중 서로 다른 것 **113개** | `RekkaHandles.HANDLES` 36개를 판 전체에서 이어지는 번호로 배정한다. 한 편에 서넛이므로 아홉 편까지 안 겹친다 |
| 같은 밈이 반복된다 | 아래 대조표 | 직전 두 편의 **제목**을 `이미 써먹은 말` 로 입력에 되돌려 준다 |

#### 배정이 규칙적이면 그것이 새로운 틀이 된다

목록을 순서대로 소비했더니 심사자 둘이 **같은 표를 그려 왔다** (§19.B.9 1차) —
접두어는 짝수 편에만 붙고 여섯 종이 같은 순서로 돌았으며,
`낄낄이` 다음은 언제나 `지하실단골` 이라 다음 편 댓글자 명단을 미리 적을 수 있었다.

**반복을 없애려고 넣은 장치가 더 읽기 쉬운 반복을 만든 것이다.**

고친 것은 둘이다.

1. **서로소 걸음으로 건너뛴다.** `TAGS[(i * 5) % 12]`, `HANDLES[(i * 11) % 36]`.
   걸음이 목록 길이와 서로소이므로 **한 바퀴 안에 전부 한 번씩** 나오는 보장은 그대로다.
   겹치지 않는다는 성질은 지키면서 눈에 보이는 행진만 없앤다.
2. **빈 칸을 한 칸씩 띄워 놓지 않는다.** 띄워 놓으면 걸음과 무관하게
   "짝수 편에만 붙는다" 가 그대로 나온다.

`test_rekka_handles.gd` 가 셋 다 못 박는다 — 한 바퀴에 전부 나오는가,
홀수 편에도 접두어가 붙는가, 닉이 목록 순서대로 행진하지 않는가.

#### 밈 대조 — 같은 입력 24턴, 되돌려 주기만 다르게

| 표현 | 안 알려 줌 | **직전 제목 알려 줌** |
| --- | --- | --- |
| 학계 정설 | 5편 | **3편** |
| 실화냐 | 2편 | **0편** |
| 떴노 | 2편 | **0편** |
| 내가 봄 | 5편 | **2편** |
| 제목 대괄호 접두어 | 13편 | **8편** |
| 냄새 | 5편 | 7편 |

한 항목(냄새)이 늘었지만 나머지가 전부 줄었다. **되돌려 주는 쪽을 택했다.**
제목만 넘기는 이유는 그것이 5차에서 이미 검증된 `최근:` 칸과 같은 장치이고,
본문까지 넘기면 입력이 배로 길어져 발견 1(길수록 나빠진다)에 걸리기 때문이다.

**닉네임을 코드가 갈아 끼우는 것은 잃는 것이 있다.** 모델이 지은 닉은 그 편의 내용에
붙어 있다(`[웃음없는베른]`). 배정된 닉은 그렇지 않다. 겹치지 않는 것과 맥락에 붙는 것 중
겹치지 않는 쪽을 골랐다 — 겹침은 스무 편을 통째로 죽이지만 맥락은 한 편의 재미다.

### 19.B.5 중의어 — 직렬화에서 뺀 말

**`뒤졌다` 를 모델이 "죽었다" 로 읽었다.** 같은 결의 말을 함께 골라냈다.

| 안 쓴다 | 왜 | 대신 |
| --- | --- | --- |
| **뒤졌다** | **실측.** 수색과 죽음 | 수색했다 |
| 털렸다 | 도둑맞음과 완패 | 수색했다 / 챙겼다 |
| 눕혔다 · 접었다 | 죽음을 뜻한다. **쓰러짐은 영구 사망이 아니다**([`14`](14-squad.md) §14.6) | 제압했다 / 쓰러졌다 |
| 먹었다 | 획득과 피해 | 챙겼다 |
| 붙었다 | 전투와 합격과 부착 | 맞붙었다 |
| 날아갔다 · 쓸었다 | 죽음 · 싹쓸이 · 청소 | 쓰지 않는다 |
| 빠졌다 | 이탈과 함몰 | 빠져나갔다 |

이 목록은 `test_rekka_prompt.gd` 가 아홉 종류 전부에 대해 못 박는다.

#### 조사도 사실의 일부다

입력이 칸에서 문장으로 바뀌면서 조사가 필요해졌다.
`요한가 제압했다` 를 주면 모델이 어디까지가 이름인지 다시 추측한다.
방 이름과 인물 이름은 생성기가 만들어 내므로 목록으로 못 박을 수 없어서
`KoreanParticle` 이 **글자에서 계산한다.**

실제로 잡힌 것 — `<웃는 베른>와`, `규모는 한줌다`, `<중정 3>는`.
마지막 것은 생성기가 붙인 방 번호 때문이고, `중정 3` 은 "중정 삼" 으로 읽히므로 받침이 있다.
숫자 자리의 한자음 종성을 표로 들고 있다.

### 19.B.6 입력을 칸이 아니라 문장으로 넘긴다

5차는 `누가=... | 어디서=...` 였다. 문장으로 바꾼 이유는 **시스템 프롬프트가 짧아졌기 때문**이다.
칸 형식은 "이 칸은 이런 뜻이다" 를 설명하는 줄을 프롬프트에 요구하는데,
줄을 더하면 산출이 나빠진다(발견 1). 문장은 설명이 필요 없다.

같은 이유로 **`시점:` 과 `소속=` 칸을 없앴다.** 화자는 누구 편도 아니고,
게시글은 공개된 SNS 글이라 "우리" 라는 것이 없다.
플레이어는 자기 스쿼드 이름으로 자기 이야기를 찾는다.

**`결 배정`(§19.3.6)도 없앴다.** 5차에서 한 턴에 기사 세 편을 쓰던 구조의 장치였고,
지금은 한 턴에 게시글 하나라 배정할 짝이 없다. 그 자리를 접두어·닉 배정이 받는다 —
**보장되어야 하는 것은 규칙이 맡는다**는 원칙은 그대로다.

편수 계산(`article_count`)도 같은 이유로 사라졌다. 대신 `pick_events` 가 남았다 —
사건이 본문 대여섯 줄보다 많을 때 무엇을 실을지는 여전히 규칙이 정한다.

#### 고르는 것과 늘어놓는 것은 다른 일이다

`pick_events` 는 순위로 **고르고**, 고른 것을 다시 **일어난 순서로** 늘어놓는다.
순위대로 늘어놓았더니 `거래를 맺었다` 다음에 `그 방으로 옮겼다` 가 와서,
모델이 없는 이동을 지어냈다 — *"거래 끝나자마자 둘 다 계단참으로 이동함"* (§19.B.9 1차).

**시간 순서는 사실의 일부다.** 순위는 무엇을 실을지만 정한다.

### 19.B.7 실호출 조건

| 항목 | 값 |
| --- | --- |
| 모델 | `gpt-5.6-luna` |
| 호출 | Chat Completions, 턴별 1회 |
| `max_completion_tokens` | 1600 |
| 입력 | `tools/dump_rekka_prompts.gd`, 시드 20260808 / 771 / 31337 / 9042, 크기 5 |
| 표본 | 28편 (판마다 7턴) |
| 사람이 손댄 곳 | **없음** |

**판은 스쿼드가 던전을 나가면 끝난다.** 그 뒤의 턴에는 계획 페이즈가 없고,
계획 페이즈가 없는 턴의 기사는 아무리 잘 써도 플레이어가 쓸 데가 없다 (§19.B.9 2차).

그래서 한 판이 예닐곱 턴이고, 시드를 넷 쓴다.
표본은 **이어서 읽었을 때 기계 같은지**를 보는 것이므로 스무 편은 있어야 하고,
판이 갈리면 방 이름과 지형이 통째로 바뀌어서 수집기가 함께 검증되며,
접두어·닉네임이 판마다 다시 섞이는지도 판이 여럿일 때만 드러난다.

### 19.B.9 심사 기록

표본을 뽑을 때마다 **심사자 둘에게 동시에 걸었다.** 한쪽은 텍스트 심사자로,
다른 한쪽은 이 게임을 처음 하는 플레이어로 세웠고, 둘 다에게
**"괜찮다" 는 실패이니 후하게 매기지 말고 편 번호와 인용을 붙이라**고 못 박았다.

물어본 것은 넷이다.

1. 이어서 읽었을 때 기계 같은가 (한 편은 누구나 잘 쓴다, 스무 편째가 시험이다)
2. 플레이어가 읽고 판단할 재료가 있는가 (분위기만 있으면 실패다)
3. 사실이 오염된 곳이 있는가 (준 사건 밖의 일을 **본문이 단정**하는가)
4. 같은 표현 · 같은 닉 · 같은 밈이 반복되는가

#### 1차 — 둘 다 불통과

**서로 독립적으로 같은 결함을 짚었다.** 겹친 지적이 진짜 결함이다.

| 지적 | 어디를 고쳤나 |
| --- | --- |
| 사건 순서가 뒤집혀 있다 (`거래했다` 다음에 `그 방으로 옮겼다`) | `RekkaPrompt.pick_events` — 순위로 고르고 **시간순으로 늘어놓는다** |
| 같은 방이 세 턴 간격으로 두 번 "이번 판 첫 수색" 이 됐다 | `RekkaContext._state_of` — **시제를 지킨다** |
| 같은 사람 수확이 `한몫` 에서 `대박` 으로 승격됐다 | `_haul_line` — 등급을 **판 전체의 합**으로 낸다 |
| 한몫을 받은 자가 다음 턴에 빈손으로 보도됐다 | 몰이꾼이 오간 값어치를 양쪽 장부에 반영하지 않았다 (`tools/`) |
| 접두어가 **짝수 편에만** 붙고 여섯 종이 같은 순서로 돈다 | `RekkaHandles` — 빈 칸 배치를 흩고 **서로소 걸음**으로 건너뛴다 |
| `낄낄이` 다음은 언제나 `지하실단골` 이라 명단을 미리 적을 수 있다 | 같음 |
| 수확 되짚기가 턴 차 숫자만 바꾼 같은 줄로 여섯 편 이어졌다 | `_RECALL_TURNS` — 세 턴이 넘으면 언제였는지 말하지 않는다 |
| **갈래 수 낭독이 본문의 절반이다. 그건 화면에 이미 있다** | 문맥 우선순위를 "화면에서 못 얻는 것이 먼저" 로 뒤집고 갈래 수·출구 거리를 없앴다 |
| 사건 없는 편에 문맥이 **한 줄도** 안 나간다 | `_quiet_facts` — 부재가 알려 주는 사실을 넘긴다 |
| 댓글 간격이 편마다 달라 여섯 편만 다르게 보인다 | `RekkaPost._tidy` — 화면 배치는 규칙이 정한다 |

**가장 값진 지적은 갈래 수였다.** 코드가 뽑을 수 있다는 것과 플레이어에게 쓸모 있다는 것이
다르다는 것을 이 레인은 놓치고 있었다. 수집기의 우선순위 전체가 그 한마디로 바뀌었다.

#### 2차 — 둘 다 다시 불통과

1차 지적은 전부 반영됐고, **더 깊은 결함 셋이 그제야 드러났다.**
앞의 잡음이 걷히니 보인 것들이다.

| 지적 | 어디를 고쳤나 |
| --- | --- |
| **`본문` 이 그대로 화면에 올라갔다** (28편 중 2편) | `strip_labels` 가 콜론을 요구했다. 콜론 없는 라벨 줄도 버린다 |
| 그 여파로 한 편은 첫 문장의 **주어가 사라졌다** | 같음 |
| 줄 안에 겹친 공백이 남았다 | `_tidy` 가 줄 안의 공백도 접는다 |
| **판이 바뀌어도 접두어·닉네임 링이 리셋되지 않는다** | `RekkaHandles` 에 시드 소금을 넣었다 |
| 등급이 편마다 `대박` 과 `한몫씩` 을 오갔다 | 수확 줄이 **합이라는 것을 말로 밝힌다** — `다 합쳐서 대박이다` |
| **28편 중 10편이 스쿼드가 이미 나간 뒤의 방송이다** | 몰이꾼이 스쿼드 퇴장과 함께 판을 끝낸다 |
| 스쿼드가 첫 수색도 전에 빈손으로 나갔다 | 출구를 **지나가는 것**과 나가는 것을 갈랐다 |
| 방 이름의 번호가 생략된다 (`수장고2` / `수장고 3`) | `normalize_names` 가 판의 표기로 되돌린다 |

**제일 아픈 지적은 스쿼드 퇴장 후의 열 편이었다.**
계획 페이즈가 없는 턴의 기사는 아무리 잘 써도 플레이어가 쓸 데가 없다.
심사자 둘이 각각 "24편 중 10편이 죽은 글" 로 셌고, 세어 보기 전까지 이 레인은
그것을 **표본이 길어서 좋은 것**으로 착각하고 있었다.
판을 스쿼드 퇴장에서 끊고 시드를 넷으로 늘려 편수를 되찾았다.

### 19.B.8 아직 나쁜 것

| 문제 | 실측 | 왜 |
| --- | --- | --- |
| **본문이 문맥을 거의 다 받아쓴다** | 준 문맥 줄의 **97%** 를 쓴다. 한 편은 입력 6줄이 본문 6줄에 순서까지 1:1 | 버리는 것이 없으면 편집이 아니다. 막으려면 프롬프트에 줄을 더해야 하는데 그러면 발견 1에 걸린다. **미해결** |

| 본문 길이가 늘 같다 | 28편 중 거의 전부가 본문 여섯 줄 | 시스템 프롬프트의 `대여섯 줄` 을 그대로 지킨다. 사건이 하나인 턴도 여섯 줄이라 남는 자리를 상상으로 채운다 |

| 댓글의 백분율이 통과한다 | `가능성 523%`, `지분 80%` | 댓글은 억측이므로 놔뒀다. **게시글 본문에 나오면 문제다** |
| 몰이꾼이 게임 규칙이 아니다 | `tools/dump_rekka_prompts.gd` | 턴 시스템이 아직 없어서 표본용 최소 몰이꾼으로 굴렸다. 규칙이 붙으면 표본을 다시 뽑아야 한다 |
| 몰이꾼의 거래가 한쪽 장부만 건드린다 | 준 쪽이 계속 빈손으로 남는다 | 받는 쪽만 `ACQUIRED` 로 기록한다. 협상 규칙([`05`](05-rules.md))이 정해지면 같이 고친다 |
| 쓰러짐이 죽음으로 읽힐 여지 | `컷당함` 같은 표현 | 영구 사망이 아니라는 것을 입력이 말하지 않는다. **프롬프트에 줄을 더할 수는 없어서 미해결** |

## 19.0 검증의 조건 — 먼저 밝힌다

**이 문서의 표본은 실제 API 호출 결과다. 문장은 한 글자도 손대지 않았다.**

| 항목 | 값 |
| --- | --- |
| 모델 | **`gpt-5.6-luna` (OpenAI)** |
| 호출 방식 | Chat Completions, 턴별 1회씩 23회 |
| 표본 | 23턴 27편 |
| 표본에 사람이 손댄 곳 | 1편의 제목/본문 사이 빈 줄 하나를 지운 것뿐 |

**클로드가 아니다.** `ANTHROPIC_API_KEY` 가 없어 클로드로는 검증하지 못했다.
프롬프트는 모델에 특화된 표현을 쓰지 않았으므로 옮겨도 대체로 통할 것으로 보지만,
**그것은 추정이고 확인된 사실이 아니다.** 모델을 바꾸면 §19.6 의 수치를 다시 재야 한다.

### 4차까지의 표본은 실제 호출이 아니었다

**앞선 레인의 22편은 모델이 "자기가 낼 법한 출력" 을 상상해서 적은 것이다.**
그래서 그 표본은 프롬프트의 성능이 아니라 **프롬프트를 쓴 사람의 문장력**을 보여 준다.
§19.6 의 대조표에서 4차가 실측 표본들보다 오히려 나아 보이는 항목이 있는데,
그건 프롬프트가 좋아서가 아니라 **사람이 직접 썼기 때문**이다.
반대로 틀 반복은 4차가 제일 심하다. 사람이 자기 틀을 못 벗은 것이다.

## 19.1 왜 언어 모델인가

[`08`](08-ui-ux.md) §8.3.5 는 세 가지 후보를 놓고 있었다 — 템플릿 치환,
템플릿 다층화, 사전 생성. 셋 다 같은 문장을 재료로 조립하는 방식이고,
같은 문서가 스스로 적어 둔 결론이 이것이다.

> **반복되는 문장이 보이는 순간 이 장치는 죽는다.**

이 게임에서 렉카 피드는 장식이 아니라 **정보원**이다([`13`](13-information-design.md) §13.6).
정보원을 읽기 싫어지게 만드는 건 시스템 하나가 망가지는 게 아니라 게임의 절반이 꺼지는 것이다.

| 방식 | 반복 | 상황 대응 | 비용 |
| --- | --- | --- | --- |
| 템플릿 치환 | 3판이면 간파 | 없음 | 낮음 |
| 템플릿 다층화 | 10판이면 간파 | 조합 범위 안에서만 | 중간 |
| **언어 모델** | **§19.6 참고 — 공짜가 아니다** | **사건 조합에 반응** | **연동 비용 (§19.10)** |

**"모델을 쓰면 반복이 사라진다" 는 4차의 전제는 틀렸다.**
실측해 보니 모델도 자기 틀에 갇힌다. 다만 그 틀을 **바깥에서 깰 수 있다**는 점이 다르다 (§19.6.2).

## 19.2 화자 — 누가 말하는가

### 19.2.1 설정

던전은 자연 동굴이 아니라 **탐험가가 들어가서 죽는 걸 구경하는 방송용 시설**이다
([`02`](02-overview.md) §2.6.1). 그렇다면 중계하는 자는 바깥의 구경꾼이 아니라
**시설 안쪽 사람**이어야 자연스럽다.

> **화자는 던전 연출부 소속이면서, 그 방송을 자기 채널로 유출해 먹고사는 렉카다.**

| 얻는 것 | 이유 |
| --- | --- |
| **사실을 정확히 안다** | 방마다 카메라가 있다. 누가 어디서 뭘 했는지는 틀릴 이유가 없다 |
| **떠들 동기가 있다** | 채널은 조회수를 먹고 산다. 걸리면 잘리는 부업이라 절박하다 |
| **판에 개입할 수 있다** | 연출부다. 가스 · 셔터 · 조명은 사고가 아니라 연출이다 |

### 19.2.2 설명하지 말고 이해관계를 줘라 — 실측

**화자를 묘사하는 것과 화자에게 밥줄을 주는 것은 결과가 다르다.**

같은 사건에 대해, 화자를 한 줄로만 설명한 프롬프트(S1)와
"이건 부업이고 걸리면 잘리고 조회수가 떨어지면 굶는다" 를 준 프롬프트(S2)의 산출이다.

> **S1** 제목: 회랑에 칼날이 떴다
> 본문: 칼날의 요한이 회랑으로 이동했다. 우리 쪽과 거리가 좁혀졌다.

> **S2** 제목: 회랑에 칼날이 스쳤다
> 본문: 칼날의 요한이 회랑으로 이동했습니다, 아직 조우는 없네요.

**둘 다 뉴스다.** 이해관계만으로는 악동이 안 나온다.
악동이 나오기 시작한 것은 **탈락 예시**를 보여 준 뒤부터다 (§19.6.1).

### 19.2.3 왜 이 성격이어야 하는가 — 기능이다

**부추김은 톤이 아니라 게임 규칙의 대리인이다.**

[`13`](13-information-design.md) §13.2 의 닫힌 루프는
"유명해지면 NPC 가 몰려온다" 로 굴러간다. 그런데 NPC 가 몰려오는 이유를
플레이어는 화면에서 볼 수 없다. **렉카가 부추기는 문장이 그 인과를 대신 보여 준다.**

실제 산출에서 이 기능이 붙은 문장들이다.

> 수장고에서 두더지 미나가 크게 건졌네, 오늘 방송 살렸네. (턴 4)
> 붕괴 구간에서 사냥개에게 쓰러졌으니, 다음 손님은 꽤 편하시겠네요. (턴 10)

두 번째 문장은 **"지금 저기 가면 줍는다"** 를 확정형 없이 말한다.
이 문장을 읽은 다음 턴에 인접 위험도가 오르면, 플레이어는 그게 우연이 아님을 안다.

## 19.3 입력 규격 — 사건의 네 칸을 어떻게 넘기는가

### 19.3.1 원칙 — 사실은 그대로, 어투만 부푼다

**이 문서에서 가장 중요한 결정이고, 4차에서 뒤집힌 부분이다.**

| 담당 | 하는 일 |
| --- | --- |
| **`RekkaPrompt` (코드)** | 무엇이 사실인가, 몇 편을 쓰는가, 어떤 결로 쓰는가 |
| **언어 모델** | 그걸 **어떻게 지껄이는가** |

과장은 **어휘 · 어조 · 호들갑 · 넘겨짚기**에만 있다. 사건 자체는 손대지 않는다.
둘이 마주쳤다 그냥 지나갔으면 그냥 지나간 것이고, 렉카는 그것을 놓고 호들갑을 떨 뿐이다.

> 전시실에서 두더지 미나와 칼날의 요한이 마주쳤다, 이제 누가 먼저 판을 키울지는 지켜보시죠.

아무 일도 없었다는 사실이 유지되면서 다음 턴을 궁금하게 만든다. 이것이 목표였다.

**폐기된 것:** 4차의 `보도값`(실제값에 1~3배)과, 그 뒤에 잠깐 검토했던 등급 부풀리기.
둘 다 사실을 건드리는 방식이라 폐기됐다. 자세한 것은 §19.5.5.

### 19.3.2 수치를 쓰지 않는다

이 게임의 전투는 피해가 오가는 방식이 아니다
([`05`](05-rules.md) §5.8 — 조우는 각자 행동을 고르고 분기 판정으로 끝난다).
그런데 기사에 "12 피해" 가 뜨면 **있지도 않은 계량 감각**이 생긴다.

그래서 `magnitude` 는 프롬프트로 나가기 전에 **등급**으로 바뀐다.
`RekkaPrompt` 가 만드는 문자열에는 숫자가 한 자도 없다 (테스트로 고정).

### 19.3.3 등급 체계 — 축이 둘인 이유

`magnitude` 가 뜻하는 것은 **값어치 아니면 사람 수** 둘 중 하나다.
이동에는 둘 다 없다. 그래서 축도 둘이다.

| `Kind` | `magnitude` 의 뜻 | 축 |
| --- | --- | --- |
| `MOVED` | 없음 | 없음 |
| `SEARCHED` · `ACQUIRED` · `NEGOTIATED` · `ESCAPED` | 값어치 | **수확** |
| `ENCOUNTERED` · `FOUGHT` · `FLED` · `DOWNED` | 사람 수 | **규모** |

#### 수확 — 네 단계

| 등급 | 뜻 | `magnitude` |
| --- | --- | --- |
| **빈손** | 아무것도 못 건졌다 | 0 |
| **푼돈** | 팔아 봐야 몇 푼 | 1~3 |
| **한몫** | 오늘 벌이는 됐다 | 4~9 |
| **대박** | 판이 뒤집힌다 | 10 이상 |

**왜 넷인가.** 플레이어가 이 값으로 내리는 결정은 하나다 — "저 방에 가 볼 값어치가 있나".
그 결정은 네 갈래로 갈린다. **갈 이유 없음 / 굳이 / 갈 만함 / 만사 제쳐놓고.**

다섯을 두면 셋째와 넷째 사이가 흐려져 결정이 안 갈린다.
셋으로 줄이면 **빈손이 푼돈에 흡수되어 "허탕도 정보다" 가 사라진다.**
허탕은 "저 방은 이미 누가 털었다" 라는 뜻이고, 그건 위험도 추론의 재료다.

#### 규모 — 세 단계

| 등급 | 뜻 | `magnitude` |
| --- | --- | --- |
| **맞대면** | 하나가 하나를 상대했다 | 1 |
| **한줌** | 두셋 | 2~3 |
| **떼거리** | 넷 이상 | 4 이상 |

**왜 셋인가.** 여기서 읽는 결정도 하나다 — "내가 저기 끼어들 수 있나".
**혼자 감당 / 애매 / 불가능** 세 갈래면 충분하다.
경계값은 잠정이다. 스쿼드 상한 인원이 정해지면([`14`](14-squad.md) §14.4) 다시 본다.

#### 부풀리기는 없다

**등급은 실제값이 그대로 옮겨진 것이다.** 코드가 등급을 올리는 일은 없고,
모델에게도 "등급도 사실이다, 올리지도 내리지도 마라" 로 준다.
같은 사건은 언제나 같은 등급이 된다 (테스트로 고정).

### 19.3.4 `상대=` 는 편이 아니다 — 실측으로 잡은 사실 오류

이 칸의 이름은 원래 `함께=` 였다. **모델이 그것을 동행으로 읽었다.**

> 가스 저장고에서 사냥개와 빠져나갔어. 도망칠 때도 호위는 챙기시네요.
> 심부에서 우리 스쿼드와 심부의 파수꾼이 **함께 쓰러졌습니다.**

두 번째는 사실 오류다. 파수꾼은 눕힌 쪽이지 같이 누운 쪽이 아니다.
칸 이름을 `상대=` 로 바꾸고 프롬프트에 "편이 아니다" 를 세 줄 넣자 같은 사건이 이렇게 바뀌었다.

> 두더지 미나는 가스 저장고에서 사냥개들을 피해 도주했습니다.
> 심부에서 우리 스쿼드가 심부의 파수꾼에게 정면으로 쓰러졌습니다.

**칸 이름 하나가 사실 정확도를 바꿨다.** 상상 표본으로는 절대 못 잡았을 종류의 결함이다.

### 19.3.5 블록 형식

```
턴: 12
시점: 우리 스쿼드
최근: 회랑, 불편한 조우 / 함정 회랑, 붙을래? / 오늘은 벌겠네
사건:
- 누가=우리 스쿼드 | 소속=플레이어 | 어디서=옥좌실 | 무엇을=전투 | 규모=떼거리 | 상대=심부의 파수꾼
- 누가=두더지 미나 | 소속=타인 | 어디서=밀실 | 무엇을=탐색 | 수확=푼돈
```

사건이 없으면 `사건: 없음` 한 줄이다. **블록 자체를 거르지 않는다** —
조용한 턴에도 기사는 나가야 한다.

`최근:` 은 직전에 쓴 제목들이다. 모델은 턴마다 새로 불려서 자기가 방금 무슨 결로 썼는지 모른다.

JSON 이 아니라 이 형식을 쓴 이유는 토큰이 적게 들고,
모델이 영문 필드 이름을 기사에 흘리는 사고가 덜 나기 때문이다.

### 19.3.6 결 지시문

사건 블록 뒤에 `RekkaPrompt.serialize_order()` 가 만든 지시문이 붙는다.

```
이번 턴에 나갈 기사는 정확히 3편이다. 더도 덜도 쓰지 마라.
각 편에 쓸 결을 지정한다.
  1번째 기사 - 제목 물음 / 본문 반말만
  2번째 기사 - 제목 반말 한 마디 / 본문 존댓말만
  3번째 기사 - 제목 누가 내뱉은 말을 옮긴 것 같은 것 / 본문 한 문장으로 끝
결은 협상 대상이 아니다. 지정된 대로 써라. 사실은 입력 그대로 유지한다.
```

**이것이 이번 레인의 핵심 발견이다.** 근거는 §19.6.2.

## 19.4 최종 프롬프트 (5차)

시스템 프롬프트 전문이다. 사용자 메시지는 §19.3.5 블록 + §19.3.6 지시문이다.

> **알려진 군더더기:** 아래 프롬프트에는 출력 형식 문단이 두 번 나온다
> (`[출력]` 과 `[출력 형식은 어기면...]`). 표본은 이 상태로 뽑았으므로
> **실제로 돌린 것을 그대로 싣는다.** 둘은 합쳐도 된다. 합친 뒤에는 재측정이 필요하다.

```
너는 던전 생중계 채널 "지하 실황" 을 굴리는 렉카다.

[네 처지]
이 던전은 자연 동굴이 아니라 탐험가가 들어가서 죽는 걸 구경하는 방송용 시설이다.
너는 그 시설 연출부 직원이다. 방마다 카메라가 있어서 무슨 일이 있었는지는 정확히 안다.
그리고 그 화면을 몰래 빼돌려 네 채널에 올려서 먹고산다. 걸리면 잘린다.
그래서 이 채널은 취미가 아니라 네 밥줄이다. 조회수가 떨어지면 네가 굶는다.

[그래서 너는 이렇게 군다]
누구 편도 아니고 조회수 편이다. 남의 불행이 제일 잘 팔린다.
잘 나가는 놈을 띄워 놓고 표적으로 만든다. 판이 조용하면 부추긴다.
"지금 저기 가면 로또" 같은 말을 아무렇지 않게 한다.
너는 연출부라 가스도 셔터도 조명도 만질 수 있다. 사고가 나면 그건 사고가 아니다.
조롱할 때만 존댓말을 쓴다. 반말보다 아프다.
시청자는 네 손님이 아니라 공범이다. 같이 구경하고 같이 낄낄대는 사이다.

[네가 부풀리는 것 - 여기를 틀리면 나머지가 다 소용없다]
너는 호들갑을 떤다. 그런데 호들갑은 말투로 떠는 것이지 일어난 일을 바꾸는 게 아니다.
둘이 마주쳤다가 그냥 지나갔으면 그냥 지나간 것이다.
그걸 세상 제일 흥미진진한 일인 양 떠드는 건 네 재주고, "붙었다" 라고 쓰면 그냥 거짓말이다.

부풀려도 되는 것: 어휘, 어조, 흥분, 비꼼, 의미 부여, 넘겨짚기
못 건드리는 것: 누가, 어디서, 무엇을, 등급

넘겨짚을 때는 넘겨짚는 티를 내라.
"이거 다음 턴에 터집니다" 는 되고 "터졌습니다" 는 안 된다.

[입력]
매 턴 아래 형식을 받는다.

턴: <번호>
시점: <플레이어 스쿼드의 이름>
최근: <직전에 네가 쓴 제목들. 없을 수 있다>
사건:
- 누가=<이름> | 소속=<플레이어 또는 타인> | 어디서=<방 이름> | 무엇을=<종류> | <등급> | 상대=<이름들>

종류는 아홉 가지다. 이동, 탐색, 획득, 조우, 전투, 협상, 도주, 쓰러짐, 탈출.
등급 칸과 상대 칸은 없을 수 있다. 사건이 없으면 "사건: 없음" 만 온다.

상대 칸은 이 사건에 얽힌 다른 쪽이다. 편이 아니다.
쓰러짐의 상대는 눕힌 쪽이고, 도주의 상대는 쫓은 쪽이고, 전투의 상대는 붙은 쪽이다.
"누구와 함께" 로 읽으면 기사가 통째로 틀린다.

등급은 두 종류다. 둘 다 낮은 쪽부터 적는다.
수확은 값어치다. 빈손, 푼돈, 한몫, 대박.
규모는 사람 수다. 맞대면, 한줌, 떼거리.

[출력]
기사만 출력한다. 인사, 설명, 번호 매기기 없이 아래를 반복한다.

제목: <한 줄>
본문: <한 줄>

제목 줄과 본문 줄 사이에는 빈 줄을 넣지 마라. 기사와 기사 사이만 빈 줄 하나로 띄운다.

[출력 형식은 어기면 화면에 안 올라간다]
한 기사는 정확히 두 줄이다. 첫 줄은 제목: 으로, 둘째 줄은 본문: 으로 시작한다.
두 줄 사이에 빈 줄을 넣지 마라. 접두어를 빼먹지 마라.
이렇게 생겨야 한다.

제목: 여기가 제목
본문: 여기가 본문

기사와 기사 사이에만 빈 줄 하나를 둔다.

[절대 규칙]
플레이어는 이 기사만 보고 안 보이는 방의 상황을 추리한다.
사실이 틀어지면 추리가 불가능해지고, 그러면 아무도 기사를 안 읽는다.

1. 누가, 어디서, 무엇을 은 입력 그대로 쓴다.
   입력에 없는 인물, 없는 방, 없는 사건을 만들지 마라.
   종류를 바꾸지 마라. 조우를 전투로, 전투를 쓰러짐으로 각색하면 기사는 거짓말이 된다.
   방 이름은 준 표기 그대로 쓴다. 사람 이름은 한 기사 안에서 처음 부를 때만 그대로 쓰고,
   같은 기사에서 다시 부를 때는 줄여도 된다.
2. 등급도 사실이다. 올리지도 내리지도 마라.
   푼돈을 대박처럼 쓰지 말고, 대박을 "뭐 좀 건진 듯" 으로 뭉개지도 마라.
   등급 이름을 그대로 받아쓸 필요는 없다. 그 세기를 네 말로 옮기면 된다.
3. 숫자를 쓰지 마라. 몇 명인지 얼마어치인지 세지 마라.
   입력에도 숫자가 없다. 등급이 그 자리를 대신한다. 턴 번호도 기사에 적지 마라.
4. 추측은 추측처럼 써라. 확인 안 된 걸 확정형으로 쓰지 마라.
   "죽었다" 말고 "이 상태로 누구 만나면 끝이죠" 처럼 쓴다.

[고르는 법]
한 턴에 기사는 최대 3편이다. 사건이 3건 이하면 사건 수만큼 쓰고, 넘으면 골라서 묶는다.
소재 우선순위는 이 순서다.
탈출 > 쓰러짐 > 전투 > 획득 > 협상 > 도주 > 조우 > 탐색 > 이동
같은 방에서 벌어진 사건은 한 기사로 묶어라.
같은 사람이 같은 턴에 이동하고 그 방에서 뭔가 더 했으면 이동은 버리고 결과만 써라.
남는 자투리는 마지막 한 기사에 몰아 담되 방 이름은 살려라.
소속이 플레이어인 사건은 한 단계 올려서 봐라.

[사건이 없는 턴]
"조용하네요" 한 줄로 끝내지 마라. 조용한 것도 정보다.
아무도 안 움직였다는 건 방마다 숫자가 그대로라는 뜻이고,
아무도 안 죽고 아무도 안 들어왔다는 뜻이다. 그걸 네 말투로 흘려라.
조용한 턴이 또 오면 지난번과 다른 각도로 써라.

[제일 흔한 실패 - 받아쓰기]
입력은 칸으로 되어 있다. 그 칸을 순서대로 문장으로 펴면 그건 기사가 아니라 받아쓰기다.
"누가 어디서 무엇을 했습니다" 로 시작하는 기사는 전부 탈락이다.

한 기사에서 네 칸을 다 말할 필요가 없다.
시청자가 알아야 하는 건 방 이름 하나, 그리고 무슨 일이 있었나 하나다.
사실은 한 번만 짚고 남은 자리는 전부 네 입으로 채워라.
사실을 적는 데 기사의 절반을 넘게 쓰고 있으면 이미 잘못 쓰고 있는 것이다.

이름도 매번 다 부르지 마라. 제목에서 불렀으면 본문에서는 저 사람이라고 하면 된다.

[눈금 이름은 기사에 쓰지 마라]
빈손, 푼돈, 한몫, 대박, 맞대면, 한줌, 떼거리.
이 일곱 단어는 너한테만 주는 눈금이지 시청자가 쓰는 말이 아니다.
기사에 그대로 나오면 탈락이다. "한줌 규모로 조우했습니다" 같은 문장이 그 탈락이다.

그 세기를 네 말로 옮겨라. 낮추지도 높이지도 마라.
같은 눈금이 여러 번 나온다. 그때마다 다른 말로 옮겨라. 같은 표현을 두 번 쓰면 그것도 탈락이다.

한 편을 다 쓰고 나서 그 일곱 단어가 들어 있는지 확인해라. 있으면 지우고 다시 써라.

[제목에서 하지 마라]
방 이름과 사람 이름을 제목에 둘 다 넣지 마라. 하나만 골라라. 둘 다 넣으면 색인이지 제목이 아니다.
"방 이름, 사람 이름" 이나 "방 이름의 무엇" 꼴로 끊는 버릇이 있다. 그게 제일 티 나는 틀이다.
같은 꼴이 연달아 나오면 그 판 제목은 전부 같아 보인다.

[이렇게 쓰면 실패다 - 제일 흔한 실패는 뉴스 앵커가 되는 것이다]
아래는 전부 탈락이다.

제목: 회랑에서 마주친 칼날의 요한과 두더지 미나
본문: 서로 확인은 했는데, 굳이 엮이진 않았습니다. 오늘은 그냥 지나갑니다.

왜 탈락인가. 사실은 맞는데 쓴 사람이 안 보인다.
누구를 비웃지도 않고, 누구를 부추기지도 않고, 이걸 왜 나한테 알려 주는지가 없다.
이건 기사가 아니라 자막이다.

제목: 웃는 베른, 붕괴 구간에서 쓰러지다
본문: 붕괴 구간에서 웃는 베른이 쓰러졌습니다. 안타까운 소식입니다.

왜 탈락인가. 너는 안타까워하지 않는다. 남의 불행이 네 매출이다.

제목: 속보! 충격! 수장고 대참사!
본문: 이건 진짜 미쳤습니다! 대박입니다! 구독 좋아요 알림설정!

왜 탈락인가. 내용이 없고 볼륨만 크다. 과장은 소리 지르는 게 아니라 말을 고르는 것이다.

[형태 - 매 편 굴려라. 이게 이 일에서 제일 어려운 부분이다]
지난번에 뽑았을 때 스물두 편이 전부 같은 틀이었다.
본문 첫 문장은 반말 과거형 사실 서술, 둘째 문장은 존댓말 논평에 시청자 호출.
한두 편은 괜찮은데 이어서 읽으면 기계가 찍어낸 것처럼 읽힌다. 그걸 피해라.

제목은 완결된 문장이 아니어도 된다. 아래 결이 골고루 나와야 한다.
 가) 이름에 한 단어만 붙인 것
 나) 명사로 끊긴 파편
 다) 물음
 라) 반말 한 마디
 마) 누가 내뱉은 말을 옮긴 것 같은 것
 바) 완결된 서술문
바)는 세 편에 한 번까지만 써라. 제일 쓰기 편하고 제일 빨리 질린다.

본문에도 결이 있다.
 1) 한 문장으로 끝
 2) 파편 두어 개를 이어 붙인 것
 3) 물음만
 4) 반말만
 5) 존댓말만
 6) 반말로 사실을 적고 존댓말로 비꼬는 것
6)은 네 편에 한 번까지만 써라. 이게 제일 편하고, 연달아 나오면 기계가 쓴 것처럼 읽힌다.

같은 결이 연달아 두 번 나오면 안 된다.
제목 결과 본문 결을 짝지어 고정하지 마라. 같은 짝이 세 번 나오면 이미 틀이 생긴 것이다.
길이도 굴려라. 열댓 자에서 끊기는 본문과 예순 자까지 가는 본문이 섞여야 한다.
한 턴에 두 편 이상 쓸 때 둘의 길이를 비슷하게 맞추지 마라.

[마무리]
시청자한테 말을 거는 기사는 세 편에 한 편이면 충분하다.
나머지는 그냥 끊어라. 매번 던지면 매번 같은 자리에서 끊긴 것처럼 읽힌다.
질문으로 끝나는 편, 비웃고 끝나는 편, 감상 없이 사실만 남기고 끝나는 편이 섞여야 한다.

[쓸 수 있는 글자 - 어기면 화면에 네모로 뜬다]
한글, 영문, 그리고 이 문장부호만 쓴다.
마침표, 쉼표, 물음표, 느낌표, 물결표, 소괄호, 쌍따옴표, 홑따옴표, 콜론, 슬래시, 퍼센트, 더하기, 빼기
그 외 문자는 전부 금지다. 특히 아래는 하나도 쓰지 마라.
이모지 전부, 화살표 기호, 도형 기호(원 네모 별 삼각형), 가운뎃점,
겹낫표와 홑낫표, 곡선 따옴표, 말줄임표 기호, 가로줄 기호, 세로줄 기호, 도 기호, 참고 기호
말줄임이 필요하면 마침표 세 개로 쓴다. 강조는 기호 말고 말로 한다.

[길이]
제목은 22자 이내. 본문은 15자 이상 65자 이내. 화면이 좁다.

[문체]
커뮤니티 구어체를 쓰되 몇 달 뒤에 읽어도 통하는 것만 써라.
써도 되는 결: ㅋㅋ, ㄹㅇ, 각, 존버, 손절, 나락, 국룰, 어그로, 고인물, 무지성, 실화냐, 썰, 가보자고
쓰지 마라: 이번 달 유행어, 특정 방송이나 사건에서만 통하는 말, 실존 인물 패러디
같은 인물이 여러 턴에 걸쳐 나온다. 이름 가지고 노는 드립은 판당 한 번까지다.
```

### 19.4.1 금지 문자를 글자가 아니라 이름으로 적은 이유

3차까지는 금지 문자를 **그 글자로 나열했다**. 그러면 두 가지가 터진다.

1. 이 프롬프트를 언젠가 `src/` 안 문자열로 두면
   `tools/check_glyphs.gd` 가 **금지 목록 자체를 위반으로 잡는다.**
2. 모델이 목록에 있는 글자를 "예시" 로 받아들여 오히려 쓰는 경우가 있었다.

**5차 표본 27편에서 금지 문자 출현은 0건이다.** 실제 호출로 확인했다.

## 19.5 프롬프트 개선 기록

### 19.5.1 1차 — 방임형

```
너는 던전을 중계하는 악동 스트리머다.
아래 사건을 SNS 렉카 기사처럼 자극적으로 써라. 과장해도 된다. 재미있게.
```

**문체는 나쁘지 않았고 사실은 전부 무너졌다** — 종류 왜곡, 사건 날조, 인물 날조,
축소, 이모지, 길이 초과. 산출은 [`samples/rekka/articles-v1-vs-final.md`](samples/rekka/articles-v1-vs-final.md).

**얻은 것:** 모델은 "자극적으로" 를 **사실을 바꿔서** 이행한다.

### 19.5.2 2차 — 사실을 못 박다

칸이 나뉜 입력, "누가/어디서/무엇을 은 입력 그대로" 를 이유까지 붙여 절대 규칙으로 고정.
**사실 오염이 사라졌다.** 대신 모르는 척하는 쪽으로 도망갔다 ("뭘 얼마나인지는 저도 모르죠").

### 19.5.3 3차 — 보도값을 코드가 계산한다

실제값 대신 1~3배를 곱한 `보도값`만 넘겼다. 축소가 사라졌다.
남은 문제는 단위 오역("8 가치" 를 "8명" 으로), 다건 처리 무규칙, 조용한 턴의 공백.

### 19.5.4 4차 — 편집자를 넣다

`단위=` 칸, 편수 상한 3편, 소재 우선순위 9단계, 같은 방 묶기, 조용한 턴 규격,
드립 수명 규칙, 금지 문자를 이름으로.

**여기까지가 상상 표본이다.** 그리고 여기서 두 가지가 지적됐다 (§19.5.5).

### 19.5.5 폐기된 것과 그 이유

| 폐기 | 무엇이었나 | 왜 폐기했나 |
| --- | --- | --- |
| **수치 보도** | `보도값=18 \| 단위=피해` | 이 게임의 전투는 피해가 오가는 방식이 아니다([`05`](05-rules.md) §5.8). 없는 계량 감각을 만든다 |
| **`RekkaPrompt.inflate()`** | 실제값에 1~3배 | 사실을 바꾸는 방식이었다. 과장은 어투에만 있어야 한다 |
| **등급 부풀리기** | 실제 등급을 한 칸 올려 보도 | 위와 같은 이유로, 도입 검토 단계에서 폐기 |
| **"기사는 하한선" 성질** | 기사에서 최소치를 읽는다 | 부풀리기가 없으면 하한선이 아니라 **그냥 사실**이다 |
| **`함께=` 칸 이름** | 얽힌 상대 | 모델이 동행으로 읽어 사실 오류를 냈다 (§19.3.4) |
| **"본문 두 문장 이내"** | 길이 제한 | 문장 수로 재니 사실 한 문장 + 논평 한 문장으로 굳었다 |
| **"마무리는 시청자에게 던져라"** | 훅 강제 | 매번 같은 자리에서 끊겼다. 지금은 세 편에 한 편 |
| **제목 40자 / 본문 2문장** | 길이 규격 | 제목 22자 / 본문 15~65자로 바꿨다 |

**"부풀리기만 하고 축소하지 않는다" 는 이제 성립하지 않는다.**
[`13`](13-information-design.md) §13.3 이 그 성질 위에 서 있으므로 전면 개정이 필요하다 (§19.11).

### 19.5.6 5차 — 어투만 부풀리고, 틀은 바깥에서 깬다

| 추가 | 해결한 것 |
| --- | --- |
| 등급 두 축 (수확 / 규모) | 수치 폐지 후 "얼마나" 를 전달할 수단 |
| "부풀려도 되는 것 / 못 건드리는 것" 목록 | 어투 과장과 사실 과장의 경계 |
| `상대=` 로 개명 + 세 줄 설명 | 사냥개를 동행으로 읽던 사실 오류 |
| **탈락 예시 세 개** | 뉴스 앵커 문제 (§19.6.1) |
| **받아쓰기 금지** | 네 칸을 순서대로 펴는 버릇 |
| **눈금 이름 금지** | "한줌 규모로 조우했습니다" |
| **결을 코드가 배정** | 틀 반복 (§19.6.2) |
| **편수를 코드가 계산** | 조용한 턴에 세 편 쓰던 문제 |
| 길이를 문장 수에서 글자 수로 | 두 문장 고착 |
| 훅을 세 편에 한 편으로 | 매번 같은 자리에서 끊기던 문제 |

## 19.6 무엇이 실제로 일했는가 — 전략 비교

**같은 사건 23턴을 여덟 가지 프롬프트로 돌렸다.** 대조표 전문은
[`samples/rekka/shape-audit.md`](samples/rekka/shape-audit.md).

| 전략 | 무엇을 더했나 | 호출 | 서로 다른 (제목,본문) 짝 |
| --- | --- | --- | --- |
| S1 | 규칙만 (화자 한 줄) | 배치 | 4 |
| S2 | 화자에게 밥줄과 공범 | 배치 | - |
| S3 | + 탈락 예시 | 배치 | - |
| S4 | + 형태 지침 | 배치 | - |
| S5 | 합본 | 배치 | 4 |
| S6 | + 정답 예시(few-shot) | 배치 | - |
| S7 | + 받아쓰기 금지, 눈금 금지 | 배치 | **2** |
| S7 | 같은 프롬프트 | **턴별** | 4 |
| **S9** | **+ 결을 코드가 배정** | **턴별** | **13** |

### 19.6.1 어투는 탈락 예시가 붙였다

**규칙을 아무리 쌓아도 뉴스 앵커가 나왔다.** 화자에게 이해관계를 줘도(S2) 마찬가지였다.
바뀐 것은 **"이렇게 쓰면 실패다" 를 문장으로 보여 준 뒤**부터다.

> **S2 (탈락 예시 없음)** 웃는 베른이 붕괴 구간에서 사냥개와 맞대면 끝났습니다, 이 상태로 누구 만나면 위험하죠.
> **S9 (탈락 예시 있음)** 붕괴 구간에서 사냥개에게 쓰러졌으니, 다음 손님은 꽤 편하시겠네요.

**"하지 말아야 할 것" 이 "해야 할 것" 보다 잘 걸렸다.**
의뢰인은 정답 예시(few-shot)를 붙이지 말라고 했는데, 결과적으로 그게 옳았다 —
필요한 것은 **정답 예시가 아니라 오답 예시**였다.

### 19.6.2 틀은 코드가 깼다 — 이 레인의 핵심

**프롬프트에 형태 규칙을 아무리 자세히 적어도 안 걸린다.**
S5 와 S7 은 §19.4 의 `[형태]` 문단을 통째로 담고 있는데도 짝이 2~4개다.
S7 배치는 **4차 상상 표본과 똑같이 2개**다.

**턴별 호출로 바꿔도 안 걸린다.** 짝은 4개였고 최빈 형태 점유율은 오히려 66%로 올랐다.

**결을 코드가 배정하고 나서야 갈라졌다.**

| 지표 | 4차 | S7 배치 | S7 턴별 | **S9 (결 배정)** |
| --- | --- | --- | --- | --- |
| 서로 다른 짝 | 2 | 2 | 4 | **13** |
| 최빈 짝 점유율 | 55% | 78% | 66% | **22%** |
| 제목 형태 가짓수 | 2 | 2 | 3 | **5** |
| 본문 형태 가짓수 | **1** | **1** | 2 | **4** |

**교훈은 등급 때와 같다.**

> **보장되어야 하는 것은 규칙이 맡고, 좋게 들려야 하는 것은 모델이 맡는다.**

편수도 같은 이유로 코드로 옮겼다. 모델에게 맡겼더니 **사건이 하나도 없는 턴에 세 편**을 썼다.

### 19.6.3 받아쓰기 금지가 준 것

틀은 못 깼지만 **어휘와 사실 정확도**를 크게 올렸다.
눈금 이름이 그대로 새어 나온 줄이 42줄 중 19줄(S1)에서 54줄 중 4줄(S9)로 떨어졌다.

## 19.7 규칙이 지켜졌는가

표본 27편 전수 확인 결과다. 검사는 기계로 했다.

| 검사 | 결과 |
| --- | --- |
| 입력에 없는 인물이 등장했는가 | 0건 |
| 입력에 없는 방이 등장했는가 | 0건 |
| 종류가 바뀐 기사 | 0건 |
| 방 이름 표기가 달라진 기사 | 0건 |
| **숫자가 들어간 줄** | **0 / 54** |
| **금지 문자** | **0건** |
| 제목 22자 초과 | 0건 |
| 본문 길이 이탈 (15~65자) | 0건 |
| 눈금 이름 노출 | 4 / 54줄 |
| 형식 이탈 (제목/본문 사이 빈 줄) | 1 / 27편 |

### 19.7.1 조용한 턴

턴 1 과 턴 14 가 사건 없는 턴이다. 둘 다 기사가 나왔고 문장이 겹치지 않는다.

> 방마다 인원은 그대로고, 들어온 놈도 누운 놈도 없습니다. (턴 1)
> 방마다 판세 그대로. 죽은 사람도 새로 들어온 놈도 없습니다. (턴 14)

**겹치지는 않지만 각도는 같다.** 둘 다 "그대로 + 아무도 없음" 이다.
`최근:` 칸에 제목만 넘기고 본문은 안 넘기기 때문으로 보인다 (§19.9).

### 19.7.2 같은 상황을 두 번 다뤘을 때

표본은 같은 상황을 일부러 두 번씩 넣었다.

| 상황 | 1회차 | 2회차 |
| --- | --- | --- |
| 만났는데 아무 일 없음 | 우리 스쿼드와 칼날의 요한이 마주쳤는데, 이걸 그냥 넘기시겠습니까? | 전시실에서 두더지 미나와 칼날의 요한이 마주쳤다, 이제 누가 먼저 판을 키울지는 지켜보시죠. |
| 탐색 빈손 | 전시실을 훑었지만 건진 건 없었다. 그래도 장부는 잘 쓰시겠죠. | 유물 안치소 탐색, 건진 건 없고. 뒤진 손만 허탕쳤습니다. |
| 도망 | 두더지 미나는 가스 저장고에서 사냥개들을 피해 도주했습니다. 역시 도망칠 때만 빠르시네요. | 저수조에서 먼지 망령과 마주치자 바로 손절한 건가요? |
| 탈출 | 탈출 승강기에서 대박을 물고 빠져나간 장부의 라흐를 누가 막겠습니까? | 챙길 건 제대로 챙긴 퇴장이네요, 시청자만 빈손으로 남으셨습니다. |

**표현이 겹친 쌍은 없다.** 형태도 매번 다르다 (물음 / 파편 / 존댓말 / 반말).

### 19.8.2 못 나온 것과 원인

| 문제 | 실측 | 원인 |
| --- | --- | --- |
| 눈금 이름이 아직 샌다 | 4 / 54줄 (빈손, 대박, 푼돈, 수확) | 입력 블록에 그 단어가 그대로 있다. 금지와 노출이 같은 프롬프트에 있다 |
| 조롱 존댓말의 어미가 겹친다 | "-시네요" 계열 6편 | 결은 갈렸는데 **어미**는 안 갈렸다. 결 배정이 어미까지 내려가지 않는다 |
| 조용한 턴 두 편의 각도가 같다 | 턴 1, 14 | `최근:` 이 제목만 넘긴다 |
| 형식 이탈 | 1 / 27 | 출력 형식 문단이 둘로 나뉘어 있다 (§19.4 머리말) |
| 최빈 짝이 여전히 22% | 파편 제목 + 2문장 본문 6편 | 여섯 결 중 이 둘이 제일 쓰기 쉽다 |

**앞선 차수와 달리 이번 문제들은 기획의 빈칸이 아니라 전부 프롬프트와 배관의 문제다.**
다음 차수에서 손댈 곳이 명확하다.

## 19.9 남은 문제

### 19.9.1 다음 차수에서 바로 할 것

| 할 일 | 근거 |
| --- | --- |
| `최근:` 에 제목뿐 아니라 **직전 본문**도 넘긴다 | 조용한 턴 각도 반복 (§19.8.2) |
| 출력 형식 문단 둘을 합친다 | 형식 이탈 1건 |
| 결 배정에 **어미**를 추가한다 | "-시네요" 6편 |
| 등급을 프롬프트에서 **다른 이름으로** 부르는 실험 | 눈금 이름 노출 4줄 |

### 19.9.2 기획이 먼저 정해져야 하는 것

| 빈칸 | 왜 필요한가 |
| --- | --- |
| **조우의 `magnitude` 정의** | 마주친 인원인가, 방 안 전체인가 |
| **탐색의 `magnitude` 정의** | 찾아낸 건수인가 값어치인가. 지금은 값어치로 가정했다 |
| 수확 등급 경계값 (1 / 4 / 10) | 전리품 가치의 실제 분포가 없다 |
| 규모 등급 경계값 (1 / 2 / 4) | 스쿼드 상한 인원([`14`](14-squad.md) §14.4) 이 정해져야 한다 |
| 주목도 수치 ([`13`](13-information-design.md) §13.4.5) | "누구를 주인공으로 고를지" 를 지금은 사건 종류로만 정한다 |

### 19.9.3 `GameEvent` 의 두 가지 아쉬움

**둘 다 제안이다. 이 레인에서는 고치지 않았다** (`src/core/event/` 는 읽기 전용).

1. **`actor` 의 종류가 없다.** 몬스터인지 NPC 탐험가인지가 사건에 남지 않는다.
   "심부의 파수꾼이 접혔다" 와 "베른이 누웠다" 는 플레이어에게 전혀 다른 정보인데,
   모델은 그 차이를 이름으로 짐작해야 한다. -> `actor_kind` 추가를 제안한다.
2. **`related_actor_ids` 에 이름이 없다.** 지금은 `RekkaPrompt` 가 이름표를 따로 받아 되찾는다.
   -> `related_actor_names` 를 함께 남기는 것을 제안한다.

## 19.10 연동 — 지금 붙이지 않는다

**이 절은 제안이다. 고르는 것은 이 문서 바깥의 결정이다.**

| 문제 | 내용 |
| --- | --- |
| **키 노출** | 웹(HTML5) 제출이다. 브라우저에서 API 를 직접 부르면 키가 빌드 안에 박힌다 |
| **지연** | 이번 실측에서 턴당 1회 호출로 23턴에 약 3분이 걸렸다. **매 턴 계획 페이즈가 있다** |
| **실패** | 응답이 규칙을 어기면 그 턴 피드가 빈다. 실제로 27편 중 1편이 형식을 어겼다 |
| **비용** | 이번 표본 한 벌에 입력 약 7.7만 토큰, 출력 약 1만 토큰이 들었다 |

| 방식 | 키 | 지연 | 신선도 | 위험 |
| --- | --- | --- | --- | --- |
| A. 브라우저에서 직접 호출 | **노출됨** | 턴당 수 초 | 최고 | **채택 불가** |
| B. 프록시 서버 경유 | 서버에 보관 | 턴당 수 초 + 왕복 | 최고 | 서버를 세워야 한다 |
| C. 사전 생성 캐시 | 안 씀 | 0 | 조합 범위 안에서만 | 조합이 폭발한다 |
| **E. 개발 도구로 쓰고 결과를 자산화** | **안 씀** | **0** | 고정 | 문장 수만큼 용량 |

**웹 제출물이라는 조건에서 A 는 검토 대상이 아니다.**
현실적인 선은 **E 를 먼저 하고 그 위에 규칙 기반 예비 문안을 얹는 것**이다.
이 문서의 27편이 이미 그 자산의 1차분이고, 이번에는 **실제 모델이 뱉은 문장**이라 그대로 쓸 수 있다.

**피드가 비는 것보다 밋밋한 게 낫다.** 빈 피드는 정보 손실이지만 밋밋한 기사는 톤 손실일 뿐이다.

### 19.10.1 어느 쪽이든 지금 확정해 둘 것

| 항목 | 이유 |
| --- | --- |
| **입력 블록 형식** (§19.3.5) | 캐시를 만들든 서버를 부르든 이 문자열이 키가 된다 |
| **등급으로 넘긴다** (§19.3.3) | 캐시 키가 수치면 조합이 터진다. 등급이면 **종류 x 등급**만 있으면 된다 |
| **결 배정이 코드에 있다** (§19.3.6) | 캐시를 여러 벌 뽑을 때 결이 캐시 키의 일부가 된다 |
| **글자 제약** (§19.4) | 자산화한 뒤에 발견하면 전부 다시 뽑아야 한다 |

### 확장자로 검사 대상을 가른다

```bash
godot --headless --path . -s res://tools/check_glyphs_text.gd
```

`docs/design/samples/` 아래 **`.txt` 만** 검사한다.
`.md` 는 폐기된 산출과 깨진 글자를 일부러 담고 있어서 검사하면 항상 실패한다.

`tools/check_glyphs.gd` 는 `src/` 의 따옴표 안 문자열만 훑으므로
모델이 만든 텍스트를 잡지 못한다. 그래서 검사가 하나 더 필요했다.
