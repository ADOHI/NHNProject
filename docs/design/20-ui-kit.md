# 20. UI 키트 — 나전(螺鈿)

> **상태: 3차 시도, 진행 중.** 이 문서는 UI **원자 단위**(버튼 · 팝업)의 조형 언어를 정한다.
> 구현은 `src/ui/kit/`, 에셋은 `assets/ui/kit/`, 확인용 화면은 `src/ui/kit/kit_showcase.tscn`.

이 문서는 **매 단계 갱신된다.** 심사를 받을 때마다 §8 에 결과를 적는다.
레인은 언제든 끊기고, 그때 남는 것은 디스크에 쓴 것뿐이다.

---

## 20.1 앞의 두 번이 왜 실패했는가 — 원인은 브리핑에 있었다

1·2차 시도는 **등고선 · 파편 · 알갱이** 세 방향을 만들었고 셋 다 불합격이었다.
평가 원문:

> "코드로만 짜야하니까 쉐이프나 쉐이더로 노이즈 넣고 이렇게만 짜네.
> 아니 그게 아니라 아름다워야 하고 스타일리시 해야 한다고.
> 레이어드 한 UI도 고려해보고 애니메이팅도 고려해보고. **이건 무슨 수학 같음.**"

**원인은 조형 감각이 아니라 제약 조건이었다.** 모든 UI 브리핑에 "에셋 추가 금지,
코드로 만들어라" 가 들어 있었다. 그러면 남는 표현 수단이 **도형과 셰이더 노이즈**뿐이고,
그 둘로 만들 수 있는 것은 필연적으로 **절차적 무늬** — 즉 「수학」이다.
재료가 없으니 재료의 아름다움이 나올 자리가 없었다.

그 금지의 근거였던 「웹 빌드 용량」은 [`01`](01-constraints.md) §1.2 에서 **실측으로 반증됐다.**

| 파일 | 크기 |
| --- | --- |
| `index.wasm` — Godot 엔진 | 37.7 MB |
| `index.pck` — 우리 게임 전부 | 1.5 MB |

**전체의 96%가 엔진이다.** 그러므로 이번 판은 **에셋을 쓴다.**

### 두 번째 원인 — 아직 없는 게임에 UI 를 재단했다

> "UI를 너무 아직 나오지도 않은 게임에 맞춰 재단하려고 한 거야.
> 그냥 팝업, 버튼 이런 것들에 좀 더 포커스 맞추고."

그래서 이번에 만드는 것은 **버튼 하나와 팝업 하나뿐**이다.
게임 화면 · 전투 HUD · 게이트 목록을 만들지 않는다.

### 세 번째 원인 — 「컨셉」을 서사로 이해했다

> "이 컨셉이라는 게 어떤 뉴스 뭐 이런 거에 맞추라는 게 아니라
> **그림체, 규격, 간격, 애니메이션, 쉐이더, 효과** 이런 것에 포커스 맞추라는 거야."

**컨셉 = 조형 언어**다. 소재(렉카 · 게이트 · 던전)를 UI 에 그려 넣는 일이 아니다.
이 문서가 정하는 것은 정확히 저 여섯 가지다.

## 20.2 나전(螺鈿) 폐기 — 재료 컨셉은 느릴 수밖에 없다

**3차 시도(나전 = 검은 옻칠 + 자개 상감)도 폐기했다.** 이 절을 남기는 이유는
다음 사람이 같은 함정을 다시 밟지 않게 하기 위해서다.

### 무엇이 일어났나

정지 화면은 통과할 만했다. **움직임이 없었다.** 모션 심사자가 눈이 아니라
**픽셀을 재서** 판정했고 결과는 아름다움 3/10 · 독창성 2/10 이었다.

측정 방법: 연속 10프레임(0.11초 간격)에서 구역별로 픽셀마다 프레임 축 표준편차를
구하고 그 평균(meanSTD)을 낸다. **빈 검은 배경의 잡음 바닥이 0.219 다.**

| 구역 | meanSTD | 10프레임 내내 같은 픽셀 |
| --- | --- | --- |
| 「탐사 개시」 옻칠 본체 | **0.153** | 49.0% |
| 「보급」 버튼 전체 | 0.168 | 44.6% |
| *(빈 검은 배경 — 잡음 바닥)* | *0.219* | *24.3%* |

**옻칠 판이 옆의 빈 검은 배경보다 더 정지해 있었다.** 일곱 버튼 중 넷은
애니메이션이 아예 없었다.

### 진짜 원인 — 컨셉을 정지 화면으로 골랐다

개별 버그도 있었다(정반사가 캡처 구간 내내 판 밖에 있었고, 호버 광택이 13px
가다 서서 주차했고, 편광은 위상차가 아니라 **시간 uniform 에 상수를 곱한 것**이라
여섯 조각이 전부 같은 방향으로 움직였다). 하지만 그것을 다 고쳐도 결론은 같다.

> **재료 컨셉은 태생적으로 느리고 은은하다.**
> 자개 · 옻칠 · 탁본 · 스테인드글라스 · 칠보 — 전부 「미묘한 변화」가 미덕인 재료다.
> **「톡톡 튀는」이 나올 수 없는 자리였다.**

사용자 평가 원문: *"아니 톡톡 튀는 스타일리시하고 동적인 느낌으로 해달라니까
컨셉이 다 왜이래"*.

### 그래서 규칙이 바뀌었다

| 전 | 후 |
| --- | --- |
| 컨셉 = 무엇으로 만들어졌는가 (재료) | **컨셉 = 어떻게 움직이는가 (모션 서명)** |
| 정지 스틸로 고른다 | **정지 스틸은 판정 기준이 아니다.** 움직이는 것으로 고른다 |
| 은은함 · 고급스러움 | **타격감 · 과장 · 대비 · 오버슛** |

**배제 목록:** 재료 시뮬레이션 · 은은함 · 「고급스러움」 · 10초 이상의 느린 주기 ·
미묘한 색 변화. 앞 판이 전부 그것으로 실패했다.

**측정 규칙:** 구역별 meanSTD 를 반드시 출력한다. **0.219 이하는 안 움직이는 것이다.**
「톡톡 튀는」이 목표면 두세 자리는 나와야 한다. 눈으로 "살아 있다" 고 말하지 않는다 —
앞 판이 정확히 그래서 틀렸다.

나전 구현은 git 이력(`0af95a5`)에 남아 있다.

## 20.3 컨셉 = 모션 서명

컨셉은 **무엇으로 만들어졌는가**가 아니라 **어떻게 움직이는가**다 (§20.2 참고).
넷을 나란히 놓고 고를 수 있어야 하므로, 서로 **변주가 아니라 반대편**이어야 한다.

| # | 이름 | 한 문장 | 배색 | 반대로 잡은 지점 |
| --- | --- | --- | --- | --- |
| 1 | **SLAM** 들이받는다 | 요소는 나타나지 않고 **들이받는다** | 검정 · 형광 주황 | 탄성 · 오버슛 · **연속** |
| 2 | **SHEAR** 베여서 어긋난다 | 판은 성한 물건이 아니라 **이미 베여 있다** | 뼈색 · 청록 | **공간**이 끊긴다. 보간이 한 줄도 없다 |
| 3 | **HOLD** 시간이 끊긴다 | 60fps 가 아니라 **초당 여덟 칸**으로 넘어간다 | 형광 노랑 · 마젠타 | **시간**이 끊긴다. 눌림은 **완전 정지** |
| 4 | **SQUASH** 부피가 보존된다 | 판은 굳은 물건이 아니라 **덩어리**다 | 짙은 남색 · 라임 | **모양**만 바뀐다. 자리도 색도 안 건드린다 |
| 5 | **AFTERIMAGE** 잔상이 상태다 | 판은 한 장이 아니라 **늘 네 장이 어긋나 겹쳐 있다** | 흰색 · 빛의 삼원색 | 잔상이 **사건이 아니라 상태**. 「너무 나간 것」 자리 |

### 고를 때 쓰는 한 줄 요약

| 컨셉 | **축** | 안 하는 것 | 눌렀을 때 |
| --- | --- | --- | --- |
| **SLAM** | 도착이 폭력적이다 | 부드러운 감속 | 색이 통째로 뒤집히고 충격 고리가 퍼진다 |
| **SHEAR** | 판이 조각나 어긋난다 | **보간 (한 줄도 없다)** | 한 번 더 베여 세 조각이 된다 |
| **HOLD** | 초당 여덟 칸으로 넘어간다 | 중간 자세 | **완전히 멎는다** |
| **SQUASH** | 부피가 언제나 1 이다 | 자리 이동 · 색 반전 | 납작해지며 옆 판까지 넓어진다 |
| **AFTERIMAGE** | 색이 늘 갈라져 있다 | 정지 (한순간도 없다) | 잔상 셋이 부챗살로 터진다 |

**넷이 서로 변주가 아니라 반대편이 되게** 잡았다. 축이 겹치면 나란히 놓아도 고를 수 없다.

### AFTERIMAGE 가 탁해지지 않게

이 컨셉의 유일한 위험은 색이 섞여 흙빛이 되는 것이다. 과함이 임무지 추함이 임무가
아니므로, 그것만 **구조로** 막고 테스트로 고정했다 (`test_afterimage_motion.gd`).

| 막은 방법 | 왜 듣나 |
| --- | --- |
| 잔상을 본체 **뒤**에 깐다 | 불투명한 흰 판이 겹치는 한복판을 덮어 **색이 가장자리로만** 보인다 |
| **빛의** 삼원색을 쓴다 | 겹치면 흰색으로 수렴한다. 감산 삼원색이면 겹칠수록 흙빛이 된다 |
| 셋이 한 자리에 못 모이게 한다 | 모이면 섞인다. 테스트가 매 순간 거리를 확인한다 |

그리고 **잔상 위치를 기록해 두지 않는다.** 궤도가 시각의 함수라 잔상은 그냥
`orbit(t - 지연)` 이다. 링 버퍼가 없고, 프레임률이 달라도 잔상 간격이 변하지 않는다.

### SHEAR 와 HOLD 를 가른 축

둘 다 「끊김」 계열이라 자칫 같아 보인다. 그래서 축을 못 박았다.

- **SHEAR — 공간이 끊긴다.** 판이 조각나 어긋난다. 판 자체는 **늘 움직인다**
- **HOLD — 시간이 끊긴다.** 판은 늘 성한 통짜이고, 대신 **멎는다**

그래서 HOLD 의 눌림은 「더 크게 움직이는 것」이 아니라 **아무것도 안 하는 것**이다.
시간이 끊기는 판에서는 정지가 가장 크게 읽힌다.

### SQUASH 가 SLAM 의 부드러운 판이 되지 않게

젤리 되튐은 어느 UI 에나 있는 가장 흔한 모션이고, SLAM 이 이미 오버슛과 되튐을
가져갔다. 그래서 규칙 셋을 못 박고 **테스트로 고정했다** (`test_squash_motion.gd`).

| 규칙 | 왜 |
| --- | --- |
| **자리를 옮기지 않는다** | SLAM 은 자리가 움직이고 SQUASH 는 비율이 움직인다 |
| **색을 뒤집지 않는다** | 반전은 SLAM 과 HOLD 의 수단이다 |
| **부피가 언제나 1** | 세로로 눌린 만큼 가로로 정확히 넓어진다 |

**되튐 타이밍이 아니라 모양이 변하는 것**이 이 컨셉을 만든다. 눌리면 세로 0.55 배가
되면서 가로가 1.82 배로 넓어져 **옆 판까지 닿는다** — 밀려난 부피가 어디로도 사라지지 않는다.

### 구조 — 렌더러는 하나다

컨셉마다 그리는 코드를 따로 두면 넷을 나란히 놓았을 때 **무엇 때문에 달라 보이는지**
알 수 없게 된다. 그래서 `PlateState` 의 채널은 고정이고, 컨셉은
`src/core/ui/motion/*` 에서 그 채널을 **얼마나 세게 미느냐**로만 갈린다.

| 파일 | 책임 |
| --- | --- |
| `src/core/ui/kit_ease.gd` | 도착 곡선. **사건 이후 흐른 시간**의 함수 |
| `src/core/ui/plate_state.gd` | 한 프레임의 판 꼴. 채널 정의 |
| `src/core/ui/polygon_cut.gd` | 다각형 자르기 (SHEAR 가 쓴다) |
| `src/core/ui/motion/*_motion.gd` | 컨셉 하나 = 파일 하나 |
| `src/ui/kit/concept_plate.gd` | 모든 컨셉이 함께 쓰는 렌더러 |
| `src/ui/kit/concept_stage.gd` | 무대 + 대본 |
| `tools/capture_concepts.gd` | 연속 프레임 캡처 |
| `tools/make_gif.py` | GIF 조립 |

### 지수 접근을 쓰지 않는다

상태를 목표값으로 지수 접근(`current += (target-current)*k`)시키면
**요소가 영원히 도착하지 않고 목표를 지나칠 방법이 아예 없다.**
타격감이 원천적으로 불가능해진다 — 앞 판이 그래서 죽었다.
전부 **사건이 일어난 뒤 흐른 시간**의 함수로 쓴다.

## 20.4 함정 — `_initialize()` 안의 `add_child()` 는 `_ready()` 를 부르지 않는다

SceneTree 스크립트(`godot -s ...`)의 `_initialize()` 안에서 `root.add_child(scene)`
해도 **그 자리에서 `_ready()` 가 돌지 않는다.** 다음 프레임으로 미뤄진다.

**실제로 난 사고:**

- `set_concept("shear")` 가 통째로 먹히지 않아 **SHEAR 를 캡처했는데 SLAM 이 나왔다.**
  `_plates` 가 아직 비어 있어서 반복문이 0번 돌았고, **오류도 경고도 안 났다**
- `set_guide_visible(false)` 도 같은 이유로 조용히 무시돼 **조작 안내가 캡처에 남았다**

**대처:** 씬 바깥에서 부르는 설정 함수는 **뜻만 받아 두고 `_ready()` 가 적용**하게 한다.
`if _node != null` 가드만 두면 조용히 아무 일도 안 일어나므로 더 위험하다.

### 같은 부류 하나 더 — GUT 은 파싱 실패한 테스트를 **조용히 건너뛴다**

파스 에러가 있는 테스트 파일을 GUT 은 실패로 세지 않고 경고 한 줄만 남기고 넘어간다.

```
[GUT WARNING]: Ignoring script res://test/unit/test_squash_motion.gd
               because it does not extend GutTest
```

**「전부 통과」가 그대로 찍히므로 눈치채기 어렵다.** 실제로 새 테스트 두 파일이
통째로 안 돌고 있었는데 초록불이 떴다. 걸린 원인 둘:

- `const _SQUARE := PackedVector2Array([...])` — 생성자 호출은 **상수 표현식이 아니다.**
  `static func` 로 바꾼다
- `var previous := <타입 없는 함수>.scale.y` — 반환 타입이 없으면 추론이 안 된다.
  헬퍼에 `-> PlateState` 를 붙인다

**대처:** 테스트를 더한 뒤 **스크립트 수와 테스트 수가 실제로 늘었는지 확인한다.**
숫자가 그대로면 새 파일이 안 돌고 있는 것이다.

## 20.5 견본 띄우는 법

```
godot --path . res://src/ui/kit/concept_stage.tscn
```

| 키 | 하는 일 |
| --- | --- |
| `1` ~ `5` | 컨셉을 SLAM / SHEAR / HOLD / SQUASH / AFTERIMAGE 로 바꾼다 |
| `S` | 대본을 끈다 (직접 조작) |
| `H` | 안내 숨김 |
| `Esc` | 닫기 |

왼쪽 아래에 **지금 보고 있는 컨셉 이름**이 뜬다. 키로 넘기며 견주다 보면
몇 번째를 보고 있는지 금방 잃어버리기 때문이다.

### GIF 뽑기

```
godot --path . --resolution 960x540 -s res://tools/capture_concepts.gd -- .renders/hold hold
python tools/make_gif.py .renders/hold .renders/hold.gif
```

**정지 스틸을 뽑지 않는다.** 「톡톡 튀는가」는 정지 화면으로 판단할 수 없다.
대본 한 바퀴(3.2초)에 idle · 올림 · 누름 · 뗌 이 다 들어 있고,
**아래 두 판은 대본을 안 받아 idle 로 남는다** — 가만히 있을 때도 죽지 않았는지를
같은 그림에서 보이게 하려는 것이다.

## 20.6 다섯을 나란히 견주기

키로 넘기는 것만으로는 부족하다. **넷 이상을 기억으로 견주면 마지막에 본 것이 이긴다.**
그래서 다섯이 **같은 대본 시각**을 각자 어떻게 다루는지 한 화면에 세운 그림을 따로 뽑는다.

```
python tools/make_compare_gif.py .renders .renders/compare.gif
```

다섯 줄이 세로로 쌓이고 이름과 한 줄 요약이 붙는다. 커서가 닿는 순간과 누르는 순간이
**다섯 줄에서 동시에** 일어나므로 차이가 가장 압축돼 보인다.
각 줄은 대본을 받는 판과 그 아래 idle 판을 함께 자른다 —
「가만히 있을 때도 죽었는지」가 비교에서도 보여야 하기 때문이다.

## 20.7 방 종류를 58x30px 에서 구분하기

던전 생성 레인의 요구다. 증상: **배율 0.40 에서 방 위젯이 58x30px 인데 보스방과
빈방이 똑같이 생겼다.** [`07`](07-level-design.md) §7.8 이 *"모양과 **색**으로 구분"*
이라 적었는데 색이라 부를 게 없었다.

**컨셉 선택과 무관하다** — 정보 설계 문제라 답이 거의 같다. 그래서 선택 전에 냈다.

### 몇 가지를 구분해야 하나 — 여섯이다 (줄지 않는다)

[`07`](07-level-design.md) §7.2.9 의 방 종류는 여섯이고, **가려지는 방이 없다.**
[`08`](08-ui-ux.md) §8.3.2 가 렉카 피드로 *"시야 시스템 · 미니맵 · 정찰 UI 가 전부 불필요"*
라 못 박았으므로 안개도 미탐색 상태도 없다. 여섯이 **항상 전부 보인다.**

다만 가지 수는 다른 데서 줄었다.

**① 빈방은 표시가 없다.** 「통로 역할」(§7.2.9)이라 판의 **바탕 상태**다.
모든 종류에 표시를 주면 판 전체가 무늬로 덮여 정작 아무것도 도드라지지 않는다.

**② 보스는 새 기호가 아니라 겹쳐 찍기다.** 「고위험 고보상」이 곧 **위협 + 보상**이다.
기호가 늘면 외울 것이 늘지만 겹쳐 찍기는 **읽는 법이 저절로 따라온다.**

그래서 원자는 **셋**뿐이다.

| 원자 | 뜻 | 어디에 |
| --- | --- | --- |
| **쐐기** | 보상이 있다 | 오른쪽 위 모서리를 채운 삼각형 |
| **빗금 띠** | 위협이 있다 | 아래 모서리를 따라 흐르는 띠 |
| **결손** | 판의 출입구다 | 옆구리를 물어낸 자리 |

| 종류 | 쐐기 | 빗금 | 결손 |
| --- | --- | --- | --- |
| 빈방 | | | |
| 귀중품 | O | | |
| 위험 | | O | |
| **보스** | **O** | **O** | |
| 입구 | | | 왼쪽 |
| 탈출 | | | 오른쪽 |

**구역이 갈려 있어야 겹쳐 찍기가 읽힌다** — 쐐기는 위 모서리, 빗금은 아래 모서리,
숫자는 복판. 셋이 서로 자리를 다투지 않는다.

### 색은 몇 개 쓸 수 있나 — **둘이다**

이게 진짜 제약이었다. 다섯 컨셉이 각자 **색을 셋씩만** 갖고 있어서(판 · 강세 · 글자)
역할 여섯에 색을 하나씩 배정할 방법이 없다. 게다가 명도를 벌리면 **방 안의 위험도
숫자와 싸운다** — 숫자는 늘 거기 있고 무료 · 정확한 정보다
([`13`](13-information-design.md) §13.6).

> **그래서 색으로 종류를 가르지 않는다. 형태가 가르고 색은 거든다.**
> `07` §7.8 이 「모양과 색」이라 한 것도 이 뜻으로 읽었다.

**결손이 가장 튼튼한 원자다.** 실루엣을 바꾸므로 채우기와 빗금이 뭉개지는 크기에서도
「옆구리가 파인 방」은 남는다. 그래서 판에서 **가장 먼저 찾아야 하는 탈출구**
(§7.2.9 — 최소 하나는 민첩 0 으로 도달 가능)가 그 원자를 받는다.

### 처지 셋은 종류와 직교한다

보스방이면서 못 가는 방일 수 있으므로 따로 잡았다.

| 처지 | 어떻게 |
| --- | --- |
| 갈 수 있다 | 판을 채운다 |
| **못 간다** | **채우지 않고 윤곽만 남긴다** |
| 여기 있다 | 강세색으로 채운다 |

**못 가는 방을 흐리게 칠하지 않는다.** 흐린 채움은 「덜 중요한 방」으로 읽히는데,
못 가는 방의 위험도는 합에 그대로 들어가므로 **덜 중요하지 않다**
([`07`](07-level-design.md) §7.2.7). 채움이 없으면 「설 수 없는 자리」가 되고
그건 사실과 맞는다.

### 역할 → 토큰 (컨셉이 정해지면 값만 꽂는다)

컨셉이 미정이고 다섯 후보의 배색이 전부 다르므로 방 위젯은 **색 값을 직접 들고 있지
않다.** `RoomPalette` 가 역할만 정하고 값은 컨셉에서 가져온다 —
값의 단일 출처는 각 모션 클래스이고, 여기에 색을 복사해 두지 않는다.

| 역할 | 무엇으로 |
| --- | --- |
| 바탕 · 숫자 | 판 색 · 글자 색 |
| **보상**(쐐기) | **강세 색** |
| **위협**(빗금) | 글자 색 |
| **출입구**(결손) | **색 없음** — 실루엣이 말한다 |

보상만 강세를 쓴다. 둘 다 강세면 보스방에서 쐐기와 빗금이 같은 색이 되어 겹쳐 찍기가 죽는다.

### 만들면서 걸린 것 셋 — 전부 테스트로 잠갔다

| 걸린 것 | 왜 | 고친 것 |
| --- | --- | --- |
| 빗금을 왼쪽 아래 구석에 셋만 두었더니 **58x30 에서 거의 안 보였고** 숫자와 자리를 다퉜다 | 구석은 면적이 없다 | **아래 모서리 전체를 따라 흐르는 띠**로 바꿈 |
| 확대하면 빗금이 겹쳐 **마름모 무늬**가 됐다 | 띠 두께를 고정 px 로 잡았다 | 판 높이에 대한 **비율**로 바꿈 |
| 「여기 있다」에서 글자가 묻혔다 | 채움을 강세로 바꾸고 글자를 판 색으로 **뒤집는 방향을 고정**했는데, 강세가 밝은 컨셉(SHEAR · HOLD)과 어두운 컨셉(SLAM · SQUASH)이 섞여 있다 | 판 색과 글자 색 중 **대비가 큰 쪽을 매번 재서** 고름 |
| 못 가는 방이 **통째로 사라졌다** (밝은 판 컨셉) | 채움이 없으니 윤곽선이 판 위가 아니라 **무대 위**에 놓이는데 글자 색을 그대로 썼다 | 무대 색에 대해 읽히는 색을 고름 |

마지막 둘은 **테스트가 먼저 잡았다.** 다섯 배색 x 세 처지를 눈으로 다 볼 수 있지만,
「어느 배색에서 대비가 몇인가」는 세어 보지 않으면 놓친다.

### 확인 화면

```
godot --path . res://src/ui/kit/room_matrix.tscn
```

`1`~`5` 로 배색을 갈아 끼운다. 위쪽은 **실제 크기 58x30px** 이고
아래 4배 확대 줄은 세공 확인용이다 — **판정은 실제 크기 줄에서 한다.**
「배율 0.40 에서 똑같이 생겼다」가 문제였으므로 확대해서 보면 답이 됐는지 알 수 없다.

```
godot --path . --resolution 1180x620 -s res://tools/capture_rooms.gd -- .renders/rooms
```

### 이 문서가 넘기는 것

**규격과 토큰 구조만 낸다.** 실제 방 위젯 적용은 통합자가 붙인다.
`RoomMark` 와 `RoomPalette` 는 노드에 의존하지 않는 순수 클래스라 그대로 가져다 쓸 수 있다.
