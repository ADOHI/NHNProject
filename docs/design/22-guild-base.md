# 22. 길드 아지트와 게이트

> **상태: 첫 조각.** 아웃게임 한 바퀴가 도는 데 필요한 최소만 세운다.
> 시설 종류와 수치는 **전부 잠정**이며 통째로 갈릴 것을 전제로 짰다.
>
> 이 문서는 코드보다 먼저 쓰였고, 구현 중 판단이 바뀔 때마다 여기를 고쳤다.

---

## 22.0 세계관 — 게이트를 여는 것은 인간이 아니다

[`02-overview.md`](02-overview.md) §2.6.1 이 확정한 것을 이 시스템의 눈으로 다시 읽는다.

> **다른 차원의 존재들이 유희를 위해 게이트를 연다.**
> **인간은 거기서 건져 올 것이 있으니 목숨을 걸고 들어간다.**

| 말 | 무엇 | 코드 |
| --- | --- | --- |
| **게이트** | **그놈들이 연** 문. 등급과 정보 공개 수준을 가지는 아웃게임 대상 | `src/core/gate/` (새로 만듦) |
| **던전** | 게이트 안쪽의 공간. 방 그래프 | `src/core/dungeon/` (기존 그대로) |

### 이 시스템이 그 설정에서 받는 것 셋

**1. 게이트는 발생하는 것이 아니라 열리는 것이다.**
자연 현상이 아니라 **누가 일부러 여는 것**이다. 그래서 게이트 목록은
"이번에 그놈들이 무엇을 열어 두었는가" 이고, 우리가 통제할 수 없다.
길드가 할 수 있는 일은 **열린 것 중에서 고르는 것뿐이다.**

**2. 등급은 그놈들이 얼마나 공들여 열었는가다.**
크게 연 판일수록 안이 넓고(방이 많고) 건질 것이 많으며 그만큼 험하다.
등급 하나가 던전 크기와 보상 배수를 함께 정하는 것은 그래서다 (`GateRank`).
난이도와 보상이 갈라지면 "위험도 <-> 보상" 이라는 단일 저울이 깨진다
([`06`](06-progression.md) §6.3).

**3. 게이트는 만료된다 — 그놈들이 흥미를 잃으면 닫힌다.**
원정을 한 번 다녀오면 **목록이 통째로 갈린다** (`Guild.board_seed_for`).
이것이 "지금 고르지 않으면 사라진다" 를 만들고, [`14-squad.md`](14-squad.md) §14.6 의
"세계가 계속 돌아간다 — 빈손으로 나오면 상대적으로 뒤처진다" 와 같은 압력을 아웃게임에 준다.
**별도의 만료 타이머를 만들지 않았다.** 원정 횟수가 곧 시간이다.

### 길드는 그놈들과 거래하지 않는다

**아지트에 그놈들과의 관계 같은 것은 없다.** 그런 설정은 아직 없고, 지어내지 않았다.
길드는 그냥 이익을 보고 들어가는 인간 조직이다 — 시설 셋(공방 · 정보실 · 접선처)은
전부 인간끼리의 일이다.

### 미정 — 정보의 출처

[`02-overview.md`](02-overview.md) §2.6.1.4 가 **"인간이 그놈들의 존재를 얼마나 아는가"** 를
미정으로 남겼다. 이것이 정보실에 직접 걸린다.

> 정보실이 게이트를 "정찰" 하고 "해부" 한다고 할 때, **그 정보는 어디서 오는가.**
>
> - 인간이 직접 관측하는가 (선발대 · 계측 · 축적된 통계)
> - 그놈들이 흘려 주는가 (중계의 부산물 — 렉카가 그놈들 중 하나라면 가능하다)
> - 둘 다인가

**정하지 않았다.** 코드는 세 경우 어디로 가도 그대로 쓸 수 있게 짰다 —
`GateDisclosure` 는 **정보실 인원 수(`int`)만** 받고 출처를 모른다.
정해지면 문구만 바뀐다.

### 플레이어의 이중 역할

플레이어는 **길드 마스터**이자 **플레이어블 캐릭터 한 명**이다 (§2.6.1.3).

이 이중 역할이 아웃게임/인게임 분리를 설정으로 정당화한다.
아지트에서 게이트를 고르고 누굴 보낼지 정하는 것은 마스터의 판단이고,
던전 안에서 스쿼드 하나를 굴리는 것은 캐릭터의 몫이다.

### 리네임하지 않는다

`src/core/dungeon/` 은 **옳은 이름이다.** 게이트물에서도 게이트와 던전은 다른 것이고,
`DungeonGraph` · `DungeonRun` 이 다루는 것은 정확히 안쪽 공간이다.
게이트는 `src/core/gate/` 에 **새로 만든다.**

> 주의: `src/proto/unit_move/` 에 `gate_cells` 라는 소문자 지역 변수가
> "좁은 문" 뜻으로 이미 있다. 층이 달라 충돌은 아니다. 그 파일은 건드리지 않았다.

## 22.1 이번 범위 — 한 바퀴만

**아지트 전체를 만들지 않는다.** 이번에 세우는 것은 이 한 바퀴다.

```
게이트 목록  →  게이트 선택  →  스쿼드 편성 (데려갈 자 / 남길 자)
                                        ↓
                                   던전 진입  (기존 SampleDungeons 그대로)
                                        ↓
                                     결과
                                        ↓
                                   아지트 정산  →  다시 게이트 목록
```

[`08-ui-ux.md`](08-ui-ux.md) §8.1 의 화면 흐름 중 `주둔지 → 던전 선택 → 던전 → 결과 정산`
구간이고, [`16-build-order.md`](16-build-order.md) §16.5 의 5번(아웃게임 최소 껍데기)과
§16.7 의 3~4번을 **앞당겨 뼈대만** 세우는 셈이다.

**연결이 이번 일이다.** 던전 안쪽은 기존 것을 그대로 쓴다.

### 범위 밖 — 일부러 비워 둔 것

| 비워 둔 것 | 왜 |
| --- | --- |
| 관계도 · 영입 실행 | [`05`](05-rules.md) §5.10 이 미구현. 없는 것을 지어내지 않는다 (§22.7) |
| 장비 세팅 | 판 단위 축은 이번 축이 아니다 ([`06`](06-progression.md) §6.1) |
| 인게임 화면 연결 | 다른 레인이 작업 중. `main.tscn` 에 붙이지 않았다 |
| 세계 갱신 · 뉴스 | [`15-world.md`](15-world.md). 정산이 붙을 자리만 있다 |
| 계열별 정보 스킬의 **실제 효과** | 인게임 정보 시스템이 아직 스킬 형태가 아니다 (§22.7) |

## 22.2 대원과 `Actor` 의 관계 (핵심 결정)

**대원은 `Actor` 가 아니다. 대원은 아웃게임 개체(`GuildMember`)이고,
편성된 대원들이 접혀서 `Actor` 하나가 된다.**

```
GuildMember × N  ──(SquadStats)──▶  Squad  ──▶  Actor 하나 (Kind.PLAYER_SQUAD)
   아웃게임                                          인게임 판 위의 말
```

### 근거 셋

1. **판 위의 말은 하나다.** [`14-squad.md`](14-squad.md) §14.2 가 확정한 규칙이다.
   대원 하나당 `Actor` 하나를 만들면 방마다 개체 수가 인원만큼 늘어나고,
   그 순간 [`13`](13-information-design.md) §13.5 의 "개체 수" 정보가 뜻을 잃는다.
   위험도 합도 갈라진다.
2. **`Actor` 는 던전 안의 개념이다.** 대원은 시설 배치 · 영입 · 관계처럼
   던전이 알 필요 없는 속성을 가진다. 그것을 `Actor` 에 붙이면
   `src/core/dungeon/` 이 아웃게임을 알게 되고, 그때부터 던전을 단독으로 테스트할 수 없다.
3. **접는 규칙이 이미 있다.** `SquadStats` 가 전투력=합 · 민첩=평균(내림)을
   이미 못 박아 두었다(§14.3.1). 대원을 `Actor` 로 두면 이 클래스가 쓸 데가 없어진다 —
   **먼저 만들어 둔 것이 쓰이는 자리가 여기다.**

### 접히는 순간이 편성이다

`Squad.to_actor()` 가 유일한 변환 지점이다. 던전에 들어가는 순간 대원 개개인은 사라지고
전투력과 민첩 두 숫자만 남는다. 이것이 §14.2 의 "모든 스쿼드 속성이 편성에서 결정되고,
던전 안에서는 바뀌지 않는다"를 코드로 옮긴 형태다.

### 기존 코드를 건드리지 않는 방법

`SampleDungeons.create_run()` 은 자체 플레이스홀더 스쿼드를 세운다.
시그니처를 바꾸지 않기 위해, **판을 만든 뒤 그 말을 우리 스쿼드로 갈아 끼운다**
(`Expedition._swap_in_squad()`). 입구 위험도 조정(`_trim_entrance_threat`)은
스쿼드를 놓기 전에 끝나므로 결과가 달라지지 않는다.

## 22.3 직업 계열 — 잠정 5계열

[`14-squad.md`](14-squad.md) §14.4.1 은 **최소 5계열**만 정하고 이름을 미정으로 두었다.
정원이 계열 수보다 적어야 한다는 §14.4.3 을 코드로 옮기려면 계열이 실체가 있어야 해서,
**잠정으로 다섯을 잡는다.** 이름과 수치는 언제든 갈린다.

| 계열 | 성향 | 이 계열의 "눈" (미구현) |
| --- | --- | --- |
| 전투 | 전투력 높음 · 민첩 낮음 | 이길 수 있는 방인지 감이 온다 |
| 정찰 | 전투력 낮음 · 민첩 높음 | 인접 방의 개체 수가 보인다 |
| 기공 | 중간 | 고도 차이와 통로 상태를 읽는다 |
| 교섭 | 전투력 낮음 | 상대의 성향 단서를 얻는다 |
| 감식 | 중간 | 고가치 방의 위치를 좁힌다 |

**"눈"은 문구만 있고 효과가 없다.** §14.4.2 가 요구하는 "계열마다 다른 각도의 눈"은
인게임 정보 시스템이 스킬 형태를 갖춘 뒤에 붙는다. 지금 지어내면 그때 전부 버려진다.

### 정원

> **스쿼드 정원 < 계열 수** ([`14`](14-squad.md) §14.4.3)

계열이 5 이므로 정원은 **3** 에서 시작하고, 아지트 레벨이 오르면 **4** 까지 늘어난다.
5 를 넘지 않는다 — 넘는 순간 편성이 결정이 아니게 된다.

## 22.4 시설과 배치 — 삼국지식 내정

**대원을 시설에 배치하면 효과가 붙는다.** 배치가 결정이 되는 이유는 하나다.

> **던전에 데려간 대원은 시설 효과를 내지 못한다.**

정원이 계열 수보다 적으므로 데려갈 사람을 고르는 순간 남는 사람이 생기고,
남는 사람을 어디에 둘 것인가가 다음 결정이 된다. 두 결정이 같은 인원 풀을 놓고 다툰다.

| 시설 | 배치 효과 | 구현 |
| --- | --- | --- |
| **공방** | 아지트 업그레이드 속도 상승 | 정산 시 진척도 가산 |
| **정보실** | 게이트 정보를 더 많이 본다 | 게이트 공개 수준 상승 (§22.5) |
| **접선처** | 영입 후보를 먼저 찾는다 | 정산 시 후보 목록에 이름이 뜬다 |

**세 시설은 방향이지 확정이 아니다.** 시설 종류를 늘리거나 바꿀 때
`Facility.Kind` 와 `GuildBalance` 두 곳만 손대면 되도록 짰다.

### 수치는 한곳에서 나온다

**모든 수치는 `src/core/guild/guild_balance.gd` 에 있다.**
[`06-progression.md`](06-progression.md) §6.5 가 요구한 "조정할 수치는 한 곳에" 다.
잠정값이므로 통째로 교체될 것을 전제로, 계산식까지 이 파일에 두었다 —
값만 모으고 식을 흩어 두면 결국 식을 고쳐야 해서 같은 일이 된다.

## 22.5 게이트

게이트 하나가 드는 것.

| 칸 | 내용 |
| --- | --- |
| 등급 | E · D · C · B · A. 안쪽 던전의 크기와 보상 배수를 정한다 |
| 이름 | 표시명 |
| **정보 공개 수준** | 정보실 배치 인원이 정한다 |
| **던전 씨앗** | 고정. 같은 게이트는 언제나 같은 던전을 낸다 |

### 정보 공개 수준

[`06-progression.md`](06-progression.md) §6.2 는 **정보 확장 계열이 이 게임과 가장 잘 맞는다**고
적었다. 주둔지 강화가 수치가 아니라 **판단 재료**를 늘리는 쪽으로 가야 한다는 뜻이다.
정보실이 그 자리를 맡는다.

| 수준 | 조건 | 보이는 것 |
| --- | --- | --- |
| 소문 | 정보실 인원 0 | 이름 · 등급 |
| 정찰 | 1명 | + 대략적인 방 개수 |
| 해부 | 2명 이상 | + 실제 방 개수 · 고가치 방 수 · 보스 유무 |

**해부 수준일 때만 설계도를 실제로 생성한다.** 소문·정찰 단계에서 미리 생성해 두면
안 볼 정보를 만드느라 판을 통째로 돌리게 된다. 씨앗이 고정이므로
나중에 생성해도 같은 판이 나온다 — 미리 만들 이유가 없다.

### 게이트 목록과 만료

`GateBoard` 가 `SampleDungeons` 로부터 "판을 만든다"를 넘겨받는다.
단 **던전 생성은 기존 것을 그대로 쓴다** — `Gate.create_run()` 은
`SampleDungeons.create_run(dungeon_seed, size)` 를 호출할 뿐이다.

같은 목록 씨앗 + 같은 길드 등급 → 같은 게이트 목록.
게이트마다 던전 씨앗이 목록 씨앗과 자리 번호에서 결정론적으로 파생된다.

**목록 씨앗은 정산이 끝난 원정 수에서 나온다** (`Guild.board_seed_for`).
한 바퀴를 돌 때마다 목록이 갈리고, 그것이 §22.0 의 만료다 —
그놈들이 흥미를 잃은 문은 닫힌다. 타이머도 만료 필드도 만들지 않았다.
**원정 횟수가 곧 시간이다.**

### 방향 의존은 한쪽뿐

> **`gate/` 는 `guild/` 를 모른다. `guild/` 가 `gate/` 를 안다.**

정보실 인원 수는 `int` 로 넘어간다. 이렇게 두면 게이트는 길드 없이 단독으로 테스트되고,
나중에 정보 공개 수준을 다른 것(아이템 · 장비)이 올리게 돼도 게이트를 고칠 필요가 없다.

## 22.6 정산 — 이 시스템의 심장

**한 판 다녀오면 배치 결과가 적용된다.**

```
ExpeditionReport (한 판의 결과)
        +
Guild (자원 · 아지트 레벨 · 배치표)
        ↓
GuildSettlement.apply()
        ↓
SettlementResult (무엇이 얼마나 변했는가)
```

| 정산 항목 | 계산 |
| --- | --- |
| 자금 | 탈출 성공 시에만. 턴 수 × 등급 배수 |
| 아지트 진척 | 기본 + 공방 잔류 인원 × 인당 가산 |
| 아지트 레벨 | 진척이 문턱을 넘으면 오른다 (정원 · 게이트 등급 상한에 영향) |
| 영입 후보 | 접선처 잔류 인원 수만큼 새 이름이 뜬다 |

**실패는 빈손 귀환이다.** [`14-squad.md`](14-squad.md) §14.6 확정 사항 —
대원은 죽지 않고, 전리품만 잃는다. 그래서 실패해도 **아지트 진척은 들어온다**
(공방에 남은 사람은 계속 일했다). 이것이 §14.6 의 "실패는 상대적으로 뒤처지는 것"과 맞는다.

### 두 번 적용되지 않는다

정산은 **길드가 처리한 원정 번호를 기억한다.** 같은 보고서를 다시 넣으면 `null` 이 나온다.

보고서 쪽에 플래그를 두는 방식도 있지만, 그러면 보고서를 복제해 오면 뚫린다.
길드 쪽 장부가 더 강한 보증이라 그쪽을 택했다. 보고서에도 표시는 남기지만
**판단의 근거는 장부다.**

### 성격을 섞지 않는다

[`06-progression.md`](06-progression.md) §6.1 의 세 축을 그대로 지킨다.

| 축 | 이번 구현에서 |
| --- | --- |
| 주둔지 — 영구 · 누적 | 아지트 레벨 · 진척. **실패해도 잃지 않는다** |
| 스쿼드 — 그 사이 | 대원 목록. 지금은 잃지 않는다 (§14.6) |
| 장비 — 판 단위 | **없다.** 이번 범위 밖 |

자금은 주둔지 축의 재료다. 잃는 것은 **이번 판에서 벌었을 자금**이지 가진 자금이 아니다.

## 22.7 자리만 비워 둔 것

**없는 것을 지어내지 않았다.** 아래는 자리만 있고 동작이 없다.

| 자리 | 지금 상태 | 무엇이 있어야 채워지는가 |
| --- | --- | --- |
| 영입 실행 | 후보 목록에 이름만 뜬다. `Guild` 에 영입 함수가 없다 | 관계도([`05`](05-rules.md) §5.10) |
| 계열별 정보 스킬 | 문구만 있고 효과 없음 | 인게임 정보 시스템의 스킬 형태 |
| 이탈 | 없음 | [`14`](14-squad.md) §14.5 가 미정으로 둔 항목 |
| 세계 갱신 | 없음 | [`15-world.md`](15-world.md) |
| 대원 성장 | 없음 | 정해진 바 없음 |
| **게이트 정보의 출처** | `GateDisclosure` 가 인원 수만 받고 출처를 모른다 | [`02`](02-overview.md) §2.6.1.4 — 인간이 그놈들을 얼마나 아는가 |
| 그놈들과의 관계 | **없다.** 길드는 거래하지 않는다 | 설정 자체가 아직 없다 (§22.0) |

**영입을 지금 넣지 않은 이유**는 [`06-progression.md`](06-progression.md) §6.1 이
"영입은 자원만으로 되지 않고 던전에서 쌓은 관계를 요구한다"고 확정했기 때문이다.
자원으로 사는 영입을 임시로 넣으면 그 확정이 코드에서 뒤집힌다.
**후보를 찾는 데까지가 접선처의 일이고, 그 다음 칸은 관계도의 자리다.**

## 22.8 화면 — 도형만 (임시)

`src/ui/base/base_screen.tscn` 은 **조형이 아니라 배선을 보여 주는 화면**이다.
다른 레인이 `src/ui/kit/` 에서 버튼과 팝업의 조형을 찾고 있고,
그것이 나오면 이 화면의 표현은 전부 버려진다.

- **사각형 · 선 · 글자뿐이다.** 색 · 모양 · 모션에 시간을 쓰지 않았다
- **`main.tscn` 에 연결하지 않았다.** 독립 씬으로 따로 실행한다
- 던전 안쪽은 판으로 그리지 않는다 — 갈 수 있는 방이 버튼 목록으로 뜨고,
  몇 턴을 굴린 뒤 결과 버튼을 누른다. 인게임 화면은 다른 레인의 몫이고,
  여기서는 **연결점만** 보인다

```bash
godot --path . res://src/ui/base/base_screen.tscn
```

### 22.8.1 한 화면에 다 놓는다 — 탭으로 나누지 않는다

**배치와 편성이 같은 인원을 놓고 다투는 것이 이 화면의 전부다** (§22.4).
둘을 다른 탭에 두면 그 다툼이 보이지 않는다. 데려갈 사람을 고르는 동안
어느 시설이 비는지가 **같은 화면 안에서 동시에** 움직여야 한다.

그래서 기둥 셋을 나란히 세운다.

```
+---------------------+------------------------+---------------------------+
| 아지트              | 대원                   | 게이트                    |
|                     |                        |                           |
| 길드 상태           | 대원 5명               | 지금 보이는 수준          |
|  등급 자금 진척     |  데려간다 / 배치        | 게이트 4개                |
|                     |  계열 전투 민첩         |  이름 + 미리보기 줄들     |
| 시설 셋             |                        |                           |
|  공방 정보실 접선처 | 편성 요약              | 원정                      |
|  일하는 인원 n/2    |  데려갈 자 / 남길 자    |  진입 이동 결과 정산      |
|  출전자는 흐려진다  |  스쿼드 전투력 민첩     |                           |
|                     |                        | 기록                      |
| 영입 후보           |                        |  정산이 쌓인다            |
+---------------------+------------------------+---------------------------+
```

**왼쪽 기둥이 오른쪽 기둥에 반응한다.** 가운데에서 "데려간다"를 켜면

1. 왼쪽 시설 칸의 그 대원이 **출전**으로 흐려지고 일하는 인원이 줄고,
2. 그 대원이 정보실 소속이면 오른쪽 게이트의 **미리보기 줄이 그 자리에서 짧아진다.**

정보실 인원을 데려가면 목록이 도로 흐려진다는 §22.5 의 규칙이
설명문이 아니라 **버튼 하나로 눈에 보이는 것**이 여기서다.

### 22.8.2 화면은 아무것도 계산하지 않는다

문장은 전부 코어가 만든 것을 그대로 쓴다 (`conventions.md` §3.1).

| 화면에 뜨는 것 | 어디서 |
| --- | --- |
| 길드 등급 · 자금 · 진척 · 정원 | `Guild` · `GuildBalance` |
| 시설 이름과 효과 문구 | `Facility.label` · `Facility.note` |
| 일하는 인원 | `Guild.staff_at(kind, 출전자)` |
| 대원 한 줄 | `GuildMember.summary()` |
| 스쿼드 전투력 · 민첩 | `Guild.form_squad()` -> `Squad.threat()` · `agility()` |
| 남길 자 | `Expedition.garrison_ids()` 와 같은 규칙 (편성 전에는 화면이 같은 뺄셈을 한다) |
| 게이트 공개 수준 | `Guild.gate_disclosure(출전자)` |
| 게이트 미리보기 | `Gate.preview_lines(level)` |
| 원정 결과 한 줄 | `ExpeditionReport.summary()` |
| 정산 결과 줄들 | `SettlementResult.lines()` |

화면이 스스로 만드는 문자열은 **버튼 이름과 칸 제목뿐이다.**

### 22.8.3 한 바퀴는 버튼 다섯 개다

```
게이트 고른다  ->  데려간다 켠다  ->  들어간다  ->  방 버튼으로 몇 걸음
                                                          ->  결과 (탈출 / 쓰러짐 / 회수)
                                                          ->  정산한다  ->  다음 원정
```

- **결과를 흉내 내지 않았다.** 실제로 `Expedition.enter()` 가 `SampleDungeons` 로 판을 세우고,
  방을 누르면 `DungeonRun.move_player()` 가 턴을 올린다. 그 턴 수가 전리품이 된다
  (`GuildBalance.loot_for`)
- 결과 세 갈래는 버튼으로 고른다. 승패 판정은 인게임의 몫이고 이 화면의 일이 아니다
- **"다음 원정" 을 누르면 게이트 목록이 통째로 갈린다** (`Guild.board_seed_for`).
  그것이 §22.0 의 만료다 — 갔다 오면 아까 그 문은 없다

### 22.8.4 파일을 나눈 기준 — 기둥 하나에 파일 하나

```
src/ui/base/
├── base_widgets.gd        사각형 · 선 · 글자를 만드는 static 공장
├── base_box.gd            제목 한 줄이 붙은 사각형 하나
├── guild_panel.gd         왼쪽 기둥 — 길드 상태 · 시설 · 영입 후보
├── member_panel.gd        가운데 기둥 — 대원 목록 · 편성 요약
├── gate_panel.gd          오른쪽 위 — 게이트 목록
├── expedition_panel.gd    오른쪽 아래 — 진입 · 이동 · 결과 · 정산 · 기록
├── base_screen.gd         코어를 들고 기둥 셋을 잇는다
└── base_screen.tscn

tools/capture_base_screen.gd   한 번 띄워 한 바퀴를 돌리고 단계마다 캡처 (§22.8.6)
test/unit/test_base_screen.gd  같은 손놀림을 헤드리스로 돌리는 배선 테스트
```

기둥마다 파일을 나눈 이유는 **버려질 단위가 그것이기 때문이다.**
`src/ui/kit/` 의 조형이 나오면 기둥 하나씩 갈아 끼우게 되는데,
한 파일에 몰아 두면 그때 전부를 한 번에 뜯어야 한다.

패널들은 **길드를 바꾸지 않는다.** 눌린 것을 시그널로 올리고
`BaseScreen` 이 코어를 부른 뒤 다시 그린다 (Godot 의 "call down, signal up").

### 22.8.5 만들면서 갈린 판단 둘

**하나. 글자에 줄바꿈을 기본으로 켜지 않는다.**
처음에는 모든 글자에 `AUTOWRAP_WORD_SMART` 를 켰다. 그러자 버튼 줄에 놓인
짧은 글자("배치")가 폭을 못 받아 **한 글자씩 세로로 쌓였다.**
폭이 정해진 본문 줄만 `BaseWidgets.wrap()` 으로 따로 연다.

**둘. 잠긴 버튼 두 종류를 색으로 가른다.**
배치 버튼이 잠기는 이유는 둘이다 — **지금 여기 있어서**와 **정원이 차서**다.
둘 다 흐리게 두면 "왜 안 눌리는가"가 구분되지 않는다.
지금 있는 곳만 `font_disabled_color` 를 밝게 준다.

### 22.8.6 캡처는 한 번 띄워서 몰아 찍는다

```bash
godot --path . -s res://tools/capture_base_screen.gd
```

`tools/capture_base_screen.gd` 가 **실제 버튼을 눌러** 한 바퀴를 돌리고
단계마다 화면을 `.captures/` 에 남긴다 (시작 - 배치 - 편성 - 던전 - 결과 - 정산 - 다음 목록).

캡처마다 창을 새로 띄우면 GL 컨텍스트를 그때마다 새로 만들게 되고,
그것이 드라이버를 흔들어 세션이 끊긴 적이 있다 (`CLAUDE.md` — GPU 를 나눠 쓴다).
같은 손놀림을 `test/unit/test_base_screen.gd` 가 헤드리스로도 돌린다 —
**화면이 안 뜨는 것은 테스트가 먼저 잡고, 어떻게 보이는가만 눈으로 본다.**

### 22.8.7 `src/ui/style/` 도 `src/ui/kit/` 도 쓰지 않았다

`UiTokens` 도 [`20-ui-kit.md`](20-ui-kit.md) 의 `KitTokens` 도 끌어 쓰지 않고
`base_widgets.gd` 에 색 몇 개를 따로 두었다.
**둘 다 아직 방향이 정해지지 않은 실험이다.** 이름이 갈리면 이 화면이 같이 깨지고,
그때 고쳐야 할 것은 조형이 아니라 배선인데 배선까지 멈춘다.
**어차피 버려질 화면이 살아 있는 코드를 붙잡고 있으면 안 된다.**
조형이 정해지면 기둥 하나씩 갈아 끼운다.

## 22.10 임의로 내린 판단

물어볼 수 없어서 **가장 단순한 쪽**을 고른 것들. 근거를 남긴다.

| 판단 | 고른 것 | 왜 |
| --- | --- | --- |
| 길드 등급과 아지트 레벨 | **같은 값** | 둘을 나누면 두 수치가 같은 일을 한다. 갈라질 이유가 생기면 그때 나눈다 |
| 시설 정원 | 시설당 2명 | 무제한이면 배치가 결정이 아니다. 값은 `GuildBalance` 에 있다 |
| 한 대원 = 한 시설 | 겸직 없음 | 겸직을 허용하면 "누굴 어디에"가 아니라 "전부 다"가 된다 |
| 실패 시 아지트 진척 | **들어온다** | 남은 사람은 계속 일했다. §14.6 의 "빈손 귀환" 은 전리품 얘기다 |
| 게이트 목록 크기 | 4 | 한 화면에 놓고 비교할 수 있는 최소. `GuildBalance` 에 있다 |
| 게이트 만료 | 원정 한 번 = 목록 한 번 갈림 | 아웃게임에 흐르는 시간은 원정 횟수뿐이다. 시계를 따로 만들지 않았다 |
| 원정 중도 포기 | 넣었다 (`RECALLED`) | 임시 화면에서 결과 분기를 눌러 볼 수 있어야 한다 |
| 스쿼드 표시명 | 고정 문자열 | 길드 이름을 짓는 기능이 없다. 생기면 여기서 가져온다 |
