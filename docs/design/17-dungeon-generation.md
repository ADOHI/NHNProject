# 17. 던전 절차 생성

> **상태: 설계 확정 / 수치 잠정.**
> 던전은 **모두 절차적으로 생성**한다. 수제작 던전은 두지 않는다.
> 공간 규칙(고도 · 방 종류)은 [`07-level-design.md`](07-level-design.md) §7.2.6~7.2.9 참고.

---

## 17.1 생성기의 진짜 요구사항

**"재미있는 판"이 아니라 "추리가 성립하는 판"을 만드는 것이다.**

이 게임에서 던전은 이동 경로가 아니라 추리판이다([`07`](07-level-design.md) §7.2).
따라서 생성기의 난이도는 만드는 쪽이 아니라 **못 쓸 판이 나오지 않게 하는 쪽**에 있다.

| 실패한 판 | 왜 못 쓰나 |
| --- | --- |
| 탈출구에 도달할 수 없다 | 시작하자마자 진 판이다 |
| 숫자만으로 정답이 나온다 | 추리가 아니라 계산이 된다 |
| 단서가 전혀 없다 | 추리가 아니라 도박이 된다 |
| 입구 옆이 즉사급 | 판단할 기회 자체가 없다 |
| **선이 서로 가로지른다** | 판이 지저분해 읽히지 않는다. 읽히지 않는 판은 추리할 수 없다 |
| **방이 한쪽에 뭉친다** | 뭉친 곳은 겹쳐 보이고 빈 곳은 판을 헛돌게 만든다 |

아래 두 줄이 이번에 추가된 요구사항이고, 그 둘 때문에 파이프라인을 통째로 뒤집었다.

## 17.2 연결 차수가 곧 정보량

인접 위험도 합은 **내가 선 방의 연결 차수**에 따라 정보량이 달라진다.
지뢰찾기에서 인접 칸 수가 정보량을 정하는 것과 같다.

| 내 방의 차수 | 보이는 것 |
| --- | --- |
| 1 (막다른 방) | 합 = **그 한 방의 정확한 위험도.** 모호함 없음 |
| 2 | 두 방이 뭉친다 |
| 4+ | 거의 읽을 수 없다 |

**연결을 촘촘하게 짜면 어려워지고 성기게 짜면 쉬워진다.**
몬스터 수치를 건드리지 않고 난이도를 조절하는 손잡이다.
현재 평균 차수는 **2.9 안팎**이다(실측, §17.9).

### 막다른 방은 정찰 지점이다

차수 1인 방에 들어가면 앞방의 위험도를 **정확히** 알 수 있다.
대신 퇴로가 하나뿐이다.

> **정보가 정확한 대신 도망칠 길이 없다.**

위험 대 정보의 트레이드오프가 그래프 모양에서 저절로 나온다.
따라서 생성기는 막다른 방을 **없애지 않는다. 비율만 관리한다.**

**그런데 새 파이프라인에서는 오히려 막다른 방이 모자란다.**
블루 노이즈 위의 근접 그래프가 너무 고르기 때문이다(저절로는 5~10%).
그래서 §17.3 6단계에서 몇 군데를 **일부러 끊는다.** 목표 범위는 14~30% 다.

## 17.3 생성 절차 (개정)

```
1. 방 자리 뿌리기      — 푸아송 디스크 샘플링 (블루 노이즈)
2. 삼각분할            — 들로네 (Bowyer-Watson). 교차하지 않는 후보 간선을 얻는다
3. 입구 고르기         — 판 가장자리의 방 하나
4. 고도                — 입구에서의 거리 + 저주파 노이즈
5. 간선 선택           — RNG(+MST) 뼈대에 가브리엘 곁가지. 비용에 고도차와 깊이를 반영
6. 막다른 방 조정      — 비율이 모자라면 끊고 넘치면 잇는다
7. 탈출 경로 파기      — 입구에서 탈출구까지 지형을 바닥까지 깎는다
8. 방 종류 배치        — 필요 민첩과 거리로 귀중품 · 보스 · 탈출구를 놓는다
9. 존재 배치           — 몬스터 · NPC (SampleDungeons)
```

단계마다 파일이 다르다. `src/core/dungeon/generation/` 참고.

| 단계 | 파일 |
| --- | --- |
| 1 | `poisson_disk_sampler.gd` |
| 2 | `delaunay_triangulation.gd` |
| 5, 6 | `proximity_graphs.gd`, `dungeon_edge_selector.gd` |
| 4, 7 | `dungeon_terrain.gd` |
| 8 | `room_kind_planner.gd` |
| 전체 조립 | `dungeon_generator.gd` |

### 17.3.1 왜 순서를 뒤집었는가

이전 파이프라인은 **그래프를 먼저 만들고 나중에 2D 로 펼쳤다.**
층을 나누고, 척추를 놓고, 곁가지를 붙인 뒤, 힘 기반 완화(밀고 당기기)로 좌표를 잡았다.

그 순서에서는 두 문제가 **원리적으로** 풀리지 않는다.

| 증상 | 원인 |
| --- | --- |
| 간선이 서로 가로지른다 | 만들어 놓은 그래프가 평면 그래프라는 보장이 없다. 평면에 그릴 수 없는 그래프는 어떤 레이아웃으로도 교차를 풀 수 없다 |
| 방이 뭉치거나 빈다 | 배치가 연결 관계를 따라가므로 밀도를 직접 정할 수단이 없다 |

순서를 뒤집으면 둘 다 사라진다.

- **자리를 먼저 정하니 밀도를 직접 정한다.** 블루 노이즈가 최소 간격과 빈 구멍 없음을 동시에 준다.
- **후보 간선이 전부 삼각분할에서 나오니 무엇을 골라도 교차하지 않는다.**

두 번째가 특히 중요하다. **교차를 검사해서 걸러 내는 것이 아니라,
교차가 나올 수 없는 후보 집합에서만 고른다.** 실패하는 재시도 루프가 통째로 사라진다.

### 17.3.2 1단계 — 왜 푸아송 디스크인가

| 방식 | 최소 간격 | 빈 구멍 | 무작위 |
| --- | --- | --- | --- |
| 균등 난수 | 없음 (반드시 뭉친다) | 생긴다 | 있다 |
| 격자 | 있다 | 없다 | **없다** (판이 매번 똑같다) |
| **블루 노이즈** | **있다** | **없다** | **있다** |

Bridson 알고리즘을 쓴다. 격자를 깔아 근처 검사를 상수 시간으로 만들기 때문에
방 개수에 선형이다.

**개수를 정확히 맞추지는 못한다.** 목표에서 ±15% 안팎으로 흔들린다.
정확히 맞추려면 뽑은 점을 도로 지워야 하는데, 그러면 방금 보장한 "구멍 없음"이 깨진다.
화면에 "방 N개 안팎"으로 적는 이유다.

영역은 가로세로비 1.45 의 직사각형이다. 정사각형이 더 단순하지만
화면이 가로로 길어서 세로 여백만 남는다.

### 17.3.3 2단계 — 왜 들로네인가

삼각분할은 **정의상 평면 직선 그래프**다. 두 간선은 공유하는 끝점 말고는 만나지 않는다.
따라서 그 부분집합은 무엇을 골라도 교차하지 않는다.

`Geometry2D.triangulate_delaunay()` 를 쓰지 않고 Bowyer-Watson 을 직접 구현했다.
판의 평면성이 이 판정 하나에 걸려 있어 내부를 알고 있어야 하고,
축퇴(네 점이 한 원 위)를 어느 쪽으로 처리할지 우리가 정해야 하기 때문이다.
현재는 축퇴를 "외접원 바깥"으로 처리한다 — 안쪽으로 처리하면 삼각형이 과하게 지워져
구멍의 경계가 별 모양이 아니게 되고, 그러면 재삼각분할이 겹치는 삼각형을 만든다.

### 17.3.4 5단계 — 왜 MST + 무작위 복원이 아닌가

MST 는 **나무**라 순환이 없다. 순환이 없으면 판의 절반이 막다른 길이 되고
되돌아 나오는 길 말고는 선택지가 없어 추리판이 아니라 미로가 된다.
거기에 들로네 간선을 무작위로 되살리면 **모양이 지형과 무관해진다** —
어떤 곳은 삼각형이 빽빽하고 어떤 곳은 한 줄만 남는다.

그래서 중간 단계를 뼈대로 쓴다.

```
MST  ⊆  RNG(상대이웃)  ⊆  가브리엘  ⊆  들로네
```

| 그래프 | 조건 | 쓰임 |
| --- | --- | --- |
| RNG | a 에서도 b 에서도 ab 보다 가까운 제3의 방이 없다 | **뼈대.** 평균 차수 2.5 안팎, 순환 있음, EMST 를 포함해 연결성 보장 |
| 가브리엘 | ab 를 지름으로 하는 원 안에 다른 방이 없다 | **곁가지 후보** |
| MST | — | 연결성의 최후 보루 (부동소수 오차 대비) |

**RNG 를 고른 이유**는 조건이 자리에서 나오기 때문이다.
"둘 사이에 낀 방이 없을 때만 잇는다"는 규칙이라 결과가 자리와 어긋날 수 없고,
사람이 손으로 그린 길처럼 통로가 이웃한 방을 건너뛰지 않고 차례로 이어진다.
그러면서 EMST 를 포함하므로 **도달 가능성이 공짜로 따라온다.**

**곁가지를 가브리엘로 제한한 이유**는 다른 성질이다.
가브리엘 간선은 두 방 사이에 낀 방이 없다는 뜻이라, 그 선을 그어도
**엉뚱한 제3의 방을 스치고 지나가지 않는다.** 교차가 없어도 선이 방을 관통하면
이름도 숫자도 못 읽으므로(§17.6) 이것도 품질 기준이다.

MST 는 이론상 RNG 에 포함되므로 보통 아무것도 더하지 않는다.
부동소수 오차로 RNG 간선 하나가 떨어져 나가는 경우에만 다리를 놓는다.
그 한 번을 위해 검증-재시도 루프를 두는 것보다 이쪽이 싸고 확실하다.

### 17.3.5 곁가지의 비용 — 여기가 레벨 디자인이다

곁가지 후보마다 점수를 매겨 높은 것부터 채택한다.

```
점수 = 완만함 x 얕음 x 흔들림
완만함 = 1 / (1 + 고도차)
얕음   = 1 / (1 + 0.3 x 입구에서의 거리)
흔들림 = 0.55 ~ 1.45 사이의 난수
```

| 항 | 판에 나타나는 결과 |
| --- | --- |
| 완만함 | 가파른 통로가 드물어진다. 흔하면 필요 민첩이라는 등급 자체가 의미를 잃는다 |
| 얕음 | **입구 근처는 촘촘하고 깊은 곳은 성기다.** 첫 턴에 고를 것이 생기고(V7), 깊은 곳에 우회로가 적어져 귀중품이 값을 치르고 닿는 자리가 된다(V3) |
| 흔들림 | 같은 지형에서 늘 같은 곁가지가 나오지 않게 |

**의뢰받은 "방의 중요도와 고도를 고려"가 이 두 항이다.**
중요도를 따로 계산하지 않고 **입구에서의 거리를 대리값으로 쓴다.**
방 종류는 아직 정해지지 않았고(8단계), 깊은 곳이 곧 중요한 곳이기 때문이다.
순환 의존을 만들지 않으면서 같은 결과를 얻는 가장 단순한 방법이다.

### 17.3.6 고도는 지형이지 그래프가 아니다

이전 생성기는 고도를 **층**으로 매겼다. 층을 나누고 층마다 방을 놓는 방식이라
고도가 그래프 구조와 한 몸이었고, 간선을 하나 더 이으면 지형이 통째로 흔들렸다.

지금은 좌표에서 바로 만든다.

```
고도 = 입구에서의 거리 x 0.85 + 노이즈 x 2.6
```

순서가 **지형 먼저, 길은 그 위에** 가 되어 5단계가 고도차를 비용으로 볼 수 있다.
그리고 입구는 언제나 판에서 가장 낮다 — "내려가는 것은 자유"라는 규칙이
입구를 향한 방향과 같은 뜻이 되어야 지도가 읽힌다([`07`](07-level-design.md) §7.2.6.2).

**탑뷰에서 고도는 배치에 쓰지 않는다.** Y 축은 고도가 아니다.
고도를 눈으로 보여 주는 것은 나중에 측면뷰가 생기면 그쪽이 맡는다
([`11-decisions.md`](11-decisions.md) 번복 기록).

## 17.4 필요 민첩 (bottleneck)

```
필요 민첩(방) = min over 경로 ( max over 간선 ( 상승폭 ) )
```

내려가는 간선의 상승폭은 0 이다([`07`](07-level-design.md) §7.2.6).
Dijkstra 와 같은 구조에 "합" 대신 "최댓값"을 쓰면 그대로 구해진다.

이 값의 쓰임:

| 용도 | 내용 |
| --- | --- |
| 방 등급 | 배치의 기준 (§17.3-8) |
| 탈출구 보장 | 필요 민첩 0 인 탈출구가 최소 하나 |
| 고가치 배치 | 가치와 필요 민첩을 비례시킨다 |
| (추후) UI | "저기 가려면 민첩이 얼마나 더 필요한가" |

### 17.4.1 탈출구는 거리로 값을 받는다

탈출구는 **민첩으로 막을 수 없다.** 민첩 0 으로 닿는 탈출구가 최소 하나 없으면
시작하자마자 진 판이 되기 때문이다([`07`](07-level-design.md) §7.2.9).

그래서 대가를 다른 축에서 받는다.

| 종류 | 치르는 값 |
| --- | --- |
| 보스 · 귀중품 | **필요 민첩** — 능력이 올라야 손이 닿는다 |
| 탈출구 | **거리** — 판을 가로질러 걸어가야 한다 |

탈출구는 입구에서의 간선 수 거리가 최대의 65% 이상인 방들 중에서 고른다.

## 17.5 검증 규칙 — 검사에서 보장으로

**옛 방식: 판을 만들고 검사해서 실패하면 통째로 버리고 다시 만든다.**
그 방식의 문제는 실패율이 파라미터에 민감하다는 점이다. 재시도 상한을 넘기면
파라미터를 완화해야 했고, 완화된 판은 의도한 판이 아니었다.

**새 방식: 각 규칙을 구조로 보장한다.** 생성기에 재시도 루프가 없다.

| # | 규칙 | 어떻게 보장하는가 |
| --- | --- | --- |
| V1 | 모든 방이 입구에서 도달 가능 | 뼈대에 MST 가 들어 있다. 간선을 끊을 때도 끊어 본 뒤 판이 갈라지면 되돌린다 |
| V2 | 필요 민첩 0 인 탈출구가 최소 하나 | 입구에서 탈출구까지의 경로를 바닥까지 깎는다 (§17.3-7) |
| V3 | 고가치 방의 필요 민첩 > 0 | 필요 민첩이 0 보다 큰 방에만 보스 · 귀중품을 놓는다. 자격이 되는 방이 모자라면 그만큼만 놓는다 |
| V4 | 입구의 인접 위험도가 상한 이하 | 배치 단계에서 덜어 낸다 (`SampleDungeons`) |
| V5 | 막다른 방 비율이 14~30% | 모자라면 끊고 넘치면 잇는다 (§17.3-6) |
| V6 | 같은 위험도 합을 만드는 서로 다른 구성이 존재 | 방 종류마다 존재 구성을 다르게 놓는다 (보스방은 큰 하나, 위험방은 작은 여럿) |
| V7 | 입구의 차수가 2 이상 | 모자라면 가장 짧은 들로네 간선을 붙인다 |
| **V8** | **어떤 두 간선도 교차하지 않는다** | **후보가 들로네 부분집합이다.** 검사 자체가 필요 없다 |
| **V9** | **밀도가 고르다** | **푸아송 디스크 샘플링.** 최소 간격과 빈 구멍 없음이 알고리즘의 성질이다 |

### 탈출 경로 파기 (V2)

입구에서 탈출구까지의 최단 경로를 잡아 그 위 방들의 고도를 전부 0 으로 내린다.

부수 효과가 오히려 이득이다 — **판을 가로지르는 낮은 길이 하나 생겨서
"돌아 나올 수 있는 길"이 지도에서 눈에 띈다.** 탈출 지점 위치는 알 수 있어야 한다는
배치 원칙([`07`](07-level-design.md) §7.6)이 지형으로도 표현되는 셈이다.

### 폐기한 것

| 폐기 | 이유 |
| --- | --- |
| 고도 층(layer) 구성 | 고도가 그래프와 한 몸이라 간선을 하나 바꾸면 지형이 통째로 흔들렸다 |
| 척추 + 곁가지 연결 | 평면성을 보장하지 못한다. 교차의 직접 원인 |
| 힘 기반 완화 배치 | 밀도를 통제할 수 없고, 평면 그래프가 아니면 교차도 못 푼다 |
| 검증 실패 시 전량 재생성 | 규칙을 구조로 보장하면 실패할 판이 나오지 않는다 |
| 파라미터 완화 재시도 | 위와 같은 이유. 완화된 판은 의도한 판이 아니다 |

힘 기반 완화는 **좌표가 없는 설계도**(손으로 짠 판, 테스트 픽스처)를 위해
`DungeonBlueprint.layout()` 안에 남아 있다. 생성된 판에는 쓰이지 않는다.

## 17.6 자동 레이아웃 — 탑뷰

**좌표는 이제 생성 단계에서 나온다.** 배치는 더 이상 별도의 문제가 아니다.

`DungeonBlueprint.layout(seed, spacing)` 는 저장된 좌표에 간격을 곱해 돌려준다.
단위는 "방 사이 최소 간격 1" 이므로 화면이 간격을 바꾸면 판 전체가 같이 커진다.
현재 화면 간격은 280 px 다(`dungeon_board.gd`).

> **그 좌표에서 간선을 골랐으므로 다른 좌표로 그리면 교차가 되살아난다.**
> 좌표와 연결은 한 몸이다.

### 품질 기준

| 기준 | 상태 |
| --- | --- |
| 간선끼리 교차하지 않는다 | **보장.** 들로네 부분집합 |
| 선이 상관없는 방을 관통하지 않는다 | **보장에 가깝다.** 곁가지를 가브리엘로 제한. 테스트로 간격 0.3 이상 확인 |
| 방이 겹치지 않는다 | **보장.** 최소 간격이 곧 화면 간격 |
| 넓은 빈 구멍이 없다 | **보장.** 어느 지점에서든 간격 1.6 안에 방이 있다 |

"완벽한 교차 제거는 비용에 비해 얻는 게 적다"고 적어 두었던 옛 판단은 **틀렸다.**
비용이 큰 것은 교차를 제거하는 일이지, 교차가 나오지 않게 만드는 일이 아니었다.

### 판은 화면보다 커도 된다

끌어서 이동하고 휠로 확대한다([`07`](07-level-design.md) §7.8).
화면에 맞춰 줄이면 읽히지 않고, 읽히지 않는 판은 추리할 수 없다.

---

## 17.7 재현성

생성은 **시드**를 받는다. 같은 시드는 같은 판을 만든다.

| 이유 | 내용 |
| --- | --- |
| 테스트 | 판을 고정해야 생성 규칙을 검증할 수 있다 |
| 버그 재현 | "이상한 판이 나왔다"를 다시 볼 수 있다 |
| 밸런싱 | 같은 판에서 수치만 바꿔 비교한다 |

Godot 의 `RandomNumberGenerator` 를 인스턴스로 들고 다닌다.
전역 난수(`randi()`)를 쓰면 시드 고정이 깨진다.

**정렬 비교 함수 안에서는 난수를 뽑지 않는다.** 비교 함수가 몇 번 불리는지는
정렬 구현에 달려 있어서, 그 안에서 난수를 뽑으면 같은 시드가 다른 판을 만든다.
점수를 미리 계산해 두고 값으로만 비교한다.

## 17.11 현재 파이프라인 재확인 (2026-08-08 조사)

> **이 절은 코드를 다시 읽어 확인한 기록이다.** §17.1~17.10 이 설계 근거이고,
> 여기는 **그 설계가 코드에서 실제로 어떻게 실행되는가**와 **어디가 비어 있는가**를 적는다.
> 이 판(조사판)에서는 코드를 고치지 않았다. 계측 도구 하나만 추가했다.

### 17.11.1 호출 순서 — 실제 코드 기준

`SampleDungeons.create_run(seed, size)` 가 유일한 진입점이다.

```
SampleDungeons.create_run(seed, size)
  ├ params_for_size(size)          room_count = 7 + size*5  (12/17/22/27/32)
  ├ DungeonGenerator.generate()
  │   ├ PoissonDiskSampler.region_for_count()  넓이 = count/0.755, 가로세로비 1.45
  │   ├ PoissonDiskSampler.generate()          Bridson, radius 1, attempts 40
  │   ├ DelaunayTriangulation.edges()          Bowyer-Watson
  │   ├ _pick_entrance()                       네 모서리 중 하나를 뽑아 최근접 방
  │   ├ DungeonTerrain.assign()                거리*0.85 + simplex(2.6, 0.16), 입구=0
  │   ├ DungeonEdgeSelector.select()           아래 17.11.2
  │   ├ _breadth_first() / _pick_exit()        깊이 >= 최대깊이*0.65 인 방 중 무작위
  │   ├ DungeonTerrain.carve_route()           입구->탈출구 BFS 경로 고도를 전부 0 으로
  │   ├ ensure_a_climb_exists()                모든 고도가 0 일 때만 한 방을 2 로
  │   └ _assemble() -> RoomKindPlanner.plan()  종류 배치 + 이름
  ├ _populate()                                종류별 몬스터 배치 (여기부터 절차 생성 밖)
  ├ _trim_entrance_threat()                    입구 인접 합 > 4 면 강한 것부터 제거
  ├ _ensure_entrance_has_something_to_read()   입구 인접 합이 0 이면 위험도 2 하나 투입
  └ _pick_rival_room()                         입구의 인접이 아닌 방 아무 곳에 요한 1명
```

**경계가 하나 있다.** `DungeonGenerator` 는 **구조까지만** 만든다.
위험도(존재 배치)는 `SampleDungeons._populate()` 가 만들고, 그쪽은 절차 생성기가 아니라
고정 규칙 + 확률이다. V4·V6 이 생성기 밖에 있는 이유이자, §17.12 후보 여럿이
`SampleDungeons` 를 건드려야 하는 이유다.

### 17.11.2 간선 선택의 실제 실행 순서

`DungeonEdgeSelector.select()` 는 다섯 단계가 **이 순서로** 돈다.

| # | 함수 | 하는 일 | 되돌릴 수 있는가 |
| --- | --- | --- | --- |
| 1 | `_skeleton()` | RNG ∪ MST | — |
| 2 | `_ranked_pool()` | 가브리엘 나머지를 점수순, 그 뒤에 들로네 나머지 | — |
| 3 | `_add_extras()` | 방 수 x 0.24 개를 붙이되 막다른 방 하한을 침범하면 건너뜀 | 아니오 |
| 4 | `_ensure_entrance_choice()` | 입구 차수 < 2 면 최단 들로네 간선 추가 (V7) | 아니오 |
| 5 | `_relieve_dead_ends()` | 막다른 방 비율 > 0.30 이면 풀에서 이어 준다 (V5 상한) | 아니오 |
| 6 | `_carve_dead_ends()` | 막다른 방 비율 < 0.14 면 끊는다. 최대 6 패스 (V5 하한) | 예 — 끊고 연결 깨지면 복구 |

**주의할 점 두 가지.**

- `_relieve_dead_ends(chosen, pool, used)` 의 `used` 는 `_add_extras` 가 **훑은 인덱스**다
  (채택 개수가 아니라 소비 위치). 하한 때문에 건너뛴 후보는 다시 보지 않는다.
- 6단계 `_carve_once` 는 `_makes_one_dead_end` 로 **차수(2,3+) 쌍만** 자른다.
  차수 4 짜리끼리 이어진 간선은 후보가 되지 않으므로, 촘촘한 한가운데는 절대 뚫리지 않는다.
  깊이 큰 순이 아니라 **`_by_key` 가 내림차순이므로 깊은 쪽부터** 자르는 것이 맞다.

### 17.11.3 고도가 실제로 만들어지는 방식과 그 결과

```
raw   = dist(입구, 방) * 0.85 + simplex(방.x, 방.y) * 2.6      # 좌표 단위 = 최소 간격 1
값    = round(raw), 전체에서 최솟값을 빼고, 입구는 강제로 0
carve = 입구->탈출구 BFS 경로 위의 방은 전부 0
```

노이즈 주파수 0.16 은 **좌표 단위 기준**이라 파장이 방 6개 정도다.
즉 옆방끼리 널뛰지 않고 **판 전체에 완만한 언덕 두어 개**가 생긴다.

`carve_route` 는 BFS 경로 위 방을 전부 0 으로 만든다.
경로 길이가 최대 깊이의 65% 이상이므로, **판을 가로지르는 폭 1 짜리 평지 띠**가 하나 생긴다.
이 띠는 §17.5 가 의도한 대로 되돌아 나올 길이 되지만, 동시에
**그 띠에 닿는 모든 간선의 상승폭을 띠 반대편 방의 고도값과 같게 만든다** — 후술(§17.12).

### 17.11.4 방 종류 배치의 실제 규칙

`RoomKindPlanner.plan()` 의 순서는 이렇다.

1. `required_agility_from(입구)` — bottleneck 최단경로
2. 입구 · 탈출구를 먼저 고정 (탈출구는 생성기가 이미 골라 넘겨준다)
3. 나머지를 `필요민첩 + 홉거리/1000` 내림차순 정렬
4. `_place_valuables` — 그 순서로 훑되 **필요 민첩 0 을 만나는 즉시 break**.
   첫 번째가 보스, 그다음부터 `max(1, 방수*0.14)` 개가 귀중품
5. `_place_hazards` — 남은 방마다 독립적으로 16% 확률

**여기서 나오는 성질이 §17.12 후보 대부분의 출발점이다.**

- 보스는 **언제나 필요 민첩이 판에서 가장 높은 방**이다. 예외가 없다.
- 귀중품은 그 바로 다음 순위들이므로 **보스 근처에 뭉칠 수 있다**
  (필요 민첩은 지형에서 나오고, 지형은 저주파라 근처끼리 값이 비슷하다).
- 필요 민첩이 0 보다 큰 방이 적으면 귀중품이 예산보다 적게 놓인다 (설계된 동작, V3).
- 위험방은 위치와 무관한 순수 확률이므로 **입구 옆에도 놓인다.**
  그 뒤 `_trim_entrance_threat` 이 사후에 걷어낸다.

### 17.11.5 기획 문서와의 대조 — 아직 생성기가 못 하는 것

`07-level-design.md` · `13-information-design.md` 를 읽으며 대조한 결과다.

| 근거 | 요구 | 현재 상태 |
| --- | --- | --- |
| `07` §7.6 | 귀중품과 위험을 **같은 곳에** 둔다 | **못 한다.** 귀중품(TREASURE)과 위험방(HAZARD)은 서로 다른 방이고, 위험방은 확률로 흩뿌린다. 귀중품방의 몬스터는 `SampleDungeons` 가 넣는 "금고 파수꾼" 하나뿐 |
| `07` §7.6 | 귀중품은 **유한해야** NPC 경쟁이 성립 | 개수는 유한하지만 **가치 개념이 없다.** `Room.Kind.TREASURE` 뿐이고 전리품 값이 없다 |
| `07` §7.6 | 탈출 지점 **위치를 알 수 있어야** 한다 | 판에 EXIT 이 그려지므로 성립. 다만 **탈출구는 정확히 하나다** — "개수와 위치가 언제 나갈까의 무게를 결정한다"는 문장에 대해 개수 축이 고정 |
| `07` §7.6 | 위험도 숫자만으로 정답이 나오는 배치 회피 | **부분적.** V6 대비(보스=큰 하나, 위험방=작은 여럿)는 있지만 EMPTY 방의 몬스터가 45% 확률 1~2 라 합의 분포가 좁다 |

| `07` §7.2.3 | 정보 수단(정찰/스킬)이 유료 | 생성기 밖의 문제. 다만 §17.2 가 말하는 "차수가 곧 정보량"은 생성기가 쥐고 있다 |
| `13` §13.5 | 숫자의 **변화량**이 사람을 알려 준다 | NPC 가 요한 1명뿐이라 변화량 축이 거의 죽어 있다. 생성기가 아니라 배치의 문제 |
| `13` §13.6 | 공짜 정보는 전부 결함이 있어야 한다 | 성립 |
| `05` §5.6 | 조우는 방에서만 | 성립 (통로는 간선일 뿐 상태가 없다) |
| `07` §7.2.6.2 | 들어가긴 쉽고 나오긴 어렵다 | **약하다.** §17.12-B 참고 — carve 된 평지 띠와 낮은 고도값 때문에 실제 상승폭이 작다 |

### 17.11.7 이 수치가 말하는 것 — 왜 유기적으로 안 느껴지는가

사용자 감상은 "그냥 나열하고 노이즈처럼 잇기만 했다" 였다. 수치가 그것을 뒷받침한다.

**(1) 대안 경로가 있어도 고를 이유가 없다.**
귀중 방의 **31~33% 만** 둘째 길이 있고, 그중 **절반은 최단 경로가 상승·위험 양쪽에서 뒤지지 않는다.**
실제로 선택이 되는 판은 귀중 방 여섯 중 하나꼴이다.
결정적인 것은 상승폭이다 — 최단 3.34 대 대안 3.52 로 **사실상 같다.**
대안은 **더 길고(+35%) 더 위험한데(+38%) 기울기는 같다.** 아무도 고르지 않는다.
"빨리 가는 길 · 돌아가는 길"이 성립하려면 축 하나가 반대로 기울어야 하는데 그런 축이 없다.

**(2) 우회로가 가장 없는 곳이 하필 보상이 있는 곳이다.**
얕은 쪽 평균 차수 3.4 대 **깊은 쪽 2.05.** 깊은 절반은 사실상 나무다.
그런데 보스는 **언제나** 필요 민첩 최고인 방이고(100%, 편차 0), 그런 방은 깊은 쪽에 있다.
버그가 아니라 §17.3.5 의 「얕음」 항이 **설계대로 작동한 결과**다 —
"깊은 곳에 우회로가 적어야 귀중품이 값을 치른다"(V3).
**그 설계와 이번 요구가 정면으로 부딪친다.** 어느 쪽을 택할지가 이번 결정이다.

**(3) 간선은 적지 않다. 오히려 많다.**
순환 계수가 크기 5 에서 15.3 — **방 개수의 0.47 배.**
방 31개 판에 독립적인 우회로가 15개인데 지름은 8.9 다.
**판 어디서든 아홉 걸음이면 반대편에 닿는다.** 길을 찾을 것이 없다.
사용자가 말한 "이어진 길이 많이 없지만 fully connected" 의 정반대다.

**(4) 갈림길 자체는 이미 많다.** 차수 3 이상이 **64.8%.**
요구 ③은 이미 충족되어 있고, **문제는 갈림길의 수가 아니라 갈림길이 전부 똑같다는 것**이다.
어느 방에 서도 서너 갈래고 어느 갈래로 가도 비슷한 곳이 나온다. 균질한 그물망이다.
따라서 ②(간선 줄이기)와 ③(갈림길)의 긴장은 **지금 판에서는 없다** — 줄일 여지가 있다.

**(5) 고도는 보상과 상관이 있다. 다만 관문 역할을 못 한다.**
귀중 방 고도 백분위 **75** — "귀중한 방은 고도가 높다"는 이미 성립한다.
그러나 민첩 2 로 판의 **87%** 가 열린다. 상승이 있는 간선이 62% 인데도 못 막는 이유는
고도가 입구를 꼭짓점으로 하는 **매끈한 원뿔**이라 어디서든 우회해 돌아 올라갈 수 있기 때문이다.
**절벽이 없고 경사만 있다.** 그래서 고도가 지도에 선을 긋지 못한다.

**(6) 가치 높은 방이 판에서 가장 외진 방이다.**
귀중·보스 방의 평균 연결 수가 **1.86** 인데 판 평균 차수는 **3.00** 이다(방 50개 기준, §17.13.1).
절반 이상(51%)이 막다른 방이다.
사용자가 요구한 "가치 높은 방은 주변과 많이 연결되어 위협에 빠진다"의 **정확히 반대**다.

**(7) 늘 똑같은 것들.** 절차 생성이 아니라 상수인 값들이다.

| 값 | 편차 | 왜 상수인가 |
| --- | --- | --- |
| 보스 = 필요 민첩 최고 방 | 0.00 | `RoomKindPlanner` 이 정렬 1순위로 뽑는다 |
| 탈출구 고도 = 0 | 0.00 | `carve_route` 가 경로를 바닥까지 깎는다 |
| 입구 차수 = 2 | 0.36 | V7 이 2 를 만들고 그 이상 붙일 이유가 없다 |
| 막다른 방 = 16% | 0.83 | 하한 14% 에 붙어 있다 |
| 평균 차수 = 2.9 | 0.10 | 곁가지 비율이 상수 0.24 |
| 던전 성격 | — | 크기 슬라이더가 `room_count` 하나만 바꾼다. 나머지 8개는 전 던전 공통 |

**판마다 다른 것은 방의 자리뿐이고 판의 성질은 매번 같다.**
「유기적이지 않다」의 실체가 이것이다 — 시드를 바꿔도 **같은 종류의 판**이 나온다.

## 17.12 설계안 — 「랜덤하게 느껴지면 실패」 (2026-08-08, 승인 대기)

> **아직 구현하지 않았다.** `src/` 는 손대지 않았다.
> 아래는 `tools/` 의 프로토타입으로 **실제로 돌려 보고 잰 결과까지** 포함한 제안이다.
> 착수 전 승인이 필요하다 (CLAUDE.md 원칙 5).

### 17.12.1 합격 기준을 먼저 못 박는다

의뢰인 확정: **"의도적 레벨디자인이 무조건 들어가야 해. 이게 랜덤하다고만 느껴지면 실패야."**

이것은 있으면 좋은 항목이 아니라 **없으면 실패**하는 조건이다. 그리고 단서가 붙는다 —

> **수치 목표는 필요조건이지 충분조건이 아니다.**
> 순환 계수 · 차수 분포 · 막다른 길 비율을 전부 맞춰도 랜덤하게 느껴질 수 있다.
> 통계가 고른 판은 「고르게 랜덤한 판」이지 「설계된 판」이 아니다.

**설계됐다고 느껴지는 것은 플레이어가 패턴을 읽을 수 있을 때다.**
방을 보고 *"아 여기는 이래서 이렇게 생겼구나"* 가 되어야 한다.
그건 분포가 아니라 **의도의 배치**다. 그래서 §17.12.3 에 **패턴의 어휘**를 정의한다.

### 17.12.2 문제의 재정의

앞 판이 푼 것은 **기하 문제**였다 — 교차와 밀도(§17.5 V8·V9). 그건 됐다.
남은 것은 **레벨 디자인 문제**다. 지금 파이프라인에는 판을 만드는 규칙은 있는데
**무엇이 플레이어의 결정이 되는가**가 없다.

지금 순서: 자리 → 간선 → **그 결과로** 방 종류.
방 종류가 마지막이라 **보상이 구조를 만들지 못하고 구조에 얹힐 뿐이다.**
그래서 보상 근처에 우회로가 있는지가 우연이 된다(실측 31%).

제안 순서: 자리 → **구역** → 구역 사이 관문 → **보상 자리** → **그 보상까지의 두 경로** → 나머지 간선.
**보상을 먼저 놓고 그 주변을 설계한다.**

### 17.12.3 패턴의 어휘 — 이게 이 설계안의 본체다

각 패턴은 **화면에서 알아챌 수 있어야** 한다. 못 알아채는 패턴은 없는 것과 같다.

| # | 패턴 | 무엇을 만드나 | 플레이어가 어떻게 알아채나 | 생성기가 어디에 놓나 |
| --- | --- | --- | --- | --- |
| **P1** | **절벽 봉우리** | 보상 방을 국소 최고점으로 세운다. 이웃 어디서 봐도 올려다본다 | 판에서 고도 숫자가 가장 큰 방인데 **선이 여러 개** 붙어 있다 | 입구에서 가장 먼 구역의 최고점. 판에 하나 |
| **P2** | **급경사 지름길 / 완경사 우회** | 같은 목적지에 성격이 반대인 두 길 | **빨간 선(상승 3+)이 이어진 짧은 사슬**과 **회색·주황 선의 긴 사슬**이 한 방에서 만난다 | P1 과 주 보상에만. 판돈이 없는 곳에는 두지 않는다 |
| **P3** | **노출된 보상** | 보상 방의 차수를 4 이상으로. 들어오는 길이 많다 = 조우가 많다 | 큰 원에 선이 사방으로 뻗어 있다 | P1 과 같은 방. 둘은 겹친다 |
| **P4** | **막다른 보물** | 차수 1 짜리 방에 부차 귀중품 | 판 끝에 **선 하나로 매달린** 방 | 구역의 잎. 높은 구역 것부터 |
| **P5** | **관문(초크)** | 구역 사이를 잇는 통로 하나 | 방 덩어리 둘이 **선 하나로만** 이어져 있다 | 구역 경계마다 하나 |
| **P6** | **저지대 귀환로** | 입구에서 탈출구까지 고도 0 인 띠 | **어두운 원들이 한 줄로** 이어진다 | 이미 있다 (`carve_route`, §17.5 V2) |

**P2 와 P4 는 결정의 종류가 다르다.**
P2 는 「빨리 갈까 돌아갈까」, P4 는 「들어갔다 나올까」다.
둘 다 있어야 판이 단조롭지 않다.

#### P1·P3 의 충돌을 정면으로 푼다

고가치 방이 **연결이 많아야 한다(P3)** 와 **접근이 어려워야 한다(고도)** 를 동시에 요구받는다.

> **길은 많되 전부 험하게.**
> 보상 방을 **봉우리**로 세우면 붙어 있는 간선이 전부 오르막이 된다.
> 차수는 4 이상이라 노출은 최대이고, 필요 민첩은 봉우리 높이만큼 든다.

그리고 §7.2.7 이 이 조합을 이미 무섭게 만들어 뒀다 —
**못 올라가는 방의 것들도 나에게는 내려올 수 있다.** 봉우리 아래에 서면
사방에서 내려올 수 있는 자리에 서는 셈이다. **보상이 곧 노출**이 지형에서 나온다.

예외를 하나 둔다 — **완경사 우회(P2)의 마지막 한 칸만 경사로로 눕힌다.**
그래야 기본 민첩으로도 닿는 길이 하나 남고, 그 길은 멀다.

### 17.12.4 네 가지 수단 (패턴을 만드는 장치)

**A. 구역(zone)과 관문 — 판에 구획을 준다. → P5**
푸아송 점들을 구역으로 나눈다(입구를 첫 씨앗으로 하는 최원점 샘플링 + 최근접 배정).

- **구역 안**은 촘촘하게 → 갈림길이 유지된다
- **구역 사이**는 가장 짧은 들로네 간선 **하나씩만** → 거시 구조가 성기다

②(간선 적게)와 ③(갈림길 많이)의 긴장은 이렇게 푼다 — **성김과 촘촘함을 다른 축척에 둔다.**
지금 판이 균질한 이유는 축척이 하나뿐이기 때문이다.

**B. 구역을 고리로 잇는다 — 「돌아가는 길」의 정체. → P2**
구역 그래프를 나무가 아니라 **고리**로 만든다(구역 중심을 각도 순으로).
입구가 반드시 고리 위에 있고 **어느 구역으로 가든 좌우 두 방향**이 생긴다.
거시 순환 계수가 정확히 1 이다 — 간선 몇 개로 대안을 얻는 가장 싼 방법이다.

> **프로토타입에서 실제로 겪은 함정:** 처음에 구역을 **나무**로 잇고 보상 구역에만
> 고리를 덧댔더니 보스에 대안 경로가 있는 판이 **8~42%** 밖에 안 됐다.
> **입구 구역이 그 고리 위에 없으면** 두 경로가 앞부분을 공유해 결국 한 길이다.
> 고리는 **입구를 포함해야** 뜻이 있다.

**C. 두 경로를 「검사」가 아니라 「시공」한다. → P2**
보상 방을 정한 뒤 입구에서 그 방까지 **간선이 겹치지 않는 두 경로를 만든다.**
없으면 들로네에 남은 미사용 간선으로 **판다.** 들로네 부분집합이라 교차는 여전히 없다(V8).
§17.5 의 「검사에서 보장으로」를 경로에 적용한 것이다.
**프로토타입에서 보스 대안 경로 보유율이 어느 크기에서도 100% 가 됐다** (지금 7~20%).

그리고 **둘의 성격을 벌린다.** 대안이 있기만 해서는 선택이 아니다(§17.11.7-1).

- **급경사 지름길**: 목표 직전 한 칸을 떨어뜨려 상승폭 3 을 만든다 → 민첩으로 값을 치른다
- **완경사 우회**: 한 칸에 1 씩만 오르도록 깎는다 → 기본 민첩으로 걸어 들어간다. 대신 멀다

> **목표 방의 고도를 올리는 방식은 틀렸다.** 두 길이 같은 방으로 들어오므로 양쪽이 똑같이
> 가팔라진다. 프로토타입에서 실제로 그랬다. **길 쪽을 손봐야 한다.**

**D. 고도를 거리가 아니라 구역 등급에서. → P1·P5**
지금은 `거리 x 0.85 + 노이즈` 라 매끈한 원뿔이고 **절벽이 없다**(§17.11.7-5).
구역 등급 x 단차 + 낮은 노이즈로 바꾸면 **구역 안은 평탄하고 경계에서만 층이 진다.**

> **여기서 두 번 틀렸고 그 기록을 남긴다.**
> 단차를 3 으로 두면 관문마다 벽이 서서 기본 민첩으로 갈 수 있는 방이 **20%** 까지 떨어진다.
> 고도 폭을 고정하고 구역 수로 나누면 이번엔 **작은 판만** 가팔라진다(구역이 적어 단차가 커진다).
> **고도로 판 전체를 막는 것이 애초에 틀린 접근이다.**
> 지형은 걸어 다닐 수 있게 두고(단차 2, 기본 민첩으로 넘는다),
> **벽은 보상 봉우리와 지름길에만 세운다.** 그래야 벽이 있는 곳이 곧 의도가 된다.

### 17.12.8 지금 구조와 충돌하는가 · 비용

**충돌하지 않는다. 갈아엎지 않는다.**
푸아송 → 들로네 → 근접 그래프 → 선택은 그대로다. 후보 간선이 여전히 들로네 부분집합이므로
**V8(교차 없음)과 V9(밀도)는 손대지 않아도 유지된다.** 바뀌는 것은 **무엇을 고르느냐**다.

| 단계 | 바뀌는가 |
| --- | --- |
| 1 푸아송 · 2 들로네 · 3 입구 | 그대로 |
| 4 고도 | **바뀐다** — 거리 원뿔 → 구역 등급 + 노이즈, 벽은 국소적으로 |
| 5 간선 선택 | **바뀐다** — 「얕음 x 완만함」 점수 → 구역 안/밖 규칙 + 경로 시공 |
| 6 막다른 방 조정 | 유지. 하한만 조정 |
| 7 탈출 경로 파기 | 그대로 (P6) |
| 8 방 종류 | **순서가 앞으로 온다** — 보상 자리를 간선 선택 전에 정한다 |
| 9 존재 배치 | 이번 범위 밖 |

**앞 레인의 판단(RNG ∪ MST + 가브리엘)을 뒤집지 않는다.**
그 근거였던 "MST 는 나무라 판의 절반이 막다른 길이 된다"(§17.3.4)는 여전히 옳고,
이번 요구 ②·③과도 같은 방향이다. 구역 **안**은 그대로 근접 그래프를 쓴다.
바뀌는 것은 **구역 사이**를 어떻게 잇느냐뿐이다.

**비용.** 구역 나누기는 방 개수 x 구역 수, 경로 시공은 BFS 몇 번이다.
방 50개에서 생성기만 재면 지금 7.04 ms, 프로토타입 5.58 ms 로 **오히려 빠르다**(간선이 적다).
다만 `SampleDungeons._populate` 는 여기 포함되지 않았으므로 **구현 후 다시 재야 한다.**

90시간 안에 되는가 — **A~D 는 프로토타입 규모로 이미 돌아간다.**
실제 비용은 §17.10 의 테스트 표를 그만큼 늘리는 쪽이다.

스쿼드 기본 민첩이 2 인데 보스 방에 닿으려면 8 이 필요하고, 우회로는 없다.

설계안은 네 판 모두 **짧고 가파른 길(상승 3~4)과 길고 완만한 길(상승 1~2)** 이 함께 있다.
**이 표는 실측 평균이 아니라 그림에 적힌 값 그대로다.** 그림에서 직접 세어 검산할 수 있다.

## 17.14 미달 셋을 좁힌 기록 (2026-08-08, 프로토타입만)

> §17.12.7 이 남긴 미달 세 줄을 프로토타입 안에서 좁혔다. **`src/` 는 여전히 손대지 않았다.**
> 여기 적는 것은 결과보다 **왜 틀렸는가**다. 같은 실수를 구현 때 다시 하지 않기 위해서다.

### 17.14.1 두 경로 상승폭 차 — 0.13 → 1.85 (목표 1.5+, 달성)

**이것이 설계안의 핵심 약속이었다.** 급경사 지름길과 완경사 우회의 차이가 0.13 이면
「빨리 갈까 돌아갈까」가 아예 없는 것이다. 세 번 틀리고 고쳤다.

| # | 무엇을 했나 | 왜 틀렸나 |
| --- | --- | --- |
| 1 | 목표 방의 고도를 올렸다 | 두 길이 **같은 방으로 들어온다.** 양쪽이 똑같이 가팔라진다 |
| 2 | 우회로를 "한 칸에 1 씩" 으로 깎았다 | 경사로가 **시작하는 지점**에서 앞 칸과의 차이가 그대로 절벽이 됐다 |
| 3 | 봉우리를 세운 뒤 계단을 맞췄다 | 경로가 짧거나 탈출 통로와 겹치면 계단이 목표에 못 미쳐 **마지막 한 칸이 절벽**이 됐다 |

**고친 방법은 순서를 뒤집는 것이었다.**

```
(예전) 봉우리를 세운다 -> 계단을 맞춰 본다 -> 안 맞으면 절벽이 남는다
(지금) 계단이 닿을 수 있는 높이를 먼저 잰다 -> 봉우리를 거기에 맞춘다
```

우회로를 앞에서부터 훑어 「여기까지는 1 씩 올라오면 몇까지 닿는가」(`reach`)를 구하고,
봉우리 높이를 `min(주변+3, reach+1)` 로 정한 뒤 계단을 거꾸로 놓는다.
그러면 **우회로의 최대 상승폭이 1 임이 계산이 아니라 구성으로 보장된다.**
§17.5 의 「검사에서 보장으로」가 고도에도 적용된 셈이다.

그리고 **고도를 건드리는 곳을 한 군데로 모았다.** 예전에는 `_sharpen` 뒤에 `_carve` 가 와서
방금 세운 경사로를 탈출 통로가 도로 0 으로 깎았다. 지금은 깎는 것을 먼저 하고,
깎인 칸을 `protected` 로 넘겨 계단이 그 칸을 피하되 **거기서부터 다시 시작**한다.

| 방 50개 | 지금 생성기 | 프로토타입 |
| --- | --- | --- |
| 지름길 최대 상승 | 4.36 | **4.08** |
| 우회로 최대 상승 | 4.64 | **2.23** |
| **차이** | **-0.28 (우회가 더 가파르다)** | **+1.85** |
| 최단이 더 완만하기까지 한 비율 | 65.1% | **20.0%** |

지금 생성기는 **대안이 더 가파르기까지 하다.** 길고, 위험하고, 가파르다. 고를 이유가 없다.

### 17.14.2 P3 와 P4 를 갈라 재기 — 진단이 맞았다

한 평균으로 재면 **둘 다 실패로 보인다.** 노출된 보상(차수 4+)과 막다른 보물(차수 1)은
서로 반대 방향이라 섞으면 가운데 값이 나온다. 종류별로 나눠 재니 그림이 완전히 달라졌다.

| 방 50개 | 지금 생성기 | 프로토타입 | 목표 |
| --- | --- | --- | --- |
| **보스 방 차수** | **1.08** | **4.20** | 4 이상 |
| 부차 귀중품 차수 | 1.99 | **1.00** | 1 |

**지금 생성기의 보스 차수가 1.08 이다.** 평균 1.86 보다도 낮다 —
보스는 거의 언제나 **막다른 방**이다. 판 평균 차수가 3.00 인데 이 판의 주인공만 외길이다.
§17.11.7-6 에서 잡은 것보다 더 심하다.

프로토타입에서는 보스가 차수 4 이면서 **봉우리**라 붙은 간선이 전부 오르막이다.
「길은 많되 전부 험하게」(§17.12.3)가 수치로 성립한다.

### 17.14.3 갈림길 45.3% → 50.4% (목표 55~60, 미달)

구역마다 허브를 하나만 두면 구역 안이 그 방을 지나는 **별 모양**이 된다.
둘로 늘리니 갈림길이 두 군데 생겼다. 다만 간선이 함께 늘어 순환 계수가 목표를 넘었고,
허브 곁가지 채택 확률을 0.75 -> 0.62 로 조여 되돌렸다.

**둘은 같은 손잡이의 양끝이다.** 갈림길을 늘리면 순환이 늘고, 순환을 조이면 갈림길이 준다.
50.4% 는 목표에 5%p 못 미치지만 **더 밀면 순환 계수가 목표를 벗어난다.**
허브를 셋으로 늘리는 대신 **허브끼리 잇는 간선을 우선 채택**하는 쪽이 남은 방법이다
(같은 간선 수로 차수를 더 몰아 준다). 미검증이다.

## 17.15 화면이 방 50개를 감당하는가 (2026-08-08 조사)

> `tools/check_board_capacity.gd` (헤드리스) + `tools/capture_board_50.gd` (창 한 번).
> **`src/` 는 고치지 않았다.** 무엇을 고쳐야 하는지까지만 적는다.

### 17.15.1 실측 — 지도의 크기와 담기는 배율

기준 화면 1280x720, 간격 280, 방 위젯 146x76, 확대 하한 0.40. 방 개수마다 시드 5개.

| 목표 방 | 실제 방 | 지도 크기 (배율 1) | 판 전체가 들어오는 배율 | **하한에서 보이는 넓이** | 최소 간격 | 전체를 볼 때 이름 |
| --- | --- | --- | --- | --- | --- | --- |
| 12 | 11.4 | 1323 x 926 | 0.778 | 100% | 98 px | 보인다 |
| 22 | 22.6 | 1926 x 1302 | 0.553 | 100% | 95 px | 안 보인다 |
| 32 | 30.2 | 2269 x 1540 | 0.468 | 100% | 92 px | 안 보인다 |
| **50** | **45.0** | **2845 x 1931** | **0.373** | **86.9%** | **92 px** | 안 보인다 |
| 64 | 59.4 | 3225 x 2189 | 0.329 | 67.6% | 88 px | 안 보인다 |

**방 50개에서 처음으로 판 전체가 화면에 들어오지 않는다.** 필요한 배율이 0.373 인데 하한이 0.40 이다.
32개까지는 100% 들어왔다. **이 문제는 50개에서 새로 생긴다.**

### 17.15.2 이름과 숫자는 겹치지 않는다 — 전제가 깨지지 않았다

`dungeon_board.gd` 의 간격 주석("방 위젯보다 넉넉해야 이름이 겹쳐 보이지 않는다")이
개수가 늘면 깨질까 걱정했는데 **깨지지 않는다.**

가장 가까운 두 방의 위젯 사이 간격이 방 12개에서 98 px, 64개에서 88 px 다. 거의 변하지 않는다.
**푸아송 디스크가 최소 간격을 보장하기 때문이다** — 방이 늘면 영역이 같은 밀도로 넓어질 뿐
이웃 사이가 좁아지지 않는다(§17.3.2). 밀도는 개수에 대해 불변이다.

> **간격 전제는 방 개수와 무관하다.** 이건 블루 노이즈로 뒤집은 파이프라인이
> 의도하지 않게 준 이득이다. 예전 힘 기반 배치였다면 개수가 늘 때마다 뭉쳤을 것이다.

### 17.15.3 창을 띄워 본 것 — 숫자가 말해 주지 않는 것 셋

방 44개(시드 11)를 실제 화면에 올려 배율 1.0 / 0.62 / 0.40 세 장을 한 번의 실행으로 찍었다.
**이번에는 그림을 눈으로 봤다** (§17.13.3 의 SVG 검증과 달리 수치 검증이 아니다).

**(1) 하한 배율에서 방은 「내용」이 아니라 「무늬」다.**
0.40 에서 방 위젯은 58x30 px 다. `RoomNode` 는 이 배율에서 이름만 감추고 숫자는 남기는데
(`Detail.MINIMAL`), 실제로는 **하프톤 망점이 칸을 채워 숫자가 묻힌다.**
`07` §7.8 이 약속한 "낮음 = 숫자만 보이는 배율"이 지켜지지 않는다.

**(2) 방 종류가 색으로 구분되지 않는다.**
같은 §7.8 이 낮은 배율을 "판의 **모양과 색**을 읽는 배율"이라고 적었는데,
화면에서 보스방과 빈방이 **똑같이 생겼다.** 색이라고 부를 것이 없다.
이건 방 개수와 무관한 문제이고, 50개에서 더 아프게 드러날 뿐이다.

**(3) HUD 가 지도를 덮는다 — 계산에 안 들어간 손실이다.**
좌측 정보판(약 290x290), 좌하단 「송출중」 명판(약 370x70), 우하단 조작바(약 540x70)가
지도 위에 얹힌다. 합치면 뷰포트의 **약 16%** 다.
지도의 86.9% 만 들어오는데 그중 16% 가 가려지므로 **실효로 보이는 판은 약 73%** 다.

한편 **이동으로는 판 구석까지 갈 수 있다.** `_clamp_pan` 이 화면 절반만큼 패딩을 두어
가장자리 방도 화면 가운데로 끌어올 수 있다. **못 보는 것이 아니라 한눈에 못 보는 것이다.**

### 17.15.4 「안 들어와도 된다」는 전제가 50개에서도 유효한가

`dungeon_board.gd` 주석과 `07` §7.8 은 이렇게 적어 뒀다.

> 판은 한 화면에 다 들어오지 않아도 된다. 지도가 화면에 맞춰 줄어들면 방이 뭉개져
> 오히려 읽기 어렵다.

**절반만 유효하다.** 같은 §7.8 이 배율마다 하는 일을 따로 정해 뒀기 때문이다.

| 배율 | §7.8 이 정한 일 | 50개에서 |
| --- | --- | --- |
| 높음 | "여기서 어디로 갈까" | 성립 |
| 낮음 | **"지금 판이 어떻게 생겼나"** | **성립하지 않는다** |

**「판이 어떻게 생겼나」를 보려면 판이 화면에 들어와야 한다.**
플레이 배율에서 안 들어오는 것은 의도지만, **훑어보는 배율에서 안 들어오는 것은 결함이다.**
32개까지는 우연히 둘 다 성립해서 이 모순이 드러나지 않았다.

> **판단: 결함이 맞다.** 다만 "화면에 맞춰 줄인다"가 답은 아니다.
> 주석의 경고("줄이면 뭉개진다")는 §17.15.3-(1)에서 실제로 확인됐다 —
> 이미 0.40 에서 뭉개지고 있다. **더 줄이는 방향은 막혀 있다.**

### 17.15.5 선택지와 대가

### 17.15.6 적용 — 간격 280 -> 240 (2026-08-08, 반영됨)

**B 를 적용했다.** `dungeon_board.gd` 의 `_SPACING` 하나를 240 으로 내렸다.
사용자가 방 50개를 요청했고 **판을 못 보면 그 요청이 통째로 막히므로**, 설계안 승인과
별개로 필요한 변경이라고 판단했다. **생성기 본체(`src/core/dungeon/`)는 손대지 않았다.**

적용 후 실측 (같은 도구, 같은 시드).

| 목표 방 | 지도 크기 | 판 전체가 들어오는 배율 | **하한에서 보이는 넓이** | 최소 간격 | 전체를 볼 때 이름 |
| --- | --- | --- | --- | --- | --- |
| 12 | 1155 x 805 | 0.896 | 100% | 63 px | 보인다 |
| 22 | 1672 x 1127 | 0.639 | 100% | 67 px | **보인다** |
| 32 | 1966 x 1331 | 0.541 | 100% | 64 px | 안 보인다 |
| **50** | **2460 x 1666** | **0.432** | **100%** | **58 px** | 안 보인다 |
| 64 | 2785 x 1887 | 0.382 | 91.0% | 64 px | 안 보인다 |

- **방 50개가 확대 하한에서 전부 들어온다.** 목표 달성
- **덤으로 방 22개(지금 기본 크기 3)에서 판 전체를 보면서 이름까지 읽힌다.**
  간격 280 에서는 필요 배율 0.553 이 이름 표시 경계(0.62) 아래라 이름이 사라졌다
- 최소 간격은 58~67 px 로 남는다. 위젯 너비 146 의 40% 이상이라 겹치지 않는다
- **방 64개는 여전히 91% 다.** 사용자 요청은 50개이므로 그대로 둔다.
  64개까지 담아야 하면 간격을 220 까지 더 내려야 하고, 그때 최소 간격이 44 px 로 줄어든다

**A(확대 하한 내리기)는 쓰지 않았다.** 이미 0.40 에서 방이 무늬로 보이므로(§17.15.3-1)
윤곽만 남는 배율을 하나 더 만드는 것은 「모양을 읽는 배율」을 만드는 것이 아니다.

#### 아직 남은 요구 — 낮은 배율에서 방 종류가 구분되어야 한다

판이 100% 담겨도 **보스방과 빈방이 똑같이 생겼으면** 「지금 판이 어떻게 생겼나」는
여전히 읽히지 않는다(§17.15.3-2). `07` §7.8 이 "모양과 **색**"이라고 적어 둔 절반이 비어 있다.

**여기서 색을 정하지 않는다.** 이건 생성기가 아니라 화면의 과제이고, 조형 언어는
UI 킷 쪽에서 나온다([`20-ui-kit.md`](20-ui-kit.md)). **요구만 남긴다.**

> **요구:** `Detail.MINIMAL` 배율에서 방 종류(입구 · 탈출 · 보스 · 귀중품 · 위험 · 빈방)가
> 서로 구분되어야 한다. 수단은 색이든 형태든 UI 킷이 정한다.

### 17.15.7 확인 방법과 그 한계

| 확인한 것 | 방법 |
| --- | --- |
| 지도 크기 · 담기는 배율 · 최소 간격 | 헤드리스 계산 (`check_board_capacity.gd`). 배치 계산의 결과라 그림이 필요 없다 |
| 하한 배율에서 방이 무늬로 보인다 | **창을 띄워 PNG 를 눈으로 봤다** (`capture_board_50.gd`) |
| HUD 가 덮는 넓이 | 같은 PNG 에서 눈으로 재고 픽셀로 어림했다. **정밀 측정이 아니다** |
| 웹 빌드에서도 같은가 | **미확인.** 브라우저 캔버스 크기가 다르면 결론이 달라질 수 있다 |
| 간격 240 적용 후 회귀 | 임포트 · GUT 409 테스트 · gdlint · gdformat · 글리프 전부 통과. **GUT 스크립트 수 36 이 `test/unit` 파일 수 36 과 일치**하므로 파싱 실패로 조용히 건너뛴 테스트는 없다 |

창은 **한 번만** 띄웠고 세 배율을 그 안에서 몰아 찍었다.

**계측 도구가 화면 상수를 베껴 적던 것은 없앴다.** 처음에는 간격 · 확대 하한 · 위젯 크기를
`check_board_capacity.gd` 안에 적어 뒀는데, 그러면 화면이 바뀔 때 도구가 옛 수치로
**조용히 거짓말을 한다.** 실제로 간격을 240 으로 내리면서 두 곳을 고쳐야 했다.
지금은 `DungeonBoard._SPACING` 을 직접 읽고(GDScript 의 밑줄은 관례일 뿐이라 상수는 읽힌다),
위젯 크기는 `room_node.tscn` 을 한 번 세워서 읽는다. **한 곳만 고치면 된다.**

## 17.16 「늘 똑같은 것」을 흔든다 — 던전마다 성격 (2026-08-08, 승인 대기)

> `tools/survey_dungeon_params.gd` · 그림은 `.shots/dungeon_characters.html`.
> **`src/` 는 고치지 않았다.** 파라미터는 이미 `DungeonGenerator.Params` 로 노출돼 있어
> 던전별로 다른 값을 주는 것은 배선 문제이지 생성기 문제가 아니다.

### 17.16.1 두 증상은 같은 병이다

§17.11.7 에서 두 가지를 찾았다.

| 증상 | 내용 |
| --- | --- |
| 랜덤한 곳은 다 똑같이 랜덤하다 | 시드를 바꿔도 **같은 종류의 판**이 나온다 |
| 의미 있어야 할 곳은 다 똑같이 고정돼 있다 | 보스 = 필요민첩 최고 방(편차 0) · 탈출구 고도 = 0(편차 0) · 입구 차수 = 2 · 파라미터 9개 중 8개가 전 던전 공통 |

**둘 다 「읽을 게 없다」로 귀결된다.** 그리고 §7.3 이 이미 답을 적어 뒀다 —
"던전끼리 강함만 다르면 선택이 아니라 순서다."

### 17.16.2 성격이냐 운이냐 — 경계를 수로 놓는다

던전마다 파라미터를 달리 주면 **「이 던전은 저 던전과 다르다」**가 되어야 한다.
그런데 **같은 던전 안에서 시드만 바꿔도 그만큼 흔들리면** 플레이어에게는
**「이번 판은 운이 나빴다」**로 읽힌다. 전자는 성격이고 후자는 불공정이다.

그 경계를 이렇게 잰다.

```
신호대잡음 = |축을 높였을 때 - 낮췄을 때| / (같은 파라미터에서 시드만 바꿨을 때의 표준편차 x 2)
```

**1 보다 작으면 그 축은 성격이 될 수 없다.** 시드가 더 크게 흔들기 때문에
플레이어는 파라미터 차이를 운으로 돌린다.

### 17.16.3 실측 — 어느 축이 실제로 읽히는가

방 50개 목표, 축마다 낮음 / 지금 / 높음, 시드 24개.

| 축 | 낮음 -> 높음 | 가장 크게 움직인 지표 | 축 폭 | 시드 폭 | **신호대잡음** |
| --- | --- | --- | --- | --- | --- |
| 귀중품 비율 | 0.05 -> 0.30 | 귀중품 개수 | 11.6 | 0.6 | **21.0** |
| 막다른 방 하한 | 0.06 -> 0.30 | 막다른 방 % | 18.8 | 1.0 | **18.8** |
| 곁가지 비율 | 0.08 -> 0.48 | 평균 차수 | 0.8 | 0.2 | **4.4** |
| 위험방 비율 | 0.05 -> 0.36 | 위험방 개수 | 12.8 | 4.9 | **2.6** |
| 고도 상승 | 0.30 -> 1.70 | 보스 필요 민첩 | 12.5 | 5.8 | **2.2** |
| 탈출구 최소 거리 | 0.30 -> 0.95 | 탈출구까지 홉 | 4.2 | 2.2 | **1.9** |
| **지형 기복(진폭)** | 0.8 -> 5.2 | 민첩 2 로 열리는 방 % | 25.5 | **48.1** | **0.53** |
| **기복의 잔 정도(주파수)** | 0.07 -> 0.34 | 지름 | 0.2 | 1.4 | **0.12** |

**여섯 축은 시드 잡음을 넘고 둘은 못 넘는다.**

- **지형 기복은 흔들면 안 된다.** 축 폭 25.5%p 인데 **시드 폭이 48.1%p 다.**
  던전 성격으로 쓰면 플레이어는 그걸 운으로 돌린다. 게다가 고도 상승과 **같은 지표**를
  움직이므로, 둘을 함께 흔들면 어느 것이 원인인지 읽히지 않는다.
  **고도 축은 「고도 상승」 하나만 쓴다.**
- **기복의 잔 정도는 아무것도 하지 않는다.** 신호대잡음 0.12 이고 **단조롭지도 않다**
  (민첩 2 로 열리는 방이 0.07 에서 75.4%, 0.16 에서 78.8%, 0.34 에서 73.0% 로 오르내린다).
  흔들면 잡음만 는다.

몇 가지 축이 서로 얽혀 있는 것도 확인했다.

| 얽힘 | 내용 |
| --- | --- |
| 귀중품 <-> 위험방 | 귀중품 비율을 0.05 -> 0.30 으로 올리면 위험방이 6.0 -> 4.2 로 준다. `_place_hazards` 가 **남은 방**에만 돌기 때문이다 |
| 곁가지 <-> 보스 필요 민첩 | 곁가지를 0.08 -> 0.48 로 올리면 보스 필요 민첩이 7.3 -> 5.0 으로 내린다. 우회로가 늘어 낮은 경로가 생긴다 |
| 막다른 방 <-> 민첩 | 하한을 0.06 -> 0.30 으로 올리면 민첩 2 로 열리는 방이 84.3% -> 71.5% 로 준다 |

**즉 축은 독립이 아니다.** 던전 하나에서 여러 축을 흔들면 서로를 상쇄해
결국 "그냥 다른 판"이 된다.

### 17.16.4 규칙

| # | 규칙 | 근거 |
| --- | --- | --- |
| R1 | **한 던전에서 흔드는 축은 둘까지** | 셋 이상이면 어느 것이 그 던전의 성격인지 읽히지 않는다. 봉우리를 판에 하나만 두는 것과 같은 논리(§17.12.5) |
| R2 | **신호대잡음 1.5 미만인 축은 쓰지 않는다** | 지형 기복(0.53) · 기복의 잔 정도(0.12) 제외 |
| R3 | **파라미터는 던전별로 고정. 시드는 자리만 바꾼다** | 입장 전에 알 수 있어야 성격이고, 입장 후에 드러나면 운이다. 선택이 곧 난이도 선택(§7.3) |
| R4 | **흔든 축이 화면에 보여야 한다** | 아래 표의 「무엇으로 읽히나」가 빈 축은 쓰지 않는다 |
| R5 | 공정성 규칙은 흔들지 않는다 | 민첩 0 탈출구(V2) · 입구 인접 위험도 상한(V4) · 입구 차수 2 이상(V7). 이건 성격이 아니라 최소 조건이다 |

### 17.16.5 축이 화면에서 무엇으로 읽히는가 (R4)

| 축 | 무엇으로 읽히나 |
| --- | --- |
| 방 개수 | 판의 크기. 화면에 "칸 N개 안팎"으로 이미 적힌다 |
| 곁가지 비율 | **선이 촘촘한가 성긴가.** 그리고 인접 위험도 합이 뭉치는 정도(§17.2) |
| 막다른 방 하한 | **판 끝에 선 하나로 매달린 방이 몇 개인가.** 정찰 지점의 수 |
| 고도 상승 | 방에 적힌 **고도 숫자의 크기**와 "오름 N" 표시의 빈도 |
| 탈출구 최소 거리 | **탈출구가 판의 어디에 있는가.** 코앞인가 반대편인가 |
| 귀중품 비율 | 귀중품 방의 개수 |
| 위험방 비율 | 위험방의 개수 |
| ~~지형 기복~~ | 고도 숫자가 들쭉날쭉한 정도. **시드 잡음과 구분되지 않는다** |
| ~~기복의 잔 정도~~ | **읽히는 것이 없다** |

### 17.16.6 「편차 0」 셋에 대한 판단

| 지금 | 흔들 것인가 |
| --- | --- |
| 보스 = 필요 민첩 최고 방 (편차 0) | **규칙은 유지하고 세기만 던전별로.** "가장 가기 어려운 방이 보스"는 **읽히는 규칙**이라 없앨 이유가 없다. 대신 고도 상승 축으로 그 어려움의 크기를 던전마다 달리 준다 (보스 필요 민첩 2.8 ~ 15.3 으로 움직인다) |
| 탈출구 고도 = 0 (편차 0) | **유지.** 민첩 0 탈출구는 공정성 규칙(V2)이다 (R5). 흔들 것은 **개수**다 — `07` §7.6 이 "탈출 지점의 개수와 위치가 「언제 나갈까」의 무게를 결정한다"고 적었는데 지금은 **언제나 하나**다. **생성기에 탈출구 개수 파라미터가 없다 — 신규 항목이다** |
| 입구 차수 = 2 | **유지.** V7 의 하한이고 공정성 규칙이다 (R5). 3~4 로 올리는 것은 효과가 작아 우선순위 낮다 |

**그리고 보스가 치르는 값 자체를 던전 성격으로 쓸 수 있다.**
§17.4.1 이 이미 두 축을 정의해 뒀다 — 보스·귀중품은 **필요 민첩**, 탈출구는 **거리**.
지금은 이 배정이 고정이다. 던전에 따라 **보스를 거리로 막는 것**도 성격이 된다
("능력이 되면 갈 수 있지만 멀다" 대 "가깝지만 못 올라간다").
**이건 `RoomKindPlanner` 를 고쳐야 하므로 신규 항목이다.**

**한 시드로는 고도 축이 깨끗하게 갈리지 않는다.** 수직 회랑(최고 고도 10)과

"평균으로는 갈리지만 한 판으로는 덜 갈린다"는 뜻이고, 그림이 그것을 보여 준다.
**연결 밀도 축(고리 5 대 21)은 한 판에서도 확연하다** — 신호대잡음 4.4 다.
