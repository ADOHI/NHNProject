# 01. 확정 제약

> **상태: 확정.** 기획 이전에 이미 고정된 조건이다. 기획은 이 안에서 이뤄져야 한다.

> ## ★ 2026-08-19 — **본판이 웹에서 PC 스탠드얼론으로 바뀌었다**
>
> 사용자 지시다.
>
> > "나 이젠 웹빌드 안하고 pc 스탠드얼론 빌드로 뽑을거야.
> > 웹빌드 사양을 남겨둬도 괜찮은데(디버깅용이나 사람들한테 데모 배포용)
> > **실제 게임은 pc로 출시할거야**"
>
> **웹은 버리지 않는다 — 등급이 내려간다.** 데모 배포와 디버깅용으로 유지한다.
> 그러므로 **웹을 깨는 변경은 여전히 금지**이고, 다만 **웹이 상한을 정하지는 않는다.**
>
> 아래 §1.1 은 그 구분에 맞춰 다시 썼다. §1.2 는 무엇이 풀렸는지 §1.2.1 에 적었다.

## 1.1 기술 제약

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 엔진 | Godot 4.7.1 | GDScript |
| **본판** | **PC 스탠드얼론 (Windows x86_64)** | **출시 대상** |
| 부판 | 웹(HTML5) | **데모 배포 · 디버깅.** 깨뜨리지 않는다 |
| 배포 | GitHub Pages 자동 배포 | https://adohi.github.io/NHNProject/ — 부판 배포처 |
| 렌더러 | `gl_compatibility` (양쪽 공통) | **PC 단독으로는 Vulkan 도 가능하다 — 아직 안 켰다. §1.1.1** |
| 스레드 | 단일 스레드 (양쪽 공통) | 웹은 `SharedArrayBuffer` 불가. **PC 는 제약 없다** |
| 기준 해상도 | 1280 × 720 | 창 크기에 맞춰 스케일 |
| 차원 | 2D | |

근거와 설정 위치는 [`../web-build.md`](../web-build.md) 에 있다.

### 1.1.1 렌더러를 아직 안 바꾼 이유

Godot 은 **플랫폼마다 렌더러를 따로 줄 수 있다**
(`rendering_method` / `rendering_method.mobile` / `rendering_method.web`).
그러므로 *"PC 는 Forward+, 웹은 `gl_compatibility`"* 가 **설정으로는 가능하다.**

**그런데 안 켰다.** 이 저장소의 셰이더 전부 — 타이틀 · UI 킷 · 스케치 · 모핑 —
가 `gl_compatibility` 에서만 그려 보고 판정받았다. 렌더러를 가르면
**화면을 두 벌 검수해야 하고**, 그 비용을 아직 아무도 안 냈다.

> **켜는 것이 공짜가 아니라 「검수 두 벌」이 값이다.**
> 재고 나서 정한다 — 무엇이 좋아지는지 실제로 보이지 않으면 안 켠다.

## 1.2 제약이 기획에 주는 영향

> **아래는 「웹이 본판이던 때」의 판단이다.** 대부분 아직 유효하지만
> **몇 줄은 등급이 내려갔다** — 무엇이 풀렸는지는 §1.2.1 에 있다.

웹 빌드라는 조건은 단순한 배포 방식이 아니라 **기획 제약**이다.

- **초기 로딩이 곧 이탈 지점이다.** 브라우저에서 여는 순간 다운로드가 시작된다.

  **다만 우리 에셋은 지금 문제가 아니다. 실측(2026-08-08):**

  | 파일 | 크기 |
  | --- | --- |
  | `index.wasm` — **Godot 엔진** | **37.7 MB** |
  | `index.pck` — **우리 게임 전부** | **1.5 MB** |
  | 합계 | 약 **39.5 MB** |

  **전체의 96%가 엔진이다.** 폰트 2.03MB 도, 방 하나 1.9MB 도, 타이틀 10.7MB 도
  이 앞에서는 결정적이지 않다. 타이틀을 통째로 넣어도 39.5 → 50MB 로 27% 늘 뿐이고,
  3D 웹 게임이 100~200MB 를 쓰는 것을 생각하면 무거운 축이 아니다.

  **그러므로 "웹 빌드니까 에셋을 넣지 말자" 는 근거가 없다.**
  실제로 그 판단이 UI 를 도형과 셰이더 노이즈로 몰아넣어 한 번 갈아엎게 만들었다
  ([20](20-ui-kit.md)). **재기 전에는 무겁다고 말하지 않는다.**

  볼 것은 용량 자체가 아니라 **첫 로딩 시간**이다. 그건 따로 재야 하고,
  지금도 이미 37MB 를 받고 있다.
- **소리는 첫 입력 전까지 재생되지 않는다.** 브라우저 정책이다.
  타이틀 화면에서 바로 BGM 이 나오는 연출은 성립하지 않는다.
- **단일 스레드다.** 무거운 연산을 별도 스레드로 넘길 수 없다.
  한 프레임에서 오래 걸리는 처리는 화면 전체를 멈춘다.
- **입력 환경을 가정할 수 없다.** 채점자가 어떤 기기·화면으로 열지 모른다.
  키보드 전용 조작은 위험하고, UI 는 화면 비율 변화를 견뎌야 한다.

### 1.2.1 PC 가 본판이 되면서 풀린 것 · 안 풀린 것

| 위 항목 | 지금 | 왜 |
| --- | --- | --- |
| **초기 로딩이 이탈 지점** | **본판에서는 사라졌다** | 설치형이다. 웹 데모에만 남는다 |
| **용량 예산** | **사실상 없어졌다** | 엔진 37MB 를 안 받는다. 소리·초상·문안을 **아끼지 마라** |
| **단일 스레드** | **본판에서는 안 그렇다** — 다만 **아직 안 쓴다** | 코드가 양쪽에서 다 돌아야 한다. 스레드를 쓰면 웹 데모가 갈라진다 |
| 소리는 첫 입력 전까지 안 난다 | **웹에만 남는다** | 브라우저 정책이다. PC 는 타이틀에서 바로 소리를 내도 된다 |
| 입력 환경을 가정할 수 없다 | **좁아졌다** | PC 다. **키보드·마우스를 가정해도 된다** |
| 화면 비율을 견뎌야 한다 | **유효하다** | 창 크기를 사용자가 바꾼다 |
| 포인터 단독 조작 (§4.1) | **유효하다 — 다만 이유가 바뀌었다** | 모바일 대응이 아니라 **조작이 단순해서 좋은 것**이다 |

> **가장 크게 바뀌는 것은 「아끼지 마라」다.**
> 이 저장소는 웹 용량을 걱정해서 UI 를 도형과 셰이더로 몰아넣었다가
> 한 번 갈아엎었다([20](20-ui-kit.md)). **그 걱정의 근거가 이제 없다.**

> **아직 안 바꾸는 것 하나 — 무거운 루프를 한 프레임에 몰지 않는 규율.**
> 스레드가 생겨도 `NpcWorld.build_chunk()` 같은 쪼개기는 그대로 둔다.
> 웹 데모가 같은 코드로 돌아야 하고, **쪼개진 코드는 안 쪼개진 코드보다 나쁠 것이 없다.**

### 이 조건이 기획에 주는 영향

90시간은 **달력 시간**이지 작업 시간이 아니다. 수면·식사·이동을 빼면
실제 작업 가능 시간은 **40~55시간** 수준이고, 그중 상당 부분이
빌드·배포·문서 작업으로 나간다. 순수 게임 제작 시간은 **30~40시간**으로 잡아야 한다.

1인이라는 조건은 **병렬 작업이 불가능**하다는 뜻이다.
아트를 만드는 동안 코드는 멈춘다. 따라서:

- **에셋 제작량이 곧 개발 시간**이다. 아트 스타일 선택이 일정에 직접 붙는다.
  → [`09-art-sound.md`](09-art-sound.md)
- **콘텐츠 양보다 시스템 하나의 완성도**로 승부하는 편이 성립 확률이 높다.
  스테이지 10개를 얕게 만드는 것보다, 잘 굴러가는 루프 하나를 만드는 쪽이다.
- **처음 보는 기술을 쓰지 않는다.** 학습 시간을 낼 여유가 없다.
- **마감 전 마지막 구간은 통합·검증에 비운다.** 웹 빌드는 로컬에서 되던 것이
  브라우저에서 안 되는 경우가 있고, 그 디버깅에 시간이 걸린다.
  → [`10-content-scope.md`](10-content-scope.md) §10.4
