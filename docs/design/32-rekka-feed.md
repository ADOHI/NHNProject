# 32. 렉카 피드 — 화면에 올리는 층

> **상태: 착수.** [`16-build-order.md`](16-build-order.md) §16.8 의 **「절대 자르지 않는 여섯」** 중
> **M6 렉카 피드**를 세운다. 저장소에는 **입력을 만드는 층만 있고 화면이 없다.**
>
> 이 문서는 [`19-rekka-voice.md`](19-rekka-voice.md) 를 **대체하지 않는다.**
> 19번은 *무엇을 어떻게 말하는가*(문체 · 사실 잠금 · 후처리)이고,
> 32번은 *그 말이 게임 안에서 어디서 나와 어디에 붙는가*(문장 공급 · 화면)다.

---

## 32.0 왜 이것이 필요한가

§16.8 이 M6 에 붙인 한 줄이다 — *"없으면 개성이 사라지고 정보원도 하나 잃는다"*.

지금 저장소에 있는 것과 없는 것.

| 층 | 파일 | 상태 |
| --- | --- | --- |
| 무엇이 사실인가 | `src/core/rekka/rekka_prompt.gd` | **있다** |
| 판이 이미 아는 것 | `src/core/rekka/rekka_context.gd` | **있다** |
| 규칙 위반 걷어내기 | `src/core/rekka/rekka_post.gd` | **있다** |
| 접두어 · 닉네임 배정 | `src/core/rekka/rekka_handles.gd` | **있다** |
| **문장을 내는 층** | — | **없다** |
| **피드 화면** | — | **없다** |

`RekkaPrompt` 는 **언어 모델에게 넘길 입력**을 만드는 데까지만 간다.
그 뒤에 모델이 없으면 화면에 올릴 글자가 한 자도 나오지 않는다.
**이 문서가 채우는 것은 그 두 칸이다.**

---

## 32.1 확정 — 물어볼 수 없는 것을 먼저 못 박는다

| 물음 | 확정 | 근거 |
| --- | --- | --- |
| 런타임에 언어 모델을 부르는가 | **안 부른다** | 키를 빌드에 박을 수 없다. §19.10 방식 A 는 **채택 불가** |
| 그럼 문장이 어디서 오는가 | **§19.10 방식 E** — 미리 만들어 **자산으로 싣는다.** 그 위에 **규칙 기반 예비 문안** | §19.10 이 *"현실적인 선"* 으로 지목했다 |
| 자산에 없는 조합이 나오면 | **규칙 문안이 반드시 나온다. 피드는 절대 비지 않는다** | §19.10 — *"피드가 비는 것보다 밋밋한 게 낫다"* |
| 자산의 키 | **수치가 아니라 등급** | §19.10.1 — 수치면 조합이 터진다 |
| 사실을 바꿔도 되는가 | **안 된다.** 과장은 어투에만 | §13.3.0 · `architecture.md` — 로그에 담기는 값은 언제나 진실이다 |
| 화면 배치 | 판 · 피드 · 상태를 **한 화면.** 세로에서는 쌓는다 | §8.2 |

### 32.1.1 플랫폼이 바뀌었다 (2026-08-19) — 이 절만 다시 읽어라

**제출은 PC 스탠드얼론이 된다. 웹 빌드는 데모·디버깅용으로 남는다.**

| 바뀌지 않는 것 | 왜 |
| --- | --- |
| 런타임 모델 호출 안 함 | PC 라도 **키를 빌드에 박는 것은 같다.** 뜯으면 나온다 |
| 자산은 `load()` 로 여는 자원 | 웹 데모가 깨지면 안 된다. 원본 직접 읽기는 여전히 금지 |

**바뀐 것은 하나다 — 용량 압박이 사라졌다.**

§8.3.2 는 이 장치의 미덕으로 *"웹 용량도 거의 0"* 을 꼽았고, 그래서 §19.10 은
방식 E 의 위험으로 *"문장 수만큼 용량"* 을 적었다. PC 가 본판이면 그 저울이 없다.

> **문안은 많을수록 좋다.** 이 기능의 진짜 실패 모드는 용량이 아니라
> **같은 틀**이다 — 5차 22편이 "어색하다" 는 평가를 받은 원인이 그것이었다 (§19.A.1).

그래서 **모든 열쇠를 문안 둘 이상으로** 채웠다. 하나뿐이면 걸음으로 건너뛰어도
소용이 없다 — 그 상황이 두 번 나오는 순간 같은 글이 그대로 다시 나온다.
`test_rekka_library_asset.gd` 가 그 하한을 못 박는다.

## 32.2 층 — 어디까지가 누구 일인가

```
GameEvent / EventLog        무슨 일이 있었나 (진실)
        |
   RekkaPrompt              그것을 사실 문장으로 (사건 줄)
   RekkaContext             판이 그 주위에 대해 아는 것 (문맥 줄)
        |
   RekkaWriter -----+-- 사실 줄 ---> RekkaStock    (규칙. **언제나 나온다**)
                    +-- 제목/논평/댓글 --> RekkaLibrary (자산. 없으면 RekkaStock)
        |
   RekkaPost.clean()        두 공급원이 함께 지나는 **하나의 문**
        |
   RekkaFeedEntry           제목 · 본문 · 댓글 · 걸린 방
        |
   RekkaFeed                판 전체의 피드. 접두어 · 닉 번호를 이어 센다
        |
   RekkaFeedView (src/ui)   최신이 위. 방 이름을 누르면 신호가 나간다
```

### 32.2.0 자산은 사실을 말하지 않는다 — 코드를 쓰면서 바뀐 판단

문서를 처음 쓸 때는 **자산이 게시글 한 편을 통째로 준다**고 적었다. 그러면 둘이 깨진다.

| 깨지는 것 | 왜 |
| --- | --- |
| 자산에 없는 조합에서 **정보가 사라진다** | 예비 문안이 낸 글에는 그 턴 사건이 덜 실린다 |
| 자산이 **사건을 지어낼 수 있다** | 한 편을 통째로 쓰려면 사실 줄도 자산이 써야 한다 |

그래서 갈래를 바꿨다 — **§19.6.2 가 이미 낸 답 그대로다.**

> **보장되어야 하는 것은 규칙이 맡고, 좋게 들려야 하는 것은 모델이 맡는다.**

| 부분 | 누가 | 없으면 |
| --- | --- | --- |
| **사실 줄** (사건 + 문맥) | **언제나 규칙** | — |
| 제목 · 논평 · 댓글 | 자산, 없으면 규칙 | 밋밋해질 뿐 |

이 나눔이 조합 폭발도 함께 닫는다. 자산 한 칸이 **그 종류 x 등급의 모든 판에**
재사용되므로, 판마다 다른 방 이름과 인물 이름에 자산을 다시 뽑을 필요가 없다.

**규칙 하나 — 후처리는 하나의 문이다.** 자산이든 규칙 문안이든 `RekkaPost.clean()` 을
**같은 인자로** 지난다. 두 경로가 갈리면 한쪽만 접두어 배정을 받거나 한쪽만 숫자 규칙을
어긴다. 그런 결함은 스무 편째에야 보인다 (§19.B.4 가 같은 함정을 이미 밟았다).

### 32.2.1 새로 만드는 파일

| 파일 | 맡은 것 |
| --- | --- |
| `src/core/rekka/rekka_slots.gd` | `{주체은}` 같은 자리표시를 이름과 조사로 채운다 |
| `src/core/rekka/rekka_library.gd` | **미리 만든 문안 자산.** `Resource` 이고 `.tres` 로 실린다 |
| `src/core/rekka/rekka_stock.gd` | 자산이 없을 때 **사실 문장에서** 게시글을 조립한다 |
| `src/core/rekka/rekka_writer.gd` | 둘 중 하나를 골라 쓰고 `RekkaPost.clean()` 에 태운다 |
| `src/core/rekka/rekka_feed_entry.gd` | 게시글 한 편. 제목 · 본문 · 댓글 · **걸린 방** |
| `src/core/rekka/rekka_feed.gd` | 판 전체의 피드. 번호와 써먹은 말을 이어 센다 |
| `src/ui/rekka/rekka_post_card.gd` | 게시글 한 편의 화면 |
| `src/ui/rekka/rekka_feed_view.gd` | 목록 · 스크롤 · 방 이름 클릭 신호 |
| `assets/rekka/rekka_library.tres` | 문안 자산 한 벌 |

`src/core/` 는 전부 노드 트리에 의존하지 않는다 (개발 원칙 2).
`RekkaLibrary` 만 `RefCounted` 가 아니라 `Resource` 인데, **`Resource` 는 `RefCounted` 의
자식이고 노드 트리를 모른다.** 자산으로 실리려면 `Resource` 여야 한다.

## 32.3 자산 — 무엇을 어떤 키로 싣는가

### 32.3.1 형식은 `.tres` 이고, 원문은 `.txt` 다

**`res://` 에서 `load()` 로 열리는 자원이어야 한다.** `FileAccess` 로 원본 파일을 읽으면
로컬은 되고 **웹 내보내기에서 깨진다** — 내보내기 필터에 걸리지 않은 원본은
`.pck` 에 안 들어간다. `.tres` 는 확장자 필터와 무관하게 언제나 실린다.

그런데 `.tres` 를 손으로 적으면 읽을 수가 없다 — 줄바꿈이 통째로 한 줄에 접힌다.
그래서 **원문은 `.txt` 로 두고 굽는다.**

```
docs/design/samples/rekka/stock-library.txt   원문. 사람이 읽고 고친다
        | tools/build_rekka_library.gd
        v
assets/rekka/rekka_library.tres               자산. 게임이 load() 한다
```

**원문이 `.txt` 라 `tools/check_glyphs_text.gd` 가 고치지 않아도 그대로 훑는다.**
그 검사는 `docs/design/samples` 의 `.txt` 만 보도록 이미 정해져 있고
(19-rekka-voice.md §19.12), 이 자산의 원문이 정확히 거기 있다.
**모델이 쓴 문장은 코드 검사에 안 걸린다** — 웹에서 두부(□)가 되는 사고가 여기서 난다.

### 32.3.2 키는 등급이다

§19.10.1 이 못 박은 그대로다. **수치를 키로 쓰면 조합이 터진다.**

```
<사건 종류>:<등급>:<결>
FOUGHT:한줌:0
SEARCHED:대박:1
QUIET::0
```

| 칸 | 값 | 왜 |
| --- | --- | --- |
| 사건 종류 | `GameEvent.Kind` 의 이름. 사건이 없는 턴은 `QUIET` | 종류는 **사실**이다 (§13.3.1) |
| 등급 | `RekkaPrompt.grade_of()` 의 결과. 축이 없는 종류는 빈 칸 | 수치가 아니라 등급 (§19.3.3) |
| 결 | 같은 키에 여러 벌을 둘 자리 | 같은 상황이 두 번 나와도 같은 글이 나오면 안 된다 |

**키는 그 턴의 머리 사건 하나로 정한다.** 사건 넷을 전부 키에 넣으면 조합이 다시 터진다.
머리 사건은 `RekkaPrompt.pick_events()` 가 이미 순위로 골라 준 것의 첫 건이다.

### 32.3.3 자리표시 — 이름은 자산에 박지 않는다

방 이름과 인물 이름은 **생성기가 만든다.** 자산에 `회랑` 을 박으면 그 방이 없는 판에서
거짓말이 된다. 그래서 자산은 자리만 비워 두고 판이 채운다.

```
{주체은} {방에서} 한 건 했다는데 {등급이} 실화냐 ㅋㅋ
```

| 자리 | 채워지는 것 |
| --- | --- |
| `{주체}` | 사건을 일으킨 자의 표시명 |
| `{상대}` | 얽힌 상대. 없으면 그 자리표시가 든 **줄을 통째로 버린다** |
| `{방}` | 사건이 일어난 방의 표시명 |
| `{등급}` | `RekkaPrompt.grade_of()` |

**조사는 자리표시에 붙여 적는다** — `{주체은}` `{방에서}` `{상대와}`.
받침은 `KoreanParticle` 이 글자에서 계산한다. **다시 만들지 않는다** (§19.B.5).

**상대가 없는데 `{상대}` 가 남으면 문장이 거짓이 된다.** 지우면 주어가 사라지고,
`누군가` 로 채우면 없는 인물을 지어낸 것이 된다. 그래서 **줄을 버린다.**
버려도 글이 비지 않는 이유는 사실 줄이 자산과 무관하게 언제나 나오기 때문이다.

제목 줄이 못 채워지면 예비 문안의 제목으로 넘어가고, 댓글이 전부 버려지면
예비 댓글이 들어간다. **어느 칸도 빈 채로 화면에 나가지 않는다.**

### 32.3.4 양보다 결

5차 22편이 **"어색하다"** 는 평가를 받은 원인은 분량이 아니라 **같은 틀**이었다
(§19.A.1 — 서로 다른 형태 짝 2개, 본문 형태 1가지).
그래서 자산은 편수를 늘리는 대신 **형태를 가른다.**

| 갈라야 하는 축 | 예 |
| --- | --- |
| 제목의 꼴 | 물음 · 인용 · 단정 · 비웃음. **`ㅋㅋ` 로 끝나는 것이 28/28 이었다** (§19.B.8) |
| 본문의 길이 | 두 줄부터 여섯 줄까지. **28편 전부 여섯 줄이었다** (§19.B.8) |
| 댓글 수 | 둘부터 다섯까지 |

**나(작성 모델)가 §19.A.4 의 시스템 프롬프트와 §19.A.5 의 입력 형식을 따라 직접 쓴다.**
이것이 §19.10 의 방식 E — *"개발 도구로 쓰고 결과를 자산화"* — 다.
재료는 `tools/dump_rekka_prompts.gd` 가 실제 판에서 뽑아 준 입력 블록이다.

**닉네임은 자산에 적지 않는다.** `RekkaPost.apply_handles()` 가 갈아 끼우므로
자리만 대괄호로 표시해 두면 된다. 접두어도 마찬가지다 (§19.B.4).

**다만 자리표시는 편 안에서 서로 달라야 한다** — `[가]` `[나]` `[다]`.
후처리는 **원래 닉이 같으면 같은 사람**으로 보므로, 전부 빈 대괄호로 두면
한 편의 댓글 넷이 통째로 한 사람이 된다. 숫자는 쓰지 않는다 (§19.B.3 의 숫자 규칙).

## 32.4 규칙 문안 — 사실에서 조립한다

자산이 없는 조합에서 **피드는 절대 비지 않는다.**

**지어내지 않는 유일한 방법은 이미 사실인 문장을 쓰는 것이다.**
그래서 규칙 문안은 새 사실을 만들지 않고, `RekkaPrompt.serialize_event()` 와
`RekkaContext.for_turn()` 이 만든 **바로 그 줄들의 어투만 바꾼다.**

```
입력 줄   <칼날의 요한>이 <회랑>을 수색했다. 수확은 푼돈이다.
규칙 문안 칼날의 요한이 회랑을 수색했다. 수확은 푼돈이다 ㅋㅋ
```

**종결어미를 갈아 끼우지 않는다.** `-다` 를 `-음` 으로 바꾸는 표를 만들면
`헤어진 사이다` 가 `헤어진 사임` 이 된다 — `사이` 는 명사이고 `이다` 가 아니다.
**못 잡은 것은 어색할 뿐이지만 잘못 잡은 것은 문장을 부순다** (§19.B.3 의 결론 그대로).
그래서 마침표를 떼고 말투만 뒤에 얹는다. 그 말투도 절반은 빈 칸이다 —
매 줄에 붙으면 그게 곧 새 틀이다.

| 하는 것 | 안 하는 것 |
| --- | --- |
| 문장 끝에 말투를 얹는다 | 사건 · 장소 · 종류 · 등급을 바꾼다 |
| 제목을 머리 사건에서 뽑는다 | 없는 인물 · 없는 방을 부른다 |
| 댓글로 억측을 붙인다 | 게시글 본문이 억측을 **단정**한다 |

**억측은 댓글이 떠맡는다** (§13.3.0). 본문은 사실만 옮기므로 밋밋해도 틀리지 않는다.
**밋밋한 것은 톤 손실이고 비는 것은 정보 손실이다** (§19.10).

어미와 댓글은 목록에서 고르되 **서로소 걸음으로 건너뛴다.** `RekkaHandles` 가 이미
같은 함정을 밟았다 — 순서대로 소비하면 그 순서 자체가 새로운 틀이 된다 (§19.B.4).

## 32.5 화면

### 32.5.1 배치

§8.2 그대로다. **탭으로 나누지 않는다** — 매 턴 판단이 판 · 피드 · 상태의 대조에서 나온다.

```
가로                                    세로 (모바일)
┌────────────────┬──────────┐          ┌────────────────┐
│                │ 렉카 피드 │          │      판         │
│      판         │  최신 위  │          ├────────────────┤
│                │  스크롤   │          │   렉카 피드     │
└────────────────┴──────────┘          └────────────────┘
```

### 32.5.2 조형은 발명하지 않는다

이 저장소의 화면은 **인쇄물**이다 (`18-visual-identity.md`). 렉카 게시글은 그중
**별색판** — *오려 낸 조각이라 찢겨 있고 기울어 있다* — 이라고 `press_panel.gd` 가
이미 적어 두었고, `PressPanel.Plate.STORY` 와 `UiTheme.SPOT_HEAD` · `HYPE` 가
그 자리를 위해 만들어져 있다. **그것을 쓴다.**

| 자리 | 쓰는 것 |
| --- | --- |
| 게시글 한 편 | `PressPanel` (`Plate.STORY`) |
| 제목 | `PlateLabel` (`Plate.SPOT`, `slip_amount = SLIP_SHOUT`) |
| 본문 | `RichTextLabel` — 방 이름만 링크 |
| 댓글 | `UiTheme.MICRO` |

**어긋난 크기가 곧 부풀린 크기다** (`plate_label.gd`). 제목이 가장 크게 어긋나고
본문은 그보다 덜하다. 플레이어는 읽기 전에 어느 쪽이 못 믿는 말인지 안다.

### 32.5.3 방 이름을 누르면 판이 그 방을 강조한다

§13.7 이 **필수**로 못 박았다 — *"안 그러면 기사는 장식이 된다"*.
§16.6 의 추리 성립 조건이기도 하다.

**판과 피드는 서로의 내부를 들여다보지 않는다.** 이 저장소의 방식이다
(`main.gd` — *"판은 여기서 만들어 화면 둘에 나눠 준다"*).

```
RekkaFeedView --room_selected(room_id)--> main.gd --> DungeonBoard.highlight_room(room_id)
```

**방 이름은 글에서 찾지 않고 판에서 찾는다.** 후처리를 지난 글에 실제로 남아 있는
표시명만 `DungeonGraph` 의 방 목록과 맞춰 링크로 만든다.
글에만 있고 판에 없는 이름은 링크가 되지 않는다 — **없는 방을 누를 수 있으면 안 된다.**

## 32.6 검증

| 검사 | 무엇을 막는가 |
| --- | --- |
| `godot --headless --path . --import` | 자산 임포트 실패 |
| `godot --headless --path . --quit-after 60` | 런타임 오류 |
| `python tools/run_gut_retry.py --expect-tests <기준선>` | 기준선 아래로 안 내려간다 |
| `python tools/run_lint_retry.py` | 컨벤션 |
| `godot --headless -s res://tools/check_glyphs.gd` | `src/` 문자열의 두부 |
| `godot --headless -s res://tools/check_glyphs_text.gd` | **자산 문안의 두부** |

자산 문안은 코드도 표본도 아니라 두 검사 사이로 샐 뻔했다. **원문을
`docs/design/samples/rekka/stock-library.txt` 에 두는 것으로 그 틈이 닫힌다** —
`check_glyphs_text.gd` 를 한 줄도 고치지 않고 그대로 훑는다 (§32.3.1).

테스트는 기능 단위로 가른다. 한 파일에 몰아넣지 않는다.

## 32.7 인계

**M6 는 섰다.** 판을 걸고 스쿼드를 움직이면 그 턴이 기사가 되어 오른쪽 단에 쌓이고,
기사 속 방 이름을 누르면 판이 그 방으로 옮겨 가 맞춤표를 찍는다.

### 32.7.2 다음 사람이 제일 먼저 볼 것

1. **턴 시스템이 붙으면 표본을 다시 뽑아라.** 지금 게임에서 실제로 나는 사건은
   `DungeonRun.move_player()` 의 `MOVED` 하나뿐이다. 그래서 화면에 걸리는 편이
   거의 전부 이동 기사다. 나머지 종류는 `tools/dump_rekka_prompts.gd` 의
   **몰이꾼**으로만 검증됐다 — 그건 게임 규칙이 아니다 (§19.B.8 이 같은 것을 적어 뒀다).
2. **`RekkaContext` 가 같은 줄을 반복한다.** `아직 아무것도 못 챙겼다` 가 편마다
   나온다. 이 레인은 수집기를 건드리지 않았다. 고치려면 §19.B.1 부터 봐야 한다.
3. **댓글에는 방 링크가 없다.** 일부러 그렇다 — 댓글은 억측이고 (§13.3.0),
   억측이 판 조작으로 이어지면 안 된다. 뒤집으려면 이 문단부터 다시 써라.

### 32.7.3 이 레인이 남긴 자국 셋 — 다른 사람 영역이다

| 고친 것 | 왜 |
| --- | --- |
| `RekkaHandles` 의 걸음 계산을 `RekkaRing` 으로 뺐다 | 예비 문안의 어미도 댓글도 같은 함정을 갖는다. 두 벌을 두면 한쪽만 고쳐진다 |
| **그러면서 진짜 결함이 나왔다** | 걸음이 목록 길이로 나눠 나머지 1 이면 **걸음 1 과 결과가 같다.** 크기 12 에 걸음 13 이 그렇고, 소금 20260808 이 실제로 그것을 골랐다 — 접두어가 목록 순서 그대로 나오고 있었다 |
| `PlateLabel` 에 `wrap` 을 더했다 | 이 부품은 숫자와 짧은 이름만 담아 와서 접는 길이 없었다. 좁은 단의 제목은 접혀야 한다 |

> **접두어·닉네임 배열이 이 판부터 달라진다.** `posts-final.txt` 는 예전 배열로 뽑힌
> 기록이라 **그대로 둔다** — 폐기한 것을 지우지 않는다는 §19.12 의 규칙 그대로다.
> 그 파일을 지금 도구로 다시 재현할 수는 없다.
