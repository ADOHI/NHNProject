## 1. 문서 개요

이 문서는 NHNProject 개발 과정에서 **어떤 AI 도구를, 어떤 프롬프트로, 어떤 판단을 거쳐 사용했는지**를 기록한다.

기록의 초점은 "AI가 무엇을 만들어 줬는가"보다 **"AI 결과물을 어떻게 검증하고 채택했는가"**에 둔다.
AI가 생성한 코드는 그럴듯하지만 틀린 경우가 있고, 특히 이 프로젝트처럼
웹 빌드라는 실행 환경 제약이 있는 경우 "로컬에서는 동작하지만 제출본은 동작하지 않는" 결과가 나오기 쉽다.
따라서 각 작업 항목마다 **검증 방법과 실제 검증 결과**를 함께 남긴다.

### 갱신 규칙

- 개발 세션이 끝날 때마다 §4 작업 로그에 항목을 추가한다.
- 사용한 프롬프트는 **원문 그대로** §5에 누적한다. 다듬거나 요약하지 않는다.
- AI가 스스로 내린 기술적 판단은 근거와 함께 남긴다. 근거 없는 채택은 기록하지 않는다.
- 검증 없이 채택한 항목이 있다면 숨기지 않고 "미검증"으로 명시한다.

### PDF 생성

제출용 PDF는 이 마크다운 파일에서 생성한다. 문서를 고친 뒤 아래를 실행한다.

```bash
python tools/build_docs.py
```

결과물은 `docs/build/AI활용기술문서.pdf` 에 생성된다. 자세한 내용은 부록 A 참고.

## 3. 활용 원칙

### AI에 맡긴 것

- 반복적이고 정형화된 작성물 — 프로젝트 설정 파일, CI 워크플로, 문서 초안
- 환경 제약에 대한 조사 — "GitHub Pages에서 Godot 웹 빌드가 동작하려면 무엇이 필요한가"
- 코드 구조 제안 — 씬/스크립트/오토로드 배치 규칙

### 사람이 판단한 것

- 제출 형태(웹 빌드)와 사용 엔진(Godot) 결정
- 저장소 공개 범위(퍼블릭) 결정
- 게임 콘텐츠의 방향

### 검증 방법

AI가 생성한 결과물은 **실행으로 검증**하는 것을 원칙으로 한다. 코드 리뷰만으로 채택하지 않는다.

| 대상 | 검증 수단 |
| --- | --- |
| 프로젝트 설정 / 리소스 | `godot --headless --import` — 임포트 오류 여부 |
| 씬 · 스크립트 | `godot --headless --quit-after` — 실제 구동 시 런타임 오류 여부 |
| 익스포트 프리셋 | `godot --headless --export-release` — 프리셋 인식 및 참조 템플릿 확인 |
| CI 워크플로 | 실제 푸시 후 GitHub Actions 실행 결과 |
| 웹 빌드 | 배포된 URL을 브라우저로 열어 콘솔 로그·캔버스 상태 확인 |

## 4. 작업 로그

### 4.1 (2026-08-07) 프로젝트 초기 구성 및 웹 배포 파이프라인

**관련 프롬프트** P-001, P-002
**커밋** `5ff63bc` chore: Godot 4.7.1 프로젝트 초기 구성 (웹 빌드 배포 포함)

#### 요청 내용

빈 폴더 상태에서 Godot 프로젝트를 생성하고, 퍼블릭 GitHub 저장소를 만들어 첫 커밋을 올릴 것.
작업 도중 "웹 빌드로 제출한다"는 조건이 추가되어, 웹 배포까지 포함하도록 범위가 확장됐다.

#### AI가 수행한 작업

1. 환경 조사 — 설치된 Godot 버전(4.7.1), 실행 파일 경로, 익스포트 템플릿 설치 여부, GitHub CLI 인증 상태 확인
2. 프로젝트 골격 생성 — `project.godot`, 부트 씬, 오토로드, `.gitignore`, `.gitattributes`
3. 웹 익스포트 프리셋 작성 — `export_presets.cfg`
4. CI 워크플로 작성 — `.github/workflows/deploy-web.yml`
5. 문서 작성 — `README.md`, `docs/architecture.md`, `docs/web-build.md`
6. 저장소 생성 및 푸시, GitHub Pages 활성화

#### AI가 스스로 내린 기술적 판단

요청에 명시되지 않았으나 "웹 빌드 제출"이라는 조건에서 도출한 판단이다.
**두 항목 모두 잘못 설정하면 빌드는 성공하지만 브라우저에서 실행되지 않는다.**

| 판단 | 설정 | 근거 |
| --- | --- | --- |
| 렌더러를 호환성 모드로 고정 | `renderer/rendering_method = gl_compatibility` | Forward+ / Mobile 렌더러는 Vulkan 기반이다. 브라우저에는 Vulkan이 없으므로 웹 빌드가 검은 화면이 된다. WebGL 2를 사용하는 호환성 렌더러만 동작한다. |
| 스레드 지원 비활성화 | `variant/thread_support = false` | 스레드를 사용하는 웹 빌드는 `SharedArrayBuffer`를 요구하고, 이는 서버가 `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy` 헤더를 보내야 한다. **GitHub Pages는 정적 호스팅이라 응답 헤더를 설정할 수 없다.** 따라서 단일 스레드 빌드를 사용해야 한다. |
| 캔버스 리사이즈 정책 | `html/canvas_resize_policy = 2` | 채점 환경의 화면 크기를 알 수 없으므로 브라우저 창에 맞춰 조정되도록 한다. `window/stretch/mode = canvas_items` 와 짝을 이룬다. |
| CI에서 도커 이미지 대신 공식 릴리스 직접 다운로드 | 워크플로 `Install Godot` 단계 | 특정 Godot 버전용 도커 이미지 태그의 존재 여부에 의존하지 않기 위함. 엔진 버전 변경 시 워크플로의 `env.GODOT_VERSION` 한 줄만 수정하면 된다. |

#### 검증 내역

| 검증 항목 | 방법 | 결과 |
| --- | --- | --- |
| 프로젝트 임포트 | `godot --headless --import` | 오류 없음. `icon.svg` 정상 임포트 |
| 씬 런타임 구동 | `godot --headless --quit-after 60` | 오토로드 출력 `[NHNProject] v0.1.0 / platform=Windows` 확인, 런타임 오류 없음 |
| 익스포트 프리셋 인식 | `godot --headless --export-release "Web"` | 프리셋 정상 인식. 엔진이 `web_nothreads_release.zip` 을 요구 → **`thread_support=false` 가 실제로 반영됐음이 확인됨** (로컬에는 템플릿 미설치라 빌드 자체는 미수행) |
| CI 빌드 · 배포 | GitHub Actions 실행 | `Export Web` 32초, `Deploy to Pages` 46초, 모두 성공 |
| 배포본 실제 구동 | 브라우저로 배포 URL 접속 후 콘솔 확인 | 아래 로그 참조. 오류 0건 |

배포된 웹 빌드의 브라우저 콘솔 출력 (실측):

```
Godot Engine v4.7.1.stable.official.a13da4feb
OpenGL API OpenGL ES 3.0 (WebGL 2.0 (OpenGL ES 3.0 Chromium)) - Compatibility
Build configuration: Emscripten 4.0.20, single-threaded, no GDExtension support.
[NHNProject] v0.1.0 / platform=Web
```

세 번째 줄의 `single-threaded` 가 위 판단이 의도대로 적용됐음을 보여준다.
또한 페이지의 `SharedArrayBuffer` 가 `undefined` 인 상태에서도 정상 구동되어,
COOP/COEP 헤더가 없는 GitHub Pages 환경에서 동작함이 실증됐다.

#### 산출물

- Godot 프로젝트 골격 (`project.godot`, `scenes/`, `scripts/`)
- 웹 익스포트 프리셋 (`export_presets.cfg`)
- CI 워크플로 (`.github/workflows/deploy-web.yml`)
- 문서 (`README.md`, `docs/architecture.md`, `docs/web-build.md`)

#### 남은 과제

- 로컬에 Godot 익스포트 템플릿이 설치돼 있지 않아 로컬 웹 빌드는 불가능하다.
  (CI는 템플릿을 자체적으로 내려받으므로 배포에는 영향 없음)

### 4.3 (2026-08-07) CI 트리거 범위 조정

**관련 프롬프트** P-004

#### 요청 내용

문서만 수정해도 웹 빌드 CI가 매번 실행되는 문제를 해결할 것.

#### 배경

§4.2 작업(문서 추가)을 푸시했을 때 게임 빌드와 Pages 배포가 그대로 재실행됐다.
워크플로가 `main` 브랜치의 모든 푸시에 반응하도록 돼 있었기 때문이다.
빌드 자체는 성공했으나, 매번 Godot 엔진과 익스포트 템플릿(약 1GB)을 다시 내려받는 것은 낭비다.

#### 조치

워크플로 트리거에 `paths-ignore` 를 추가해 `docs/`, `tools/`, 최상위 `.md`,
`.gitignore`, `.gitattributes` 변경만으로는 실행되지 않도록 했다.

`.github/workflows/**` 는 의도적으로 제외 목록에 넣지 **않았다.**
워크플로 자신을 무시하면 워크플로 수정이 반영됐는지 확인할 수단이 사라진다.

문서만 고친 뒤에도 재배포가 필요한 경우를 위해 `workflow_dispatch`(수동 실행)는 유지했다.

#### 검증 내역

무시 목록은 "실행되지 않는 것"이 정상 동작이므로, 눈으로 확인하지 않으면
설정이 틀렸는지 알 수 없다. 양쪽 방향을 모두 실측했다.

| 검증 항목 | 방법 | 결과 |
| --- | --- | --- |
| 워크플로 변경 시 **실행됨** | 워크플로 파일을 수정한 커밋 `abca25a` 푸시 | 실행됨 — `Export Web` / `Deploy to Pages` 모두 success |
| 문서만 변경 시 **건너뜀** | 이어서 `docs/` 만 수정한 커밋 푸시 | 신규 워크플로 실행 없음 |

### 4.4 (2026-08-07) 개발 원칙 성문화 및 폴더 구조 정리

**관련 프롬프트** P-005

#### 요청 내용

개발 원칙 다섯 가지가 제시됐다 — 기획/개발 문서화, 재사용성, 보편적 폴더 컨벤션,
기능 유지를 전제로 한 과감한 리팩토링, 그리고 **개선안은 제안 후 허가받고 착수할 것.**

#### AI가 수행한 작업

1. 원칙을 저장소에 성문화 — `CLAUDE.md` 신설
2. 개발 컨벤션 문서 작성 — `docs/conventions.md`
3. 기획 문서 골격 작성 — `docs/game-design.md`
4. 폴더 구조 개편 — 타입별(`scenes/` + `scripts/`) → 기능별(`src/`)
5. `docs/architecture.md` 를 "현재 구조 기록" 역할로 재정의 (컨벤션 내용은 분리)

#### AI가 스스로 내린 기술적 판단

| 판단 | 근거 |
| --- | --- |
| `scenes/` + `scripts/` 를 `src/` 기능 단위로 개편 | 타입별 분리는 파일이 늘수록 기능 하나를 고치는 데 여러 폴더를 오가게 만든다. Godot 공식 문서도 타입이 아닌 맥락 단위로 묶을 것을 권한다. 파일이 5개뿐인 지금이 옮기기 가장 싼 시점이다. |
| 파일 이동에 `git mv` 사용 | 삭제 후 재생성으로 기록되면 파일 이력이 끊긴다 |
| 컨벤션과 구조를 별도 문서로 분리 | `architecture.md` 하나에 규칙과 현황이 섞여 있었다. 규칙은 자주 안 바뀌고 현황은 매번 바뀌므로 갱신 주기가 다르다 |
| 문서를 코드와 같은 커밋에 넣도록 규칙화 | 나눠 올리면 문서가 반드시 뒤처진다 |

#### 검증 내역

구조 변경은 경로가 깨져도 캐시 때문에 한동안 드러나지 않는다.
따라서 `.godot/` 캐시를 **삭제한 뒤** 클린 상태에서 검증했다.

### 4.10 (2026-08-07) 고도 개념 도입과 던전 절차 생성

**관련 프롬프트** P-024

#### 요청 내용

2단계(턴 엔진) 착수 전에 던전 생성을 고도화할 것.
던전을 모두 절차 생성으로 바꾸고, 방 연결에 **고도** 개념을 두어
스쿼드의 민첩에 따라 갈 수 있는 곳이 달라지게 한다(메트로배니아).
고가치 방과 탈출구는 접근이 어렵게 한다.

#### AI가 수행한 작업

| 항목 | 결과물 |
| --- | --- |
| 설계 문서 | `17-dungeon-generation.md` 신설, `07` 에 고도·방 종류 절 추가 |
| 고도 규칙 | `Room.elevation`, `Actor.agility`, `DungeonGraph.can_traverse()` |
| 방 등급 | `required_agility_from()` — bottleneck path |
| 스쿼드 집계 | `SquadStats` — 전투력은 합, 민첩은 평균 |
| 생성기 | `DungeonGenerator` — 척추 우선 생성 + 검증 규칙 6종 |
| 자동 배치 | `DungeonBlueprint.layout()` — 고도를 Y 축으로 |
| 화면 | 막힌 방을 붉게 + 필요 상승폭 표시, 막힌 간선 색 구분 |

#### AI가 스스로 내린 기술적 판단

| 판단 | 근거 |
| --- | --- |
| **고도를 Y 축으로 삼아 좌표를 저장하지 않음** | 절차 생성의 숨은 비용이 자동 배치인데, 고도가 그 문제를 동시에 해결한다. 플레이어도 "위로 갈수록 어렵다"를 설명 없이 읽는다 |
| 층 **순서**로 배치 (고도 실값 비례 아님) | 실값에 비례시키면 고도차가 큰 판에서 방이 한쪽에 뭉쳐 못 읽는다 |
| 층마다 좌우로 엇갈리게 배치 | 층별 방 개수가 같으면 방들이 격자처럼 줄을 맞춰 판이 표처럼 보인다 |
| 민첩 검사를 `move_actor()` 안에 넣음 | 호출자에게 맡기면 빠뜨린 경로가 하나만 생겨도 판의 규칙이 깨진다 |
| 척추를 먼저 잇고 곁가지를 붙임 | 무작위로 잇고 도달성을 검사하면 대부분 실패해 재시도가 폭증한다 |
| 검증 실패 시 **부분 수정이 아니라 재생성** | 부분 수정은 다른 규칙을 깨고, 그 연쇄 추적 비용이 재생성보다 크다 |
| 검증 규칙을 함수로 분리 | 실패한 규칙을 특정할 수 있어야 하고, 규칙이 늘어날 때 한 함수가 계속 길어지면 안 된다 |
| 생성기에 **시드**를 강제 | 시드가 없으면 버그 재현도 밸런싱 비교도 불가능하다 |
| 입구 인접 위험도 조정은 **생성이 아니라 배치 단계**에서 | 생성 단계에서 이 조건까지 맞추려 하면 재시도가 폭증한다 |

#### 화면 확인에서 드러난 문제와 조치

렌더링 캡처로 보고서야 드러난 것들이다. 테스트는 전부 통과하고 있었다.

| 문제 | 조치 |
| --- | --- |
| 방들이 서로 붙어 판이 표처럼 보였다 | 방 위젯 축소 + 배치 영역 확대 + 층 엇갈림 |
| **입구의 갈림길이 하나뿐이라 첫 턴에 결정이 없었다** | 검증 규칙 **V7(입구 차수 ≥ 2)** 추가 |
| 입구 인접 위험도가 0 이라 읽을 숫자가 없었다 | 0 이면 탈출구가 아닌 인접 방에 약한 개체를 하나 놓는다 |

**세 가지 모두 규칙상으로는 멀쩡한 판이었다.**
"검증을 통과한 판"과 "플레이할 만한 판"이 다르다는 것이 이번 작업의 교훈이고,
V7 은 그 간극을 검증 규칙으로 옮긴 것이다.

#### 검증 내역

| 항목 | 결과 |
| --- | --- |
| GUT 단위 테스트 | 95/95 통과 (생성 규칙은 12개 시드에 걸쳐 검사) |
| `gdlint` · `gdformat --check` | 통과 (`_validate` 의 return 개수 지적을 받아 함수 분리) |
| `godot --headless --quit-after 60` | 오류 없음 |
| 렌더링 캡처 | 판 생성 · 고도 게이트(붉은 ▲3) · 이동 확인 |

헤드리스 검증은 통과하는데 화면에서 파스 에러가 난 경우가 있었다
(`var touches_current := …` 의 타입 추론 실패). 씬을 실제로 띄우는
캡처 단계가 없었으면 못 잡았을 오류다.

### 4.11 (2026-08-07) 고도 상시 표시와 개발 모드

**관련 프롬프트** P-025, P-026

#### 요청 내용

배포본에서 고도 표시가 보이지 않는다는 지적.
이어서 **개발 빌드는 최대한 많은 정보를 볼 수 있게** 하고,
모드 전환 수단(키 또는 우측 상단 버튼)과 시각 로그를 넣을 것.
이 내용을 개발 사양서에도 반영할 것.

#### 원인 — 배포 지연이 아니라 설계 결함

배포본은 최신이었다(pck 갱신 시각과 크기 변화로 확인).
문제는 **▲ 표시를 막힌 방에만 넣어 둔 것**이었다.
입구에서는 인접한 방을 모두 갈 수 있어 고도 관련 표시가 하나도 뜨지 않고,
고도 자체는 어디에도 숫자로 없이 Y 위치로만 암시되고 있었다.

#### AI가 수행한 작업

| 항목 | 결과물 |
| --- | --- |
| 고도 상시 표시 | 인접 방은 상대(`▲3` / `▼1` / `평지`), 그 외는 절대값(`고도 6`) |
| HUD | 현재 방의 고도 표시 |
| 개발 패널 | `src/ui/debug_overlay/` — 요약 · 판의 진실 · 사건 기록 |
| 토글 | InputMap 액션 `toggle_debug`(F1) + 우측 상단 버튼 |
| 판 숨김 해제 | 개발 모드에서 모든 방이 실제 위험도와 개체 수를 표시 |
| 사양 문서화 | `conventions.md` §8 신설 |

#### AI가 스스로 내린 기술적 판단

| 판단 | 근거 |
| --- | --- |
| **고도는 숨기지 않는다** | 지형은 숨길 정보가 아니다. 숨기는 것은 방 안의 내용물뿐이고, 고도가 보여야 "민첩 얼마면 저기 간다"는 계획이 선다 |
| 인접 방은 **상대 고도**, 나머지는 절대 고도 | 인접 방에서 필요한 것은 "얼마나 올라야 하나"이지 절대값이 아니다. 먼 방은 지형 파악용이라 절대값이 맞다 |
| 키와 **버튼을 함께** 제공 | 조작을 포인터 단독으로 가정하므로(design/04 §4.1) 키만 두면 모바일에서 열 수 없다 |
| 개발 패널이 열리면 **판 영역을 좁힘** | 패널이 판을 가리면 확인하려던 것을 못 본다 |
| 판과 패널이 서로를 참조하지 않게 함 | `main.gd` 가 판을 만들어 둘에게 넘기고, 판은 시그널로 알린다. 처음엔 패널이 판의 비공개 멤버를 꺼내 쓰게 짰다가 되돌렸다 |
| **"새 시스템은 개발 패널에 상태를 노출한다"를 규칙으로** | 드러나지 않는 상태는 디버깅할 수 없고, 디버깅할 수 없는 상태는 반드시 틀린다 |
| 사건 로그를 개발 패널에 포함 | 이것이 나중에 렉카 기사가 읽을 바로 그 자료다. 여기서 사실을 보고 기사에서 과장된 것을 본다 |

#### 검증 내역

| 항목 | 결과 |
| --- | --- |
| GUT 단위 테스트 | 95/95 통과 |
| `gdformat --check` | 통과 |
| `godot --headless --quit-after 60` | 오류 없음 |
| 렌더링 캡처 | 고도 상시 표시 · 개발 패널 · 판 숨김 해제 확인 |

**로컬 `gdlint` 가 간헐적으로 크래시한다.** 파서 내부 오류(`TypeError` / `SystemError`)이며
코드 문제가 아니다. Windows · Python 3.10 에서만 나타나고 CI 에서는 재현되지 않는다.
`conventions.md` §5 에 적어 두었다.

| "Y 축을 고도로 쓴다" | 고도가 관문·등급·배치를 한꺼번에 푼다고 봤으나, **탑뷰에서 높이는 평면 위치와 무관하다.** 위에서 내려다보는 화면에 높이를 세로축으로 그리면 지도가 아니라 단면도가 된다 |
| "판 전체를 한 화면에" | 방이 늘면 화면에 맞추려고 판을 줄여야 하고, 그러면 이름도 숫자도 읽히지 않는다. **읽히지 않는 판은 추리할 수 없다** |

원래 의도(플레이어가 판 전체를 본다)는 버리지 않고
**축소 배율에서 정보량을 줄이는 방식**으로 지켰다.

### 4.13 (2026-08-07) 두부 글자 · 확대 반응성 · 카메라 경계

**관련 프롬프트** P-029 ~ P-032

#### 요청 내용

배포본에서 **글자가 깨져 보이고**(두부), 마우스 휠 확대가 되지 않거나 느리다는 지적.

#### 원인 1 — 로컬 렌더링이 문제를 숨기고 있었다

### 4.14 (2026-08-07) 카메라 이동 범위 재정의

**관련 프롬프트** P-033 ~ P-035

#### 요청 내용

끌기도 가장자리 이동도 되지 않고 휠은 방 위에서만 동작한다는 지적.
이어서 **지도 전체 크기를 추산해 사방에 패딩을 두고,
카메라는 그 안에서만 움직이도록** 하라는 구체적 지시.

#### 원인 — 웹이 아니라 직전에 넣은 이동 제한

측정해 보니 생성된 지도가 화면(1280×720)보다 **가로로 항상 작았다.**

```
크기 1  방  6개  지도  640 x  565  이동 불가
크기 3  방 13개  지도  935 x  900  세로만 이동 가능
```

"화면이 지도 안에 있어야 한다" 는 제한이 이 경우 허용 범위를 뒤집어
이동량을 한 점에 고정했다. 끌어도 움직이지 않았고, 커서 기준 확대도
위치를 옮기는 즉시 제한이 도로 당겼다.

#### AI가 수행한 작업

| 항목 | 결과물 |
| --- | --- |
| 세계 범위 | 지도 경계 + 사방 패딩. 카메라는 이 안에서만 움직인다 |
| 패딩 크기 | **화면 절반** 이상 — 가장자리 방도 가운데에 놓고 볼 수 있게 |
| 방 간격 | 210 → 280. 지도가 화면보다 커야 훑어볼 여지가 생긴다 |
| 가장자리 스크롤 | 커서가 실제로 움직인 뒤에만, UI 위에서는 멈춤 |

#### AI가 스스로 내린 기술적 판단

| 판단 | 근거 |
| --- | --- |
| 패딩을 **화면 절반**으로 | 처음에는 고정 260 을 썼는데, 입구가 지도 왼쪽 끝이라 중앙까지 오지 못했다. 어느 방이든 가운데에 놓으려면 패딩이 화면 절반은 되어야 한다 |
| **커서가 움직이기 전에는 카메라를 멈춤** | 창이 열리자마자 커서가 우연히 가장자리에 있으면 카메라가 저 혼자 흘러간다. 캡처에서 화면이 어긋나 있어 발견했다 |
| **UI 위에서는 가장자리 스크롤 정지** | HUD 를 읽으려 커서를 올렸을 뿐인데 지도가 흐르면 읽던 곳을 놓친다 |

#### 진단 방법

**측정하고 나서야 원인을 알았다.** 지도 크기와 화면 크기를 실제로 재는
임시 도구를 만들어 "지도가 화면보다 작다" 를 확인했고,
캡처에 `pan` 값을 찍어 제한의 상한에 정확히 걸려 있음을 확인했다.
증상만 보고 고쳤다면 엉뚱한 곳을 만졌을 것이다.

### 4.15 (2026-08-07) 병렬 작업 방식 확립

**관련 프롬프트** P-037 ~ P-040

#### 요청 내용

토큰 여유는 있으나 한 작업의 소요 시간이 길다는 지적에서 출발해,
**하위 에이전트로 작업을 병렬화할 수 있는가**, 그 에이전트들을 **통제할 수 있는가**,
그리고 **작업 도중 사용자 메시지를 즉시 읽을 수 있는가** 를 차례로 확인했다.

#### 확인한 제약 — 되는 것과 안 되는 것을 먼저 갈랐다

능력을 부풀려 답하지 않고, 실제 한계를 먼저 특정한 뒤 그 위에서 방식을 설계했다.

| 항목 | 가능 여부 |
| --- | --- |
| 여러 에이전트 동시 실행 | 가능 |
| 각자를 독립 워크트리에 격리 | 가능. 서로의 파일을 건드리지 못한다 |
| 실행 중인 에이전트에게 추가 지시 | 가능. 문맥이 유지된 채로 전달된다 |
| 작업 중간을 실시간 감독 | **불가.** 결과가 돌아와야 안다 |
| 에이전트끼리 결과 공유 | **불가.** 서로의 존재를 모른다 |
| 에이전트가 사용자에게 질문 | **불가.** 애매하면 추측해서 만든다 |
| 턴 도중 사용자 메시지 수신 | **불가.** 큐에 쌓였다가 턴이 끝나야 도착한다 |

#### 판단 — 응답 끊김은 병렬화로 우회한다

마지막 항목은 기능으로 해결할 수 없었다. 대신 **원인이 "내가 오래 붙잡혀 있는 것"** 임에 착안해,
긴 작업을 백그라운드로 넘기면 대화권이 즉시 돌아온다는 점을 이용하기로 했다.

즉 병렬화의 일차 목적은 속도가 아니라 **대화 가능 상태의 유지**다.
사용자는 기다리지 않고 지시를 넣고, 그 지시는 돌아가고 있는 에이전트에게 전달된다.

#### 정한 규칙

| 규칙 | 근거 |
| --- | --- |
| 파일이 겹치지 않는 작업만 병렬 | 같은 파일을 두 레인이 고치면 덮어쓴다 |
| 공유 인터페이스는 **먼저 확정** 후 분기 | 에이전트끼리 조율할 수단이 없다 |

| 공용 문서 3개는 통합자가 단독 작성 | 결정 기록·프롬프트 순번이 어긋나면 제출물이 깨진다 |

### 4.16 (2026-08-07) 레인 운영 규칙 교정과 렉카 문체 확립

> 내가 각각 명령하는거 위주로 처리하고 그때마다 레인 띄우고 완료되면 레인 죽이는 식으로 해

지적이 옳았다. 넷 중 하나만 실제로 승인된 작업이었고 나머지 셋은 **앞으로 필요할 것 같다는 이유로 내가 미리 깐 것**이었다. 오래 사는 레인은 의뢰인이 방향을 바꿔도 옛 지시대로 계속 만든다. 그 결과물은 전부 버려진다.

넷을 중단하고 워크트리와 브랜치까지 지웠다. 다행히 넷 다 아직 문서를 읽는 단계라 실제로 버려진 산출물은 없었다. `CLAUDE.md` 에 **「레인은 명령 단위로 산다」** 항을 추가했다 — 지시 하나 = 레인 하나 = 결과 하나.

#### 렉카 기사를 언어 모델로 만들기로 했다

당초 계획은 규칙 기반 조합이었다. 이 기사는 **읽는 재미 자체가 기능**이라, 틀에 값을 끼우는 방식으로는 몇 편만 읽어도 틀이 보인다.

| 차수 | 무엇이 나빴나 | 무엇을 고쳤나 |
| --- | --- | --- |
| 1차 | 종류 왜곡(탐색→전투), 인물 날조, **수치 축소**, 이모지 | 방임형 지시였다 |
| 2차 | 모르는 척하며 수치를 뭉갬 | 사실 규칙 + **그 이유까지** 명시. 이유를 적기 전에는 "재미를 위해" 규칙을 어겼다 |
| 3차 | 단위 오역("8 가치"→"8명") | **실제값 대신 보도값만 넘긴다.** 축소가 사라졌다 |
| 4차 | 6건이 6편, 조용한 턴이 빔 | 편수 상한 · 소재 우선순위 · 같은 방 묶기 · 조용한 턴 규격 |

#### 핵심 발견 — 과장을 언어 모델에 맡기면 안 된다

모델은 규칙보다 **문맥상 자연스러운 표현**을 고르고, 그러다 값을 줄인다. 축소가 한 번이라도 나오면 §13.3 의 "기사는 하한선"이 깨지고, 플레이어가 기사를 역보정하며 쌓은 숙련이 통째로 무의미해진다.

그래서 경계를 이렇게 그었다.

> **무엇이 사실이고 보도값이 얼마인가는 코드가, 그것을 어떻게 지껄이는가는 모델이.**

과장 배율은 `RekkaPrompt` 가 계산하고 모델에는 이미 부풀려진 값만 넘긴다. 문장이 어떻게 나오든 부풀리기 방향이 코드에서 보장된다.

#### 제출 빌드에서 모델을 부르지 않기로 했다

웹으로 제출하므로 브라우저에서 API 를 부르면 **키가 빌드에 박힌다.** 프록시 서버가 옳은 답이지만 1인 90시간에 서버 운영을 얹는 결정이다.

**모델을 개발 도구로만 쓰고 문안을 자산으로 굳힌다.** 런타임 호출이 없으니 키도 지연도 비용도 없다. 단 자산화할 때 **숫자를 문장에 박지 않는다** — 보도값까지 캐시 키에 들어가면 조합이 터진다. 자리표시자로 두고 런타임에 끼우면 종류 × 규모 구간까지만 나누면 된다.

#### 부수적으로 드러난 것

- **금지 문자를 프롬프트에 글자로 나열하면 역효과다.** 글리프 검사기가 금지 목록 자체를 위반으로 잡고, 모델은 그 글자를 예시로 받아 오히려 쓴다. 이름으로 적어야 한다.
- 화면에 나갈 표본은 `.txt`, 실패 기록은 `.md` 로 갈랐다. 실패한 산출물을 지우면 왜 그 규칙이 생겼는지 알 수 없게 된다.
- 잘 안 나온 기사 셋은 **프롬프트가 아니라 기획의 빈칸에서 나왔다.** 이동만 있는 턴에는 부풀릴 수치가 없고, 조우의 `magnitude` 정의가 아직 없다.

규칙은 그대로 두고 **원인 설명만** 정정했다.

#### 대비책 — 없앨 수 없으면 노출을 줄인다

폭사율이 **프로세스가 한 일의 양에 비례한다**는 것을 재서 찾았다.

| 부하 | 폭사율 |
| --- | --- |
| `gdlint <파일 하나>` | 1 / 10 |
| `gdlint src test tools` (547 파일) | **12 / 12 — 한 번도 못 끝냈다** |

그래서 **긴 실행 하나를 짧은 실행 여럿으로 쪼갰다.**
`run_lint_retry.py` 는 파일 하나씩 돌리고 폭사한 것만 다시 돌린다 —
**폭사 62회를 흡수하고 지적 3건을 정확히 집어냈다.**
통째로 돌릴 때의 「지적 0건」은 깨끗한 것이 아니라 **검사를 못 한 것**이었다.

**둘 다 실패를 숨기지 않는다** — 단정 실패와 진짜 지적은 재시도하지 않고,
판정을 못 얻은 파일이 남으면 빨갛게 끝난다.

#### 소프트바디 — 물리를 넣는데 순수 함수를 안 깬다

사용자가 지정한 헤드라인은 **레이맨 리그에 물리력을 얹고 가슴·헤어 모핑으로 통합**하는 것이다.
정면으로 부딪히는 것이 있었다 — **물리는 정의상 상태인데 이 구조는 상태가 없다**(§25.3).
적분기를 넣으면 링 버퍼 없음 · 프레임률 무관 · 결정적 캡처 셋을 다 잃는다.

**빠져나가는 길은 감쇠진동에 닫힌 해가 있다는 것이다.** 주기 구동은 진폭·위상만 옮긴
같은 주파수이고, 충격은 「사건 이후 흐른 시간」의 함수다 — **§25.3 이 이미 쓰던 형태 그대로다.**
즉 물리를 넣는 것이 구조를 깨는 것이 아니라 **이 구조가 처음부터 물리의 형태였다.**

모핑은 부위별로 갈랐다. 머리카락을 일곱째 파츠로 떼는 안은 실물 그림에 `hair.png` 가
없어 보류했고, **둘 다 프래그먼트 셰이더의 UV 워프**로 간다 —
`Sprite2D` 는 사각형 네 점이라 버텍스로는 국소 부풀림이 원천적으로 안 된다.

### 4.19 (2026-08-19) 본판 전환 · 게임 루프 완성 · 구조 정리

#### 본판이 웹에서 PC 스탠드얼론으로 바뀌었다

작업 도중 사용자가 방향을 바꿨다 — *"실제 게임은 pc로 출시할거야"*.
**웹은 버리지 않고 데모·디버깅용으로 남긴다.**

문서 셋을 고쳤는데 **가장 크게 바뀐 것은 「아끼지 마라」**다 —
이 저장소는 웹 용량을 걱정해 UI 를 도형과 셰이더로 몰아넣었다가 한 번 갈아엎었는데,
**그 걱정의 근거가 사라졌다.**

**렌더러는 안 바꿨다.** Vulkan/Forward+ 로 구동은 확인했지만(RTX 4090, 오류 0),
셰이더 전부가 `gl_compatibility` 에서만 판정받았다.
**켜는 값은 성능이 아니라 「화면 검수 두 벌」이고 그 비용은 통합자가 임의로 낼 것이 아니다.**

#### 캡처가 시험이 못 보는 것을 두 번 잡았다

**시험은 한 턴만 묻는다.** 턴 루프 레인이 여덟 턴을 걸어 보고서야
**신중한 NPC 가 위험한 방 앞에 서서 판이 끝날 때까지 안 움직이는 것**을 잡았다.
회피가 아니라 정지였고, 그러면 위험도 변화량이 사라져 §13.5 가 죽는다.

정산 레인은 캡처를 **두 번째** 돌리다 **두 번 정산을 막는 장치가 첫 정산을 막는 것**을 잡았다.
원정 번호는 프로세스마다 0으로 돌아가는데 정산 장부는 세이브에 남아서다.
**오류는 안 났다** — 저장과 정산이 한 흐름에 처음 놓여서야 드러났다.

> **둘 다 「각각은 맞는데 만나면 틀린」 종류다.** 단위 시험으로는 원리적으로 안 나온다.

사용자가 *"코드 모듈화 커플링 분리, 리팩토링도 같이"* 를 지시했다.
