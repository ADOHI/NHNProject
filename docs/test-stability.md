# 테스트 안정성 — 무작위 `0xC0000005` 조사

**상태:** 원인 특정됨 — **이 개발 기계의 하드웨어 결함.** 우리 코드가 아니다 (2026-08-18)
**대상:** `godot --headless --path . -s res://addons/gut/gut_cmdln.gd`
**결론 요약:** 코드는 정상이다. 기준선 **811/811** 은 유효하다.
같은 기계에서 Godot·Python 을 가리지 않고 무작위로 프로세스가 죽고, **틀린 값도 나온다.**

> 이 문서는 조사하면서 썼다. 결론이 나기 전에 관측한 것도 그대로 남긴다.

---

## 1. 증상

- 전체 스위트가 **가끔** 죽는다. 나머지는 811/811 전부 통과한다
- **죽는 자리가 매번 다르다.** 전부 평범한 GDScript 산술/대입이고 그 코드에 잘못이 없다
- 종료 코드는 `0xC0000005`(ACCESS_VIOLATION). Git Bash 에서는 139(SIGSEGV)로 보인다

---

## 2. 측정 — 추측하기 전에 잰다

도구는 전부 `tools/` 에 있고 **빌드에 들어가지 않는다.**

| 도구 | 하는 일 |
| --- | --- |
| `tools/repeat_gut.py` | 스위트를 N회 돌려 재현률·죽는 자리·RSS 를 표로 만든다 |
| `tools/crash_matrix.py` | 서로 무관한 부하(Godot · gdformat · 순수 계산)의 폭사율을 비교한다 |
| `tools/run_gut_retry.py` | CI 용 — **폭사에만** 재시도하는 러너 |

```bash
python tools/repeat_gut.py -n 12 --rss
python tools/crash_matrix.py -n 20
python tools/run_gut_retry.py --max-attempts 3 --expect-tests 811
```

### 측정 도구부터 검증했다 — 첫 판독은 틀렸다

첫 파서는 **모든 회차가 스크립트 9개·76단정에서 멈춘 것처럼** 읽었고,
죽은 자리가 전부 `dungeon_blueprint.gd:54` 인 것처럼 보고했다. **전부 거짓이었다.**

원인: Godot 은 `push_error` 마다 GDScript 백트레이스를 찍는데, 이 백트레이스에는
**종료 표시가 없다.** 파서가 크래시 덤프와 구별하지 못해, 정상 로그의 나머지를
통째로 백트레이스로 먹었다.

가르는 기준은 **들여쓰기**다 — 크래시 덤프의 `GDScript backtrace` 는 1열에서 시작하고,
`push_error` 가 찍는 것은 들여쓰여 있으며 `-- END OF GDSCRIPT BACKTRACE --` 가 없다.

> **교훈.** 「도구가 조용히 틀린 답을 준다」를 이 저장소는 또 겪었다
> (앞선 사례: GUT 의 `-gtest=` 인자가 조용히 무시된 건).
> 측정값을 믿기 전에 **완주한 회차가 811/811 로 읽히는지**부터 확인할 것.

**재현률 5/12 (42%).**

여기서 읽히는 것 셋.

1. **죽는 지점이 균일하게 흩어져 있다.** 진행률로 11% · 39% · 41% · 68% · 99%.

   터지는 사건의 모양이다

   프로세스가 사라졌다
3. **고아 객체 수는 2193 으로 모든 회차가 똑같다** — 죽은 회차도, 완주한 회차도.
   GUT 의 정리 동작은 크래시와 **상관이 없다**

## 4. 결정적 증거 — 죽지 않고 **틀린 값**이 나온다

`crash_matrix` 1회차에서 스위트가 죽지 않고 **정상 종료하며 2개를 실패로 보고했다**
(809/811). 실패 내용이 결정적이다. 서로 **무관한 두 코드 경로**에서 같은 종류의 오류가
같은 실행 안에 났다.

```
SCRIPT ERROR: Invalid call. Nonexistent 'float' constructor.
   at: ProtoMoveTuning.get_value (res://src/proto/unit_move/core/move_tuning.gd:138)

SCRIPT ERROR: Invalid access to property or key 'delay' on a base object of type 'float'.
   at: CharSwingClip.torso_angle_at (res://src/core/char_anim/swing_clip.gd:394)
```

두 줄 다 **정상 실행에서는 일어날 수 없다.**

- `move_tuning.gd:138` 은 `return float(_values.get(key, 0.0))` 이다.
  `float()` 은 **엔진 내장 생성자**다. "존재하지 않는다"는 말이 나올 수 없다 —
  VM 의 내장 함수 디스패치가 오염된 것이다
- `swing_clip.gd:394` 는 `progress_for(t, LEAD_TORSO * f.delay)` 이고,
  `f` 는 **정적 타입 매개변수** `f: AnimFeatures` 다. GDScript 가 호출 시점에 타입을
  검사하므로 들어올 때는 `AnimFeatures` 였다. 읽을 때 `float` 였다.
  **정적 타입 매개변수는 도중에 타입이 바뀔 수 없다**

즉 **Variant 의 타입 태그가 실행 중에 뒤집혔다.** 이것이 이 조사의 결정적 증거다.
같은 결함이 어떨 때는 폭사로, 어떨 때는 **조용히 틀린 값으로** 나타난다.

> **이것이 무서운 이유.** 폭사는 눈에 띄지만, 틀린 값은 **가짜 테스트 실패**로 보인다.
> 위 두 건은 다행히 엔진이 오류로 잡았지만, 잡히지 않는 오염은 그냥 잘못된 결과다.
> **설명이 안 되는 테스트 실패를 만나면 코드를 파기 전에 한 번 더 돌려 볼 것.**

## 5. 하드웨어 확정 — 우리 코드도, Godot 도 아니다

통합자가 병행해 잰 값과 이 레인의 측정이 같은 곳을 가리킨다.

| # | 관측 | 뜻 |
| --- | --- | --- |
| 1 | **`gdformat` 도 12회 중 2회 죽는다** | Godot 과 무관한 **Python** 프로세스다. 파일과도 무관(여러 파일에서 재현) |
| 2 | Git Bash 2/12 · PowerShell 2/12 | 셸·MSYS 계층과 무관 |
| 3 | 종료 코드 `0xC0000005` | 두 런타임이 **같은 예외**로 죽는다 |
| 4 | 여유 RAM 14.3/31.6 GB · VRAM 848 MiB/16376 MiB · ComfyUI 미기동 | **메모리 압박이 아니다** |
| 5 | **`WHEA-Logger` 이벤트 19 (2026-08-15)** — *Corrected Machine Check · **Translation Lookaside Buffer Error** · Reported by component: **Processor Core*** | **CPU 자신이 하드웨어 오류를 보고했다** |
| 6 | 최근 3주 커널 버그체크 5회 — `0x1E`(첫 인자 `0xC0000005`) · `0x50`×3 · `0x3B`(첫 인자 `0xC0000005`) | 전부 메모리 오염 계열 |
| 7 | CPU: **13th Gen Intel Core i9-13900H** (Family 6 Model 186) | 전압/열화 불안정이 널리 보고된 세대 |
| 8 | RAM: 삼성 DDR5-4800 2×16GB, **정격**(XMP 아님) | 사용자 오버클럭이 원인이 아니다 |

**서로 무관한 두 런타임(네이티브 C++ · Python)이 같은 예외 코드로 무작위로 죽고,
CPU 가 정정된 기계 검사 오류를 스스로 보고했다.** GDScript 버그로는 설명되지 않는다.

특히 5번의 **TLB 오류**는 주소 변환 캐시가 틀린 물리 주소를 준다는 뜻이다.
그러면 프로세스는 남의 메모리를 읽는다 — 운이 나쁘면 접근 위반(`0xC0000005`),
운이 나쁘고 주소가 매핑돼 있으면 **조용히 틀린 값**(4장). 관측된 두 증상이
정확히 이 하나의 원인에서 나온다.

### 대조군 — 저장소와 무관한 순수 계산 부하

`crash_matrix.py` 의 `control` 부하는 파일도 네트워크도 건드리지 않고
정수 연산과 힙 할당만 20초 돌린다. 매 라운드 같은 체크섬이 나와야 하므로
**죽지 않고 값만 틀려도 잡힌다.**

## 8. 처방

### 8-1. CI·로컬 — 폭사에만 재시도하는 러너

`tools/run_gut_retry.py`. **회피책이 실패를 숨기면 지금보다 나쁘다**는 원칙 위에 세웠다.

- **단정 실패는 재시도하지 않는다.** GUT 가 정상 종료하며 실패를 보고하면(종료 코드 1)
  그대로 빨갛게 끝난다
- **폭사(`0xC0000005`·신호 11 등)만** 다시 시도한다
- **시도 횟수와 매 시도 결과를 반드시 찍는다.** 몇 번 만에 통과했는지가 로그에 남는다
- **최대 시도를 넘기면 빨갛게 실패한다** (종료 코드 2)
- `--expect-tests 811` — **덜 돌고 통과한 실행은 통과로 치지 않는다.**
  이 저장소가 `-gtest=` 무시로 이미 한 번 당한 실패 모드를 막는다

```bash
python tools/run_gut_retry.py --max-attempts 3 --expect-tests 811
```

**CI(`quality.yml`) 반영은 아직 하지 않았다.** 이유 둘 —
CI 는 GitHub 의 우분투 러너에서 돌므로 **이 기계의 결함과 무관**하고,
워크플로 변경은 개발 원칙 5(제안 후 승인)에 해당한다. 승인되면 `Run GUT` 단계를
위 명령으로 바꾸면 된다.

### 8-2. 사용자 — 기계 점검 권고

**아래는 재부팅이 필요하거나 판단이 필요한 항목이라 이 레인에서 실행하지 않았다.**

1. **메모리 진단** — `mdsched.exe`(Windows 메모리 진단) 또는 MemTest86 을 여러 패스 돌린다.
   DDR5 는 정격이라도 모듈 불량이 있을 수 있다
2. **BIOS·마이크로코드 갱신** — 13세대 Intel 의 불안정 문제로 제조사가
   마이크로코드를 배포했다. 노트북 제조사의 최신 BIOS 를 확인한다
3. **Intel 의 해당 세대 권고 확인** — 13/14세대 Core 의 전압 관련 권고와
   보증 연장 정책이 있는지 확인한다
4. **열·전력 상태 확인** — i9-13900H 는 노트북 부품이다. 장시간 부하에서
   온도와 클럭이 정상 범위인지 본다
5. **WHEA 이벤트 추적** — 이벤트 뷰어에서 `WHEA-Logger` 를 계속 관찰한다.
   **정정된**(corrected) 오류가 늘어나면 정정 불가로 넘어가기 전 단계다

> **이 결함은 이 저장소의 산출물에 영향을 주지 않는다.** 웹 빌드는 GitHub Actions 에서
> 만들어지고, 게이머의 브라우저에서 돈다. 영향받는 것은 **이 기계에서 도는 개발·검증뿐**이다.
